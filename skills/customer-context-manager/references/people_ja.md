# 人物の記録

SKILL.md から参照される、人物の分類と人名の記録規則。お客様の `people.md` や
共有の people ファイルに人物を追加する前に読む。

English version: [people.md](people.md)

## 人物の分類

お客様の `people.md` に人物を追加する前に、`people/internal.md` や
`people/partners.md` に既に存在しないか確認する。お客様との打ち合わせで
言及された名前が、社内メンバーやパートナーである可能性がある。手順：

1. `people/internal.md` で名前を検索
2. `people/partners.md` で名前を検索
3. 見つかった場合、お客様の `people.md` に重複登録しない — 新しい情報があれば既存エントリを更新
4. どちらにも見つからない場合、お客様の `people.md` にお客様担当者として追加

検索は与えられた文字列の完全一致だけで行わない。名字と読みでも引く — 同一人物が
フルネームで登録されているのに会話では名字だけだった、あるいは別の文字種で書かれている
場合がある。

人物の所属（お客様 vs 社内 vs パートナー）が不明な場合、会話の文脈から
手がかりを得る（例：「うちのチーム」「自社側」、「技術コンサルタント」「営業担当」などの
肩書き）。それでも曖昧な場合はユーザーに確認する。

## 人名の記録

名字だけでは足りない。`A様（IT戦略部）` ではメールの送信者・出席者リスト・CRMの担当者レコードと
照合できず、一度判明していた情報を次のタスクでユーザーに聞き直すことになる。
後続タスクが聞き直さずに済むよう、人物は一度で完全に記録する。

人物テーブル（お客様の `people.md`、`people/internal.md`、`people/partners.md`）には
最低限次を記録する：

| 項目 | ルール |
|------|--------|
| Name | 本人が書く表記のフルネーム。原文の文字種のまま、姓*と*名の両方。 |
| Reading | 読み。日本語名はかな。ラテン文字名は日本語読みが実際に使われている場合のみ。 |
| Source | その名前をどこで得たか（[ソース追跡](#ソース追跡)参照）。 |

文字種のルール — 本人が書いている表記で記録する：

- **日本語名**: 漢字・かなを書かれているまま保持し（`山田 太郎`）、読みを記録する
  （`やまだ たろう`）。読みは漢字から導出できない — `新谷`・`丁野`、名前の `一` などは
  複数の妥当な読みを持ち、一般的な読みを選ぶのは推測であり、いずれお客様の前で
  声に出して繰り返される
- **ラテン文字名**: 本人の綴りをそのまま保持する — 大文字小文字、ハイフン、アポストロフィ、
  アクセント、姓名の順序を含めて（`Anne-Marie O'Brien`、`José Álvarez`、`LEE Min-ho`）。
  カタカナ表記を主たる記録にしてはならない。その表記が実際に使われている場合にのみ
  Reading にカタカナを補う
- **両方の表記を使う人**（`山田 太郎` / `Taro Yamada`）: 主たる表記を Name に、もう一方を
  Notes に記録し、どちらの綴りでも検索で解決できるようにする
- **敬称・肩書きを名前そのものに含めない。** `様`・`さん`・`-san`・`Mr.`・`Dr.` は呼称であり、
  `部長`・`CTO` は役割である。いずれも Name 列には入れないし、人物を特定するラベル付きフィールド
  （`Primary contacts:`、`SA Assignment:` など）にも入れない。これらはメール・出席者リスト・
  CRMレコードと照合するための「記録された名前」を保持する場所である — `山田様` や `山田部長` ではなく
  `山田 太郎`。
- **散文では、普通に書くとおりに人を書く。** Notes セル、`- What happened:` 行、自由記述の箇条書き、
  組織図への注記 — これらは文章であるから、言語と関係性に応じた呼称を使う（`乙野様`、`甲山さん`）。
  日本語の文章から敬称を剥がすと不自然に読め、お客様に対しては失礼にも読める。敬称を持たない言語では
  名前だけを使う。これを安全にしているのがレジストリである: `people.md` がフルネームと読みを
  保持しているから、文章が `乙野様` と書いてもそれが誰かを解決する手段が失われない。
- **散文で名前の隣に書いた役割は主張であり、黙って陳腐化する。** 肩書きより敬称を選ぶ —
  `甲野CTO` ではなく `甲野様`。役割は当該人物の people テーブル行に置く。異動時に修正される唯一の
  場所である。`甲野CTO` と書いた散文は、組織変更の何年後もその肩書きを主張し続ける。
- **どこかで名前が出る人物は、必ず people テーブルに行を持つ。** `notes.md`・出来事・組織図で
  言及する価値がある人物は、`people.md`（または `people/internal.md` / `people/partners.md`）に
  読みとソースを伴う行を持つ価値がある。散文にしか現れない名前は読みも出所も持たない —
  名字だけの記録が生まれた経路がまさにこれであり、文章中の `乙野様` が解決不能になる理由でもある。

欠落は固定せず埋める。印は[不完全な情報の印](#不完全な情報の印)に定義したものを使う：

- **名（ファーストネーム）や読みを創作してはならない。** 欠けているものは `{unknown}`、
  導出した値は `{inferred}` とし Source を `inferred` とする
- 名字しか分かっていない場合は `山田 {unknown}` と書く。この印は記録が未完であることを示す
  可視かつ検索可能な宣言であり、裸の `山田` は完成した記録に見えてしまう
- 次の機会に根拠から補完する: メール署名、会議招集の出席者リスト、名刺、組織図、
  ドキュメントの署名、CRMの担当者レコード。口頭情報より書かれた情報を優先する
- 目下の作業に不完全な名前が必要なときは、ユーザーに一度確認し、読みとあわせて保存する。
  名字のまま黙って進めない。後続タスクで再度聞き直さない
- 完全性を保存のブロッカーにしない: `{unknown}` とソースを付けて部分的に保存し、後で埋める

テーブル外でも同じ扱いとする。`organization.md` の組織図、`history.md` の出来事、散文メモでは
初出時にフルネームを使う（`山田 太郎 CTO`）。`people.md` にフルネームが記録済みであれば、
同一ファイル内の以降の言及は短縮形で構わない。

## 類似した人名の区別

同一のお客様内に同姓の人物がいるのはよくあることであり、名字だけの記録がまさに区別を
不能にしている。フルネームと読みがあれば通常はそれだけで解決する。それでも足りない場合：

- 部署や文脈情報をエントリに加える
- 記録時点で区別できない場合は、分かっている情報を保存し曖昧さを明示的に注記する
  （`山田 {unknown}（部署 {unknown} — 営業部の山田 太郎とは別人の可能性）`）
- 後から情報が判明した時点でエントリを更新する。2行の統合は同一人物であることを確認した後に
  のみ行う — 似た2行が残る方が、誤った統合よりは安全である

完璧な特定をブロッカーにしない — 部分的と明記された部分的な情報は、無いよりは良い。
