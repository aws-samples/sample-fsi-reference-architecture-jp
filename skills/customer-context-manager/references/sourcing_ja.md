# 出所の記法と不完全な情報の印

SKILL.md から参照される、出所と欠落の記録規則。Source 欄を書くとき、
または確信のない値を記録するときは、事前にこのファイルを読む。

English version: [sourcing.md](sourcing.md)

## 不完全な情報の印

不完全さは4つの固定マーカーのいずれかで、波括弧に包んで記録する。数ヶ月後に読み返されても、
別ファイルへ転記されても、周囲の文章に混ざっても、欠落が欠落として残るようにするためである —
裸の `?` ではそれができない。1文字しかなく、通常の句読点と衝突し、実質的に検索できない。

軸は独立に2つある。**値**のマーカーは「無い・作った」を示す。**信頼**のマーカーは
「成り立たないかもしれない」を示す。1行が両方から1つずつ持つことがある。

| マーカー | 軸 | 意味 | 例 |
|---------|-----|------|-----|
| `{unknown}` | 値 | 値が分かっていない。埋めるべき実際の欠落。 | `己野 {unknown}` |
| `{inferred}` | 値 | エージェントが導出した値。誰も明言していない。 | `ていの しろう {inferred}` |
| `{unconfirmed}` | 信頼 | 出所は特定できているが、裏付けが取れていない。 | `meeting 2026-02-10 {unconfirmed}` |
| `{unsourced}` | 信頼 | 出所を特定できない。Source 欄に書く。 | `{unsourced} recorded 2026-05-12` |
| `-` | — | 該当なし、意図的に空。欠落では**ない**。 | `Anne-Marie O'Brien` の読み |

5つ目のマーカー `{no-url}` は、出所は特定できているが共有可能なアドレスを持たないソースに付す。
定義は[ソース追跡](#ソース追跡)にある。

**角括弧ではなく波括弧を使う。** `[unknown]` は Markdown の *link label* として完全に有効である。
同一ファイル内のどこかに `[unknown]: url` という参照定義があれば — リストやブロック引用の中でも
足りる — そのファイル内の全出現が静かにリンクへ変わる。ラベル照合は大文字小文字を無視し内部の空白も
畳むため、`[Unknown]` や `[ unknown ]` も同じく衝突する。波括弧は CommonMark のインライン構文に
一切割り当てられていないため、どんな定義にも捕まらない。この線引きは覚えておく価値がある:
**角括弧は Markdown のもの**（リンク、`[^1]` のような脚注）、**波括弧はこのマーカーのもの**。

マーカーを機能させるためのルール：

- **どの言語のファイルでも、ASCII・波括弧のまま字義通りに書く。** ファイルが日本語でもマーカーは
  翻訳しない。日英混在のストア全体を1回の検索で洗い出せるようにするためである：
  ```
  grep -rn '{unknown}\|{inferred}\|{unconfirmed}\|{unsourced}\|{no-url}' <データディレクトリ>
  ```
- **波括弧をエスケープしてはならない。** エスケープは不要であり、エスケープした形は表示は同じでも
  文字列としては別物になるため、上記の検索から静かに漏れる
- **より短い形・緩い形で代用してはならない。** `?` も `不明` も `TBD` も `n/a` も使わず、
  空欄にもしない。空欄は書き忘れと区別できない
- **`{unknown}` はフィールドを占有する。** 本来の値が入る場所に欠落が見える。
  `己野 {unknown}` は未完に読め、裸の `己野` は完成に読める
- **`-` と `{unknown}` を区別する。** `-` は記録すべきものが無く誰も探す必要がないことを意味し、
  `{unknown}` は誰かが探すべきことを意味する
- **マーカーを書く場所が、それが何に係るかを示す。** 値のマーカーは、それが説明する
  フィールドの中に置く。信頼のマーカーは既定で `Source` 欄（脚注では出所の後ろ）に置く —
  これにより行全体の信頼度が1列を見るだけで読み取れる。`{unconfirmed}` を値の隣に置くのは、
  他は確かな行の中で特定の1フィールドだけが疑わしい場合に限る
- **冗長なマーカーを重ねない。** `{unsourced}` は裏付けの無さを含意するため `{unconfirmed}` を
  併記しない。より多くを語る方だけを使う
- **マーカーは値と一緒に移動する。** 印の付いた値を別の場所（他ファイル、他スキル、要約）へ
  引用するときは、印も一緒に運ぶ
- **マーカーは成果物に出さない。** これは内部管理用である。提案書・レポート・メッセージに印付きの
  値が必要な場合は、先に解消するかユーザーに確認する。印を黙って外して事実として印字してはならない

## ソース追跡

すべての事実は出所を伴う。出所がなければ、保存された記述は検証も訂正も重み付けもできず、
半年前に書き留めた推測が、お客様が直接述べた事実と区別できなくなる。

**ソースが必要なもの。** 自分の頭の外から来たものすべて: 人物、システム、用語、組織構造、
出来事、提案、数値、制約、好み。財務数値に限らない。

**必要でないもの。** 世界についての主張ではなく自分が管理する記録項目には、ソースは不要である。
無理に付けるとノイズになる：

- 自分で維持する識別子・状態: `Status`、`Last synced`、slug、`Group` の割り当て、`Date Added`
- 置かれているファイル自体から定義的に決まる値（お客様自身のファイル冒頭の表示名）
- セクション見出し、テンプレートのコメント、自分の移行メモ

**ブロック単位のソース。** `## Key Events` 配下の出来事や `### YYYY-MM-DD:` の変更記録は、
1つの事実を複数行で述べたものである。ブロック末尾の `- Source:` 1行がブロック全体を担保し、
個々の `- What happened:` / `- Significance:` 行にそれぞれ付ける必要はない。
ブロック内の1行だけ別の出所から来た場合にのみ、その行に脚注を足す。

標準テンプレートに無いセクション — お客様固有の設計セクション、構成図、その場の分析 — も
記録された内容であり、その中の事実も同じくソースを伴う。独自セクションは出所が静かに欠落する
最も典型的な場所である。

- **テーブル内**: `Source` 列を設け、全行を埋める。唯一の例外は `index.md` である。これは事実の
  集合ではなく名前解決のレジストリであり、毎タスクで読み込まれるため軽量に保つ — 別名の出所は
  当該お客様の `profile.md` の `Common aliases` 行に置く。
出所はファイルごとに1回だけ定義し、キーで参照する。20個の事実を支える出所を20回書かずに済み、
入れ子リストを置けないテーブルセルにも、長い文字列ではなく短い参照を入れられる。

**参照側**は、事実が置かれている行の末尾に `[[KEY](#KEY)]` を書く — 角括弧で括った引用の形にし、
文の一部ではなく印として読めるようにする。テーブルの場合は列見出しが役割を示しているため、
`Source` 列に素の `[KEY](#KEY)` を入れる:

```markdown
| Name | Reading | Department | Source | Notes |
|------|---------|-----------|--------|-------|
| 乙野 次郎 | おつの じろう | 財務部 | [AP20260512](#AP20260512) | 銀行取引の窓口 |

- 総合振込の承認は経理課長 → 財務部長の2段階 [[AP20260512](#AP20260512)]
- 基幹システム更新に伴い設備資金の需要が生じ得る [[M20260804](#M20260804)] {unconfirmed}
```

外側の角括弧はエスケープ不要である。内側のインラインリンクは入れ子にならないため外側はリテラルとして
残り、`[AP20260512]` と描画される。仮に `[AP20260512]: url` という参照定義が紛れ込んでいても、
インラインリンクが shortcut reference より優先されるためリテラルのままである。

置き場所は3つで、位置が適用範囲を示す:

| 置き場所 | 適用範囲 |
|---------|---------|
| 箇条書き行の末尾（`[[KEY](#KEY)]`） | その事実 |
| テーブル行の `Source` 列 | その行 |
| 出来事ブロック内の `- Source:` フィールド（`- What happened:` と同列） | ブロック全体 |
| 箇条書きでない内容（図・段落）に隣接する `Source:` 段落 | その内容 |

事実の下に入れ子の `- Source:` 行を作ってはならない — キーは事実の行に収まる長さであり、
1事実1行のほうが読みやすく、機械処理も単純になる。

**定義側**はファイル末尾の `## Sources` セクションに1行ずつ置き、アンカーを付けて参照が実際に
飛べるリンクになるようにする:

```markdown
## Sources

- <a id="AP20260512"></a>**AP20260512** — doc:account-plan 2026-05-12 {no-url}
- <a id="M20260804"></a>**M20260804** — meeting 2026-08-04（設備投資計画のヒアリング）
```

**キー形式は `<種別><YYYYMMDD>`** — 出所から導出するものであり、創作しない。同じ出所からは必ず
同じキーが生成されるので、1つの出所に由来する2つの事実がばらけることが構造的に起きない。
月・年までしか分からない場合は `<種別><YYYYMM>` / `<種別><YYYY>`、日付が出所に一切無い場合は `<種別>000000`
（それ自体が埋めるべき欠落である）。異なる出所が同一キーに当たる場合のみ、安定した順序で
`b`、`c` … を付す。

| 種別 | 出所の種類 | 種別 | 出所の種類 |
|------|-----------|------|-----------|
| `M` | お客様との打ち合わせ | `AP` | アカウントプラン |
| `IS` | 社内ミーティング・アカウントチーム内 | `AR` | 活動レポート |
| `U` | ユーザー（操作者）が伝えた | `D` | その他のドキュメント |
| `SIG` | メールのヘッダ・署名 | `L` | その他のリンク付きレコード |
| `DIR` | 人材ディレクトリ | `AC` | CRM のアカウントレコード |
| `SL` | チャットのメッセージ | `OP` | CRM の商談 |
| `INF` | エージェントが導出 | `ACT` / `TA` | CRM の活動・タスク |
| `ORG` | 組織図 | `UNS` | `{unsourced}` |

マーカーの置き場所:

- `{no-url}` は出所自身の性質なので**定義側**に置く
- `{unconfirmed}` と `{inferred}` は*その事実*の確度を表すので**参照側に残す** —
  さもなければ行ごとの疑いが失われる
- スコープ注記（`（このセクション全体）`）も参照側に置く

参照の位置が適用範囲を示す: 見出し直下の `Source:` 段落はセクション全体、事実の下に入れ子にした
`- Source:` はその事実、出来事ブロック内の同列の `- Source:` はそのブロックに係る。

**Markdown の脚注（`[^1]`）を使ってはならない。** 脚注は CommonMark に含まれない。
GitHub は描画するが、VS Code の組み込み Markdown プレビューを含む多くのビューアは対応しておらず、
しかも目に見えて失敗するのではなく静かに劣化する: `[^1]` はそのままの文字列として残り、
すべての定義が1つの連結された段落に潰れる。上記のキー方式はその可搬な代替である。
`[KEY](#KEY)` はどのパーサでも実際のリンクとして描画され、定義リストは1行1ソースで描画される。

**編集後は検証する。** キー方式は冗長さと引き換えに、機械的な誤り —
未定義キー・孤児定義・重複 — の余地を生む。信頼せず検査する:

```
python3 <skill>/scripts/validate-store.py <データディレクトリ>
```

テーブルの列数、空の `Source` 欄、`Name` 列に残った敬称、旧形式の角括弧マーカー、
出所のない事実行、脚注の使用もあわせて検査する。一括更新の後、および `## Sources` を
手で編集した後には必ず実行する。

以下が実際に使う形式である。先頭のラベルはソースの*種類*を表し、新しい種類も同じ形に従う —
種類＋日付、またはリンク。ファイルパスは決して使わない：

| 形式 | 意味 |
|------|------|
| `meeting 2026-03-19` | その日の打ち合わせでお客様が述べた |
| `user 2026-03-19` | ユーザー（操作者）がエージェントに伝えた |
| `email signature 2026-02-14` | メールのヘッダや署名から読み取った |
| `internal directory 2026-05-01` | 自組織の人材ディレクトリ |
| `[<タイトル> 2026-03-19](https://…)` | ドキュメント・メッセージ・レコード — **リンクで記録する** |
| `doc:<タイトル> 2026-03-19 {no-url}` | 共有可能なアドレスを持たないドキュメント（後述） |
| `inferred 2026-03-19` | エージェントが導出した。誰も明言していない |
| `{unsourced} recorded 2026-03-19` | 出所を特定できなかった |

[コンパニオンスキル](#コンパニオンスキル)は、それが到達するシステム向けに種類を追加してよい。
この表を置き換えるのではなく拡張する。

### 名前より URL を優先する

ソースは他者が到達できて初めて役に立つ。たまたま届いた入れ物ではなく、アドレスを記録する。

- **アドレスが存在するなら必ずリンクで記録する。** ドキュメントライブラリの項目、Wikiページ、
  メッセージのパーマリンク、CRMレコード、課題チケット、公開ページ — いずれも単なるタイトルより
  価値がある。別の人が別の端末で読んでも生き残るからである
- **ローカルのファイルパスを記録してはならない。** `~/Downloads/plan_final_v3.xlsx` は他者にとって
  無意味であり、ファイルが移動した瞬間に自分にとっても無意味になる。これはソースではない
- 一時的なものより安定したものを選ぶ: 単発のダウンロードリンクよりファイルを保持するページや
  レコード、「あのチャットにあるファイル」よりパーマリンク
- 到達可能性を読者に合わせる: 社内ストアには社内Wikiの URL で十分であり、想定読者が開けない
  リンクはソースにならない

### ドキュメントに URL が無い場合

アドレスの無いソースは2通りの経路で発生する: ファイルとして渡された場合と、会話に直接貼り付けられた
内容の場合。次の順で進める — 最後の手段に飛ばさないこと。

1. **アドレスを特定する。** 利用可能なドキュメント検索・メッセージ・CRM のスキルを使って
   そのドキュメントの正規の置き場所を特定し、それをリンクする
2. **ユーザーに確認する。** 「これは URL か恒久的な置き場所がありますか」という1問は、後から誰も
   辿れないソースを残すより安い。一度確認し、その答えを保存する
3. **`{no-url}` を付けて正直に記録する。** ドキュメント自身のタイトルと日付は保持する:
   `doc:FY26 クラウド移行計画 2026-05-12 {no-url}`

会話に貼り付けられた内容には探すべきドキュメントが存在しないため、受け渡しそのものが唯一辿れる
手がかりになる。両方を記録する: `doc:<提示されたタイトル> {no-url} via user 2026-08-20`。
この `via user <日付>` が復元性を担保する — ユーザーはその日に何を渡したかを特定できる。

- **URL を創作してはならない。** もっともらしいリンクは `{no-url}` より悪い。でっち上げた
  打ち合わせ日が `{unsourced}` より悪いのと同じ理由である
- 日付を混同しない: ドキュメント自身の日付が事実の日付であり、受け渡し日はそれが手元に届いた日に
  過ぎない。ドキュメントに日付が無い場合は受け渡し日を記録し、その旨を明示する
  （`recorded 2026-08-20`）
- `{no-url}` は `{unsourced}` ではない。`{no-url}` は*それが何かは分かっているがアドレス化できない*、
  `{unsourced}` は*それが何かが分からない*ことを意味する。`{no-url}` のソースは事実を支えている —
  次の機会にアドレスを解決する

日付と確度はソースとは別に記録する：

- 事実が指す日付を記録し、書き留めた日付と混同しない。記録日しか分からない場合はその旨を明示する
  （`recorded 2026-05-12`）
- 未検証の口頭情報は裏付けが取れるまで `{unconfirmed}` を付す。`Source` は主張の出所を記録するもので、
  それによって主張が検証済みになるわけではない
- 外部ドキュメントから得た事実はその文書に帰属させ、検証済みの事実として断定しない

**出所のロンダリングを禁じる。** ファイル間で事実を転記する場合、またはドキュメントからストアへ
取り込む場合は、元のソースを引き継ぐ。転記元のファイルをソースとして記録してはならない —
起源へ辿る唯一の手がかりを消し、伝聞を事実らしく昇格させる行為である。

### 出所不明の情報の扱い

出所を辿れない事実は必ず生じる: ストアに既に書かれていた、ドキュメントが典拠なしに繰り返している、
誰の発言か記憶に残っていない。破棄はしない — ただし必ず印を付けて残す。

- Source 欄に `{unsourced}` と記録日を併記する。もっともらしいソースで穴を埋めてはならない。
  でっち上げた `meeting 2026-03-19` は `{unsourced}` より悪い — 検証済みに見えてしまうからである
- 出所不明の事実は仮説として扱う: 自分の思考の方向付けと、確認すべき問いを立てるために使う。
  お客様提示物で事実として記述せず、それ単独で推奨の根拠にせず、印を外して他スキルへ渡さない
- 次の機会に検証する — ユーザーに聞く、あるいはお客様に確認する — その上で印を実際のソースに
  置き換える。`{unsourced}` と `{unconfirmed}` のエントリは定期見直しの最優先候補である
  （[保持と剪定](#保持と剪定)参照）
- ソース付きの事実と矛盾する場合はソース付きを優先する。片方を黙って削除せず、矛盾を Notes に
  見える形で残す
- ソース追跡の導入前に書かれたエントリは `{unsourced} pre-existing` とする。当該エントリに触れる
  ときは、出所を推測せずこの印を付ける
