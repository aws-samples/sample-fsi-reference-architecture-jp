# メインフレーム連携 (Mainframe Integration)

## ワークロード概要

本アセットは、BLEA for FSI (金融リファレンスアーキテクチャ日本版) v1.6 の「メインフレーム連携
(Mainframe Integration)」リファレンスアーキテクチャである。本リファレンスアーキテクチャにおける
「メインフレーム」とは、固有の命令セットを持つプロセッサーを搭載し、独自 OS の上で大量の業務データを
処理する基幹系システムが稼働する大型コンピューターを指す。メインフレーム用の OS の例としては、
IBM z/OS、富士通 OS IV/MSP、日立製作所 VOS3、日本電気 ACOS-4 等が挙げられる。

本アセットのスコープは **メインフレームと AWS の間のデータ連携** であり、メインフレーム内部の
アプリケーションロジックは対象としない。以下の 3 つの連携パターンを提示する。

1. **データレプリケーション** — メインフレームのデータを AWS にレプリケーションし、データの活用や
   新規サービスの開発 (分析 / AI / 機械学習、ニアリアルタイムでのビジネス革新、ダウンタイムをほぼ
   ゼロとしたシームレスなアプリケーション移行) を促進する。
2. **非同期メッセージング** — IBM MQ を用いて、直接的な同期結合をせずシンプルな API を通じて
   メインフレームシステムと AWS 上のシステムとの間でデータを交換する。
3. **ファイル転送** — 外部システム連携、分析 / AI / 機械学習、バックアップ / アーカイブ、クラウド
   モダナイゼーションにおけるデータ移行のために、メインフレームと AWS の間でファイルを転送する。

> ここで言及するサードパーティ製ソフトウェア製品の動作を AWS がサポートもしくは保証するものではない。
> 各製品の前提条件や詳細は各ベンダーに確認すること。特に、AWS Mainframe Modernization Data
> Replication with Precisely がサポートするレプリケーション元の環境は IBM z/OS と IBM i (AS/400)
> のみである。

3 つのパターンすべての詳細な技術解説 (基本動作、フェイルオーバー挙動、モニタリング、特性、バリエーション)
は [references/architecture.md](references/architecture.md) にある。

## ベストプラクティスと主要コンポーネント

### ベストプラクティス

- MUST NOT: 多数の AWS 側 MQ クライアントがアクセスするメインフレーム側キューマネージャーのみに依存
  してはならない。クライアントアクセスの集中はメインフレームに過負荷をかけ、メインフレーム側の
  キューマネージャーがダウンすると MQ クライアントが失敗しアプリケーションがエラーになる。
- SHOULD: メインフレーム側と AWS 側の双方にキューマネージャーを立て、両者の間にチャネル接続を確立
  することで、宛先のキューマネージャーがダウンしていてもローカルのキューマネージャーがメッセージを
  受け付け続けられるようにすべきである。
- MUST NOT: メッセージの順序保証が必要な場合 (例: 金融取引)、クラスター全体で順序が維持されないため、
  MQ クラスター (アクティブ/アクティブ) パターンを使用してはならない。
- SHOULD: ダウンしたキューマネージャーが保持する永続メッセージを迅速に復旧する必要がある場合、
  そのキューマネージャーが再起動するまでメッセージが利用不可となるため、MQ クラスターパターンを
  HA 構成と組み合わせるべきである。
- MAY: MQ クラスターパターンではクラスタリングソフトウェアによるインスタンス間同期を前提としない
  ため、IBM MQ をコンテナで稼働させることを検討してもよい。
- SHOULD: メインフレームのアプリケーションやデータの改修は避け、追加した開発がメインフレームの
  負荷を増やさないよう、分析や新規サービスは AWS 側で実装すべきである。
- MAY: VSAM ファイルのレイアウトを定義した COBOL コピーブックをスキーマ情報として利用し、Lambda
  関数で入力データフォーマットを対象テーブルにマッピングしてもよい (Precisely パターン)。
- SHOULD: Precisely コンポーネントの高可用性のため、z/OS 側の Publisher エージェントをアクティブ/
  スタンバイ構成で稼働させ、AWS 側では複数の EC2 インスタンスをマルチ AZ 構成で稼働させて Amazon MSK
  クラスターに供給すべきである。
- MAY: Amazon MSK に対するスループットを高めるため、必要に応じて Apply エージェントに複数の
  ワーカー (コネクターロジックを実行する JVM プロセス) を追加してもよい。
- SHOULD: Apply エージェント、MSK、データベースの CloudWatch Logs とメトリクスをモニタリングし、
  それらを相互参照して問題の発生箇所を特定すべきである。
- SHOULD: AWS 上の HULFT をアクティブ/スタンバイ構成で稼働させる場合、2 つのインスタンス間で
  データを同期するために HULFT がサポートするクラスタリングソフトウェアを使用すべきである。
- MAY: HULFT Cloud Storage Option を使用して Amazon S3 バケットのオブジェクトを直接読み書きしても
  よい。
- SHOULD: バックアップファイルはメインフレームに保持するよりコストを削減できる Amazon S3 バケットに
  格納すべきである。DR のためにクロスリージョンレプリケーションを設定し、長期アーカイブ用に S3
  ストレージクラスを選択する。
- MAY: エラー時のリトライや項目単位のデータ / 文字コード変換が不要な場合、ファイル転送に ftp または
  sftp を使用してもよい (z/OS Communication Server の FTP サーバーと AWS Transfer Family、または
  sftp には z/OS OpenSSH)。
- SHOULD: DR 側の環境に対して、プライマリで採用した連携アーキテクチャと同じ構成を、DR 側の
  メインフレームに合わせて用意すべきである (FISC 実 71 / 実 74 / 実 106)。
- SHOULD: メインフレームと AWS の間のプライマリの AWS Direct Connect 接続の予備として、AWS Direct
  Connect または AWS Site-to-Site VPN による予備接続を設けるべきである (FISC 実 87)。
- WILL: HA 構成はフェイルオーバーをまたいでメッセージ順序を維持し、RTO は数分である。マルチインスタンス
  キューマネージャー構成も順序を維持し、RTO は 30 秒から数分で、共有ファイルストレージを必要とする。
- WILL: z/OS はマルチインスタンスキューマネージャー構成をサポートしておらず、この構成は AWS 側でのみ
  実現できる。

### 主要コンポーネント

#### データレプリケーション (Precisely)

- **コンポーネント概要**: メインフレームのデータ (z/OS 上の Db2 for z/OS、IMS/DB、VSAM、IBM i 上の
  Db2 for IBM i) を AWS のデータストアにレプリケーションする。Log Reader が Db2 のログを Coupling
  Facility (CF) ベースの Log Stream にキャプチャし、LPAR 上のプライマリ Publisher エージェントが
  ログを読み取って AWS 上の Apply エージェントに配信する。アクティブな Apply エージェントが Amazon
  MSK に書き込み、MSK が AWS データストアを更新する。Publisher エージェントは z/OS 上でアクティブ/
  スタンバイで稼働し、Apply エージェントは AWS 上でアクティブ/アクティブで稼働し、コントローラー
  デーモンがフェイルオーバーを処理する。
- **想定される AWS サービス**: AWS Mainframe Modernization Data Replication with Precisely、
  Amazon Managed Streaming for Apache Kafka (MSK)、Amazon RDS (Oracle / Microsoft SQL Server /
  PostgreSQL / Amazon Aurora PostgreSQL) または EC2 上の DB、Amazon S3、AWS Lambda、Amazon EC2、
  Amazon CloudWatch (Logs およびメトリクス)。

#### 非同期メッセージング (IBM MQ)

- **コンポーネント概要**: IBM MQ を用いた、ACID トランザクション保証付きの Point-to-Point および
  publish/subscribe メッセージング。メインフレーム側と AWS 側のキューマネージャーがチャネルで接続され、
  どちらの側からもメッセージを発信でき、相関 ID (correlation ID) によってリクエスト/レスポンスの
  対応付けが可能である。高可用性のキューマネージャーパターンとして次の 3 つを提供する。(2.1) HA 構成
  (アクティブ/スタンバイ)、(2.2) MQ クラスター (アクティブ/アクティブ)、(2.3) マルチインスタンス
  キューマネージャー (アクティブ/ウォームスタンバイ)。
- **想定される AWS サービス**: Amazon EC2 上の IBM MQ (または Amazon ECS / Amazon EKS 上のコンテナ)、
  Amazon Elastic File System (EFS) または Amazon FSx for Windows File Server (マルチインスタンス
  パターン向けの共有ストレージ)、Amazon CloudWatch。

#### ファイル転送 (HULFT / AWS Transfer Family)

- **コンポーネント概要**: メインフレームと AWS の間でファイルを転送する。HULFT for z/OS と AWS 上の
  HULFT の間の HULFT は、バイナリ (無変換) 転送、プラットフォーム間の文字コード変換を伴うテキスト転送、
  固定長レイアウトに対する項目単位のデータ型変換をサポートする。送信前、送信後、受信後のジョブを登録
  できる。HULFT Cloud Storage Option は Amazon S3 オブジェクトへの直接 I/O を可能にする。バリエーション
  として、リトライ / 変換機能が不要な場合には ftp (AWS Transfer Family 経由) または sftp を使用できる。
- **想定される AWS サービス**: Amazon EC2 上の HULFT (HA のための HULFT サポート済みクラスタリング
  ソフトウェアを含む)、Amazon S3 (クロスリージョンレプリケーションおよびアーカイブ用ストレージクラスを
  含む)、AWS Transfer Family、Amazon CloudWatch、Amazon ECS / Amazon EKS / Amazon EC2。

## FISC 準拠サマリー

本アセットは、FISC 安全対策基準の実務基準 (原典の表タイトルは第 12 版) の項目 実 1 から 実 149 に
対してマッピングされている。マッピング表は、項目ごとに、共通統制環境 (ガバナンスベーステンプレート)
の対策と、3 つのパターン (データレプリケーション / 非同期メッセージング / ファイル転送) それぞれに対する
追加の対策 / 考慮事項の両方を記録している。実務基準の項目のみを対象としており、総合的なシステム全体の
安全対策は、ユーザーアプリケーション側および運用 / 開発プロセスにおいて別途検討する必要がある。多くの
項目は、業務アプリケーション、管理 / 運用プロセス、開発プロセスに属する、あるいは AWS クラウド側で
既に対処済みであるため、対象外とされている。代表的な対象内の対策としては、通信の TLS 暗号化 (実 4 /
実 7 / 実 69)、未使用権限に対する IAM Access Analyzer (実 5)、最小権限の IAM (実 25)、KMS 鍵の
ローテーション / 職掌分離 (実 13 / 実 30)、Amazon Inspector とセキュリティグループ (実 20)、
CloudWatch モニタリング (実 46 / 実 47 / 実 101〜実 103)、マルチ AZ アクティブ/スタンバイの可用性
(実 71 / 実 84 / 実 104)、大阪リージョンと Direct Connect / VPN 予備接続による DR (実 74 / 実 87 /
実 106) が挙げられる。

項目ごとの完全な表 (すべてのエントリを保持) は [references/fisc-mapping.md](references/fisc-mapping.md)
にある。
