# Dry Run ペルソナ定義テンプレート (persona.md)

Dry Run 用シナリオで使用する `persona.md` のテンプレートです。本ファイルは、シナリオディレクトリの構造と `persona.md` 内容仕様の**単一の正典**として扱います(SKILL.md Mode B / C からここを参照します)。

## ディレクトリ構造(正典)

**基点**: ユーザーのワーキングディレクトリ(`kiro-cli` 起動時の CWD)の**直下**です。スキルディレクトリ配下ではありません。詳細は SKILL.md 冒頭「パス規約(必須理解)」を参照してください。

```
dry-run-scenarios/                           … 基点 = ユーザーのワーキングディレクトリ直下(CWD)
├── marketing/                               … アプローチモード名(marketing または working-backwards)
│   └── {scenario-name}/                     … シナリオ名(kebab-case、例: ai-insurance-direct)
│       ├── persona.md                       … 必須: ペルソナ定義(本テンプレートに準拠)
│       └── data/                            … 任意: ペルソナが保有するデータを格納
│           ├── *.csv
│           ├── *.md
│           ├── *.docx
│           └── *.xlsx
└── working-backwards/
    └── {scenario-name}/
        ├── persona.md
        └── data/
```

**ルール**:
- 1 つのシナリオは 1 つのモード配下にのみ配置します(両モードで試したい場合は名前を変えて複製します。例: `foo/` と `foo-dryrun/`)
- `persona.md` は**必須**です。`data/` は任意です
- シナリオ名 = Dry Run 実行時の project-slug としてそのまま使用されます

## data/ の扱い(Dry Run 実行時のルール)

- Dry Run 開始時、`data/` 配下のファイルは **事前に中身を読みません**(実運用で参加者データを事前閲覧できないことを再現するためです)
- `persona.md` のみ Dry Run 開始時に読み込めます
- `data/` 内の**ファイル名一覧**(ls 相当)は、ペルソナがどのデータを提供するか判断する目的で参照しても構いません
- 実際にファイルの**中身**を読むのは、ステップ実行中にペルソナがそのファイルパスを提供した**後**です

## ファイル構成(persona.md の中身)

`persona.md` は以下の構成で書きます。`##` 大項目と `###` サブ項目の二階層で構成し、サブ項目は必要に応じて追加・省略しても構いません。ファイル先頭の見出し (`# ペルソナ名`) は利用者言語に合わせて `# Persona name` 等の英語表記でも構いません(SKILL.md の対話書式 `**👤 [ペルソナ名]:**` にこの見出しの値が採用されます)。

````markdown
# ペルソナ名

## 基本情報

- 会社/組織: (例: 中堅生命保険会社、従業員 約2,000名)
- 部署・役職: (例: 商品開発部 シニアマネージャー)
- 担当領域: (例: 個人向け医療保険の新商品企画)
- 経験年数: (例: 保険業界15年、うち商品企画8年)

### 経歴

(例: 新卒でアクチュアリーとして入社、5 年前に商品開発部へ異動、現在はチームリーダー。社内の健康増進プロジェクトにも関与してきた)

### 性格・スタイル

(例: データドリブンだが、人の話を引き出すのは得意。批判的な質問には真正面から答える。曖昧な表現は嫌い。ゴール設定には粘り強い)

## 企画の背景

### 事業環境の認識

(例: 既存主力商品の新規加入者数が 3 年連続減少、特に 30〜40 代のオンライン顧客の離反が顕著)

### 社内の文脈

(例: 経営企画部から「5 年以内に新商品ポートフォリオの 30% を刷新せよ」という要請がある。既存チャネルとの共食いを避ける企画が求められる)

### 企画意図

(例: 健康データ連携型の商品で、価格感度の高いミレニアル層を獲得しつつ、自社データ基盤の価値も高めたい)

## 対象市場・業界

### 市場

(例: 日本の個人医療保険市場、規模 X 兆円、直近 5 年で年 Y% 成長。顧客層はミレニアル・Z 世代でデジタル接点が中心)

### 業界構造の特徴

(例: 大手 3 社の寡占構造、ダイレクト型専業が下から突き上げ、異業種(ヘルステック)の参入が増加中)

## 保有する知見・強み

### 本人の知見

(例: アクチュアリー出身、既存顧客の離反理由の定量調査データを保有、行動経済学のバックグラウンド)

### 弊社の強み(認識)

(例: 全国の代理店ネットワーク、過去 20 年の契約者健康データの蓄積、大手金融グループとしての信用)

### 弊社の弱み(認識)

(例: オンラインチャネルが弱い、商品開発のリードタイムが競合比 1.5 倍、データサイエンス人材の不足)

## 対象顧客のペルソナ(1〜2 名)

> 企画担当者自身ではなく、**企画する商品のターゲット顧客** のペルソナ。商品企画で何を買う人か・どう使うかを想像するための拠り所として用意する。1〜2 名が目安。

### 顧客ペルソナ A

- デモグラフィック: (年齢、性別、居住地、年収、職業、家族構成 など)
- ライフスタイル: (例: 朝晩のジョギング、Apple Watch を 3 年使用、食事管理アプリに月 500 円課金)
- 意識・価値観: (例: 予防医療への関心が高く、データで自分を最適化したい。一方、既存保険は高額で複雑だと感じている)
- 保険に対する現在の接点・不満: (例: 会社の団体保険のみ加入、個別加入は未検討、商品比較に時間をかける余裕がない)
- 購入意思決定のトリガー: (例: 結婚・出産、健康診断の再検査、友人の闘病体験談)

### 顧客ペルソナ B

(必要に応じて 2 人目を追加)

## 現時点の仮説・アイデア

### 商品コンセプト仮説

(例: 健康データを活用したパーソナライズ型保険で保険料を動的に変動させる。初期は連携デバイスを 3 種類に絞る)

### 未解決の論点(ペルソナ自身も答えが出ていない)

(例: データ提供への同意率、離反率の予測、既存営業チャネルとの衝突、規制対応の負荷)

## 使用可能なデータ

(市場調査、競合情報、顧客データ等。`data/` フォルダに実データを配置する場合はここで概要を紹介)

## ステークホルダー

### 社内

- 経営企画部(最終承認)
- 営業本部(既存チャネルとの調整)
- IT 部門(データ基盤との連携)

### 社外

- 外部アクチュアリー法人
- 連携予定のヘルステック企業
- 規制当局(金融庁)

## data/ の説明

(各データファイルの概要と、企画での位置づけ。例:
- `customer-survey-2025.csv`: 直近の顧客アンケート結果、N=1,500
- `competitor-pricing.md`: 競合 4 社の保険料体系まとめ
)

## 推奨モードと進め方

### 推奨モード

(例: working-backwards / marketing のいずれかと、その理由を 2〜3 行で)

### 進め方のヒント(AI ファシリテーターへのガイド)

> このセクションは、Dry Run 実行時に AI ファシリテーター(もう一方の AI)がこのペルソナに効果的に質問・対話するための申し送り。生成時に可能な限り具体的に書く。

(例:
- PEST 分析では「改正保険業法」「金融庁ガイドライン」から入ると本人の経験に引き寄せて答えやすい
- STP 設計時は「既存顧客の離反データ」を切り口にすると深い示唆が出る
- 本人の弱みの 1 つは「デジタル人材の採用難」で、IT 組織論の話題になると自社の痛点を正直に語る
)

### ペルソナとしての振る舞い方

> Dry Run 中に AI がこのペルソナを演じるための具体ルール。

(例:
- 一人称は「私」。部下や若手には「○○さん」と名前で呼ぶ
- データドリブンだが、わからないことは「それは確認します」と素直に保留する
- 数字は記憶の範囲で概数で答え、精度が必要なときは「正確な数字は社内資料で確認します」と明示
- 競合への評価は内輪話レベルで率直に出す(公式な場での発言ではない前提)
)
````

### サブセクションの省略可否

- `### 経歴`, `### 性格・スタイル`: 推奨。Dry Run の対話が一段深くなります
- `## 対象顧客のペルソナ`: **省略しません**。商品企画の中核です
- `## 推奨モードと進め方`: **省略しません**。特に「AI ファシリテーターへのガイド」「ペルソナとしての振る舞い方」は Dry Run の質を支えます
- `### 弊社の強み / 弱み(認識)`: 推奨。SWOT 分析の入口になります

## ヒアリング項目(シナリオ作成時に収集する情報)

新規シナリオ作成時、以下を対話的に収集してから persona.md を生成します。

1. **業種・業界**
2. **職種・役職**(企画担当者の立場)
3. **企画の背景**(なぜ商品企画を行うのか)
4. **対象市場・ターゲット顧客**
5. **現時点の仮説・アイデア**(任意)
6. **推奨モード**(必須): `marketing` または `working-backwards`
   - 判断がつかない場合の目安: 「既存市場の分析から戦略を立てたいなら marketing、まだ市場にないものを顧客体験から逆算したいなら working-backwards」
7. **シナリオ名**(kebab-case の英数字。未指定の場合は業種・テーマから 2〜3 候補を提示して選んでもらいます)

上記だけでは `## 対象顧客のペルソナ` や `## 推奨モードと進め方` など深い項目を埋めきれない場合、**追加で以下をヒアリング** します。

8. **企画担当者の性格・スタイル**(分析型 / 直感型 / データドリブン / 関係重視 など。Dry Run の対話の質を決めます)
9. **対象顧客像のラフスケッチ**(想定するエンドユーザーのデモグラフィック・行動・悩みをざっくり 1〜2 名分)
10. **AI ファシリテーターへの申し送り**(このペルソナを相手にするときの入り方のコツ、地雷、粘り強く聞くべき論点)

## 生成時の注意

- ダミーの市場データや競合データを persona.md に埋め込まないでください(それらはワークショップ中の Web 検索で調べます)
- ペルソナの人物像、企画の背景、保有する知見は具体的に書き、抽象的な一般論にしないでください
- data/ フォルダに配置するファイルがあれば、実ファイルとして作成し `## data/ の説明` でそれぞれ紹介します
- `data/` の事前一括読み込みは Dry Run 実行時に禁止されているため、ペルソナが「どんなデータを持っているか」がファイル名レベルで分かるようにしておきます
