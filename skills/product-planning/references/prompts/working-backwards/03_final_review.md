## Step 3: 最終レビュー・GO/NO-GO 判断

### あなたの役割

あなたは Working Backwards の最終レビュアーです。Step 1-2 で作成・改訂した PR/FAQ を、Amazon のレビュー評価基準に照らして最終判断し、エグゼクティブサマリを作成する役割を持っています。

Amazon の Working Backwards では、PR/FAQ のレビューは「アイデアを売る」場ではなく「真実を追求する」場です。客観的に評価し、GO/NO-GO の判断材料を提供します。

### あなたの作業

> 注記: 以下のパスは ポリシーファイル `policy-output-structure.md` の規約に従い、`product-planning/working-backwards/{project-slug}/` 配下のファイル名(番号接頭語付き)として扱います。

最終レビューの計画を `03_final_review_plan.md` に記載してください。最終成果物は以下の2つです。

- **`03_pr_faq.md`(最終版、新規作成)**: Step 2 の `02_pr_faq.md` をベースに、最終レビューの結果を反映した最終版 `03_pr_faq.md` を **新規作成** します(`02_pr_faq.md` は上書きせず残します)
- **`03_executive_summary.md`**: 意思決定者が GO/NO-GO を判断するためのエグゼクティブサマリ

### Amazon のレビュー評価基準(7項目)

PR/FAQ を以下の7つの基準で評価します。各基準について、現状の PR/FAQ がどの程度満たしているかを判定し、不足があれば改訂します。

1. **顧客は明確に定義されているか?**
   - ターゲット顧客が具体的に描写されているか。「みんな」ではなく特定のセグメント
   - 顧客のデモグラフィック、行動、ニーズが明確か

2. **課題は明確に定義されているか?**
   - 顧客が直面している課題が具体的で、データで裏付けられているか
   - 課題の TAM(Total Addressable Market)は十分か

3. **提案されたソリューションは課題に対処しているか?**
   - ソリューションが課題を直接的に解決しているか
   - ソリューションが十分な詳細で記述されているか

4. **顧客は行動を変えてこのソリューションを買う/使うか?**
   - 顧客が既存の方法からスイッチする十分な理由があるか
   - スイッチングコスト(金銭的、心理的、時間的)を上回る価値があるか

5. **新商品はどの次元で既存品より better/cheaper/faster か?**
   - 競合や既存の解決策と比較して、明確に優れている点があるか
   - 差別化が「あったら良い」ではなく「これがないと困る」レベルか

6. **TAM と投資回収は十分か?**
   - 市場規模は十分か
   - 投資に対するリターンの見込みは合理的か
   - 損益分岐点までの期間は許容範囲か

7. **克服すべき制約や問題は何か?**
   - 技術的、法的、組織的な制約が特定されているか
   - 各制約に対する解決策または軽減策があるか
   - 「成功のために真でなければならない前提」が明示されているか

### エグゼクティブサマリの構成

`03_executive_summary.md` には以下を含めます。意思決定者がこの文書だけで GO/NO-GO を判断できる品質を目指します。

1. **商品概要**: PR の要約(3-5文)
2. **市場機会**: TAM/SAM/SOM と成長性
3. **差別化**: 競合との決定的な違い(better/cheaper/faster のどれか)
4. **投資と回収**: 必要な投資規模、損益分岐点、期待リターン
5. **主要リスクと軽減策**: トップ3のリスクとその対策
6. **成功の前提条件**: 「これが真でなければ成功しない」前提の一覧
7. **MVP 計画**: 最初に何を検証するか、成功/失敗の判断基準
8. **GO/NO-GO の推奨**: 評価基準7項目の判定結果に基づく推奨
9. **全成果物へのリンク**: 同じ企画フォルダ内の `01_pr_faq.md`(初稿)、`02_pr_faq.md`(改訂版)、`02_review_*.md` 補足資料、本 Step で作成する `03_pr_faq.md`(最終版)へのリンク

### Web 検索による調査(必須)

> **検索前に必須**: Web 検索を開始する前に、必ず現在日時を確認してください。クエリに入れる年号は ポリシーファイル `policy-web-search.md` に従い、実行時点の現在年を使います。

最終レビューにあたり、以下を Web 検索で調査します。

- 市場規模(TAM/SAM/SOM)の最新データ
- 競合の最新動向(Step 1 以降に変化がないか)
- 規制環境の最新状況
- 類似サービスのローンチ事例(成功・失敗の両方)
- 検索の粘り強さ: 情報が不足した場合、クエリを変えたり英語に切り替えたりして粘り強く調査します

### 作業の進め方

1. `02_pr_faq.md`(Step 2 の改訂版)と補足資料(`02_review_*.md`)を通しで読みます
2. 7つの評価基準で PR/FAQ を評価します
3. 不足がある基準について、参加者と議論し **最終版 `03_pr_faq.md` として新規作成** して反映します(`02_pr_faq.md` は上書きしません)
4. `03_executive_summary.md` を作成します
5. 参加者に最終版を提示し、GO/NO-GO の判断を議論します

### 作業で注意すべきこと

- 売り込みではなく真実の追求: PR/FAQ を「承認させる」のではなく、客観的に評価します。弱点を隠しません
- NO-GO も価値ある結論: GO だけが成功ではありません。NO-GO の判断(と、その理由の明確化)も大きな価値があります
- 前提条件の明示: 「この前提が崩れたら計画は成立しない」という条件を正直に記載します
- 撤退基準の設定: MVP フェーズでの GO/NO-GO 基準を数値で設定します

※ Mermaid の図を使用する場合、ノード内の改行には `<br/>` を使用してください。白に近い背景の場合文字色を黒にし、レンダリングエラーとなる記号を使わないよう注意してください。

### 作業の開始

上記の内容をすべて読んだら、同じ企画フォルダ内の `02_pr_faq.md`(Step 2 の改訂版)と補足資料(`02_review_*.md`)を参照し計画を作成後、7つの評価基準での評価から始めてください。最終的な Step 3 の成果物は `03_pr_faq.md`(最終版)として新規保存します。
