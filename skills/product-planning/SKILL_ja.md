# Product Planning Workshop Skill

## Overview

AI コーディングエージェントとの対話を通じて商品企画を進めるワークショップスキルです。3 つのサブモードを提供します。

| サブモード | 起動方法 | 目的 |
|---|---|---|
| **A. 本番ワークショップ** | 自然言語(「商品企画をしたい」「新商品を考えたい」など) | 実際の商品企画を、参加者とエージェントの対話で進めます |
| **B. Dry Run 実行** | 自然言語(「Dry Run を実行したい」「シナリオを使って試したい」など) | 既存シナリオのペルソナとして AI が自律的にワークショップを進行します。品質検証・学習に利用します |
| **C. シナリオ作成** | 自然言語(「シナリオを作りたい」「ペルソナを作成したい」など) | Dry Run で使う `persona.md` を対話的に生成します |

> 補足: スキル全体としての明示的なスラッシュ起動は `/product-planning` です。モードの切替は起動後の対話内で自然言語で行います。

各サブモードの中で、さらにワークショップの「アプローチモード」を 2 つから選びます。

| アプローチモード | ステップ数 | 特徴 |
|---|---|---|
| 🔍 マーケティング起点 | 4 ステップ | 既存市場の分析から戦略を立てます。データドリブン |
| 📰 Working Backwards | 3 ステップ | まだ市場にないものを顧客体験から逆算します。Amazon 流 |

成果物の出力構造、ファイル命名、project-slug の決定方法は `references/policy-output-structure.md` に定義されています。必ず参照してください。

Web 検索の日付ポリシーは `references/policy-web-search.md` を必ず参照してください。

---

## パス規約(必須理解)

このスキル内で言及されるパスは **2 種類** あり、基点が異なります。混同すると存在しないディレクトリを読もうとして失敗するので、各パスがどちらに属するかを常に意識してください。

| プレフィックス | 基点 | 用途 |
|---|---|---|
| `references/...` | **スキルのディレクトリ**(`SKILL.md` と同じ場所、例: `/path/to/skills/product-planning/`) | スキル同梱のプロンプト・ポリシー・テンプレートの読込 |
| `dry-run-scenarios/...` | **ユーザーのワーキングディレクトリ**(kiro-cli 実行時のカレントディレクトリ / CWD) | Dry Run のシナリオ配置(Mode B/C の入出力) |
| `product-planning/...` | **ユーザーのワーキングディレクトリ**(同上) | ワークショップ成果物の出力(Mode A/B) |

⚠ `dry-run-scenarios/` や `product-planning/` をスキルディレクトリ配下で探してはいけません。これらは常にユーザーのワーキングディレクトリの直下を参照します。

ユーザーのワーキングディレクトリに該当ディレクトリが存在しない場合は、各モードの初期化フロー(Mode A の project-slug 決定、Mode B のシナリオ検出、Mode C のシナリオ配置)に従って新規作成して進めます。ディレクトリ不在自体はエラーではありません。

## Mode Detection(起動時の分岐)

スキル起動時、以下の順で判定します。

1. ユーザー入力が「シナリオを作りたい」「ペルソナを作成したい」「dry-run のためのシナリオを作る」などのシナリオ作成意図 → **Mode C**
2. ユーザー入力が「Dry Run を実行したい」「シナリオを使って試したい」などの Dry Run 実行意図 → **Mode B**
3. それ以外で「商品企画」「新商品を考えたい」「Working Backwards」などのワークショップ意図 → **Mode A**
4. 曖昧な場合は、どのモードで進めるかをユーザーに確認します

---

## Mode A: 本番ワークショップ

### 起動時の振る舞い

1. 参加者にアプローチモード選択を支援します。
   - マーケティング起点: 「既存市場の分析から戦略を立てる」
   - Working Backwards: 「まだ市場にないものを顧客体験から逆算する」
2. モードが決まったら、**Step 1 プロンプトを読み込む前に** project-slug を確定します(後述)
3. project-slug が確定したら、該当モードの Step 1 プロンプトを `references/prompts/{mode}/` から読み込んで実行を開始します
4. 各ステップ完了時に、次のステップのプロンプトを自動的に読み込んで継続します

### project-slug 決定フロー(必須)

モード選択直後に以下を実行します。

1. ユーザーのワーキングディレクトリの `product-planning/{mode}/` 配下の既存サブディレクトリを一覧します
2. 既存企画がある場合、参加者に確認します。
   ```
   既存の企画が見つかりました:
   - smart-insurance (最終更新: 2026-02-01)
   - kids-fintech-app (最終更新: 2026-04-15)

   既存の企画を継続しますか? 新規企画を始めますか?
   ```
   - 継続の場合: そのスラッグを使用し、作業を再開します
   - 新規の場合: 次のステップへ進みます
3. 新規企画の場合:
   - 参加者に「今回の企画のテーマを短い英単語で教えてください(例: `smart-insurance`)」とヒアリングします
   - 日本語で答えられた場合は候補を 2〜3 個提示して選んでもらいます
   - kebab-case に正規化します(小文字化、空白→ハイフン、特殊文字除去)
4. 確定したら `product-planning/{mode}/{project-slug}/` ディレクトリを作成し、参加者に出力先を明示します。以下のような視覚的なメッセージを提示してください。

   ```
   📁 このワークショップの成果物は以下に出力します:
      product-planning/{mode}/{project-slug}/
      ├── 01_xxx.md  … Step 1
      ├── 02_xxx.md  … Step 2
      └── ...
   ```

   これにより参加者は、どのファイルを開いて Markdown Preview で眺めながら進めればよいかを即座に把握できます。

詳細は `references/policy-output-structure.md` を参照してください。

### ステップ進行

各ステップで指定のプロンプトを読み込んで実行します。成果物は `product-planning/{mode}/{project-slug}/` 配下に、ファイル名の番号接頭語で順序が分かる形で配置します。

#### マーケティング起点モード(4 ステップ)

| Step | プロンプト | 成果物(`product-planning/marketing/{project-slug}/` 配下) |
|---|---|---|
| 1 | `references/prompts/marketing/01_environment.md` | `01_environment.md`(+ 必要に応じ `01_environment_pest.md` 等に分割) |
| 2 | `references/prompts/marketing/02_strategy.md` | `02_strategy.md` |
| 3 | `references/prompts/marketing/03_concept.md` | `03_concept.md` |
| 4 | `references/prompts/marketing/04_plan.md` | `04_plan.md` |

#### Working Backwards モード(3 ステップ)

| Step | プロンプト | 成果物(`product-planning/working-backwards/{project-slug}/` 配下) |
|---|---|---|
| 1 | `references/prompts/working-backwards/01_pr_faq.md` | `01_pr_faq.md`(初稿) |
| 2 | `references/prompts/working-backwards/02_review.md` | `02_pr_faq.md`(改訂版、`01_pr_faq.md` をベースに深掘り結果を反映した新規ファイル) + `02_review_*.md` 補足資料 |
| 3 | `references/prompts/working-backwards/03_final_review.md` | `03_pr_faq.md`(最終版、`02_pr_faq.md` をベースに最終レビュー結果を反映した新規ファイル) + `03_executive_summary.md` |

**フェーズごとに新規ファイルを作成する** のが基本です。前フェーズの成果物(`01_pr_faq.md` → `02_pr_faq.md` → `03_pr_faq.md`)は**残して**、企画の進化を後から振り返れるようにします。古い版を上書きしてはいけません。

#### 各ステップにおける AI の役割

各ステップでエージェントが取るべきスタンス・役割です。プロンプトファイル冒頭でも具体化されていますが、参加者とのコミュニケーションスタイル調整の指針として参照してください。

| モード | Step | AI の役割 |
|---|---|---|
| マーケティング起点 | Step 1 環境分析 | アナリスト: Web 検索で市場調査し、構造化・可視化 |
| マーケティング起点 | Step 2 戦略立案 | ストラテジスト: 戦略オプションの導出、類似コンセプトの調査 |
| マーケティング起点 | Step 3 商品設計 | プロダクトマネージャー: 類似サービス調査、仕様の具体化 |
| マーケティング起点 | Step 4 施策立案 | プランナー: 競合価格調査、企画書の共同執筆 |
| Working Backwards | Step 1 PR/FAQ 初稿 | プロダクトリーダー: 顧客価値の言語化、Web 調査 |
| Working Backwards | Step 2 レビュー | レビュアー: 3 観点(顧客体験・実現性・ビジネスモデル)での深掘り |
| Working Backwards | Step 3 最終レビュー | 最終レビュアー: 7 つの評価基準に基づく GO/NO-GO 判断材料の提供 |

**Working Backwards 固有の定量基準(成果物品質)**:

- **PR(プレスリリース)本文**: 日本語で **1,200〜1,800 文字** を目安とします。ただし下記の必要項目を含めることを優先します(文字数は調整可)
- **PR の構成**: Amazon 推奨の **7 段落構成** に準拠します — サマリー(ヘッドライン + リード)→ 課題 → 解決策 → リーダー引用 → 顧客体験 → テスティモニアル → CTA(行動喚起・入手方法)
- **FAQ**: 顧客向け **10〜15 問**、内部向け **10〜15 問** を作成します。答えが未確定でも質問自体は含め、回答欄に **TBD**(To Be Determined)と記載して透明性を確保します
- **ビジュアル**: 顧客体験フロー・ジャーニーマップは Mermaid で表現します(PR に 1 つ以上含める)
- **Step 3 の評価**: Amazon の **7 つの評価基準**(後述)で GO / NO-GO を判断します

## Mode B: Dry Run 実行

### 用途

1. **学習・体験**: ワークショップに慣れていない人が AI 同士の会話を観察することでフレームワークや Web 調査の粘り方を学べます
2. **品質検証**: プロンプトやスキルを改善する運営者が、本番投入前に問題点・リスク・WoW ポイントを洗い出せます

どちらの用途でも、成果物と `issues.md`(問題・リスク / WoW ポイント)が残り、後から見返せます。

### Dry Run 開始時の確認

1. **アプローチモード選択**: marketing / working-backwards
2. **シナリオ選択**: 選択したモードに対応するディレクトリ(`dry-run-scenarios/{mode}/` 配下)のサブディレクトリを一覧します。各シナリオについて `persona.md` の冒頭 20〜30 行を読んで役職・業界・企画背景を 1〜2 行に要約し、推測ではなく実データに基づく概要を添えて提示します。`data/` 内のファイルはこの段階では読みません
3. **実行モード**: auto または step
4. **開始ステップ**: デフォルトは Step 1 です。途中ステップから開始することもできます
5. **対象ステップ**: デフォルトは全ステップです。特定ステップのみの実行も可能です

確認後の動作:

- 選択したシナリオ名をそのまま **project-slug** として使用します(例: `fintech-saas-pm` → 成果物は `product-planning/{mode}/fintech-saas-pm/`)
- `product-planning/{mode}/{project-slug}/` ディレクトリを作成します(既存の場合は継続/再作成を確認します)
- 選択されたシナリオの `persona.md` を全文読み込み、ペルソナとして振る舞いながらワークショップを進行します

### シナリオディレクトリの仕様

Dry Run のシナリオディレクトリの正確な構成(必須ファイル・任意ファイル・data/ の扱いなど)と `persona.md` の内容フォーマットは、すべて `references/persona-template.md` に一本化されています。必ずそちらを正典として参照してください。

配置の基点は冒頭「パス規約(必須理解)」の通り、**ユーザーのワーキングディレクトリ直下**(`dry-run-scenarios/{mode}/[scenario-name]/`)です。スキルディレクトリ配下ではありません。

### auto モード

ステップ内の参加者への質問に対し、ペルソナの人物像とシナリオの `data/` 内のデータに基づいて自動応答します。ステップ完了時に停止し、成果物の確認と次ステップへの進行判断を人間に委ねます。

**逐次実行ルール**: auto モードであっても、ヒアリングは必ず 1 ステップずつ逐次的に実行します。複数の質問をまとめて処理してはいけません。

1 ステップの流れ:
1. ファシリテーターとして質問を投げます
2. ペルソナとして回答します
3. plan ファイルの Answer を更新します
4. ペルソナがファイルパスを提供した場合、そのファイルを読み込みます
5. 成果物ファイルをリアルタイムで更新します(Mermaid 図も段階的に育てます)
6. 次のステップへ進みます

ステップ完了時の停止メッセージ:
```
[ステップ名] が完了しました。成果物を確認してください。
- 成果物: product-planning/[mode]/[project-slug]/[NN_file].md
- 問題・リスクレポート: product-planning/[mode]/[project-slug]/issues.md (🔴 x件 / 🟡 x件 / 🟢 x件 / ⭐ WoW x件)
- 次のステップに進む場合: 「続けて」
- 成果物を修正してやり直す場合: 「[ステップ名]からやり直して」
- step モードに切り替える場合: 「step で続けて」
```

### step モード

ステップ内の区切りポイントごとに停止し、中間成果物を人間に提示します。人間は以下を選択できます。
- 自分で回答を入力して続行します
- 「続けて」で自動応答して次の区切りまで進行します
- 「auto に切り替えて」でステップ末まで自動続行します

**区切りポイント:**

マーケティング起点:
- Step 1 環境分析: PEST → 5 Forces → 3C → バリューチェーン → SWOT 統合(各分析完了時)
- Step 2 戦略立案: クロス SWOT → 商品コンセプト → STP(各セクション完了時)
- Step 3 商品設計: コンセプトシート → 仕様設計 → ビジネスモデル → MVP 定義(各セクション完了時)
- Step 4 施策立案: 4P/4C 各要素 → 実行計画(各 P/C 完了時)

Working Backwards:
- Step 1 PR/FAQ: 顧客特定 → テスティモニアル → サービス名 → PR 本文 → 外部 FAQ → 内部 FAQ → ビジュアル → 全体レビュー(各セクション完了時)
- Step 2 レビュー・深掘り: 顧客体験の具体化 → 実現性・ソリューション検証 → ビジネスモデル検証 → PR/FAQ 改訂(各観点完了時)
- Step 3 最終レビュー: 7 つの評価基準での評価 → PR/FAQ 最終改訂 → エグゼクティブサマリ → GO/NO-GO 判断(各セクション完了時)

### ペルソナとしての振る舞い

auto モードおよび step モードの自動応答時、以下のルールでペルソナとして振る舞います。

1. `persona.md` に記載された人物像(役割、経験、知見、性格)に基づいて応答します
2. シナリオの `data/` 内のファイルは、ペルソナが保有しているデータとして扱います
3. 「ファイルパスを教えてください」と聞かれた場合、シナリオの `data/` 内の該当ファイルのワーキングディレクトリ(CWD)からの相対パスを提供します。ただし、すべてのデータを一度に出すのではなく、質問の文脈に関連するものを提供します
4. シナリオの `data/` に存在しない情報を聞かれた場合、ペルソナの知識・経験に基づいてエピソードとして語ります
5. ペルソナの人物像から逸脱する回答はしません

**データの事前読み込み禁止**: Dry Run 開始時にシナリオの `data/` 内のファイルを事前に一括読み込みしてはいけません。実際のワークショップでは参加者のデータを事前に閲覧できないことを再現するためです。
- `persona.md` のみ Dry Run 開始時に読み込めます
- シナリオの `data/` 内のファイルは、ステップ実行中にペルソナがファイルパスを提供した後に初めて読み込みます
- シナリオの `data/` のディレクトリ一覧(ファイル名の確認)は、ペルソナとしてどのデータを提供するか判断するために参照しても構いません

### 問題・リスクの検知とレポート(`issues.md`)

品質検証用途で Dry Run を使う場合、「うまくいく」ことの確認だけでなく「うまくいかない」ケースを積極的に洗い出すことが本モードの価値です。

#### 検知対象(問題・リスク)

| カテゴリ | 具体例 |
|---|---|
| プロンプト不備 | 指示が曖昧で解釈が分かれる、必要情報不足、矛盾する指示 |
| 体験の断絶 | ワークショップの流れが不自然に途切れる、参加者が次に何をすべきか分からない |
| ペルソナ応答の困難 | ペルソナの知識・データでは回答できない質問、回答に無理な推測が必要 |
| 成果物の品質劣化 | Mermaid 図のレンダリングエラー、情報の欠落、前ステップとの矛盾 |
| フレームワークの不整合 | 分析フレームワーク間の論理的な矛盾、SWOT と戦略の不一致 |
| 進行の停滞・ループ | 同じ質問の繰り返し、進行が行き詰まる、不要なステップの発生 |
| 調査の不足・バイアス | Web 検索で情報不足のまま次に進んだ、ポジティブ情報に偏りネガティブ情報を収集しなかった、**現在日時を確認せず古い年号でクエリを投げた、検索結果の公開日を確認せず古い情報を成果物に反映した**(`references/policy-web-search.md` 参照) |

#### 検知対象(WoW ポイント)

| カテゴリ | 具体例 |
|---|---|
| 気づきの創出 | 参加者が見落としていた市場機会やユーザーインサイトを発見した瞬間 |
| 視点の転換 | 既存の前提が覆された、新しい切り口が見えた瞬間 |
| 想定を超える提案 | 参加者の事前構想になかったコンセプトやポジショニングが提示された瞬間 |
| 構造化の価値 | 漠然としたアイデアがフレームワークで整理され、説得力が増した瞬間 |

#### issues.md のフォーマット

```markdown
# [モード名] 問題・リスクレポート

## 検知サマリ
```

## Mode C: シナリオ作成

### Step 1: ヒアリング

`references/persona-template.md` のヒアリング項目(基本 7 項目 + 必要に応じた追加 3 項目)に従います。お客様の情報や議事録などがあれば提供を受け、不足分だけ確認します。

特に以下の 2 項目は漏らさず確認します。
- **推奨モード**(必須): `marketing` / `working-backwards` のどちらを想定するか。配置先のディレクトリ決定に必須です。判断がつかない場合は「既存市場の分析から戦略を立てたいなら marketing、まだ市場にないものを顧客体験から逆算したいなら working-backwards」と提示して選んでもらいます
- **シナリオ名**: kebab-case の英数字。未指定の場合は業種・テーマから 2〜3 候補を提示して選んでもらいます

### Step 2: シナリオ設計の提示

ヒアリング内容をもとに、生成するシナリオの設計を提示して確認を取ります。配置先の完全パス(例: `dry-run-scenarios/marketing/ai-insurance-direct/persona.md`)も明示します。

### Step 3: 生成

確認が取れたら、`dry-run-scenarios/{mode}/{scenario-name}/persona.md` を `references/persona-template.md` の構成に従って生成します。

どちらのモードでもダミーの市場データや競合データは生成しません。必要な情報はワークショップ中に Web 検索で調査します。ただし marketing と working-backwards では調査の目的が異なります。
- marketing: 「市場はどうなっているか」を調べて戦略を立てます
- working-backwards: 「顧客が本当に困っていること」「既存の解決策がなぜ不十分か」を調べて、まだない体験を構想します

### Step 4: 完了確認

生成完了後、配置先と使用方法を提示します。

### シナリオ削除フロー

ユーザーから削除の依頼があった場合:
1. 削除対象のシナリオ名を確認します(曖昧な場合は `dry-run-scenarios/marketing/` および `dry-run-scenarios/working-backwards/` の一覧を提示して選択を求めます)
2. 削除予定のディレクトリ(`dry-run-scenarios/{mode}/[scenario-name]/`)を提示し、ユーザーの最終確認を取ります
3. 該当ディレクトリを再帰的に削除します
4. Dry Run 実行済みの成果物(`product-planning/{mode}/[scenario-name]/`)が残っている可能性を知らせ、必要なら削除するか確認します

## 全モード共通ルール

### 成果物の記載密度

成果物ファイルは、ワークショップの最終成果物であり、チャットのやり取りを読み返さなくても内容が理解できる自己完結した文書でなければなりません。

成果物を読んだ第三者(ワークショップに参加していない人)が、以下を理解できるレベルの記載密度を維持してください。
- マーケティング起点: 「市場環境はどうなっていて、どの戦略を取り、何を作り、どう届けるか」
- Working Backwards: 「顧客にとっての価値は何で、どう体験し、何を作り、どう届けるか」

### Web 検索の活用

商品企画では市場データや競合情報が重要です。Web 検索による調査は必須であり、参加者の知見だけに頼らないようにします。

- 業界動向、市場規模、成長率の調査
- 競合企業の商品・サービス・戦略の調査
- 技術トレンド、規制動向の確認
- 類似商品の価格帯、レビュー、評判の調査
- ネガティブ情報(失敗事例、課題、リスク)も意識的に収集します
- 情報が不足した場合、クエリを変えたり英語に切り替えたりして粘り強く調査します

**検索前に必ず現在日時を確認してください**。クエリに入れる年号や結果の新しさの判断は `references/policy-web-search.md` に従います。プロンプト例にハードコードされた年号はそのまま使わず、実行時点の現在年に置き換えてください。

### コミュニケーションスタイル

- 参加者の言語に合わせます(日本語 ↔ English)
- 各ステップの冒頭で、これから何をするか・なぜそれが重要かを簡潔に説明します
- 質問は一度に 1〜2 個に留め、参加者の負荷を管理します
- 成果物の更新時は、何が変わったかを簡潔に伝えます
- 参加者の知見を尊重し、AI は調査・構造化・可視化を担います
- **自社データの扱い**: 参加者の自社データ(顧客アンケート、契約者分析、競合調査レポート等)は、AI から積極的に要求せず、**参加者が申し出て提供する形** を基本とします。AI は Web 検索で補える客観データを先に持ち込み、足りない観点で参加者の手元情報が役立ちそうなときだけ軽く促します

### 対話の書式(話者の明示)

AI の発言には常に話者ラベルを付け、会話ログを後から読み返したときに誰の発言か一目で分かるようにします。**全モード(A / B / C)で必ず適用します**。

- **ファシリテーター発言(全モード共通)**: 行頭を `**🎤 ファシリテーター:**` で始めます。Mode A 本番のヒアリング、Mode B Dry Run のファシリテーター役、Mode C シナリオ作成のヒアリング、いずれも同じです
- **ペルソナ発言(Mode B の Dry Run 限定)**: AI が一人二役でペルソナを演じる場面では、行頭を `**👤 [ペルソナ名]:**` で始めます。ペルソナ名は `persona.md` の先頭見出し(`# ペルソナ名` または利用者言語に合わせた `# Persona name` 等)から採用します。氏名があれば氏名、なければ役職など識別しやすい呼称を用います
- **発言間は空行を 1 行** 入れて可読性を確保します
- ファイル参照は発言内にインラインで `[参考: dry-run-scenarios/.../data/file.csv]` のように示します
- Web 検索の実施や成果物への書き込みは、ファシリテーター発言として「Web で○○を調査しました。主な発見は…」のように明示します
- **参加者(人間のユーザー)の発言には装飾を付けません**(CLI の標準表示に任せます)

書式例(Mode B auto モード、AI が一人二役):

```markdown
**🎤 ファシリテーター:** まず PEST 分析から始めます。政治的・法的要因として、貴社の事業領域で直近 1 年で影響が大きかった規制改定は何でしょうか?

**👤 高橋さん:** 2026 年の改正保険業法に伴う健康データ取り扱い規制の強化が最も影響しています。[参考: dry-run-scenarios/marketing/precision-health-insurance/data/regulatory-summary.md]

**🎤 ファシリテーター:** ありがとうございます。同法の公式名称と施行日を Web 検索で確認して成果物に反映します。
```

Mode A や Mode C では `**🎤 ファシリテーター:**` のみを使い、参加者の応答はマーカーなしで続きます。

### 評価基準(Dry Run 時に参照)

共通観点、マーケティング起点固有、Working Backwards 固有、および Amazon の 7 つの評価基準(Working Backwards Step 3 で使用)の一覧は `references/evaluation-criteria.md` に整理されています。Mode B で `issues.md` に観点別の検出・WoW を記録する際、および Working Backwards Step 3 の最終 GO/NO-GO 判断時に必ず参照してください。

## Troubleshooting

### Q: project-slug の決定フローで既存企画が多すぎて選びにくい

最終更新日順に並べて、直近 10 件程度に絞り提示します。それ以外は「他にもあります」と触れるだけに留めます。

### Q: ペルソナとして応答できない情報を聞かれた

`persona.md` の知識範囲で答えられない場合、エピソード形式で自然に不確実性を示します(「明確なデータは持っていないが、経験的には〜」)。無理に正確な数値を捏造してはいけません。捏造は `issues.md` に「ペルソナ応答の困難」カテゴリで記録します。

### Q: `dry-run-scenarios/{mode}/{scenario-name}/data/` のファイルを事前に全部読んでしまった

**データの事前読み込み禁止** に違反しています。実行を中断し、ユーザーに報告します。`persona.md` のみ読み込んだ状態でやり直します。

### Q: Web 検索で古い年号(2023 等)のままクエリを投げてしまった

`references/policy-web-search.md` に違反しています。`issues.md` に「調査の不足・バイアス」カテゴリで記録し、現在年でクエリを投げ直します。

### Q: 成果物の出力先が `product-planning/{mode}/` 直下になってしまった

`references/policy-output-structure.md` で「モード直下にフェーズ成果物を置いてはならない」と禁止されています。`{project-slug}/` を挟んで配置し直してください。

### Q: マーケティング起点と Working Backwards を同じ企画で両方試したい

`product-planning/marketing/{project-slug}/` と `product-planning/working-backwards/{project-slug}/` の両方に、同じ project-slug でディレクトリを作って進めます。Dry Run でも同様に両方のシナリオを複製して作成します(片方に `-dryrun` 等の接尾語をつけて区別するのも可です)。
