## 移行の概要

### なぜAWS Payment Cryptographyに移行するのか？

オンプレミスの決済HSMを管理する組織は、運用負荷の増大、先行的なハードウェア調達コスト、
人材確保の課題に直面しています。AWS Payment Cryptographyは以下の利点を提供します：

| 推進要因 | メリット |
|----------|----------|
| **TCO削減** | HSMハードウェア調達（1台あたり約$50K〜$150K）、保守契約、物理セキュリティ、専任管理者の人件費を排除 |
| **弾力性** | トランザクション量に応じて暗号化オペレーションを動的にスケール — ピーク時のキャパシティプランニングが不要 |
| **データセンター撤退** | 決済ワークロードを物理データセンターに紐づける最後の依存関係を解消 |
| **API簡素化** | プロプライエタリなHSMソケットコマンドをRESTful API、AWS SDK、IaCツールに置き換え |
| **コンプライアンス効率化** | AWSのPCI PTS HSMおよびPCI PIN認証を活用し、独自の監査証跡管理を軽減 |

### 一般的な移行タイムライン

完全移行は組織の複雑さに応じて通常 **4〜9ヶ月** を要します：

```
1-2ヶ月目:  ディスカバリー＆計画（鍵インベントリ、依存関係マッピング）
2-3ヶ月目:  鍵同期セットアップ（KEK確立、ワーキングキー同期）
3-4ヶ月目:  統合開発（APIトランスレーション、アプリケーション変更）
4-6ヶ月目:  テスト＆検証（シャドウモード、認証テスト）
6-8ヶ月目:  段階的トラフィック移行（カナリア → 段階的移行 → カットオーバー）
8-9ヶ月目:  デコミッショニング（レガシーHSM撤去、契約終了）
```

> **注**: シンプルな組織では最短3ヶ月で完了する場合があります。
> マルチアクワイアラー・マルチリージョンの複雑な構成では12ヶ月以上の可能性があります。

## ソースHSM

### Thales payShield 10K

**鍵同期アプローチ：**
- `EY`コマンドファミリーを使用してTR-34プロトコルでZMKをエクスポート
- payShieldとAWS Payment Cryptography間でTR-34 KEKを確立
- 共有KEKを使用してTR-31鍵ブロックでワーキングキーをラップ

**考慮事項：**
- 完全なTR-34サポートにはファームウェアバージョン1.4a以上を推奨
- バリアントLMK鍵はエクスポート前にキーブロック形式への再暗号化が必要
- レガシー鍵タイプ（バリアントモードのZPK、ZMK）はTR-31形式への変換が必要

### Utimaco/Atalla AT1000

**鍵同期アプローチ：**
- Master File Key（MFK）エクスポートセレモニーで鍵暗号化鍵を抽出
- AtallaはTR-31鍵ブロックエクスポートをネイティブサポート
- TR-34または手動鍵セレモニーを通じて共有KEKを確立

**考慮事項：**
- Atallaの鍵命名規則はTR-31の鍵使用属性と異なる
- AKB（Atalla Key Block）形式の鍵はインポート前にTR-31への変換が必要

### Futurex GSP3000

**鍵同期アプローチ：**
- Futurex Excrypt ManagerがTR-34鍵配布をサポート
- AES-256鍵の直接確立にECDH鍵合意が利用可能
- KEK確立後のワーキングキーにTR-31エクスポートをサポート

**考慮事項：**
- FXKB（Futurex Key Block）形式はANSI TR-31への変換が必要
- ファームウェアがASC X9 TR-34-2019をサポートしていることを確認
- マルチテナント鍵パーティションは個別の移行セッションが必要

## 鍵同期方法

### TR-34（KEKに推奨）

TR-34は、オンプレミスHSMとAWS Payment Cryptography間でKEKを確立する**推奨方法**です。

```
┌─────────────────┐         TR-34プロトコル          ┌──────────────────────┐
│  オンプレミスHSM │ ◄──── 証明書交換 ──────────────► │  AWS Payment         │
│  (KDH)          │ ────── ラップされたKEK ────────► │  Cryptography (KRD)  │
└─────────────────┘                                  └──────────────────────┘
```

**プロセス：**
1. AWS Payment Cryptographyが鍵受信用の非対称鍵ペアを生成
2. APCからKRD証明書をエクスポートし、オンプレミスHSMにロード
3. オンプレミスHSMがKRD公開鍵を使用してKEKをラップ
4. TR-34でラップされたKEKをAWS Payment Cryptographyにインポート
5. 両システムが後続のTR-31鍵ラッピング用にKEKを共有

**利点：** 非対称交換（事前共有シークレット不要）、X.509証明書による相互認証、
監査証跡、PCI PINアネックスA準拠。

### TR-31（ワーキングキー用）

TR-34でKEKが確立された後、TR-31を使用してすべてのワーキングキーを同期します。

**サポートされる鍵タイプ：**
- `B0` — BDK（Base Derivation Key）DUKPT用
- `P0` — PIN暗号化鍵
- `C0` — CVK（Card Verification Key）
- `M1`/`M3` — MAC鍵（ISO 9797-1）
- `D0` — 対称データ暗号化鍵
- `K0`/`K1` — 鍵暗号化鍵

**プロセス：** オンプレミスHSMからTR-31鍵ブロック形式でエクスポート → `ImportKey` APIで
APCにインポート → APCが鍵ブロックMACを検証し適切な属性で保存。

### ECDH（AES-256鍵用）

TR-34の鍵長制限が適用される場合にAES-256鍵の直接確立に使用：

1. APCでECDH鍵ペアを生成（P-256またはP-384カーブ）
2. オンプレミスHSMとAPC間で公開鍵を交換
3. 両サイドが共有シークレットを導出; KDFでAES-256 KEKを導出
4. 導出されたKEK配下でワーキングキーをラップ

### 自動鍵同期ツール

AWSはオンプレミスHSMとAPC間の継続的な鍵レプリケーションのための
自動同期ソリューションを提供しています。

> **参考**: [Synchronize keys automatically from payment HSMs to AWS Payment Cryptography](https://aws.amazon.com/blogs/industries/synchronize-keys-automatically-from-payment-hsms-to-aws-payment-cryptography/)（2025年6月）

**機能：**
- 継続的な鍵モニタリングと自動同期
- Thales payShield、Utimaco/Atalla、FuturexソースHSMのサポート
- 鍵ライフサイクルイベント検知（作成、ローテーション、削除）
- ハイブリッド運用期間中の双方向同期
- CloudWatchメトリクス/アラームおよびEventBridge統合

## 段階的移行戦略

### フェーズ1: 鍵同期（並行運用）— 2〜4週間

- オンプレミスHSMとAPC間でTR-34 KEKを確立
- すべてのワーキングキー（PEK、BDK、CVK、MAC鍵）を同期
- 既知応答テスト（KAT）を使用して鍵の整合性を検証
- 自動鍵同期を設定 — 両システムが同一の鍵マテリアルを保持、トラフィック移動なし

**成功基準：** すべてのKCVが一致、自動同期がSLA内で複製、不一致ゼロ。

### フェーズ2: カナリアトラフィックルーティング — 1〜2週間

- 非クリティカルなトラフィックの1〜5%をAWS Payment Cryptographyにルーティング
- レスポンスコード、タイミング、暗号化出力を比較
- エラーレート、レイテンシパーセンタイル（p50、p95、p99）を監視

**成功基準：** エラーレート ≤ ベースライン、p99レイテンシ < 50ms、暗号化不一致ゼロ。

### フェーズ3: 段階的トラフィック移行 — 2〜4週間

- トラフィックを増加: 5% → 25% → 50% → 75% → 90%
- 各増分で次に進む前に48時間以上保持
- 各段階でロールバック機能を維持

**ルーティングオプション：** フィーチャーフラグ、BIN範囲ベース、トランザクションタイプベース。

### フェーズ4: 完全カットオーバー — 1週間

- 本番トラフィックの100%をAPCにルーティング
- オンプレミスHSMをスタンバイモードで稼働維持（アクティブトラフィックなし）
- フル本番負荷で5〜7日間モニタリング; エッジケースとバッチ処理を検証

### フェーズ5: レガシーHSMのデコミッショニング — 2〜4週間

- ネットワークルートを無効化; 鍵破壊セレモニーを実行（PCI PIN準拠）
- デュアルコントロールと監査証跡で破壊を文書化
- ハードウェアの返却/廃棄; 保守契約を終了

## ハイブリッド運用

### 両システムの同時稼働

```
                    ┌─────────────────────┐
                    │  決済ゲートウェイ    │
                    │  / ルーティング層    │
                    └──────────┬──────────┘
                    ┌──────────┴──────────┐
          ┌────────▼────────┐  ┌─────────▼──────────┐
          │  オンプレミスHSM │  │  AWS Payment       │
          │  （レガシー）    │  │  Cryptography      │
          └─────────────────┘  └────────────────────┘
```

### 鍵の整合性

- **自動同期**: 両システムが常に同一の鍵マテリアルを保持
- **ローテーション調整**: SLA 5分以内に相手側に伝播
- **KCV検証**: 定期的にシステム間でKey Check Valueを比較
- **バージョントラッキング**: ドリフト検出のための鍵バージョンレジストリ

### フェイルバック戦略

1. **即時フェイルバック**（1時間以内）: ルーティング層がオンプレミスHSMにリダイレクト
2. **鍵状態検証**: オンプレミスHSMの鍵が現在の本番状態と一致することを確認
3. **根本原因分析**: APC設定の問題を特定し解決
4. **再移行**: 解決後に適切なフェーズから再開

## 3DESからAESへの移行

### 業界のマンデート

- **ANSI X9.24-3**: PIN暗号化用AESベースDUKPTを定義
- **PCI SSC**: 2023年12月31日以降、新規実装で3DES使用不可
- **カードネットワーク**: Visa/Mastercardが新端末でAESサポートを義務化
- **NIST SP 800-131A Rev 2**: 3DES廃止、2023年以降使用禁止

### APCのAESサポート

AES-128/192/256、AES-DUKPT（X9.24-3-2017）、AESベースMAC（CMAC、ISO 9797-1
アルゴリズム5）、AES鍵ラッピング（NIST SP 800-38F）をネイティブサポート。

### 移行計画

**アプローチ1 — そのまま移行し後にアップグレード：**
既存3DES鍵を同期 → トラフィック移行完了 → カウンターパーティーとAESにローテーション

**アプローチ2 — 移行時にアップグレード（推奨）：**
APCでAES相当鍵を確立 → カウンターパーティーとAES鍵交換を調整 →
3DES（オンプレミス）とAES（APC）を並行運用 → エンドポイント対応次第AESへ移行

> **ヒント**: HSM移行と3DES→AESの組み合わせはプロジェクト数を減らしますが
> 複雑さは増加します。組織の変更許容度を評価してください。

## テスト戦略

### シャドウモード（デュアルプロセス＆比較）

すべてのトランザクションを両システムで処理し結果を比較：

```
トランザクション ──┬──► オンプレミスHSM ──► レスポンスA ──┐
                   └──► APC             ──► レスポンスB ──┘──► 比較
```

**比較対象：** PIN検証結果、PINトランスレーション出力、CVV結果、
MAC出力（ビット同一）、ARQC検証結果。

**考慮事項：** レイテンシ追加（非同期比較を使用）、DUKPTカウンターの慎重な取り扱い、
すべての不一致を根本原因分析のためにログ記録。

### テストカード範囲

- カードネットワークの専用テストBIN範囲を使用
- 本番から隔離されたテストPINとテスト鍵セット
- すべてのPINブロックフォーマット（ISO Format 0、1、3、4）
- DUKPTカウンターエッジケース（枯渇、再同期）

### 認証テスト

- **Visa**: VTS PINセキュリティテスト
- **Mastercard**: MIPテスト
- **その他**: Discover、Amex、JCB、UnionPayの要件
- **アクワイアラーテスト**: 各アクワイアラーとのエンドツーエンドフロー検証

## 一般的な課題

### ソケットからAPIへの変換

| レガシーHSMコマンド | AWS Payment Cryptography API |
|---|---|
| Thales `BA`/`BC`（PIN検証） | `VerifyPinData` |
| Thales `JG`/`JI`（PINトランスレート） | `TranslatePinData` |
| Thales `CY`/`CZ`（CVV生成/検証） | `GenerateCardValidationData` / `VerifyCardValidationData` |
| Thales `MS`/`MU`（MAC生成/検証） | `GenerateMac` / `VerifyMac` |
| Atalla `31x` / `30x` | `VerifyPinData` / `TranslatePinData` |

**推奨事項**: アプリケーションを暗号化プロバイダーから分離する抽象化レイヤーを構築。

### レイテンシの差異

- オンプレミス: サブミリ秒LAN + 約2-5ms処理
- APC: ネットワークラウンドトリップ + 約10-30ms処理
- **対策**: コネクションプーリング、リージョナルエンドポイント、VPCエンドポイント、バッチング

### ピーク負荷のクォータ計画

- サービスクォータ（オペレーション別TPS）を確認; ピークボリュームをモデル化
- 移行前にクォータ引き上げをリクエスト（2週間のリードタイム）
- スロットリング対応のクライアントサイドリトライ（指数バックオフ）を実装

### スタッフの再教育

- HSM管理者 → クラウドセキュリティエンジニア
- ソケットコマンドの専門知識 → API/SDKの習熟
- ベンダー固有ツール → AWSコンソール、CLI、CloudFormation/Terraform

## ロールバック計画

### オンプレミスHSM機能の維持

1. フェーズ5の成功基準完全達成まで**HSMをデコミッションしない**
2. 移行期間 + バッファ期間を通じて**保守契約を維持**
3. すべてのフェーズを通じて**鍵マテリアルを双方向に同期**し続ける
4. オンプレミスHSMへの**ネットワーク接続を維持**
5. 移行完了まで**HSM管理者スタッフ**または専門知識を保持

### 鍵再エクスポート手順

1. `ExportKey` APIでAPCから現在の鍵をエクスポート
2. 確立されたKEKを使用してTR-31鍵ブロックでトランスポート
3. オンプレミスHSMにインポート; KCV一致を確認
4. トラフィックを戻す; 完全復帰前にテストトランザクションで検証

### ロールバック判断基準

以下のいずれかが1時間以上持続する場合にロールバックをトリガー：
- 暗号化不一致率 > 0.01%
- トランザクション拒否率がベースラインより > 0.5%増加
- APIエラーレート > 1%
- P99レイテンシがSLA閾値を超過
- データ整合性に関する懸念（疑いの段階でも）
