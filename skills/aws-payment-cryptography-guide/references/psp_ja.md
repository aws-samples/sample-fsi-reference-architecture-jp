# PSP（決済サービスプロバイダー / 決済ゲートウェイ / 決済ファシリテーター）

## 概要

決済サービスプロバイダー（PSP）、決済ゲートウェイ、および決済ファシリテーターは、加盟店と決済エコシステム全体を結ぶ仲介者として機能します。これらの事業者は複数の加盟店に代わって取引を処理するため、運用効率を維持しながら暗号鍵の分離を確保する堅牢なマルチテナントアーキテクチャが求められます。

AWS Payment Cryptography（APC）は、物理HSMフリートの運用負担を排除しつつ、マルチ加盟店・マルチアクワイアラー環境に必要な複雑な鍵管理階層を支えるクラウドネイティブなHSMバックエンドプラットフォームをPSPに提供します。

---

## マルチテナント鍵管理

### 加盟店ごとの鍵分離

PSPは加盟店間の厳密な暗号鍵分離を確保する必要があります。APCでは、IAMポリシー、鍵エイリアス、タグベースのアクセス制御を組み合わせてこれを実現します。

#### IAMポリシーによる分離

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "payment-cryptography:Encrypt*",
        "payment-cryptography:Decrypt*"
      ],
      "Resource": "arn:aws:payment-cryptography:*:*:key/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/MerchantId": "${aws:PrincipalTag/MerchantId}"
        }
      }
    }
  ]
}
```

#### 鍵エイリアス戦略

階層的なエイリアス命名規則を採用します：

```
alias/psp/merchant-{merchant_id}/zone-{zone_key_type}
alias/psp/merchant-{merchant_id}/bdk-{terminal_group}
alias/psp/merchant-{merchant_id}/pin-{acquirer_id}
```

#### タグベースのアクセス制御

リソースタグを体系的に適用します：

| タグキー | 値の例 | 用途 |
|---------|--------|------|
| `MerchantId` | `MERCH-00142` | テナント分離 |
| `Environment` | `production` | 環境分離 |
| `KeyPurpose` | `pin-encryption` | 機能分類 |
| `AcquirerLink` | `ACQ-VISA-JP` | アクワイアラー関連付け |
| `ComplianceScope` | `pci-dss-4.0` | 監査分類 |

### 組織鍵階層設計

典型的なPSP鍵階層はレイヤー構造に従います：

```
プラットフォームマスターKEK（APC管理）
├── 加盟店A KEK
│   ├── ワーキングキー: PEK（PIN暗号化）
│   ├── ワーキングキー: MACキー（取引認証）
│   └── ワーキングキー: DEK（データ暗号化）
├── 加盟店B KEK
│   ├── ワーキングキー: PEK
│   ├── ワーキングキー: MACキー
│   └── ワーキングキー: DEK
└── 共有サービスKEK
    ├── トークナイゼーションマスターキー
    └── 3DS暗号鍵
```

**鍵ローテーション戦略**: ワーキングキーは加盟店ごとのスケジュールでローテーション（通常24時間または取引回数ベース）し、KEKは四半期ごとにローテーションします。

## トークナイゼーション連携

### PAN暗号化/復号フロー

PSPは一般的に加盟店のPCI DSSスコープを縮小するためトークナイゼーションを実装します：

```
┌─────────┐    PAN     ┌──────────┐   暗号化   ┌─────┐
│  加盟店  │───────────▶│  PSP GW  │──────────▶│ APC │
└─────────┘            └──────────┘            └─────┘
                             │                      │
                             │ トークン              │ 暗号文
                             ▼                      ▼
                       ┌──────────┐          ┌──────────┐
                       │トークン保管庫│◀─────────│鍵ストア  │
                       └──────────┘          └──────────┘
```

### トークナイゼーションサービスとの連携

APCはトークナイゼーションワークフローに2つのパターンで統合されます：

1. **暗号化後トークン化**: PANはトークン生成前にAPCで暗号化されます。トークン保管庫は暗号化されたPANを保存し、デトークン化にはAPCでの復号が必要です。

2. **APC鍵によるトークン化**: トークナイゼーションサービスが内部FPE操作にAPC管理鍵を使用し、専用ハードウェアなしでHSMグレードの鍵保護を確保します。

### フォーマット保持暗号化（FPE）の考慮事項

- APCはFPEラッパー実装に適したAESベースの操作をサポート
- FPEワーキングキーには `TR31_D0_SYMMETRIC_DATA_ENCRYPTION_KEY` の使用を検討
- FPE実装がNIST SP 800-38G（FF1/FF3-1）要件を満たすことを確認
- FPEフォーマット保持の要件と暗号強度要件のバランスを考慮

## 3-Dセキュア

### APCの3DS暗号操作における役割

3-D Secure（3DS）プロトコル2.x系では以下の暗号操作が必要です：

- **ACS（アクセスコントロールサーバー）**: 認証値（CAVV/AAV）の生成
- **DS（ディレクトリサーバー）**: 参加者間のメッセージ署名および暗号化
- **3DSサーバー**: DSとの通信におけるリクエスト/レスポンスの署名

APCはこれらの操作の基盤となる鍵を管理できます：

```
3DSトランザクションフロー（APC連携）：
────────────────────────────────────
カード会員 → 加盟店 → 3DSサーバー → ディレクトリサーバー → ACS
                          │                                │
                          ▼                                ▼
                   ┌────────────┐                  ┌────────────┐
                   │    APC     │                  │    APC     │
                   │（署名鍵）   │                  │（CAVV鍵）   │
                   └────────────┘                  └────────────┘
```

### 3DSサーバー連携ポイント

| 操作 | APC鍵の用途 | 鍵タイプ |
|------|-------------|---------|
| AReq署名 | メッセージ認証 | `TR31_M3_ISO_9797_3_MAC_KEY` |
| CAVV生成 | クリプトグラム計算 | `TR31_E0_EMV_MKEY_APP_CRYPTOGRAMS` |
| DS通信 | 暗号化/復号 | `TR31_D0_SYMMETRIC_DATA_ENCRYPTION_KEY` |
| 証明書鍵保管 | 鍵ペア管理 | RSA/ECC鍵 |

## マルチアクワイアラー接続

### 各接続先アクワイアラー/ネットワーク向け鍵ペア管理

PSPは通常、複数のアクワイアラーおよびカードネットワークに接続します。各接続には固有の暗号鍵セットが必要です：

```
PSPプラットフォーム
├── アクワイアラーA（Visa Direct）
│   ├── ZPK-A（ゾーンPINキー）
│   ├── ZMK-A（ゾーンマスターキー）
│   └── MAC-A（メッセージ認証キー）
├── アクワイアラーB（Mastercardネットワーク）
│   ├── ZPK-B
│   ├── ZMK-B
│   └── MAC-B
└── アクワイアラーC（国内 - JCB）
    ├── ZPK-C
    ├── ZMK-C
    └── MAC-C
```

### アクワイアラー間でのPINトランスレーション

加盟店とアクワイアラー間のトランザクションルーティング時に、PINトランスレーションはPSPの重要な機能です：

```python
# PINトランスレーションの概念フロー
# 1. インバウンド鍵で加盟店端末からのPINブロックを復号
# 2. アウトバウンドのアクワイアラー鍵で再暗号化

response = client.translate_pin_data(
    IncomingKeyIdentifier="alias/psp/merchant-142/pek-inbound",
    OutgoingKeyIdentifier="alias/psp/acquirer-visa/zpk-outbound",
    IncomingTranslationAttributes={
        "IsoFormat0": {
            "PrimaryAccountNumber": pan_12_digits
        }
    },
    OutgoingTranslationAttributes={
        "IsoFormat4": {
            "PrimaryAccountNumber": pan_12_digits
        }
    },
    EncryptedPinBlock=incoming_pin_block
)
```

### ルーティングベースの鍵選択

取引ルーティング決定に基づく鍵選択ロジックを実装します：

| ルーティング要素 | 鍵選択ロジック |
|----------------|--------------|
| カードBIN範囲 | BIN-アクワイアラーマッピングによるアクワイアラー鍵の選択 |
| 取引通貨 | 一致する決済通貨のリージョナルアクワイアラーにルーティング |
| 加盟店指定 | 加盟店固有のアクワイアラールーティングルールを尊重 |
| フェイルオーバー | アクワイアラー接続障害時の自動鍵切替 |
| コスト最適化 | 最低コストのアクワイアラーにルーティングし対応する鍵を選択 |

## P2PEアズ・ア・サービス

### APCを使用した加盟店向けP2PEサービスの提供

PSPはAPCを復号バックエンドとして使用し、加盟店にPoint-to-Point Encryption（P2PE）をマネージドサービスとして提供できます：

```
┌────────────┐        ┌───────────────┐        ┌─────────────┐
│   加盟店    │  P2PE  │     PSP       │  APC   │   AWS APC   │
│   端末     │───────▶│  復号環境      │───────▶│   (HSM)     │
│   (POI)    │ 暗号文  │               │  API   │             │
└────────────┘        └───────────────┘        └─────────────┘
       │                      │                        │
       │ DUKPT/AES            │ BDKをAPCで             │ 鍵をHSMに
       │ 暗号化               │ 管理                   │ 保管
```

#### P2PEサービスの鍵管理

- **ベース導出鍵（BDK）**: APCに保管し、平文では公開しない
- **IPEK導出**: 端末インジェクション用にAPC内で実行
- **復号**: すべての取引復号はAPC API呼び出しを通じて実施
- **鍵インジェクション**: 端末鍵インジェクションプロセスはAPC管理のBDKを参照

### コンポーネントリスティングの考慮事項

PCI P2PEバリデーションにおいて、PSPは以下に対応する必要があります：

1. **復号環境**: APCはAWSのPCI認定済みインフラストラクチャ内で稼働
2. **鍵管理文書化**: APC鍵ライフサイクルをP2PEコンポーネントリスティングに文書化
3. **責任共有**: P2PE実装マニュアル（PIM）におけるAWSとPSPの責任を明確に区分
4. **端末管理**: 復号がクラウドベースであっても、POIデバイス管理手順がP2PE要件に適合することを確認

## スケーリングの考慮事項

### ゲートウェイワークロード向け高TPSデザイン

PSPゲートウェイは高スループットを要求します。APC大規模運用のデザインパターン：

| パターン | 説明 | メリット |
|---------|------|---------|
| コネクションプーリング | APCエンドポイントへの永続HTTPS接続を維持 | TLSハンドシェイクのオーバーヘッド削減 |
| リクエストバッチ処理 | 関連する操作を可能な限りグループ化 | 呼び出しごとのオーバーヘッド削減 |
| 非同期処理 | ノンブロッキングフローに非同期API呼び出しを使用 | スループット向上 |
| リージョナルルーティング | 最寄りのAPCエンドポイントにルーティング | レイテンシー最小化 |
| キャッシュ（非機密情報） | 鍵メタデータ、エイリアスをキャッシュ（鍵素材は除く） | API呼び出し削減 |

### サービスクォータ管理

APCサービスクォータをプロアクティブに監視・管理します：

- **デフォルトTPSリミット**: トラフィック増加を十分に先取りして引き上げリクエスト
- **CloudWatch監視**: クォータ使用率70%でアラーム設定
- **バースト処理**: トラフィックスパイク時のクォータ対応バックオフを設計
- **鍵ごとのリミット**: 必要に応じて複数の鍵エイリアスに負荷を分散

### グローバルPSP向けマルチリージョンデプロイ

```
┌─────────────────────────────────────────────────┐
│           グローバルPSPプラットフォーム             │
├──────────────┬──────────────┬───────────────────┤
│  米国リージョン│  欧州リージョン│  APACリージョン    │
│  us-east-1   │  eu-west-1   │  ap-northeast-1   │
│  ┌────────┐  │  ┌────────┐  │  ┌────────┐      │
│  │  APC   │  │  │  APC   │  │  │  APC   │      │
│  └────────┘  │  └────────┘  │  └────────┘      │
│              │              │                    │
│  米国加盟店   │  欧州加盟店   │  APAC加盟店       │
└──────────────┴──────────────┴───────────────────┘
```

**クロスリージョンの考慮事項**：

- 鍵同期: TR-31鍵ブロックを使用してリージョン間で鍵をエクスポート/インポート
- データレジデンシー: PANデータと鍵が要求された管轄内に留まることを確認
- フェイルオーバー: アクティブ-パッシブまたはアクティブ-アクティブのクロスリージョンフェイルオーバーを設計
- レイテンシー: 100ms未満の暗号処理のため最寄りリージョンにトランザクションをルーティング

## 日本固有の考慮事項

### PCI DSSアウトソーシングスコープの定義

APCを使用する際、PSPはPCI DSSスコープの境界を明確に定義する必要があります：

| コンポーネント | スコープ所有者 | 根拠 |
|--------------|--------------|------|
| APC HSMインフラストラクチャ | AWS（PSPスコープ外） | AWS PCI DSS AOCがカバー |
| 鍵管理手続き | PSP（スコープ内） | PSPが鍵ライフサイクルを定義 |
| APCへのAPI呼び出し | PSP（スコープ内） | PSPアプリケーションの責任 |
| APCへのネットワーク接続 | PSP（スコープ内） | VPCおよびネットワーク設計 |
| 物理HSMセキュリティ | AWS（PSPスコープ外） | AWSファシリティ管理 |

## まとめ

AWS Payment Cryptographyを活用するPSPのメリット：

1. **運用負担の軽減**: 物理HSMフリート管理が不要
2. **弾力的なスケーラビリティ**: 取引量に応じた暗号操作のスケーリング
3. **マルチテナント分離**: IAMとタグベース制御による加盟店分離
4. **グローバルリーチ**: 国際PSP運用のためのマルチリージョンデプロイ
5. **コンプライアンス適合**: PCI DSS、FISC、資金決済法への対応支援
6. **コスト効率**: 固定HSMインフラコストに対する従量課金モデル
