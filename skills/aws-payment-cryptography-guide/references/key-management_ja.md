# AWS Payment Cryptography 鍵管理ベストプラクティス

## 概要

鍵管理は決済セキュリティの基盤です。AWS Payment Cryptography（APC）は、PCI PIN、
PCI P2PE、PCI DSS に準拠した暗号鍵ライフサイクル管理のフルマネージドサービスを提供します。
本ガイドでは、インポート/エクスポート方式、鍵階層、ローテーション戦略、
非標準ベンダーとの連携について解説します。

---

## 鍵インポート方式

### TR-34（非対称鍵交換）

TR-34 は APC への鍵暗号化鍵（KEK）インポートの**推奨方式**です。

- **プロトコル**: 非対称（RSA ベース）鍵転送
- **用途**: 二者間での初期 KEK 確立
- **対応鍵タイプ**: TDES（2鍵、3鍵）および AES-128
- **役割**: Key Distribution Host（KDH）が Key Receiving Device（KRD）に鍵を送信
- **APC の役割**: インポート時は KRD として動作

```
┌─────────────┐         TR-34         ┌─────────────┐
│  外部 HSM   │  ───────────────────►  │     APC     │
│   (KDH)    │   TR-34 エンベロープ    │    (KRD)    │
│             │   でラップされた KEK   │             │
└─────────────┘                        └─────────────┘
```

**ワークフロー**:
1. APC が RSA 鍵ペアを生成し、公開鍵証明書を提供
2. 外部 KDH が APC の公開鍵を使用して KEK をラップ
3. KDH が自身の秘密鍵でペイロードに署名
4. APC がインポートされた KDH 証明書を使用して署名を検証
5. APC が KEK をアンラップして格納

### TR-31（対称鍵ラッピング）

TR-31 は既に確立された KEK 配下での**ワーキングキー**インポートに使用されます。

- **プロトコル**: ANSI X9.143 準拠の対称鍵ラッピング
- **用途**: PIN 暗号化鍵、MAC 鍵、データ暗号化鍵のインポート
- **前提条件**: APC に KEK が既に存在すること（TR-34 等でインポート済み）
- **鍵ブロック形式**: 鍵用途、使用モード、エクスポート可能性属性を含む

### RSA Wrap/Unwrap

TR-34 をサポートできないが非対称暗号化が使用可能な環境向け：

- **プロトコル**: RSA OAEP 鍵ラッピング
- **対応鍵タイプ**: TDES および AES-128
- **用途**: TR-34 ツールが利用できない場合のシンプルな非対称インポート
- **セキュリティ**: TR-34 よりメタデータ保護が弱い（転送中に鍵ブロック属性なし）

### ECDH（楕円曲線ディフィー・ヘルマン）

最も新しく柔軟な鍵合意方式：

- **プロトコル**: ECDH 鍵合意（NIST P-256、P-384、P-521 曲線）
- **対応鍵タイプ**: **AES-256** まで対応（最強の鍵強度）
- **用途**: AES-256 鍵の共有シークレット確立
- **利点**: TR-34 や RSA Wrap より高い鍵強度をサポート

### ルート公開鍵証明書インポート

信頼アンカーの確立用：

- **用途**: TR-34 検証用の外部パートナー CA 証明書のインポート
- **形式**: X.509 証明書（DER または PEM エンコード）
- **信頼モデル**: インポートされた証明書が TR-34 インポート時の KDH 署名を検証

## 鍵エクスポート方式

### TR-34 エクスポート（APC が KDH として動作）

APC が Key Distribution Host として外部システムへ KEK をエクスポート：

- **APC の役割**: KDH（送信者）
- **用途**: パートナー HSM、決済端末への KEK 配布
- **プロセス**: APC が受信側の公開鍵を使用して KEK をラップ

### TR-31 エクスポート

共有 KEK 配下でワーキングキーをエクスポート：

- **用途**: 処理パートナーへの PIN 鍵、MAC 鍵の配布
- **前提条件**: APC と受信側間の共有 KEK

### DUKPT IPEK エクスポート（BDK から導出）

Base Derivation Key（BDK）から Initial PIN Encryption Key（IPEK）を導出してエクスポート：

- **用途**: DUKPT ベース POS デバイスへの端末鍵インジェクション
- **プロセス**: APC が BDK + 初期 KSN から IPEK を導出し、TR-31 でラップしてエクスポート

## 非標準ベンダーへの対応

外部パートナー（カードビューロー、レガシープロセッサー、ネットワークゲートウェイ）が
TR-31、TR-34、ECDH を**サポートしない**場合：

### オプション A: ブリッジ HSM アプローチ

仲介 HSM を使用してフォーマット間を変換：

```
┌──────────────┐    独自形式      ┌──────────────┐    TR-31/34    ┌─────────┐
│   レガシー    │  ──────────────► │ ブリッジ HSM │  ───────────►  │   APC   │
│   パートナー  │                  │ (CloudHSM    │   標準形式    │         │
│              │                  │  またはオンプレ)│             │         │
└──────────────┘                  └──────────────┘               └─────────┘
```

- **AWS CloudHSM**: VPC にデプロイし、パートナーの独自ファームウェア/鍵をロード
- **オンプレミス HSM**: 既存の HSM インフラを変換レイヤーとして使用

### オプション B: クリアテキスト鍵コンポーネント交換

他に手段がない場合：

- **方式**: デュアルコントロール、分割知識の鍵コンポーネント
- **転送**: 各コンポーネントを別々のセキュアチャネルで送信
- **PCI リスク**: ROC に文書化された代替統制が必要
- **必要な統制**: 身元調査、改ざん防止パッケージング、管理の連鎖ログ、ロード後の即時破棄、QSA 承認

### オプション C: 交渉戦略

パートナーの標準規格採用を推進：

1. **教育**: TR-31/TR-34 実装ガイドをパートナーと共有
2. **タイムライン**: 6〜12 ヶ月の移行ロードマップを提案
3. **暫定措置**: 移行期間中はブリッジ HSM を使用
4. **インセンティブ**: セレモニーコスト削減と鍵ローテーション高速化を強調
5. **エスカレーション**: パートナーのコンプライアンスチームを巻き込む（PCI は電子交換を推奨）

## DUKPT 鍵階層

### アーキテクチャ

```
┌─────────────────────────────────────────────────────┐
│              BDK（Base Derivation Key）               │
│                    APC に格納                         │
└───────────────────────────┬─────────────────────────┘
                            │ 導出
                ┌───────────┼───────────┐
                ▼           ▼           ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │  IPEK 1  │ │  IPEK 2  │ │  IPEK N  │
        │(端末1)   │ │(端末2)   │ │(端末N)   │
        └─────┬────┘ └─────┬────┘ └─────┬────┘
              ▼             ▼             ▼
        セッション鍵   セッション鍵   セッション鍵
```

### KSN（鍵シリアル番号）構造

| フィールド | ビット数 | 説明 |
|-----------|---------|------|
| BDK ID | 22 | BDK の識別子 |
| 端末 ID | 10 | 一意の端末識別子 |
| トランザクションカウンター | 21 | トランザクションごとにインクリメント |

### 端末鍵インジェクションワークフロー

1. **BDK 作成**: APC で BDK を生成またはインポート
2. **IPEK 導出**: APC が BDK + 初期 KSN から IPEK を導出
3. **IPEK エクスポート**: IPEK を TR-31 鍵ブロックでラップしてエクスポート
4. **インジェクション**: セキュア鍵インジェクション施設で端末に IPEK をロード
5. **運用**: 端末がトランザクションごとに IPEK からセッション鍵を導出
6. **復号**: APC が BDK を使用して同じセッション鍵を導出し復号

## 鍵ローテーション戦略

### 鍵タイプ別ローテーション頻度

| 鍵タイプ | 推奨頻度 | 方式 |
|---------|---------|------|
| KEK（ゾーンマスター鍵） | 年次 | 手動（TR-34 再交換） |
| PIN 暗号化鍵（PEK） | 四半期 | 自動（KEK 配下で TR-31） |
| MAC 鍵 | 四半期 | 自動（KEK 配下で TR-31） |
| データ暗号化鍵 | 月次またはセッション毎 | 自動 |
| BDK（DUKPT） | 100万トランザクション毎または年次 | 手動（新 BDK + 端末再インジェクション） |
| カード検証鍵 | 年次 | カードネットワークと調整 |

### ゼロダウンタイムローテーションパターン

```python
# ゼロダウンタイム鍵ローテーションの擬似コード
def rotate_working_key(current_key_arn, kek_arn):
    # 1. 新しい鍵を作成
    new_key = apc.create_key(key_attributes=current_key.attributes)
    # 2. 新しい鍵をエクスポート（TR-31）してパートナーに配布
    tr31_block = apc.export_key(new_key.arn, wrapping_key=kek_arn)
    # 3. パートナーに配布
    distribute_to_partner(tr31_block)
    # 4. 切替: エイリアスを新しい鍵に向ける
    apc.update_alias(alias="alias/pin-key-prod", target=new_key.arn)
    # 5. 猶予期間: インフライトトランザクション用に旧鍵をアクティブ維持
    schedule_deactivation(current_key_arn, delay="24h")
    # 6. 猶予期間後に旧鍵を削除
    schedule_deletion(current_key_arn, delay="7d")
```

**手順**: 作成 → 配布 → デュアルアクティブ期間 → 切替 → 猶予期間 → 削除

## マルチリージョン鍵

### レプリケーションアーキテクチャ

```
┌─────────────────┐       レプリケーション       ┌─────────────────┐
│   us-east-1     │  ◄─────────────────────────► │   eu-west-1     │
│  (プライマリ)    │          同期               │   (レプリカ)     │
│  KEK/PEK/BDK   │                              │  KEK/PEK/BDK   │
└─────────────────┘                              └─────────────────┘
```

### ユースケース

- **災害復旧（DR）**: レプリカリージョンへの自動フェイルオーバー
- **レイテンシー最適化**: 端末に最も近いリージョンでトランザクション処理
- **コンプライアンス**: データレジデンシー要件に応じた特定地域での鍵保持
- **アクティブ-アクティブ**: 同一鍵で複数リージョンで同時処理

### 考慮事項

- レプリケーションは非同期（結果整合性）
- 鍵属性とタグは鍵と共にレプリケート
- 削除は全リージョンに伝播
- CloudWatch メトリクスでレプリケーションラグを監視

## ANSI TR-31 鍵ブロック形式

### 構造

```
┌─────────────────────────────────────────────────────────────────┐
│ ヘッダー │  鍵長    │  鍵データ（暗号化済み） │     MAC        │
│ (16+ B)  │ (4 hex)  │                        │   (8-16 B)    │
└─────────────────────────────────────────────────────────────────┘
```

### ヘッダーフィールド

| フィールド | 長さ | 説明 |
|-----------|------|------|
| バージョン | 1文字 | `A`/`B`/`C`=TDES、`D`=AES |
| 鍵ブロック長 | 4 hex | ブロック全体の長さ |
| 鍵用途 | 2文字 | 目的コード（例: `P0`=PIN 暗号化） |
| アルゴリズム | 1文字 | `T`=TDES、`A`=AES、`R`=RSA |
| 使用モード | 1文字 | `E`=暗号化、`D`=復号、`B`=両方、`N`=制限なし |
| エクスポート可能性 | 1文字 | `E`=可、`N`=不可、`S`=センシティブ |

### 鍵用途コード

| コード | 意味 | コード | 意味 |
|--------|------|--------|------|
| `P0` | PIN 暗号化鍵 | `K0` | 鍵暗号化（KEK） |
| `B0` | BDK | `K1` | 鍵ブロック保護鍵 |
| `M1` | MAC（アルゴリズム1） | `V0` | PIN 検証（Visa PVV） |
| `M3` | MAC（アルゴリズム3） | `V1` | PIN 検証（IBM 3624） |
| `D0` | データ暗号化 | | |

### 使用モード

| コード | 意味 | コード | 意味 |
|--------|------|--------|------|
| `B` | 暗号化と復号の両方 | `G` | 生成のみ |
| `C` | 計算（MAC 生成） | `N` | 制限なし |
| `D` | 復号/アンラップのみ | `S` | 署名のみ |
| `E` | 暗号化/ラップのみ | `V` | 検証のみ |
| `X` | 鍵導出 | | |

## 外部 HSM からの鍵同期

### 参考: ブログ記事

> **「Synchronize keys automatically from payment HSMs to AWS Payment Cryptography」**
> （決済 HSM から AWS Payment Cryptography への鍵自動同期）
> 公開日: 2025年6月
> https://aws.amazon.com/blogs/security/synchronize-keys-automatically-from-payment-hsms-to-aws-payment-cryptography/

**主要コンセプト**: オンプレミス HSM からの自動 TR-31 鍵エクスポート → S3 → Lambda イベント駆動型 APC インポート。鍵属性パリティを維持し、本番を中断せず段階的移行をサポート。

```
┌───────────┐    TR-31 エクスポート  ┌─────────┐   S3 イベント  ┌────────┐   インポート  ┌─────┐
│ オンプレ   │ ───────────────────► │   S3    │ ────────────► │ Lambda │ ──────────► │ APC │
│ HSM       │   (スケジュール)      │ バケット │               │        │   TR-31    │     │
└───────────┘                      └─────────┘               └────────┘            └─────┘
```

## 鍵交換決定マトリクス

| パートナーの能力 | 推奨方式 | フォールバック | コスト |
|---|---|---|---|
| TR-34 対応 | TR-34（電子） | — | 低 |
| TR-31 のみ対応 | 既存 KEK 配下で TR-31 | まず TR-34 で KEK 確立 | 低 |
| ECDH 対応 | ECDH 鍵合意 | — | 低 |
| RSA のみ対応 | RSA Wrap/Unwrap | — | 低 |
| 電子交換不可 | ブリッジ HSM 変換 | デュアルコントロールのクリアテキストコンポーネント（最終手段） | 中 |
| 独自形式のみ | ブリッジ HSM 変換 | パートナーの標準規格採用 | 中 |
| クリアテキストのみ | デュアルコントロール | ブリッジ HSM | 中（+ PCI リスク） |
