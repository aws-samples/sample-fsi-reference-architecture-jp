# 資本市場 OMS（Capital Market OMS）

## ワークロード概要

これは、デプロイ可能なリファレンス実装ではなく、証券会社の **オーダー管理システム（OMS: Order Management
System）** のクラウドネイティブなアーキテクチャを解説する **ケーススタディ** である。OMS は証券会社のシステム
群の中で **フロント～ミドル** の位置づけとなる基幹システムである。本デザインは、国内・海外で実際に稼働している
証券会社の OMS アーキテクチャを参考としており、それらの会社が求めるレイテンシー・可用性要件を満たすように
形づくられている。

**シナリオ.** OMS は一般投資家、機関投資家、トレーダーからの注文を受け付けて約定を管理し、取引所へ発注する。
また、情報ベンダーから受信した相場情報（値動き・気配値）を投資家へリアルタイム配信する。取引時間中、
フロント～ミドルのシステムは顧客注文の処理と、ポジション・残高・買付余力の暫定的な加減算をリアルタイムで
行う。本 OMS の対象外である別の **バックシステム** は、市場取引終了後に取引所・清算機関からの最終決済データを
受信・処理して確定値を算出し、その確定データを **夜間バッチ** でフロント～ミドルのシステムへ転送して、翌営業日
開始前に洗い替えられるようにする。

**目的と意義.** 証券会社の OMS は **レイテンシー・スケーラビリティ・高可用性のトリレンマ** を抱えている。歴史的
に各社は独自の OMS を開発し、長らくオンプレミスで保守運用してきた。大規模システムでは今もメインフレームが
利用されていることは珍しくない。本リファレンスアーキテクチャの目的は、各社の多様化するニーズに応じてこの
トリレンマの最適なバランスを実現する、クラウドネイティブな OMS の指針を提供することである。

**ビジネスドライバー / 課題.** 近年著しく増加した取引量を背景に、受発注システムの柔軟なキャパシティ調整と
コスト最適化のため、クラウド活用への期待が高まっている。以下の 3 点が課題として挙げられる。

- **レイテンシー要件.** 注文受付から執行までの価格乖離（スリッページ）を最小化し、最良気配値での約定確率を
  高めるには、極めて低いレイテンシーが求められる。従来は取引所コロケーションサービスや同一データセンター
  配置で対応してきたが、商品や投資家へのサービスの多様化により、一律にレイテンシーへ最優先で大きなコストを
  かけることの投資対効果が高いという状況は変化してきた。
- **スケーラビリティ.** 増大を続ける取引量と、相場イベント時の予測困難な急激なピークは、平常時との必要
  キャパシティのギャップを拡大させ、ピーク対応リソース確保のコストが課題となっている。
- **高可用性.** 社会インフラとして重要性を増す証券取引において、トレードライフサイクルの中心となる OMS の
  可用性要件は一層厳格化している。

**ケーススタディが挙げるクラウドネイティブ OMS の実事例:** Vanguard critical trading platform、Fidelity Asset
Management's Equity Trading Platform、Santander trading platform。（公開事例のリンクは
`references/architecture.md` にまとめてある。）

EMS（Execution Management System）を含めて AWS Outposts 上で稼働させる場合のアーキテクチャについては、
BLEA for FSI の **ハイブリッド** 証券取引システムのリファレンスアーキテクチャを参照すること。

## ベストプラクティスと主要コンポーネント

### ベストプラクティス

- MUST: 「受注と約定」（受注・約定）の処理と「発注と出来」（発注・出来）の処理を分離し、両者を非同期
  メッセージング基盤で連携させること。この疎結合により各層が独立してスケールでき、各層内の一貫性を確保
  しやすく、メッセージング基盤を各社のニーズに応じて交換できる。
- SHOULD: 「発注と出来」の処理を、取引所へ注文を回送する EMS（Execution Management System）に近い位置に
  配置し、取引所との通信レイテンシーを最小化すること。
- PREFER: 極めて低いレイテンシーが必要な場合は、クロス AZ 通信を無効化しシングル AZ 内で全ての処理を完結
  させる AZ の Active/Standby アーキテクチャとすること。レイテンシー要件が緩和される場合は、同じ
  アーキテクチャでクロス AZ を許容する Active/Active のマルチ AZ 構成に構成できる。
- SHOULD: AWS Auto Zone Shift を有効化し、AZ 障害時に影響のある AZ から自動的にトラフィックを退避させること。
  クロス AZ 無効化の Active/Standby 構成でも、クロス AZ を許容する Active/Active 構成でも、障害 AZ を迅速に
  切り離す機能として推奨される。
- MUST: Auto Zone Shift の直接サポート対象外のサービス（2025/08 時点で Amazon ECS と Amazon ElastiCache for
  Redis）については、Amazon EventBridge 経由の Auto Zone Shift 開始イベント通知を用い、AWS Step Functions と
  AWS Lambda で独自のフェイルオーバー処理を実装すること。
- SHOULD: 負荷に応じたリアクティブなオートスケーリングと、スケジュールスケーリングを組み合わせること。
  例えば寄り付き時の注文量を事前に予測して寄り付き前にスケールアウトさせておく。負荷ベースのスケーリング
  単独では反応速度が急激なバーストに対して課題となるためである。
- SHOULD: OMS・バックシステム間のデータ連携（ポジション・残高、顧客マスター、与信情報、手数料・税金計算
  結果）には、マネージドサービスを用いること。Amazon S3 をデータ授受の中継点、AWS Step Functions を
  ワークフロー制御、AWS Lambda を処理実行に用いることで、夜間バッチ（取込、整合性検証、洗い替え）の
  スケーラビリティを高め運用負荷を軽減できる。
- PREFER: ミッションクリティカルな DR にはマルチリージョン構成を採用すること。データロストを避けるため
  Aurora のクロスリージョンレプリケーションを用いるが、メッセージング基盤に残存するデータには別途、損失
  パターンを考慮した保護策が必要である。
- SHOULD: DR 切替は、取引所との接続再確立やバックシステムとのデータ整合性確保など、慎重で多くは手動の
  プロセスとして計画すること。数時間から 1 営業日程度の現実的な時間枠を確保し、ビジネス影響を最小化する
  タイミングを選定する。
- MAY: 取引所への FIX プロトコル通信遅延を最小化するため、取引所近接地やコロケーションセンターに配置した
  AWS Outposts の活用を検討すること。基本構成は単一 Outposts であり、より高い可用性のためには複数 Outposts
  も検討できるが、その場合はデータ整合性確保の仕組みの追加実装が必要となる。
- MUST NOT: Auto Zone Shift 対象外サービス用のカスタムフェイルオーバー実装が AWS コントロールプレーン障害時
  にも機能すると想定しないこと。この実装は AWS コントロールプレーンに依存するため、その障害時には機能しない
  可能性がある。
- WILL: 注文受付（フロント）と執行・取引所対応の処理は負荷特性もビジネスロジックの変更頻度も異なるため、
  本アーキテクチャは Amazon ECS 上のコンテナによるマイクロサービスを採用している。
- WILL: 疎結合でメッセージング連携されたコンポーネント設計により、メッセージング基盤を柔軟に選択・交換できる。
  長期のメッセージ保持や多数のコンシューマーグループが必要なら Amazon MSK、順序性の重要度が低くシンプルな
  キューイングで十分なら Amazon SQS を選択できる。

### 主要コンポーネント

#### 受注・約定（フロント）マイクロサービス

- **コンポーネント概要**: 一般投資家、機関投資家、トレーダーからの注文を受け付け、約定を管理する。負荷特性と
  ビジネスロジックの変更頻度が発注側と異なるため、コンテナによるマイクロサービスとして稼働し、独立して
  スケールできる。
- **想定される AWS サービス**: Amazon Elastic Container Service (ECS)

#### 発注・出来（執行）マイクロサービス

- **コンポーネント概要**: 取引所への発注と出来（執行結果）を処理する。取引所との通信レイテンシー最小化のため
  EMS と論理的に近い位置に配置する。最も低いレイテンシーのためには取引所近接の AWS Outposts 上へ配置できる。
  フロント層とは独立してスケールする。
- **想定される AWS サービス**: Amazon Elastic Container Service (ECS)、オプションで AWS Outposts

#### 低レイテンシーメッセージング基盤

- **コンポーネント概要**: 「受注と約定」層と「発注と出来」層を連携する非同期メッセージング基盤。インメモリの
  Redis Streams を用いて高速・低レイテンシーな処理をシンプルな運用で実現する。コンポーネントは交換可能で、
  長期保持や多数コンシューマーグループには MSK、順序性の重要度が低い場合は SQS を選択できる。
- **想定される AWS サービス**: Amazon ElastiCache for Redis（Redis Streams）、代替として Amazon MSK、Amazon SQS

#### メインリレーショナルデータベース

- **コンポーネント概要**: OMS データのメインとなるリレーショナルデータベース。AZ 障害時のデータ永続性のため
  クロス AZ レプリケーション、DR のためクロスリージョンレプリケーションに対応する。
- **想定される AWS サービス**: Amazon Aurora

#### 相場情報配信

- **コンポーネント概要**: 情報ベンダーから相場情報（値動き・気配値）を受信し、WebSocket を通じて投資家クライ
  アントへリアルタイム配信する。
- **想定される AWS サービス**: WebSocket ベースのリアルタイム配信（OMS アプリケーション層から配信）

#### バックシステムデータ連携 / 夜間バッチ

- **コンポーネント概要**: 証券バックシステムと日次で連携し、確定した顧客ポジション・残高、顧客マスター、与信
  情報、手数料・税金計算結果で OMS データを洗い替える。S3 をデータ授受の中継点、Step Functions をワークフロー
  制御、Lambda を処理実行（取込、整合性検証、洗い替え）に用いる。
- **想定される AWS サービス**: Amazon S3、AWS Step Functions、AWS Lambda

#### AZ フェイルオーバーオーケストレーション

- **コンポーネント概要**: AZ の自動フェイルオーバーを提供する。AWS Auto Zone Shift が障害 AZ からトラフィック
  を退避させる。直接サポート対象外のサービス（2025/08 時点で Amazon ECS、ElastiCache for Redis）については、
  EventBridge 経由の Auto Zone Shift 開始イベントを起点に、Step Functions と Lambda でカスタムフェイルオーバー
  を駆動する。
- **想定される AWS サービス**: AWS Auto Zone Shift、Amazon EventBridge、AWS Step Functions、AWS Lambda

#### 取引所接続

- **コンポーネント概要**: 取引所へのネットワーク接続ポイント。オンプレミス環境に配置されることを想定し、
  FIX プロトコルで取引所と通信する。執行側を取引所近接の AWS Outposts 上へ配置することでこのネットワーク遅延
  を最小化できる。
- **想定される AWS サービス**: オンプレミスのネットワーク接続ポイント、（近接配置のため）AWS Outposts

## FISC コンプライアンス概要

本ケーススタディには **FISC マッピング専用ファイルは存在せず**、元となるケーススタディ資料にも FISC 安全対策
基準のマッピングや明示的な FISC 統制への参照は含まれていない。したがって、ここでは FISC / 規制の統制マッピング
は再現しない（存在しないものを捏造しない）。

元資料に *存在する* 規制関連のポイントは、FISC 統制マッピングというよりも、業務・運用上のレジリエンス特性で
ある。すなわち、証券取引は重要な社会インフラとして扱われ可用性要件が一層厳格化していること、そのため本設計
は AZ 耐障害性（Auto Zone Shift とカスタムフェイルオーバー）、データ永続性（Aurora のクロス AZ レプリケーション
と複数 ElastiCache for Redis クラスタへの同期書き込み）、および数時間から 1 営業日程度の慎重で多くは手動の
切替を伴うマルチリージョン構成によるミッションクリティカルな DR を重視している。
