# 保険ワークロード：データ分析基盤

## ワークロード概要

本ケーススタディは、AWS 上の**保険データ分析基盤**のリファレンスアーキテクチャを解説するものである。現在実際に稼働している保険会社のデータ分析基盤のアーキテクチャを参考にし、保険のワークロードに典型的なデータ処理・セキュリティ要件を実現する。保険ワークロードでデータ分析基盤を実現している公開事例には、**New York Life** と **Sun Life** がある。

**目的。** 本アーキテクチャは、保険業務に必要なデータ処理を効率的かつ経済的に実現するデータプラットフォームを構築する。これにより、代理店や契約者への多様なサービス提供を支える分析基盤を提供する。

**現状の課題（ビジネス上の動機）。** 保険会社の既存オンプレミスデータプラットフォームは、データ量急増により処理能力不足とコスト増大に直面している。レガシーシステムの機能制約により、多様化する利用者ニーズに対応できない状況となっている。また、セキュリティ境界が曖昧で、コンプライアンス要件への対応が困難であり、各処理段階での障害や変更が他システムに影響を与えるリスクが存在している。

**本アーキテクチャで実現したいこと。** 以下の 4 点である。

- **コスト効率的なスケーラビリティ** — データ量の変動に応じて自動的にリソースを増減し、必要な時に必要な分だけコストを支払う従量課金モデルを実現する。
- **高性能データ処理** — 大量データの高速処理と複数ユーザーからの同時アクセスに対応できる処理能力を提供する。
- **高可用性の確保** — システム障害時でも業務継続できる冗長化を実現する。
- **セキュリティとガバナンスの強化** — セキュリティ境界の明確化、コンプライアンス要件への対応、責任分離とガバナンスの強化、運用の独立性確保を実現し、各処理段階での障害や変更が他に影響しないよう、役割（データエンジニア・アナリスト・セキュリティチーム等）に応じた適切なアクセス制御と権限管理を行う。

## ベストプラクティスと主要コンポーネント

### ベストプラクティス

- SHOULD: 統合データレイクを中心にデータプラットフォームを構成し、保険業務における契約者情報・健康情報・財務データの取り込みから分析機能までをクラウド上でシステム化する。
- SHOULD: データ量の変動に連動する自動スケーリングと従量課金モデルを採るマネージドサービスを採用し、コスト効率的なスケーラビリティを実現するとともに、オンプレミス環境の固定コストと過剰プロビジョニングの課題を解決する。
- SHOULD: データレイクとデータウェアハウスを組み合わせた統合処理基盤により、大量データの高速処理と複数ユーザーからの同時アクセスに対応する。自動化された ETL / ELT パイプラインでデータ変換処理を並列実行する。
- SHOULD: データレイクの自動レプリケーション、クラスターのマルチノード構成、ジョブの自動再試行により、業務継続のための冗長化を実現する。
- MUST: 取り込み、データレイク、変換、データウェアハウス、分析の各処理を分離アカウントで実行するマルチアカウント戦略を導入し、PII / PHI トークン化、アカウント分離、最小権限アクセス制御を盛り込んで、保険業界特有のデータプライバシー要件と規制遵守を実現する。
- SHOULD: Amazon Aurora メタデータリポジトリと AWS Glue フレームワークを併用し、データソースのパターンに応じて Glue ジョブを自動生成することで、ポイントツーポイント型の個別取り込みソリューションを排除し、100 以上の異なるソースからの効率的な取り込みを実現する。
- SHOULD: Amazon Redshift Data Sharing により ETL / ELT 処理と分析処理を完全分離し、データサイエンティストにサーバーレスクラスターで本番データへの安全なアクセスを提供しつつ、パフォーマンス競合を回避する。
- MUST: 着地バケットにはソースシステムと全く同じ状態でデータを着地させ、そこでは変換を一切実行しない。標準化と PII / PHI トークン化はその後の統一パイプラインでのみ実施する。
- MUST: データ取り込みアカウント内の Raw バケットには変更・標準化・トークン化されたデータのみを保存し、その後データレイクアカウントに変更を適用する。
- SHOULD: 役割ごとに最小権限を付与し、データ取得部分は着地バケットへの書き込みアクセス権のみ、処理部分は読み取りアクセス権のみとする。トラストポリシーによるクロスアカウントアクセスで、侵害時の迅速な遮断を可能にする。
- MUST: 最小権限の IAM ロールベースのクロスアカウントアクセスを適用し、信頼関係を設定した特定のアカウントからのみリソースアクセスを許可する。
- SHOULD: 機微情報は AWS Secrets Manager と AWS Systems Manager Parameter Store（ SecureString ）で暗号化保存し、AWS KMS でキー管理を行う。
- SHOULD: AWS CloudTrail で全 API 呼び出しを監査ログとして記録し、AWS Config でリソース設定変更を追跡する。
- MAY: AWS Glue Studio のビジュアル ETL ジョブで Detect PII transform を使用して個人情報を自動検出し（検出パターン・閾値・サンプリング率を設定）、機密データをマスキングする。AWS Glue DataBrew レシピと組み合わせて日付フォーマット変換を行い、AWS Glue の正規表現 ( regex ) で日本語に対応した機密データの検出エンティティを作成する。
- MAY: Salesforce、Adobe、SharePoint 等の構造化・非構造化データに対応する汎用の取り込みフレームワークを構築する。
- SHOULD: Parquet から Apache Iceberg への移行で利益が得られるテーブル（約 4,000 テーブルのうち 1,200 - 1,400 テーブルを特定）を Iceberg へ移行する。
- WILL: 約 500 テーブルを Iceberg 変換することで、更新・書き込み処理に対し 25 - 40 % のパフォーマンス向上を実現した。
- MAY: 分析・レポーティング用途で数時間の停止が許容できる場合、完全な DR （災害復旧）環境の構築を見送り、S3 の耐久性とマルチ AZ 配置に依拠し、ビジネス要件の変化に応じて DR を段階的に実装する。

### 主要コンポーネント

#### データレイク

- **コンポーネント概要**: レイクハウスの中核となるストア。約 100 の異なるソースからデータを取り込み、99.999999999 % ( 11 ナイン ) の耐久性と実質無制限のスケーラビリティを提供し、保険業界で必要な 30 - 40 年の長期データ保持に適する。データレイクアカウントはエンドユーザーがデータを消費できる最初のレイヤーであり、30 - 40 年間の契約者履歴を Type 2 （履歴保持）の slowly changing dimension として維持する。
- **想定される AWS サービス**: Amazon S3、AWS Lake Formation。

#### メタデータリポジトリと取り込みフレームワーク

- **コンポーネント概要**: 統一的でメタデータ駆動型の取り込みフレームワーク。メインのメタデータリポジトリがソースパターンを保持し、メタデータをロードすると Glue ジョブが自動生成される。ポイントツーポイント型の取り込みを排除し、100 以上のソース（ SFTP、DMS、CDC、メッセージベース等 ）からの効率的な取り込みを実現する。
- **想定される AWS サービス**: Amazon Aurora、AWS Glue、AWS Lambda。

#### ETL / ELT と変換

- **コンポーネント概要**: 自動化された変換パイプライン。統一パイプラインで、1. 独自のデルタ検出、2. 標準化（日時形式、住所ドクター呼び出し）、3. 3rd Party サービスによる PII / PHI トークン化を実施する。任意で、AWS Glue Studio の Detect PII transform と AWS Glue DataBrew レシピを用いた PII 検出・マスキングが可能である。
- **想定される AWS サービス**: AWS Glue（ジョブ、Studio、DataBrew）、AWS Lambda、AWS Step Functions、3rd Party トークン化サービス。

#### データウェアハウス

- **コンポーネント概要**: Redshift Data Sharing による計算分離型ウェアハウス。メインプロビジョニングクラスターで ETL / ELT 処理を実行し、データサイエンティスト用・分析用のサーバーレスクラスターに本番データを共有することで、パフォーマンス競合を回避する。権限管理は AWS Lake Formation と Redshift 外部テーブルで実装する。
- **想定される AWS サービス**: Amazon Redshift（プロビジョニング + サーバーレス）、Amazon Redshift Data Sharing、Amazon Redshift Spectrum、AWS Lake Formation。

#### 分析・レポーティング

- **コンポーネント概要**: 共有された本番データを消費し、レポーティングやデータサイエンス用途に用いる分析レイヤー。ETL / ELT の計算基盤から分離されている。
- **想定される AWS サービス**: Amazon Athena、Amazon QuickSight、Amazon Redshift（サーバーレス）。

#### マルチアカウントのセキュリティとガバナンス

- **コンポーネント概要**: Well-Architected に準拠したマイクロアカウント戦略。データパイプラインの各段階を専用アカウントに分離し、PII / PHI の完全分離を実現する。役割別の権限（取得は書き込みのみ、処理は読み取りのみ）とトラストポリシーによるクロスアカウントアクセスにより、侵害時の迅速な遮断を可能にする。機微情報は暗号化・監査される。
- **想定される AWS サービス**: AWS IAM（ロール、トラストポリシー、クロスアカウントアクセス）、AWS Secrets Manager、AWS Systems Manager Parameter Store、AWS KMS、AWS CloudTrail、AWS Config、AWS Organizations。

- 保険業界特有のデータプライバシー要件と規制遵守が、マルチアカウント戦略、PII / PHI トークン化、アカウント分離、最小権限アクセス制御を採用する理由として挙げられている。
- 曖昧なセキュリティ境界の明確化、責任分離とガバナンスの強化、運用の独立性確保が、コンプライアンス志向の動機として述べられている。
- これらの一般的な記述を超える、特定の FISC 管理番号・法令・固有名詞の基準は出典に現れない。これ以上の FISC マッピングを推測してはならない。

## リファレンスアーキテクチャ

本アーキテクチャは、Amazon S3 データレイクと Amazon Redshift によるレイクハウスへの移行を行い、約 100 の異なるソースからデータを取り込み、マネージドサービス（ AWS Glue、AWS Lambda、Amazon Redshift 等）を活用する。メタデータ駆動型の取り込みフレームワーク、Redshift Data Sharing による計算分離、PII / PHI をパイプライン全体で完全分離するセキュリティ重視のマルチアカウント（マイクロアカウント）構成を中心に構成される。

技術的詳細（着地 → Raw → データレイクの取り込みフロー、データ消費レイヤー、テーブル数・Iceberg の数値、権限管理・機微情報管理、「実装しなかったこと」（完全な DR）の判断、FAQ、SCD Type の注釈を含む）は `references/architecture.md` を参照。アーキテクチャ図は `assets/images/` にある（ `overview.png`、`reference-architecture.png` ）。
