ABOUT THIS REPORT

本レポートは、ランサムウェア対策の 4 フェーズ（保護（Protect）・検知（Detect）・対応（Respond）・復旧（Recover））のうち 保護（Protect）フェーズ を対象としている。検知・対応・復旧の各フェーズは別途扱う。

本レポートは、AWS 金融リファレンスアーキテクチャ日本版で公開されているランサムウェア対策向けの SKILL を用いて、お客様の既存バックアップ環境に対する改善ロードマップを整理したものである。「評価結果レポート」で示した不足ポイントに対する具体的な実装ロードマップ (短期・中期・長期) と、各施策の設計判断・期待される防御効果をまとめている。

短期項目 (最優先・即着手)

1
SCP によるバックアップ・ログ保護の予防的統制
短期

位置づけ

既存の Organizations + SCP 基盤がそのまま使えるため、新規アカウント作成やアーキテクチャ変更なしで即座に防御力を引き上げられる。攻撃者が業務アカウントの管理者権限を奪取した場合でも、SCP で Deny されたアクションは実行できない (ルートユーザーでも不可) ため、現状構成のまま適用できる最も効果的な予防策である。

設計すべき SCP のパターン

(1) バックアップ・スナップショット削除防止

統制対象Deny するアクション例
EBS スナップショット削除ec2:DeleteSnapshot
RDS スナップショット削除rds:DeleteDBSnapshot, rds:DeleteDBClusterSnapshot
EFS バックアップ削除(AWS Backup 移行後は backup:DeleteRecoveryPoint で統一可能)
FSx バックアップ削除fsx:DeleteBackup

現状は各サービス個別のスナップショットで運用しているため、サービスごとの削除アクションを個別に Deny する必要がある。中期で AWS Backup に移行した後は、backup:DeleteRecoveryPoint と backup:DeleteBackupVault の Deny に集約することが可能である。

例外運用の考慮: 不要になったスナップショットの削除が完全にできなくなるため、特定の管理者ロール (Break Glass ロール) のみ除外する条件キーを付けるか、Organizations 管理アカウントから一時的に SCP をデタッチする運用手順を事前に整理しておく。

(2) KMS キー削除・無効化防止

統制対象Deny するアクション例
キー削除のスケジュールkms:ScheduleKeyDeletion
キーの無効化kms:DisableKey

CMK で暗号化されたスナップショットは、キーが削除されると復号不能になる。攻撃者がキーを削除するだけでバックアップを使い物にならなくできるため、この SCP は暗号化対策の補完として重要である。

(3) CloudTrail / Config 停止・削除防止

統制対象Deny するアクション例
CloudTrail 停止cloudtrail:StopLogging, cloudtrail:DeleteTrail, cloudtrail:UpdateTrail
Config 停止config:StopConfigurationRecorder, config:DeleteConfigurationRecorder, config:DeleteDeliveryChannel

攻撃者は証跡を消すためにログ取得を停止しようとする。SCP で予防的に Deny しておくことで、フォレンジック分析の基盤を確保する。

(4) 組織離脱防止

統制対象Deny するアクション例
組織からの離脱organizations:LeaveOrganization

アカウントが組織を離脱すると SCP の統制が外れるため、攻撃者が離脱 → 削除の手順を踏むリスクを防ぐ。

設計時の共通考慮事項

  • Condition キーによる例外: Break Glass ロールを aws:PrincipalArn 条件で除外する設計が一般的
  • 適用範囲: 業務アカウントが所属する OU 全体に適用。Organizations 管理アカウント自体には SCP は効かない仕様のため、管理アカウントの保護は別途 IAM レベルで対応
  • テスト: 本番適用前に、テスト用 OU で影響範囲を確認することを推奨

ログ保管 S3 の改ざん防止
短期

位置づけ

CloudTrail / Config のログは S3 に一元保管されているが、改ざん防止が未設定のため、攻撃者が S3 バケットへの権限を得た場合にログを削除・上書きできる状態である。フォレンジック分析の基盤を確保するため、ログ保管 S3 バケットに多層防御を適用する。

適用すべき保護機構

#保護機構役割適用方法
1S3 Versioning上書き・削除があっても旧バージョンが残るバケット設定で有効化
2S3 Object Lock (Compliance mode)保持期間内のオブジェクトを WORM 保護バケット作成時に有効化 (既存バケットへの後付けも可能)
3MFA Deleteバージョンの完全削除に MFA 認証を要求バケット設定で有効化 (ルートユーザーのみ設定可能)
4バケットポリシーの最小権限化ログへのアクセスを限定書き込みはログ転送の仕組みのみ、読み取りは分析チームのみ

設計判断のポイント

  • Object Lock の保持期間: 規制要件で定められた保管期間 (例: 7 年) を基準に設定する。直近 1 年程度は即時アクセス可能な Standard クラスで保管し、それ以降は S3 Glacier へのライフサイクル移行でコスト最適化する設計が一般的
  • 既存バケットへの適用: S3 Object Lock は既存バケットに対しても有効化が可能 (バージョニングが有効であることが前提)。Object Lock 有効化後に書き込まれるオブジェクトから保護が適用され、既存オブジェクトに対しても個別にリテンション設定を適用することが可能
  • SCP との組み合わせ: 短期項目 1 の SCP で s3:PutBucketPolicy や s3:DeleteBucket を Deny しておくことで、バケットポリシー改変やバケット削除も防止。ログ保管バケットの ARN を条件に含めた SCP を追加することを推奨

マルチアカウント構成の導入
中期

位置づけ

現状は業務アカウント内でバックアップを保管しているため、業務アカウントが侵害されればバックアップも同時に破壊される。Vault Lock を業務アカウント内の Vault に適用してもアカウントごと侵害されるリスクは残るため、まずはバックアップを業務アカウントから物理的に分離するアカウント構成を作ることが、後続のすべての中期施策の前提となる。

追加すべきアカウント

新設アカウント役割配置 OU の推奨
Backup アカウント 組織全体のバックアップポリシーを集中管理。Organizations から AWS Backup の delegated administrator として委任。組織横断のモニタリングと監査レポートの集約先 専用 OU (Security OU 配下、または独立した Backup OU)
隔離アカウント (Isolated) 業務アカウントから切り離されたバックアップの追加保護先。クロスアカウントコピーで業務アカウントから複製を受け取り、Vault Lock で改変・削除耐性を担保
リカバリアカウント フォレンジック分析、リストアテスト、有事の際の復旧確認の場。隔離アカウントから平時から継続的にコピーを受ける (推奨)

アカウント分離の設計判断

  • Backup アカウントと隔離アカウントを分ける理由: ポリシー管理 (Backup アカウント) とデータ保管 (隔離アカウント) の責務を分離。責務の分離 (Separation of Duties) が成立し、Backup アカウントが侵害されてもデータそのものは隔離アカウントで生き残る
  • リカバリアカウントが必要な理由: リストア操作とバックアップ操作の責務分離を IAM ロールレベルで実現。フォレンジック分析時、感染した可能性のあるデータを業務アカウントに戻して調査するのはリスクがあるため、隔離された分析環境が必要
  • OU 設計: 既存の SCP (短期項目 1) は業務アカウント向けに設計されており、Backup / 隔離 / リカバリアカウントには異なる SCP を適用。200 アカウントが既に業務システム単位で分離されているため、新設 3 アカウントは Security OU または独立した Backup OU を作成して配置するのが運用上整理しやすい

AWS Backup への移行と組織横断管理
中期

位置づけ

現状は各サービス個別のスナップショット機能を使っているが、200 アカウントで以下の課題が想定される。

  • 各アカウント・各サービスで個別に設定する必要があり、設定漏れ・不整合が発生しやすい
  • 取得頻度・保持期間の標準化が困難
  • クロスアカウント・クロスリージョンコピーや Vault Lock といったランサム対策機能が AWS Backup を経由しないと使えない (一部のサービスでは個別機能でも実現可能だが、統一的な管理にはならない)

AWS Backup と Organizations のバックアップポリシーを組み合わせて、200 アカウントを Backup アカウントから一元管理する構成に移行することを推奨する。

Organizations のバックアップポリシーによる組織横断管理

仕組みは以下のとおり。

  1. Backup アカウントでバックアップポリシー (JSON) を定義
  2. Organizations の OU またはアカウントにアタッチ
  3. 適用された業務アカウントに、対応するバックアッププランが自動作成される
  4. バックアッププランに従って AWS Backup がバックアップを実行

この仕組みにより、各業務アカウントへ個別ログインしてバックアッププランを設定する必要がなくなり、Backup アカウントから組織全体に統一されたバックアップ標準が適用される。

業務影響度別のバックアッププラン分割

基幹系と情報系でバックアップ要件 (求められる取得頻度・周期) が異なる (基幹系: 1 時間ごと / 情報系: 日次) ため、業務影響度別に複数のバックアッププランを作成することを推奨する。

プラン対象取得頻度保持期間 (例)
Critical (基幹系)タグ Backup-Tier: critical のリソース1 時間ごと、または Continuous backup規制要件に基づく長期保管
Standard (情報系)タグ Backup-Tier: standard のリソース日次中期保管

タグベース運用とすることで、新規リソース作成時にタグを付ければ自動的に対象に含まれる運用が可能となる。Organizations のタグポリシーを併用すると、200 アカウント横断でのタグ命名統一が実現できる。

リソース別の特性整理

リソースごとに AWS Backup での扱いが異なる点に注意する。

リソースAWS Backup での独立暗号化Continuous backup (PITR)留意点
EC2 / EBS非対応 (ソース EBS の暗号化キーを継承)非対応既存 EBS が CMK 暗号化済みであれば問題なし
RDS / Aurora非対応対応 (PITR 活用が可能)基幹系の短い取得間隔の要件は PITR で実現容易
S3対応 (Vault の KMS で再暗号化)対応周期的バックアップ + Continuous backup の組み合わせ可能
EFS対応非対応業務側ジョブ完了との連携で静止点を確保する運用設計が必要
FSx for Windows非対応 (FSx 側の暗号化キーを継承)非対応VSS 連携でアプリケーション整合性のあるバックアップが取得可能

基幹系のバックアップ要件 (1 時間ごとの取得) の達成方針

  • RDS / Aurora: Continuous backup (PITR) で対応
  • S3: Continuous backup + 周期的バックアップの組み合わせで対応
  • EC2 / EBS、EFS、FSx: 1 時間ごとのスナップショット取得 + バックアップ開始ウィンドウを最小値 (60 分) に設定

FSx for Windows の静止点確保

FSx for Windows は VSS (Volume Shadow Copy Service) 連携の AWS Backup 統合がサポートされており、アプリケーション整合性のあるバックアップが取得可能である。業務システムによって静止点の厳密性が求められる場合、業務側ジョブ完了との連携を運用設計に組み込む。

既存スナップショットからの段階的移行

  1. AWS Backup での新規バックアップ取得を開始 (既存スナップショットと並走)
  2. 一定期間並走させ、AWS Backup でのバックアップが正常に取得できることを確認
  3. 既存の個別スナップショット取得を停止
  4. 既存スナップショットは保持期間満了まで残し、自然消滅させる

並走期間中はストレージコストが二重にかかるが、移行リスクを最小化するために必要なステップとなる。

クロスアカウント・クロスリージョンコピーの実装
中期

位置づけ

中期 3 で新設したアカウント間でバックアップを複製する経路を構築する。バックアップ取得と同時に自動的にコピーが作成される仕組みとし、運用負荷を最小化する。

コピー経路の設計

業務アカウント(東京)でバックアップ取得
  ├─→ 業務アカウント(大阪)        [クロスリージョンコピー: DR 対策]
  └─→ 隔離アカウント(東京)        [クロスアカウントコピー: ランサム対策]
        └─→ リカバリアカウント(東京)  [クロスアカウントコピー: 復旧基盤]

各コピーは、バックアッププラン内の Copy Action 設定で定義する。

コピー成立のためのポリシー連携 (4 レイヤー)

クロスアカウントコピーは以下の 4 つのポリシーが連携して初めて成立する。1 つでも欠けるとコピーは失敗する。

レイヤーポリシー配置場所役割
1バックアップ実行 IAM Role業務アカウントコピー操作を実行する権限
2KMS キーポリシー (コピー元)業務アカウントコピー元データの復号許諾
3Vault アクセスポリシー (コピー先)隔離 / リカバリアカウントクロスアカウントからのコピー受け入れ許諾
4KMS キーポリシー (コピー先)隔離 / リカバリアカウントコピー先データの再暗号化許諾

重要な制約: クロスアカウントで許可される操作

  • Vault アクセスポリシーで許可できるクロスアカウントアクションは backup:CopyIntoBackupVault のみ
  • これ以外のアクション (リカバリポイント削除等) はクロスアカウントでは実行不可能な仕様
  • 結果として、業務アカウントが侵害されても、隔離アカウントの Vault 内のリカバリポイントは削除できない構造になる

この仕様自体がランサム対策として効果を持つ点が、クロスアカウントコピーを採用する大きな理由のひとつである。

KMS CMK のアカウント別・リージョン別分離

各コピー先で KMS CMK を独立して管理することで、単一鍵掌握のリスクを回避する。

リカバリアカウントへのコピー方針

基幹系については、ランサム被災時に迅速に復旧へ着手できるよう、平時からリカバリアカウントにコピーしておく構成を推奨する。

アプローチ復旧着手への影響コスト
平時から継続的にコピー (推奨)即座にリストア開始可能ストレージコスト二重
インシデント発生時にオンデマンドコピーコピー完了まで復旧着手が遅延コスト最適

基幹系は復旧着手の迅速性が求められるため、隔離 → リカバリのコピーが間に合わない可能性を踏まえ、平時からの継続コピーを推奨する。情報系は復旧着手までの許容時間に余裕があるため、コスト最適化の観点でオンデマンドコピーでも対応が可能となる。なお、復旧完了までの所要時間 (RTO) はバックアップ・コピー設計だけでなく、リストア・切替・検証等の運用要素を含めて確保されるものであり、本項目はそのうちの復旧着手の準備性に寄与する位置づけである。

設計判断のポイント

grace time の設定

  • Vault Lock 有効化直後に設けられる猶予期間
  • grace time 中は設定変更や Lock 解除が可能、grace time 経過後は一切不可
  • 慎重に検証してから grace time を経過させることが重要

保持期間の慎重な設計

Compliance mode では grace time 経過後は保持期間の変更ができないため、以下を慎重に決定する。

  • 最小保持期間: 規制要件・業務要件で定められた最低限の保管期間 (例: 7 年)
  • 最大保持期間: コスト膨張を防ぐための上限 (無期限設定は避ける)
  • バックアップライフサイクルの保持期間との整合: Vault Lock の範囲内に収める

コールドストレージへの移行

  • 長期保管のコスト最適化のため、ライフサイクルでコールドストレージへ移行する設計を推奨
  • Compliance mode では移行設定も Lock の対象となるため、Vault Lock 有効化前に移行設計を確定する

Cohasset Associates によるコンプライアンス評価

AWS Backup Vault Lock は、SEC 17a-4、CFTC、FINRA 規制の環境での利用に対する適合性評価が Cohasset Associates によって実施されている。金融機関での採用に際して、規制対応の観点での説明材料として活用することが可能である。

第一候補: GuardDuty Malware Protection for Backup

AWS Backup と Amazon GuardDuty の統合機能で、Backup vault 内の復旧ポイントに対して直接マルウェアスキャンを実施することが可能となる。リストアを経ずにスキャンが完結する点が運用上の大きな利点である。

本機能でネイティブにスキャンが可能なリソースは以下のとおり。

リソース備考

クロスアカウントでコピーされた EC2 復旧ポイントは増分スキャンが利用できず、フルスキャンが必要となる点に注意する。隔離アカウント・リカバリアカウントでスキャンを実施する場合は、フルスキャンのコスト・実行時間を運用設計に組み込む。

クォータ起因の事前確認

GuardDuty Malware Protection for Backup には複数の調整不可クォータが定義されている (スナップショットサイズ上限、AMI 内スナップショット数上限、S3 オブジェクトサイズ上限等)。具体的な数値は機能拡張により変わるため、AWS 公式ドキュメントの最新版で確認する。

特に以下のワークロードは事前確認が必要である。

  • 大容量 EBS ボリュームを持つデータベースサーバー
  • 多数のディスクを持つ EC2 インスタンス
  • 大容量 S3 オブジェクトを扱うシステム

クォータに収まらない場合は、ワークロード側の構成見直し (ボリューム分割等) か、後述のサードパーティ製品との併用ワークアラウンドを検討する。

EC2 上の EDR との関係

既に EC2 上で EDR が稼働しているが、EDR は稼働中の OS 上で動作するエージェント型のため、バックアップデータ (スナップショット) に対する直接スキャンには対応していないのが一般的である。GuardDuty Malware Protection for Backup と EDR は補完関係にあり、以下のように役割を分けることを推奨する。

検知層機能
EC2 稼働中のリアルタイム検知既存 EDR
バックアップデータの定期スキャンGuardDuty Malware Protection for Backup

両者を併用することで、攻撃のタイミングと検出経路を多層化する。

サードパーティ製品でのチェック (補完アプローチ)

組織の標準セキュリティ製品 (既存 EDR と同系列の製品等) でバックアップデータもチェックしたい場合、リストア → 実機スキャンのワークアラウンドが選択肢になる。

アーキテクチャ概要は以下のとおり。リカバリアカウント内で AWS Backup の Restore testing 機能を活用し、定期的に復旧ポイントをリストア → EDR でスキャン → 結果を記録 → 復元したインスタンスを破棄、というフローを自動化する。

  1. AWS Backup の Restore testing で定期的にリカバリポイントを EC2 として復元
  2. EventBridge で EC2 起動を検知し、Lambda が EDR 管理サーバーへスキャン指示
  3. スキャン結果を DynamoDB 等に記録 (AWS Backup 側に検査ステータスをマーキングする仕組みは現時点では提供されていないため、外部データストアでの管理が必要)
  4. 感染検知時は SNS で通知
  5. スキャン完了後、Lambda で復元 EC2 を停止・削除

留意点:

  • 定期的なリストアによりストレージ・コンピュートコストが発生
  • GuardDuty Malware Protection for Backup と比較してコストが高くなる傾向
  • ただし、組織で標準化された EDR の検知エンジン・SOC 運用プロセスとの統合が可能

RDS / Aurora / EFS / FSx for WindowsEDR 系製品でのリストア → 実機スキャン、または運用上スキャン対象外として受容

RDS / Aurora / EFS / FSx for Windows のスキャン対象外分については、組織のセキュリティ部門との合意形成が必要となる。完全なスキャンを求める場合はリストア → 実機スキャンの実装、コストとのバランスで運用上スキャン対象外として受容するのも選択肢になる。

LAG vault (Logically Air-Gapped vault) はさらに踏み込んだ保護機構として位置づけられる発展構成。中期で構築した「通常 Vault + Vault Lock」の構成でもランサム対策として有効だが、LAG vault には以下の追加的な特性がある。

観点内容

Multi-party approval の運用設計

LAG vault を採用する場合、Multi-party approval は単独攻撃者による不正復元への強力な防御となるが、運用上の準備が必要となる。

  • 承認者の選定: 復旧オペレーションを承認できる権限者を平時から指名しておく
  • 緊急時の承認プロセス: 夜間・休日のインシデント時にも承認者が確実に対応できる体制を整備
  • 承認ログの保全: 承認の証跡を CloudTrail で記録し、監査対応に活用

組織のインシデント対応プロセスと整合する形で、承認体制を設計する。

採用判断のステップ

  1. 中期項目 6 までを完了し、通常 Vault + Vault Lock の構成で運用を安定化
  2. LAG vault の対応リソース最新状況、Multi-party approval の運用設計を確認
  3. 組織のキー管理ポリシーとの整合を確認 (特に「顧客管理キーでの暗号化」が必須要件かを確認)
  4. ハイブリッド構成への移行計画を策定 (RDS / Aurora は通常 Vault + Vault Lock を継続)
