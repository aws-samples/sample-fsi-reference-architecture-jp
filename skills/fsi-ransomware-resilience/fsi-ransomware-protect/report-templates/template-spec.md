# レポートテンプレート仕様書 (template-spec)

本ファイルは `fsi-ransomware-protect` Skill の Workflow 完了時に生成するレポートについて、AI エージェントが毎回同じフォーマット・粒度・デザインで生成するための仕様書である。本ファイルおよび同階層の HTML テンプレートに完全準拠してレポートを生成すること。

レポートを生成する Workflow と生成物は以下のとおり。

| Workflow | レポート 1 | レポート 2 |
|---|---|---|
| Workflow A (全体設計) | 設計提案レポート (design-proposal) | ロードマップ詳細レポート (roadmap-detail) |
| Workflow B (既存環境評価) | 評価結果レポート (evaluation-report) | ロードマップ詳細レポート (roadmap-detail) |

両 Workflow とも 2 レポート構成で、2 つ目のロードマップ詳細レポートは共通のテンプレート (`roadmap-detail-template.html`) を流用する (表紙ラベルと内容のみ Workflow ごとに差し替える)。

## 本ディレクトリのファイル構成

```
report-templates/
├── template-spec.md                       (本ファイル: 仕様書)
├── design-proposal-template.html          (Workflow A: 設計提案レポートのテンプレート)
├── evaluation-report-template.html        (Workflow B: 評価結果レポートのテンプレート)
└── roadmap-detail-template.html           (Workflow A・B 共通: ロードマップ詳細レポートのテンプレート)
```

AI エージェントは以下を順に参照する。

1. 本ファイル (template-spec.md): 仕様・粒度・スタンスを把握
2. 対象 Workflow の 1 つ目のレポートテンプレート (Workflow A は design-proposal-template.html、Workflow B は evaluation-report-template.html): スタイル・構造のリファレンス
3. roadmap-detail-template.html: ロードマップ詳細レポートのスタイル・構造のリファレンス

## レポート生成のタイミングと進め方

Workflow A・B とも、ロードマップ提示の完了後に 2 段階でレポートを生成する。1 つ目のレポート (Workflow A = 設計提案レポート、Workflow B = 評価結果レポート) は MUST で自動生成し、2 つ目のロードマップ詳細レポートはユーザー承認後に生成する。以下では Workflow B を例に記述するが、Workflow A も `workflow-b` を `workflow-a`、`evaluation-report` を `design-proposal` に読み替えて同じ進め方を適用する。なお、レポート生成に対応する処理ステップ番号は Workflow ごとに異なる (Workflow A は SKILL_ja.md の Step 5・6、Workflow B は Step 8・9)。本ファイルの「Step 8a / 8b」は Workflow に依存しない便宜上のラベル (1 つ目のレポート生成 / ロードマップ詳細レポート生成) として用いる。

### Step 8a: 1 つ目のレポート生成 (MUST、ユーザー確認なしで実行)

ロードマップ提示完了後、1 つ目のレポート (評価結果レポート / 設計提案レポート) を Markdown と HTML の両形式で自動生成する。

出力先 (Workflow B の例):
```
fsi-ransomware-protect/report/workflow-b-{YYYYMMDD}-{NN}/
├── html/
│   └── evaluation-report.html
└── md/
    └── evaluation-report.md
```

Workflow A の場合の出力先:
```
fsi-ransomware-protect/report/workflow-a-{YYYYMMDD}-{NN}/
├── html/
│   └── design-proposal.html
└── md/
    └── design-proposal.md
```

`{YYYYMMDD}` は生成日 (ローカルタイムでの 8 桁日付)、`{NN}` は同日内の連番 (`01` から開始する 2 桁ゼロパディング)。同一日に複数回同じ Workflow を実行した場合、連番が増えていく形でディレクトリが分かれる。

生成完了後、ユーザーに以下を提示する。

- 1 つ目のレポートの保存先パス (HTML / Markdown)
- 続けてロードマップ詳細レポートを生成する旨と、内容量が多いため生成に相当な時間を要する旨
- 生成に進んでよいかの対話的な確認

### Step 8b: ロードマップ詳細レポート生成 (ユーザー承認後に実行)

ユーザーから生成同意を得た後、ロードマップ詳細レポートを Markdown と HTML の両形式で生成する。

出力先 (Step 8a と同じディレクトリの html / md 配下、Workflow B の例):
```
fsi-ransomware-protect/report/workflow-b-{YYYYMMDD}-{NN}/
├── html/
│   └── roadmap-detail.html
└── md/
    └── roadmap-detail.md
```

生成完了後、保存先パスをユーザーに提示する。

### ディレクトリ命名規則

- ベースパス: `fsi-ransomware-protect/report/`
- セッション単位ディレクトリ: `workflow-{a|b}-{YYYYMMDD}-{NN}` (Workflow 種別 + 生成日 8 桁 + 同日内連番 2 桁ゼロパディング)
- 同一セッションで生成された 4 ファイル (1 つ目のレポート + ロードマップ詳細、各 HTML/Markdown) は同一の `workflow-{a|b}-{日付}-{連番}/` 配下に格納する

### 連番の決定方法

- AI エージェントは正確な時刻を取得する手段を持たないため、時刻ではなく日付ベース + 連番で管理する
- レポート生成前に `fsi-ransomware-protect/report/` 配下をリストアップする
- `workflow-{a|b}-{今日の日付}-*` に該当する既存ディレクトリを抽出する (Workflow 種別ごとに連番を管理する)
- 既存ディレクトリの連番の最大値 + 1 を採用 (該当なしの場合は `01`)
- 例: 同日に Workflow A を 3 回目の生成なら `workflow-a-20260528-03/` を作成する

### 1 つ目のレポートとロードマップ詳細レポートのディレクトリ整合性

- 1 つ目のレポートとロードマップ詳細レポートは必ず同一の `workflow-{a|b}-{YYYYMMDD}-{NN}/` ディレクトリ配下に配置する
- Step 8a → Step 8b の通常フローでは、Step 8b は Step 8a と同じディレクトリに追加生成される
- ユーザーが既存の 1 つ目のレポートに対するロードマップ詳細レポートを後追いで希望した場合、AI は新規ディレクトリを作成せず、対象となる既存ディレクトリをユーザーに対話的に確認した上で、そのディレクトリに追加格納する
  - 例: 「対象となるレポートを教えてください。以下のいずれかでしょうか?」と既存ディレクトリ一覧 (`workflow-a-20260528-01` / `02` 等) を提示してユーザー選択を受ける
  - 確認後、対象ディレクトリ内の 1 つ目のレポートと整合する形でロードマップ詳細レポートを生成し、同じディレクトリの `html/roadmap-detail.html` および `md/roadmap-detail.md` として格納する
- 完全な新規セッションとして Workflow を最初から実行する場合は、新規連番ディレクトリを作成する

### 日付の取得

- AI エージェントが認識している現在日付 (年月日) をそのまま使用する
- 時刻は使用しない (時刻は AI が正確に取得できないため、仮の時刻を入れるとレポート信頼性が損なわれる)
- レポート内の表紙・フッターの日時表記も日付のみとする (例: `GENERATED — 2026-05-28`)

## 共通の執筆スタンス (両レポート共通)

### 表現の禁止事項

- **「執筆時点」「対応 (執筆時点)」「対応 / 非対応」のような Skill 開発側のメタな表記を使ってはならない**。レポートはお客様向け成果物のため、Skill 内部視点の表現は不適切である
- 機能・サービスの対応リソースを示す場合、対応リソースのみを肯定列挙する。対象外リソースは別段落で「ただし、〇〇 はネイティブスキャン対象外であるため、補完アプローチを検討する」のように補完への導線として 1 〜 2 行で言及する
- **ロードマップの各項目に具体的な期間 (「1〜2 ヶ月」「Phase 1: 2〜3 ヶ月」「2〜3 週間」等) を提示してはならない**。期間は顧客側の組織体制・予算・既存運用等により大きく左右されるため、短期・中期・長期のフェーズ分類のみで示す
- Before/After 比較表で現状を示す際は、「成功する」「実行できる」のような曖昧表現ではなく、**「リスクあり」** と明示する。改善後は「Deny される」「保護される」「即時把握可能」のように防御効果が明確に伝わる表現を用いる

### 推奨される表現

- 総合評価コメントでは、できていること・足りないこと・早急対応すべきことを 3 段構成で記述。重要キーワード (「アカウント分離」「イミュータブル化」「削除防止 SCP の追加」等) は `<strong>` タグで赤字強調 (HTML 側で `color: var(--ng)` が適用される)
- 「より詳細な改善設計について」セクションのアピール文は `<span class="callout">` でティール色の太字を付与
- 文体は Skill 全体の規約に従い、断定すぎない柔らかい文末を選ぶ (「〜することが可能」「〜効果を見込むことができる」等)。Constraints の MUST/MUST NOT のような強制ルールは明確に断定する

## データ構造 (AI が内部で保持すべき構造化データ)

レポート生成時、AI は以下の構造化データを内部で保持してから HTML/Markdown を組み立てる。

## 設計提案レポートのセクション構成と粒度 (Workflow A)

`design-proposal-template.html` のセクション順・スタイルに完全準拠する。本レポートは「評価」ではなく「設計提案」がメインである点が Workflow B の評価結果レポートとの最大の違いである。

### 設計提案レポートの位置づけ

- Workflow A は既存環境を活かしてランサム対策アーキテクチャの全体設計を新たに組み立てる提案である
- 各設計領域には、対応の優先度・スピード感を示すフェーズ (短期 / 中期 / 長期) を付す。フェーズは重要度ではなく「対応の容易さ・既存環境への影響の小ささ」を軸に分類する (SKILL_ja.md の PR-C12 に準拠)
- 詳細な実装ステップ・期待される防御効果はロードマップ詳細レポートに委ね、本レポートは設計方針と各領域の核心・概略に集中する (情報スコープの住み分けは後述)

### セクション順序 (固定)

1. 表紙
2. このレポートについて
3. 提案サマリ (設計方針 3 本柱 + ロードマップ早見表 + Overall Direction)
4. ヒアリング結果 (必須項目 + 未確認項目を表形式)
5. 設計方針の大枠 (全体アーキテクチャ図 + 採用 AWS サービス表 + 判断ポイント)
6. アカウント構成の詳細設計 (新設アカウント表 + OU 構造図 + Backup Policy 配り分け + データフロー)
7. コア構成要素の設計 (4 領域カード: バックアッププラン / イミュータブル化 / 暗号化 / ポリシー設計)
8. 周辺機能の設計 (3 領域カード: マルウェアスキャン / ログ収集・保護 / 監視・監査)
9. 段階的ロードマップ概観 (短期 / 中期 / 長期の項目一覧)
10. 未確認事項とフォローアップ推奨
11. より詳細な実装ロードマップについて (ロードマップ詳細レポートへの導線 + 住み分け表 + 読み方ガイド)
12. 付録 (参照 reference 一覧)

### 表紙

- ラベル: `FSI RANSOMWARE PROTECT — WORKFLOW A`
- タイトル: `【保護フェーズ】<br>AWS ランサムウェア対策設計提案レポート`(`<br>` で 2 行に改行。`【保護フェーズ】` を 1 行目、`AWS ランサムウェア対策設計提案レポート` を 2 行目とする)
- フェーズインジケータ: タイトルの直下に、ランサム対策 4 フェーズ(保護 / 検知 / 対応 / 復旧)を横並びで表示する。`.cover .phase-nav` 内に各フェーズを `<span class="phase">`(日本語 `.ja` + 英語 `.en` の 2 段)で配置し、本レポートが対象とする **保護(Protect)** のみ `class="phase active"` で強調する(塗りチップ + 白文字 + 太字)。他フェーズは淡色・枠線のみ。日英併記(保護/Protect、検知/Detect、対応/Respond、復旧/Recover)
- サブタイトル: 設計提案レポートでは表紙にサブタイトルを設けない
- 生成日: `GENERATED — {YYYY-MM-DD}` (日付のみ)
- 表紙背景は他レポートと差別化するため淡いラベンダー系グラデーション (`linear-gradient(120deg, #C9B8E8 0%, #D6C6E8 45%, #C6D6EC 100%)`)、文字色は濃色 (`#2A2342`)、アクセントは紫系 (`#6A4F9C`)。フェーズインジケータの強調色(`.phase.active` の背景)はアクセントの紫系を用いる

### このレポートについて (静的文言)

以下の文言を必ず使用する。

> 本レポートは、AWS 金融リファレンスアーキテクチャ日本版で公開されているランサムウェア対策向けの SKILL を用いて、お客様のランサム対策アーキテクチャの全体設計をまとめたものである。AWS Well-Architected Framework Financial Services Industry Lens、AWS Blueprint for Ransomware Defense 等の AWS 公式ガイダンスをベースに、金融機関の文脈で求められる設計考慮を加味したうえで、お客様環境に合わせた設計提案を行っている。

2 段落目で、各設計領域にフェーズ (短期 / 中期 / 長期) を付していること、詳細な実装手順・防御効果はロードマップ詳細レポートに記載していることを明示する。

### 提案サマリ

- 設計方針 3 本柱: 3 カラムのカード (3-2-1 ルール / 多層防御 / 責務分離)。評価結果レポートの円グラフ枠を置き換える位置づけ
- ロードマップ早見表: フェーズ × 主要な取り組みの 2 列表
- Overall Direction: **約 400〜500 字**で記述。設計の方向性・3 本柱・ハイブリッド構成・段階的アプローチ (アカウント構成変更は長期である旨) を記述。重要キーワードは `<strong>` で赤字強調 (重要事項の強調の意味合い)

### ヒアリング結果

- 必須項目 (保護対象 / オンプレ要否 / バックアップ要件 / マルチアカウント構成) と推奨・任意項目を 1 つの表で提示
- ID は連番 (1〜)。Skill 内部の PR-H1〜PR-H8 識別子は使用しない
- 未取得項目は `<span class="verdict unknown">未確認</span>` バッジで明示し、推測で埋めない

### 設計方針の大枠

- 全体アーキテクチャ図: HTML/CSS の構造化図 (`.arch` / `.arch-node` / `.arch-arrow`) で表現する。ASCII アートは使用しない。管理アカウント → Backup アカウント → 業務アカウント群 → 隔離アカウント → リカバリアカウントの階層を、役割注記とフェーズ色付きノードで示す
- 採用 AWS サービス表: サービス名と役割の 2 列
- 重要な判断ポイント: ハイライト枠 (`.core`) で 4 点程度を箇条書き

### アカウント構成の詳細設計

- 冒頭で「アカウント構成の変更は影響範囲が大きいため長期の取り組みと位置づける」旨を明示
- 新設アカウントと既存リソース活用の表 + OU 構造図 (`.ou-tree`) + Backup Policy 配り分け + データフロー (テキスト型データフロー図)
- 詳細パラメータ (リソース別の細目等) はロードマップ詳細レポートに委ね、ここは概略にとどめる

### コア構成要素の設計 (4 領域カード)

各領域はフェーズ色付きカード (`.domain` + `.domain-header.{short|mid|long}`) で展開する。各カードに以下を含める。

| ブロック | 内容 |
|---|---|
| 設計の核心 (`.core.{short|mid|long}`) | その領域でなぜその設計を採るかを 2〜4 行。フェーズ色の左罫線付き |
| 主要パラメータの簡略表 | 判断軸・選択肢を 3〜5 行の表で要約 (詳細はロードマップ詳細へ) |
| 注意点 (`.note`) | 設計上の注意・最新仕様確認の喚起を 1〜3 行 |

フェーズ割当 (優先度 = 対応の容易さ・即効性の順):

| 領域 | フェーズ | カラー |
|---|---|---|
| ポリシー設計 (SCP) | 短期 | 緑 |
| ログ収集・保護 | 短期 | 緑 |
| バックアッププラン設計 | 中期 | 青 |
| イミュータブル化 | 中期 | 青 |
| 暗号化・KMS キー管理 | 中期 | 青 |
| アカウント構成の詳細設計 | 長期 | 紫 |
| マルウェアスキャン | 長期 | 紫 |
| バックアップ運用の監視・監査 | 長期 | 紫 |

注: コア構成要素のうちポリシー設計 = 短期、バックアッププラン / イミュータブル化 / 暗号化 = 中期。周辺機能のうちログ収集・保護 = 短期、マルウェアスキャン / 監視・監査 = 長期。

### 周辺機能の設計 (3 領域カード)

コア構成要素と同じカード構造 (設計の核心 + 簡略表 + 注意点) で、マルウェアスキャン / ログ収集・保護 / 監視・監査 の 3 領域を展開する。フェーズ色は上表に従う。

### 段階的ロードマップ概観

- 短期 / 中期 / 長期の 3 見出しで、各フェーズの項目を箇条書きで一覧化する (見出しレベル、詳細はロードマップ詳細レポート)
- PR-C12 の判断軸 (影響小・即効性のある対策を短期、個別アカウント単位を中期、組織横断の構成変更を長期) に沿って項目を配置する
- 具体的な期間 (週・月) は記載しない

### 未確認事項とフォローアップ推奨

- 未取得のヒアリング項目 (規制由来の保護要件、既存 EDR/AV、取得優先度、既存 SIEM 等) と影響箇所を表で提示する
- 組織内で確認・合意形成を進めるべき事項を箇条書きで提示する
- 未取得情報を推測で設計値に組み込まず、お客様側で確定する前提を明示する

### より詳細な実装ロードマップについて

ロードマップ詳細レポートへの導線。Workflow B の評価結果レポートの同名セクションとは異なり、以下を Workflow A 固有の内容として含める。

- 設計提案レポートとロードマップ詳細レポートの記載内容の住み分け表 (本レポート = 設計方針・各領域の核心と概略 / ロードマップ詳細 = 実装ステップ・設計判断の根拠・期待される防御効果)
- 読み方ガイド (経営層・コンプライアンス層は本レポートで全体像を把握、実装担当はロードマップ詳細を併読)
- ファイルパス (`../html/roadmap-detail.html` / `../md/roadmap-detail.md`)

### 付録

- 参照 reference 一覧: 評価結果レポートと同じ説明文 + references/01〜08 をリンクとして列挙する

## レポートセクションと必要情報源の対応 (情報充足性の担保)

| レポートセクション | 必要なユーザー固有情報 | 主な情報源 |

### 評価結果レポート (Workflow B) のセクション ⇔ 必要情報源

Workflow B は評価項目 1〜9 と現状ヒアリング PR-HB1〜PR-HB9 が 1 対 1 対応する構造により、評価結果レポートの各評価項目を埋める情報が必須ヒアリングで取得できることを担保している (`01-skill-format-guide.md` のベストプラクティス項目 5 を参照)。お客様環境の前提情報セクションは PR-H1〜PR-H8、現在のバックアップ環境の状況セクションは PR-HB1〜PR-HB9 に対応する。

## 評価結果レポートのセクション構成と粒度

`evaluation-report-template.html` のセクション順・スタイルに完全準拠する。本仕様書では各セクションの内容粒度を定義する。

### セクション順序 (固定)

1. 表紙
2. このレポートについて
3. 評価サマリ (円グラフ + 凡例 + 総合評価コメント)
4. 評価結果サマリ (9 項目の表)
5. 評価項目の詳細 (9 項目を全てカード形式で展開)
6. お客様環境の前提情報 (8 項目を表形式)
7. 現在のバックアップ環境の状況 (9 項目を表形式)
8. より詳細な改善設計について (ロードマップ詳細レポートへの導線)

### 表紙

- ラベル: `FSI RANSOMWARE PROTECT — WORKFLOW B`
- タイトル: `【保護フェーズ】<br>AWS ランサムウェア対策評価結果レポート`(`<br>` で 2 行に改行)
- フェーズインジケータ: タイトルの直下に、ランサム対策 4 フェーズ(保護 / 検知 / 対応 / 復旧)を横並びで表示し、**保護(Protect)** のみ `class="phase active"` で強調する(設計提案レポートと同じ構造)。評価結果レポートは表紙背景が濃色のため、非強調フェーズは白の半透明枠 + 半透明白文字、強調フェーズは `--gold` 塗り + 濃紺(`--navy-1`)文字とする
- サブタイトル: `既存バックアップ環境のランサムウェア対策十分性評価`
- 生成日: `GENERATED — {YYYY-MM-DD}` (日付のみ、時刻は含めない)
- お客様情報 (組織概要・対象リージョン・保護対象リソース等) は表紙に記載しない。これらは「お客様環境の前提情報」セクションで提示する

### このレポートについて (静的文言)

以下の文言を必ず使用する (お客様情報により変動しない静的文言)。

> 本レポートは、AWS 金融リファレンスアーキテクチャ日本版で公開されているランサムウェア対策向けの SKILL を用いて、お客様の既存バックアップ環境をランサムウェア対策の観点で評価した結果をまとめたものである。AWS Well-Architected Framework Financial Services Industry Lens、AWS Blueprint for Ransomware Defense 等の AWS 公式ガイダンスをベースに、金融機関の文脈で求められる設計考慮を加味した観点で評価を実施している。

### 評価サマリ

- 円グラフ: インライン SVG。判定区分 (OK / 一部対応 / NG / 未確認) を時計回りに、12 時方向開始で描画
- 凡例: 各区分の件数と割合 (%)
- 総合評価コメント: **約 500 字** で記述。3 段構成 (できていること約 100 字 → 不足ポイント約 200 字 → 早急対応の示唆約 150 字 → 締め約 50 字)。重要キーワードは `<strong>` で赤字強調

### 評価結果サマリ表

- 9 項目を 1 つの表で提示
- 列: # / 観点 / 現状 / 判定 / 不足ポイント / リスク
- 行ごとに判定別の薄背景色 (NG = 薄赤、一部対応 = 薄黄、OK = 薄緑、未確認 = 薄グレー)
- 観点列は太字 + 紺色で強調

### 評価項目の詳細 (9 項目すべてフル展開)

各項目はカード形式で以下のブロックを必ず含める。1 項目あたり全体で 200〜400 字程度。

| ブロック | 内容 |
|---|---|
| 現状の整理 | お客様回答に基づく現状を 1〜3 文で記述 |
| 判定の根拠 | なぜその判定になったかの理由を 1〜3 文で記述 |
| 不足している要素 / なぜそれが問題か | 不足要素を箇条書きで 3〜5 項目、必要に応じて補足文を追加 |
| 想定されるリスクシナリオ | 攻撃者の動き → 結果 を 1 行のシナリオ文で記述 (専用の枠で表示) |
| 関連する改善項目 | ロードマップ詳細レポートでの対応項目への参照 (短期 N / 中期 N / 長期 N の形式) |
| 参照 reference | 関連する references/ ファイル名 |

### お客様環境の前提情報・現在のバックアップ環境の状況

- それぞれ別の表として提示
- ID は連番 (1〜)。`PR-H1` `PR-HB1` のような Skill 内部識別子は使用しない
- 「未確認」回答は `<span class="verdict unknown">未確認</span>` バッジで明示

### より詳細な改善設計について

ロードマップ詳細レポートへの導線。固定の文言を使用 (テンプレート HTML 内の `.about` スタイルブロックの内容を踏襲)。重要文 2 箇所に `<span class="callout">` を付ける。

## ロードマップ詳細レポートのセクション構成と粒度

本テンプレート (`roadmap-detail-template.html`) は Workflow A・B 共通で流用するが、項目数・項目立ては Workflow およびお客様環境により異なる。

- **Workflow B (既存環境評価)**: 評価で判明した不足項目に対する改善ロードマップ。下記の実装例は短期 1〜2 / 中期 3〜6 / 長期 7〜9 の 9 項目構成
- **Workflow A (全体設計)**: 全体設計の実装ロードマップ。サンプル (`memo/report-samples/roadmap-detail-workflow-a.html`) は短期 1〜3 / 中期 4〜7 / 長期 8〜13 の 13 項目構成

フェーズ分類は PR-C12 の判断軸 (影響小・即効性のある対策を短期、個別アカウント単位を中期、組織横断の構成変更・集中管理基盤の整備を長期) に従う。項目数はお客様環境・評価結果により変動するが、各項目の粒度 (位置づけ + 設計内容 + 期待される効果) は維持する。

#### Workflow による表紙・内容の差し替え

| 項目 | Workflow A | Workflow B |
|---|---|---|
| 表紙ラベル | `FSI RANSOMWARE PROTECT — WORKFLOW A` | `FSI RANSOMWARE PROTECT — WORKFLOW B` |
| タイトル | `【保護フェーズ】<br>AWS ランサムウェア対策ロードマップ詳細レポート`(2 行) | `【保護フェーズ】<br>AWS ランサムウェア対策<br>ロードマップ詳細レポート`(3 行。文字量が多く切れるため `AWS ランサムウェア対策` の後で改行) |

| サブタイトル | `全体設計の実装ロードマップと各項目の設計詳細 (短期 / 中期 / 長期)` | `改善ロードマップと各項目の設計詳細 (短期 / 中期 / 長期)` |
| このレポートについて | 冒頭にフェーズ位置づけ(本レポートは 4 フェーズのうち保護(Protect)フェーズを対象、保護(Protect)フェーズを `.phase-hl` で強調)を記載した上で、「全体設計提案レポート」で示した設計方針・各設計領域に対する実装ロードマップ | 冒頭に同様のフェーズ位置づけを記載した上で、「評価結果レポート」で示した不足ポイントに対する改善ロードマップ |
| 期待される効果の比較表 | 「対策前のリスク vs 対策後」(既存環境の現状を細かく取らないため) | 「現状 vs 改善後」(評価で現状を把握済みのため) |

表紙のグラデーション・フェーズ色・カード構造等のスタイルは Workflow A・B で共通 (変更しない)。Workflow A の項目立ては以下のとおり。

| フェーズ | Workflow A の項目 |
|---|---|
| 短期 | 1. SCP による予防的統制の追加 / 2. ログ保管 S3 の改ざん防止 / 3. 最重要システムの選定とタグ設計 |
| 中期 | 4. 業務影響度別バックアッププランの整備 / 5. Vault Lock (Compliance mode) の適用 / 6. リソース暗号化の点検と KMS CMK 統一 / 7. タグポリシーによる命名統一 |
| 長期 | 8. マルチアカウント構成の新設 / 9. 組織横断 Backup Policy とクロスアカウント・クロスリージョンコピー / 10. クロスアカウントモニタリング + Audit Manager / 11. マルウェアスキャンの導入と ECR 保護 / 12. LAG vault への段階移行と Multi-party approval / 13. フォレンジック体制と他フェーズ統合 |

以下は Workflow B (9 項目構成) を実装例とした記述である。Workflow A の場合は上記の項目立てに読み替える。`roadmap-detail-template.html` のセクション順・スタイルに完全準拠する。

### セクション順序 (固定)

1. 表紙 (淡い紫〜水色グラデーション、文字色は黒に近い紺色)
2. このレポートについて
3. ロードマップ全体像 (フェーズ × 主要施策の表 + 縦型 Progression フロー)
4. 短期項目 (項目 1〜2 をカードで展開)
5. 中期項目 (項目 3〜6 をカードで展開)
6. 長期項目 (項目 7〜9 をカードで展開)
7. 付録 (参照 reference 一覧)

### 表紙

- 評価結果レポートと差別化するため、表紙背景は淡い紫〜水色グラデーション (`linear-gradient(180deg, #B8C8E8 0%, #C8B8D8 50%, #D8C8E0 100%)`) を使用する
- 文字色は黒に近い紺色 (`#0A1A2F`)
- ラベル・タイトル・サブタイトル・生成日時の構成は評価結果レポートと同じ

### ロードマップ全体像

- フェーズ表: フェーズ列 + 主要施策列の 2 列。期間目安列は設けない
- 縦型 Progression フロー: 全 9 ステップを上から下へ縦並び。1 行 1 ノード、矢印「↓」で接続
- ノードの色分け: 短期 = 緑、中期 = 青、長期 = 紫
- 補足文: 「中長期にわたる取り組みとなるが、短期項目だけでも防御力は大きく向上するため、まずは短期項目に着手しつつ、中期・長期の計画を並行して立案することを推奨する」 (期間の数値は記載しない)

### 各項目のカード構成 (全 9 項目共通の必須ブロック)

各項目は項目特性に応じてサブセクションを追加するが、以下のブロックは **全項目で必須**。

| ブロック | 内容 | 文字量目安 |
|---|---|---|
| 位置づけ | 本項目が解決する課題、後続項目との依存関係 | 100〜200 字 |
| 設計内容 (項目特性に応じたサブセクション) | 設計判断、構成図、ポリシー、選択肢比較等 | 項目により大きく変動 |
| 期待される効果 | Before/After 比較表 (攻撃シナリオ / 現状 = リスクあり / 改善後) | 3〜5 行のシナリオ |

### 項目別の追加サブセクション (テンプレートに準拠)

- **短期 1 (SCP)**: 設計すべき SCP のパターン (4 種類) + 設計時の共通考慮事項
- **短期 2 (ログ S3)**: 適用すべき保護機構 + 設計判断のポイント
- **中期 3 (マルチアカウント)**: 追加すべきアカウント表 + アカウント分離の設計判断 + 各アカウントに配置するリソース表 + リージョン戦略 (テキスト型データフロー図) + 金融機関の文脈での補足
- **中期 4 (AWS Backup 移行)**: Organizations のバックアップポリシー + 業務影響度別プラン分割 + リソース別特性整理 + バックアップ要件 (取得頻度・周期) の達成方針 + 既存スナップショットからの段階的移行
- **中期 5 (コピー)**: コピー経路 (テキスト型データフロー図) + 4 レイヤーポリシー連携表 + 重要な制約 + KMS CMK のアカウント別分離 + リカバリアカウントへのコピー方針
- **中期 6 (Vault Lock)**: 適用対象 + モード選択 + 設計判断のポイント (grace time / 保持期間 / コールドストレージ移行) + Cohasset 評価 + Vault Lock と S3 Object Lock の使い分け
- **長期 7 (マルウェアスキャン)**: GuardDuty Malware Protection for Backup の対応リソース + スキャンモード運用設計 + スキャン実行アカウント + クォータ起因の事前確認 + EDR との関係 + サードパーティ製品での補完アプローチ + 推奨アプローチ
- **長期 8 (モニタリング)**: クロスアカウントモニタリング + Audit Manager レポート (機能・出力仕様・配置と保護) + マルウェアスキャン結果との連携 + 金融機関の文脈での活用
- **長期 9 (LAG vault)**: LAG vault の特性 + 採用判断 (対応リソース整理) + 推奨構成 (ハイブリッド) + 採用検討時のトレードオフ + Multi-party approval の運用設計 + 採用判断のステップ

各項目の文字量は本テンプレート (`roadmap-detail-template.html`) の実装内容を基準とし、お客様情報により内容を調整しても粒度を著しく落とさないこと。

- 参照 reference 一覧: 冒頭に説明文として「ランサムウェア対策 SKILL の保護 (Protect) フェーズの `references/` フォルダに格納された以下の詳細ガイドファイルを参照して作成している。」を記載した上で、references/01〜08 をリンクとして列挙する (各 reference の役割を 1 行で説明)

- 配色 (CSS カスタムプロパティの値)
- フォント (Inter + Noto Sans JP)
- 表紙のグラデーション (設計提案レポート = ラベンダー系、評価結果レポート = 紺〜ティール、ロードマップ詳細レポート = 淡い紫〜水色)
- 評価サマリブロックのグラデーション (ティール → 白 → 紺ライト)
- 判定色 (OK = 緑、一部対応 = 黄、NG = 赤、未確認 = グレー)
- フェーズ色 (短期 = 緑、中期 = 青、長期 = 紫)
- 項目カードのヘッダーグラデーション
- 各種シャドウ (二重シャドウで浮遊感を演出)
- 表のヘッダー (紺グラデーション、17px、白文字)
- 円グラフの開始位置 (12 時方向)、時計回り
- メイン背景色 (`--bg-card: #F7F9FC`)、ページ背景色 (`--bg-page: #F4F6FA`)
- 表紙のフェーズインジケータ (`.cover .phase-nav`): ランサム対策 4 フェーズ(保護 / 検知 / 対応 / 復旧)を横並び・日英併記で表示し、本レポートが対象とする **保護(Protect)** のみ `class="phase active"` で強調する構造・配置・並び順。強調色は各レポートの表紙アクセント色に合わせる(設計提案 = 紫系、ロードマップ詳細 = 紫系 `--long`、評価結果 = `--gold`)。なお、`.phase-hl`(本文中で保護(Protect)フェーズを強調するインライン用クラス)は表紙の `.cover .phase-nav` とは別物であり、本文の `.label`(小見出し用クラス)には影響を与えないこと

データ部分 (お客様情報、評価結果、ロードマップ内容) のみテンプレートから差し替える。

## Markdown 版の生成

両レポートは HTML と同等の内容を Markdown でも生成する。

- HTML のセクション構造をそのまま踏襲
- 表は GFM (GitHub Flavored Markdown) 準拠
- HTML の `.callout` `<strong>` 等のスタイル装飾は Markdown では強調 (`**...**`) のみで表現
- 円グラフ・グラデーション・カード装飾等の視覚要素は Markdown では再現できないため、テキストとして「(図: 判定サマリ - OK 1 件 / 一部対応 3 件 / NG 5 件 / 未確認 0 件)」のような形で簡略表現する
