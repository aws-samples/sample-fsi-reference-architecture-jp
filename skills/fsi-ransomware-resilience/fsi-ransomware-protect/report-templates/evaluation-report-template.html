ABOUT THIS REPORT

ランサムウェア対策は、保護（Protect）・検知（Detect）・対応（Respond）・復旧（Recover）の 4 つの観点で体系的に整備することが有効である。本レポートは、このうち 保護（Protect）フェーズ ― 攻撃を受けてもデータを失わない・改ざんされないバックアップ環境 ― を対象に、既存環境の十分性を評価したものである。検知・対応・復旧の各フェーズは別途扱う。

本レポートは、AWS 金融リファレンスアーキテクチャ日本版で公開されているランサムウェア対策向けの SKILL を用いて、お客様の既存バックアップ環境をランサムウェア対策の観点で評価した結果をまとめたものである。AWS Well-Architected Framework Financial Services Industry Lens、AWS Blueprint for Ransomware Defense 等の AWS 公式ガイダンスをベースに、金融機関の文脈で求められる設計考慮を加味した観点で評価を実施している。

Overall Assessment

暗号化については CMK によるバックアップデータの保護が実装されており、暗号化レイヤーでの基盤対応はできている状況である。また、CloudTrail / Config によるログ収集の有効化と一元保管も整備されており、フォレンジック分析の前提となる証跡基盤は一定確保されている。SCP の利用による予防的統制の枠組みも既に組織内で運用されている点は、今後の拡張のベースとして活用が可能である。

一方で、ランサムウェア対策の核心となる「アカウント分離」「イミュータブル化」「クロスアカウント / クロスリージョンコピー」のいずれもが未対応であり、現状では業務アカウントが侵害された場合にバックアップデータも同時に破壊される構成となっている。加えて、200 アカウント規模の運用にも関わらず、バックアップ運用の組織横断的な監視・監査の仕組みが整備されておらず、有事の際に復旧不能が発覚するリスクを抱えている。

早急に対応が必要なのは、既存の Organizations + SCP 基盤を活用したバックアップ・KMS キー・ログ取得の削除防止 SCP の追加と、ログ保管 S3 バケットへのObject Lock / Versioning / MFA Delete の適用である。これらは新規アカウント作成やアーキテクチャ変更を伴わず、1〜2 ヶ月の短期で防御力を大きく引き上げられる。中期では Backup / 隔離 / リカバリの 3 アカウント新設と AWS Backup への移行を計画的に進めることを推奨する。

評価項目の詳細

1
アカウント分離
NG

現状の整理

バックアップ専用アカウントは設置されておらず、各業務アカウント内でスナップショットとして保管されている。Organizations は利用しているが、200 アカウントすべてが業務システム単位で並列に存在する構成。

判定の根拠

ランサムウェア対策の前提となる「責務の分離 (Separation of Duties)」が成立しておらず、業務アカウントが攻撃者に掌握された場合にバックアップデータが同一権限境界内で削除可能な状態となっている。

不足している要素 / なぜそれが問題か

  • Backup アカウント (組織横断のバックアップポリシー集中管理) が未設置
  • 隔離アカウント (Vault Lock を適用した最終保護先) が未設置
  • リカバリアカウント (フォレンジック分析・復旧オペレーション専用) が未設置

200 アカウント規模の組織では、各アカウントで個別運用するのは設定漏れ・統制バラつきの温床となるため、Backup アカウントによる集中管理の効果が大きく出る領域でもある。

想定されるリスクシナリオ

攻撃者が業務アカウントの管理者権限を奪取 → 同一アカウント内のスナップショットを全削除 → バックアップ消失 → 復旧不能

2
バックアッププラン設計
一部対応

現状の整理

各サービス個別のスナップショット機能を利用 (EBS スナップショット、RDS 自動バックアップ、FSx 自動バックアップ等)。AWS Backup による組織横断の一元管理は未導入。取得頻度・保持期間は各アカウントで個別に設定されており、組織全体での標準化・把握はできていない。

判定の根拠

バックアップ自体は取得されているため一定の備えはあるが、200 アカウントで個別設定する構造のため、設定漏れ・標準からの逸脱・取得頻度の不整合が発生しやすい。ランサム対策の観点では、組織横断で一元的に管理され、イミュータブル化・適切な取得世代/保管が担保された構成になっていない点が懸念。

不足している要素 / なぜそれが問題か

  • 組織横断のバックアップポリシー (Organizations のバックアップポリシー機能) が未利用
  • 業務影響度別のプラン分割 (基幹系 / 情報系) が体系化されていない
  • タグベースの対象選定が標準化されておらず、新規リソース作成時に保護対象から漏れるリスク

想定されるリスクシナリオ

200 アカウントの一部で取得頻度・対象設定が誤っており、ランサム被災時に必要な時点のクリーンなバックアップが存在しないことが被災時にはじめて発覚 → 想定外のデータロス

3
イミュータブル化
NG

現状の整理

AWS Backup Vault Lock、S3 Object Lock いずれも未適用。バックアップデータへの WORM (Write Once, Read Many) 保護機構が一切組み込まれていない状態。

判定の根拠

イミュータブル化はランサムウェア対策の核心要素のひとつであり、これが未適用であるとは「攻撃者が管理者権限を奪取した場合、バックアップデータの削除・改ざんが何の追加障壁もなく成立する」ことを意味する。

不足している要素 / なぜそれが問題か

  • Backup vault に Vault Lock (Compliance mode) 未適用
  • ログ・監査証跡保管 S3 への Object Lock 未適用
  • 金融機関の規制対応 (SEC 17a-4、CFTC、FINRA 等の Cohasset 評価) の説明材料としての WORM 保護が確保されていない

想定されるリスクシナリオ

攻撃者が管理者権限を奪取 → Backup vault のリカバリポイントを全削除 / 暗号化キーを削除して復号不能化 → 復旧手段の喪失

関連する改善項目

中期 6 Vault Lock (Compliance mode) の適用、短期 2 ログ保管 S3 への Object Lock 適用

参照 reference

references/02-immutability.md

4
コピー戦略 (3-2-1 ルール)
NG

現状の整理

クロスアカウント・クロスリージョンコピーいずれも未実施。バックアップは取得元と同一アカウント・同一リージョンに留まっている。

判定の根拠

「コピーを 3 つ、異なる場所に 2 つ、オフサイトに 1 つ」という 3-2-1 ルールが未達であり、単一アカウント・単一リージョンへの完全依存となっているため、ランサムウェア対策・事業継続の両面で脆弱な構成。

不足している要素 / なぜそれが問題か

  • 業務アカウント (東京) → 業務アカウント (大阪) のクロスリージョンコピーなし → リージョン障害でバックアップごと消失
  • 業務アカウント (東京) → 隔離アカウント (東京) のクロスアカウントコピーなし → 業務アカウント侵害でバックアップ全滅
  • 隔離アカウントから リカバリアカウントへの平時コピーなし → ランサム被災時の復旧着手に追加のコピー時間を要する

想定されるリスクシナリオ

攻撃者が業務アカウントを掌握、または東京リージョンで広域障害が発生 → コピー先が存在しないためバックアップが完全に失われる

関連する改善項目

5
暗号化
OK

現状の整理

EBS スナップショットは顧客管理キー (CMK) で暗号化済み。S3 バケットも SSE-KMS が適用されている。

判定の根拠

主要なバックアップデータに対して顧客管理キーによる暗号化が実装されており、暗号化レイヤーの基本対応は完了している。AWS マネージドキーではなく CMK を採用している点も、キー管理の透明性・統制可能性の観点で適切。

留意点 / 残存リスク

  • KMS キー削除防止の SCP が未設定のため、攻撃者が kms:ScheduleKeyDeletion や kms:DisableKey を実行することでキーを使用不能にし、結果としてバックアップを復号不能にできる状態
  • キーローテーションの設定状況、キーポリシーのアクセス制御範囲も継続的にレビューする運用が望ましい

想定されるリスクシナリオ

攻撃者が KMS キー管理権限を奪取 → 暗号化キーを削除 → バックアップは存在するが復号できず実質的に喪失

6
マルウェアスキャン
一部対応

現状の整理

EC2 稼働中のリアルタイム検知は EDR で対応済み。ただし、バックアップデータ (スナップショット) に対する直接スキャンの仕組みは未整備。リストア前のクリーンチェックの仕組みもない。

判定の根拠

稼働中のリアルタイム検知層は確保されているが、ランサムウェア対策で重要となる「バックアップ自体が感染していないことの保証」が不足。EDR は OS 上のエージェント型のため、スナップショット内部の検査には対応しないのが一般的。

不足している要素 / なぜそれが問題か

  • バックアップデータに対する定期的なマルウェアスキャンがない (GuardDuty Malware Protection for Backup 等)
  • リストア時のクリーンチェック手順が運用に組み込まれていない
  • 結果として、感染した状態のスナップショットが保管され、それを元にリストアして再感染するリスクが残る

想定されるリスクシナリオ

攻撃者が一定期間潜伏 → 既に感染済みのデータがバックアップに含まれる → 復旧時に感染状態をそのまま戻し再感染が発生

関連する改善項目

長期 7 マルウェアスキャンの導入 (GuardDuty Malware Protection for Backup + EDR の補完)

参照 reference

references/05-malware-protection.md

7
ログ収集・保護
一部対応

現状の整理

CloudTrail / Config が有効化されており、ログは S3 バケットに一元保管されている。フォレンジック分析の前提となる証跡基盤は確保されている。一方で、ログ保管 S3 バケットへの改ざん防止 (Object Lock、MFA Delete 等) が未設定。

判定の根拠

ログを集めること自体はできているが、攻撃者がログ保管 S3 への権限を獲得した場合、ログを削除・改ざんできる構成のため、有事のフォレンジック分析が成立しないリスクがある。

不足している要素 / なぜそれが問題か

  • S3 Versioning が未有効化 (オブジェクト上書き時に旧バージョンが残らない)
  • S3 Object Lock (Compliance mode) が未適用 (削除に対する WORM 保護がない)
  • MFA Delete が未設定 (ルートユーザーが削除アクションを実行できる)
  • バケットポリシーによる読み書き権限の最小化が未徹底

想定されるリスクシナリオ

攻撃者がログ保管 S3 への書き込み権限を獲得 → 痕跡となるログを削除・上書き → 攻撃の経緯が追跡不能に

関連する改善項目

短期 2 ログ保管 S3 の改ざん防止 (Versioning + Object Lock + MFA Delete)、短期 1 CloudTrail / Config 停止防止 SCP

参照 reference

references/07-log-collection-and-protection.md

8
SCP・予防的統制
NG

現状の整理

SCP は組織内で既に利用されており、利用禁止サービスのアクション制御は実装済み。一方で、バックアップ・KMS キー・CloudTrail / Config 等のランサムウェア対策に直結する SCP は未設定。

判定の根拠

SCP の運用基盤は整備されているが、ランサムウェア対策の文脈で求められる予防的統制 (削除防止系 SCP) が組み込まれていないため、攻撃者が管理者権限を奪取した場合の防御として機能しない。

不足している要素 / なぜそれが問題か

  • EBS / RDS / FSx スナップショット削除防止 SCP がない
  • KMS キー削除・無効化防止 SCP がない
  • CloudTrail 停止・削除防止 SCP がない
  • Organizations 離脱防止 SCP がない

想定されるリスクシナリオ

攻撃者が業務アカウントの管理者権限を奪取 → スナップショット削除、KMS キー削除、CloudTrail 停止を順次実行 → 復旧基盤と監査証跡の両方を喪失

9
バックアップ運用の監視
NG

現状の整理

バックアップジョブの成功 / 失敗の監視、組織横断の可視化、Backup Audit Manager によるレポート出力 のいずれも未実施。200 アカウントのバックアップ状況を集中的に把握する仕組みがない状態。

判定の根拠

200 アカウント規模の運用において、各アカウントに個別ログインしてジョブ状況を確認するのは現実的ではなく、組織横断の可視化は事実上必須。バックアップ失敗の検知が遅れることで「復旧不能が有事に判明する」最悪のシナリオが現実化しうる構成。

不足している要素 / なぜそれが問題か

  • クロスアカウントモニタリングが未利用 (Organizations 配下のジョブを Backup アカウントから一元確認できない)
  • Backup Audit Manager のレポートプランが未設定 (継続的な監査証跡が自動化されていない)
  • バックアップ失敗時のアラート通知が組み込まれていない

想定されるリスクシナリオ

特定アカウントでバックアップジョブが数週間失敗継続 → 組織として誰も気づかない → ランサムウェア被災時にそのシステムだけ復旧データが古い、または存在しないことが発覚
