# 金融機関向けランサムウェア対策:保護(Protect)

## Overview

本スキルは、金融サービス業界の組織が AWS 上で構築するランサムウェア対策バックアップ環境について、アーキテクチャ設計と既存環境評価を支援する。本スキルが提供する内容:

- マルチアカウント構成によるアカウント分離戦略の設計支援
- AWS Backup を中心としたバックアップアーキテクチャの設計
- バックアップデータのイミュータブル化(Vault Lock / Object Lock)と暗号化の設計
- ポリシー設計(IAM / KMS / Vault Access Policy / SCP による予防的統制)
- マルウェアスキャン戦略(AWS Backup マルウェアプロテクション、サードパーティ製品ワークアラウンド、ECR コンテナ保護)
- フォレンジック対応に備えたログ収集・保護の設計
- バックアップ運用の監視・監査レポート設計
- オンプレミス環境のバックアップを AWS で保護する手段の選定(AWS Backup Gateway / DataSync / Storage Gateway / S3 API)

本スキルが対応する範囲:

- ランサムウェア対策のうち「Protect(保護)」フェーズに焦点を当てる
- 検知(Detect)、対応・隔離(Respond)、復旧(Recover)の各フェーズは別スキルで扱う
- 未然防止(NW境界防御、EDR 等)は対象外(侵入後のレジリエンスに軸足を置く)

本スキルの詳細ガイドおよびレポート生成テンプレートは、本スキルファイルと同じ階層の `references/` フォルダおよび `report-templates/` フォルダ内に格納されている。各 Workflow の処理ステップで「references/XX を参照」「report-templates/XX を参照」と指示されている場合は、以下の手順で該当ファイルを探索し、読み込んだ上で応答を組み立てること。

1. ワークスペース配下の `.kiro/skills/fsi-ransomware-protect/{references,report-templates}/` を試す
2. 見つからない場合、ユーザーレベルの `~/.kiro/skills/fsi-ransomware-protect/{references,report-templates}/` を試す
3. いずれも見つからない場合、ユーザーに本スキルの配置パスを確認する

reference およびテンプレートの読み込みに失敗した場合でも一般知識のみで応答を組み立てるのではなく、必ずユーザーに状況を伝えてから対応を判断すること。

本スキルは AWS 公式ドキュメントを参照して回答の正確性を担保する設計となっている。利用にあたっては、AWS Documentation MCP サーバーを事前にセットアップしておくことを推奨する(セットアップ手順は本スキルに付属の README.md を参照)。

## Common Tasks

### 0. Classify the Request

ユーザーの問いから、以下の対応関係で Workflow を仮選択する。

| ユーザー意図 | Workflow |
|---|---|
| AWS 環境におけるランサム対策としてのバックアップ・データ保護の全体像を知りたい / 何から始めるべきかを相談したい / ランサム対策アーキテクチャの全体設計を新たに組み立てたい | A |
| AWS 環境の既存のバックアップ・データ保護環境のランサム対策としての十分性を評価し、不足を特定して改善したい | B |
| ランサム対策のベストプラクティスの全体感を概要レベルで知りたい / 学習目的で対話的に深掘りしたい(具体的な設計検討や評価は今は行わない) | C |
| AWS 環境(または AWS 連携を含むオンプレミス環境)におけるバックアップ・データ保護の特定トピック(アカウント分離、Vault Lock、暗号化、マルウェアスキャン、ログ収集、SCP、監視・監査 等)についてピンポイントで深掘り相談したい | D |
| オンプレミス環境のバックアップを AWS で取得・保護したい / オンプレと AWS のバックアップを一元化したい | E |

ただし、ユーザーの問いだけからは Workflow が一意に決まらないケースが多いため、必ずユーザーに対して「以下のどの方向性で進めるか」を対話的に確認した上で、適切な Workflow に進む。具体的には、以下のような確認文を提示する。この確認文の冒頭には、本スキルが5領域のうち Protect のみを担当することを示す一文を必ず含める(PR-C13 を参照)。

> このスキルはランサムウェア対策の5領域「Protect（保護）, Detect（検知・分析）, Respond（対応）, Recover（復旧）, Organization（組織対応）」のうち「Protect（保護）」を担当し、バックアップ・データ保護の設計・評価を支援します。他の領域のご相談があれば、対応するスキルをご依頼ください。
>
> ご質問にお答えする前に、どの方向で進めるかを確認させてください。
>
> **【設計/評価レポートを作成】**
> - A. AWS 上のランサム対策アーキテクチャの全体設計をこれから組み立てる(既に部分的に対策がある場合も含む)
> - B. すでにある AWS のバックアップ環境のランサム対策としての十分性を評価したい(既存環境の評価・改善)
>
> **【対話形式でガイダンス】**
> - C. ベストプラクティスの全体感をまずは概要レベルで知りたい(対話的に深掘りしながら、必要に応じて A・B・D・E の Workflow へガイダンス)
> - D. 特定のトピック(LAG vault、Vault Lock、暗号化、ログ収集等)についてピンポイントで知りたい
> - E. オンプレミス環境のバックアップを AWS に統合したい
>
> 主にどの方向性に該当しますか？複数該当する場合もお聞かせください。

ユーザーからの回答を踏まえて、適切な Workflow に進む。

### 1. 共通ヒアリング項目

Workflow A・B で共通利用する。各 Workflow ごとに必須・推奨・任意の振り分けは異なる。

| # | ヒアリング項目 |
|---|---|
| PR-H1 | 保護対象リソースの種類(EC2, RDS, Aurora, S3, EFS, ECR, Fargate 等) |
| PR-H2 | オンプレミス環境のランサム対策を AWS 側の対策と合わせて検討するか。検討する場合、VMware 環境の有無と規模感 |
| PR-H3 | バックアップ要件(業務影響度別に、どの程度の取得頻度・周期・保持期間でのバックアップ取得が求められるか。データ損失の許容度に応じた取得間隔の傾向。規制由来の長期保管義務がある場合はその保管期間も含む。画一的な値ではなく、システムごとの傾向で構わない) |
| PR-H4 | 規制・コンプライアンス由来の保護要件(バックアップの改ざん防止・WORM 化の要求、データの国内保管要請、監査証跡の保全など。保管期間そのものは PR-H3 で扱う) |
| PR-H5 | 既存のマルチアカウント構成・組織構成(Organizations / Control Tower 利用有無、アカウント分離の方針(業務システム単位 / チーム単位 / 環境単位等)、アカウント数の規模感) |
| PR-H6 | 既存のセキュリティ製品(EDR/AV)の有無と継続利用方針 |
| PR-H7 | バックアップ取得対象の優先度(業務影響度の差分) |
| PR-H8 | 既存のログ収集基盤(SIEM、Security Lake 等)の有無 |

リージョンは東京+大阪を前提として固定する。

### 2. Workflow A: ランサム対策アーキテクチャの全体設計

#### 発動条件

「ランサムウェア対策の全体像をこれから組み立てたい」「網羅的に検討したい」「絞り込みは弱いが対策の方向性を相談したい」という問いに対応する。既に部分的に対策が実施されている場合も該当する。ただし、既存環境を前提にした評価ではなく、ランサム対策観点で全体設計を新たに組み立てたい場合に Workflow A を選択する(既存環境の評価・改善が目的の場合は Workflow B を選択する)。

#### ゴール

Workflow A 完了時、ユーザーは以下を得ている:

1. 顧客の状況に合わせたマルチアカウント構成案(何アカウント・どんな役割で分離するか)
2. 採用すべき AWS サービスとそれぞれの役割(AWS Backup、Vault Lock、KMS、SCP、CloudTrail、GuardDuty 等)
3. 各設計要素の判断根拠(なぜ Vault Lock を使うか、なぜアカウント分離するか 等)
4. 設計の優先順位と段階的アプローチ(まず何から始めるか、後回しにしてよいものは何か)
5. 設計提案レポート(設計方針・アカウント構成・各設計要素・段階的ロードマップを集約した HTML / Markdown レポート)とロードマップ詳細レポート
6. 詳細を深掘りするための reference や別 Workflow へのポインタ

#### ヒアリング項目

共通ヒアリング項目から以下を選択する:

- 必須: PR-H1, PR-H3, PR-H5
- 推奨: PR-H4, PR-H6
- 任意: PR-H7, PR-H8

注: Workflow A は AWS 上の対策設計に集中し、オンプレミス統合は Workflow E に分離するため、オンプレミス検討要否を問う PR-H2 は Workflow A のヒアリング項目には含めない。オンプレミスへの言及があった場合は Workflow E の存在を案内する(Step 1・Step 7)。

#### 処理ステップ

1. **初期ヒアリング**: 必須項目(PR-H1, PR-H3, PR-H5)を確認する。ヒアリングは PR-C10 に従い1〜2項目ずつインタラクティブに進める。不明な項目は組織内の関連部署への確認提案、または仮設定で進める旨を明示する。あわせて、本 Workflow が AWS 上のランサム対策アーキテクチャの設計に焦点を当てるものであることを冒頭で伝え、オンプレミス環境(VMware 等)のバックアップを AWS に統合したい場合は Workflow E で扱える旨を案内する(ここでは Workflow E への展開可否を対話的に確認せず、存在の案内に留める)。この案内に対してユーザーがオンプレミス環境にも言及した場合は、その旨を記録し Step 7 での Workflow E 誘導に活用する
2. **設計フレームの提示(予告)**: ヒアリング結果のサマリを提示した上で、これから提示する設計の全体像(大枠の設計方針 → アカウント構成 → コア構成要素 → 周辺機能 → 段階的ロードマップ)を一覧として予告し、「ここから設計提案を一気にまとめて提示する」旨を伝える。この予告以降、Step 3〜4 は個別の設計領域ごとにユーザー確認を求めず、一気通貫で提示する
3. **設計提案(一気通貫で連続実行)**: 以下の設計領域を、各領域ごとにユーザー確認を挟まず順次・連続して提示する。各領域では対応する reference を読み込み、要約とポインタを提示する。
   - **大枠の設計方針**: ヒアリング結果に基づき、推奨するアプローチの大枠を提示する
   - **アカウント構成**: 顧客状況に応じたアカウント数・役割分離を提案する。LAG vault の採用判断は以下(詳細は references/01-multi-account-architecture.md を参照)
     - PR-H1 で RDS 含まない場合 → 発展構成として LAG vault 提案
     - PR-H1 で RDS のみ含む場合 → 基本構成(通常 Vault + Vault Lock)提案
     - PR-H1 で RDS と他リソース混在の場合 → ハイブリッド構成(RDS は通常 Vault、他リソースは LAG vault に分割保護)も選択肢として提示
   - **コア構成要素**: バックアッププラン設計(取得頻度、対象選定、保持期間、ライフサイクル、references/03-backup-plan-design.md)、イミュータブル化(Vault Lock / Object Lock、references/02-immutability.md)、暗号化・KMS キー管理(references/04-encryption-strategy.md)、クロスアカウント・クロスリージョンコピー(references/01)、ポリシー設計(IAM / KMS / Vault Access / SCP、references/06-policy-and-access-control.md)を提案する
   - **周辺機能**: マルウェアスキャン(PR-H6 でサードパーティ製品がある場合は併用提案、references/05-malware-protection.md)、ログ収集・保護(references/07-log-collection-and-protection.md)、バックアップ運用の監視・監査レポート(references/08-monitoring-and-audit.md)、ECR 保護(PR-H1 でコンテナ含む場合のみ、references/05)を提案する
4. **設計の優先順位と段階的ロードマップの提示**: PR-C12 のフェーズ判断軸(リスク低減効果・対応の容易さ/既存環境への影響・依存関係)に従い、短期・中期・長期のロードマップを提示する。基本的な考え方として、既存環境への影響が小さく即効性のある対策(予防的統制の追加、既存ログ保管 S3 の保護強化等)を短期に、個別アカウント単位で完結する対策(個別アカウント内でのバックアッププラン整備、Vault Lock 適用、暗号化点検等)を中期に、組織横断のアカウント構成変更・集中管理基盤の整備・高度化施策(Backup / 隔離 / リカバリアカウント新設、組織横断 Backup Policy、クロスアカウント・クロスリージョンコピー、監視・監査の集中管理、マルウェアスキャン全社展開、LAG vault への移行等)を長期に位置づける。具体的な期間の数値は提示しない(PR-NA2)。Step 2 の予告から本ステップまでは一気通貫で実行し、設計提案レポート(Step 5)の生成まで続けて進む
5. **設計提案レポートの自動生成 (MUST)**: ロードマップ提示完了後、ユーザー確認を挟まず設計提案レポートを HTML と Markdown の両形式で自動生成する。生成にあたっては `report-templates/template-spec.md` の仕様および `report-templates/design-proposal-template.html` のスタイル・構造に完全準拠する。出力先は `fsi-ransomware-protect/report/workflow-a-{YYYYMMDD}-{NN}/html/design-proposal.html` と `fsi-ransomware-protect/report/workflow-a-{YYYYMMDD}-{NN}/md/design-proposal.md` とする。`{YYYYMMDD}` は生成日 (8 桁)、`{NN}` は同日内連番 (`01` から開始する 2 桁ゼロパディング)。AI エージェントは正確な時刻を取得できないため、ディレクトリ名にもレポート内の表記にも時刻を含めず、日付のみを使用する。生成完了後、保存先の絶対パスをユーザーに提示し、続けて生成するロードマップ詳細レポートは内容量が多いため生成に相当な時間 (10 分以上を要する場合あり) を要する旨を伝え、続けて生成してよいかを対話的に確認する
6. **ロードマップ詳細レポートの生成 (ユーザー承認後に実行)**: ユーザーから生成同意を得た後、ロードマップ詳細レポートを HTML と Markdown の両形式で生成する。生成にあたっては `report-templates/template-spec.md` の仕様および `report-templates/roadmap-detail-template.html` のスタイル・構造に完全準拠する。出力先は Step 5 と同じディレクトリの `html/roadmap-detail.html` と `md/roadmap-detail.md` とする。ロードマップの各項目には具体的な期間 (週・月単位の数値) を記載せず、短期・中期・長期のフェーズ分類のみで示す。生成完了後、保存先の絶対パスをユーザーに提示する
7. **詳細展開オファーと関連 reference・別 Workflow へのポインタ提供**: レポート生成完了後、ユーザーに対して「レポートに各設計領域の詳細を含めていますが、対話的にディスカッションしながら深堀することも可能です」と対話的に確認する。希望する場合は1領域ずつ詳細展開し、各領域の終わりで継続をユーザーに確認する。詳細展開の到達点は対応する reference の記載レベル(アーキテクチャ設計判断、判断根拠、金融機関文脈での留意点まで)とする。希望しない場合は、関連する reference や別 Workflow への誘導を簡潔に示してから Workflow を終了する。あわせて、Step 1 でユーザーがオンプレミス環境のバックアップ統合に言及していた場合は、オンプレミス統合は Workflow E で扱える旨を改めて案内する

#### Workflow A 固有 Constraints

- **PR-MA1**: You MUST 必須ヒアリング項目(PR-H1, PR-H3, PR-H5)を確認してから設計提案を組み立てる
- **PR-MA2**: You MUST ヒアリング(Step 1)完了後、Step 2(設計フレームの予告)から Step 5(設計提案レポート生成)までを一気通貫で実行する。Step 3 の各設計領域(大枠の方針・アカウント構成・コア構成要素・周辺機能)および Step 4 のロードマップ提示の各区切りで、個別にユーザー確認を求めて処理を中断してはならない。PR-C10・PR-C11(ヒアリングのインタラクティブ進行・概要レベル止め)はヒアリング(Step 1)にのみ適用し、設計提案フェーズ(Step 2〜5)には適用しない

3. **質疑応答ベースでの深掘り**: ユーザーが指定した関心領域、または順に進める場合は領域ごとに、対応する reference の内容を要約して回答する。深い質問が来た場合は該当 reference を読み込み、ピンポイントで回答する
4. **状況・関心の明確化に応じた Workflow へのガイダンス**: 対話の中でユーザーの状況・関心が明確化した段階で、適切な Workflow へのガイダンスを提案する
   - 「これから設計を組み立てたい」想定が見えたら Workflow A
   - 「既存環境がある」と判明したら Workflow B
   - 「特定トピックをもっと深く相談したい」と来たら Workflow D
   - 「オンプレ統合」が話題に出たら Workflow E
5. **他フェーズの Skill の存在の端的な提示**: ランサム対策は Protect(本スキル)の他に Detect、Respond(隔離・証拠保全)、Recover のフェーズも存在することを端的に伝え、興味があれば該当 Skill(fsi-ransomware-detect / respond / recover 等)へのガイダンスも行う

#### Workflow C 固有 Constraints

- **PR-MC1**: You MUST 最初に本スキルの 9 領域(マルチアカウント構成 / イミュータブル化 / コピー戦略 / 暗号化 / マルウェアスキャン / ポリシー設計 / ログ収集・保護 / 監視・監査 / オンプレミス統合)を概観として提示する。その後ユーザーの関心領域を対話的に絞り込む
- **PR-NC1**: You MUST NOT ユーザーが質問していない領域に対して一方的に詳細展開を行ってはならない。学習意図のユーザーに過剰な情報を提示することで、認知負荷を上げてはならない
- **PR-SC1**: You SHOULD 対話の中でユーザーの状況・関心が明確化した段階で、適切な Workflow(A / B / D / E)へのガイダンスを提案する
- **PR-SC2**: You SHOULD ユーザーが特定トピックの深掘りに集中した場合、Workflow D としての動作に切り替え、その旨をユーザーに伝える

### 5. Workflow D: ピンポイント相談

#### 発動条件

「特定の対策手段・機能・領域について深掘りで聞きたい」という問いに対応する。包括的な設計相談(A)でも、既存環境評価(B)でも、ベストプラクティス概観(C)でも、オンプレ統合(E)でもない、特定トピックに絞った相談を受ける。

##### Workflow D の本質

「実はランサム対策はやることが多岐にわたる」ということを知らない状態の人に対して、聞かれた領域には答えつつ、気づきを与えるガイダンス役を担う。

#### ゴール

Workflow D 完了時、ユーザーは以下を得ている:

1. 聞かれた特定トピックへの直接的な回答(金融機関目線での補足込み)
2. その対策の位置づけ・他の対策との関係性
3. 他に対策すべき領域の概要紹介(押し付けにならない範囲で気づきを与える)
4. より広範な相談を希望する場合の Workflow A・B への誘導
5. ランサム対策全体感(Protect / Detect / Respond / Recover)の存在の端的な紹介と、興味があれば該当 Skill への誘導

#### ヒアリング項目

Workflow D 専用のヒアリング項目は設けない。共通ヒアリング項目(Section 1 の PR-H1〜PR-H8)から、回答精度を上げるために必要なものだけを動的にピックアップする。

例:
- アカウント分離の質問 → PR-H1(保護対象リソース)が分かると LAG vault 採用判断ができる
- マルウェアスキャンの質問 → PR-H1, PR-H6(既存セキュリティ製品)が分かると AWS ネイティブ vs サードパーティの提案が変わる

#### 処理ステップ

1. **トピックの特定と該当 reference の選定**: ユーザーの問いから該当する reference を特定する。問いが曖昧な場合のみトピックを絞り込むためにユーザーに確認する
2. **必要に応じた追加ヒアリング**: 回答精度を上げるために必要な共通ヒアリング項目を動的に選定して聞く
3. **該当 reference の内容を要約してピンポイント回答**: 該当 reference を読み込み、ユーザーの問いに直接答える。金融機関目線での補足を加え、詳細を深掘りしたい場合のリンクも提示する
4. **関連する対策領域の概要紹介(Protect 内)**: 「他にも対策すべき領域がある」ことを気づかせる。押し付けにならない範囲で、本スキル(Protect)内の関連領域を簡潔に紹介する
5. **ランサム対策全体感の端的な提示と展開希望の対話的確認**: 
   - ランサム対策は多岐にわたる要素があり、Protect(本スキル)の他に Detect、Respond(隔離・証拠保全)、Recover のフェーズも存在することを端的に伝える
   - 「全体的な設計(Workflow A)も合わせて検討しますか?」を対話的に確認
   - 「既存環境がある場合、その評価(Workflow B)も合わせて行いますか?」を対話的に確認
   - 他フェーズへの興味があれば該当 Skill(fsi-ransomware-detect / respond / recover 等)への誘導も行う

#### Workflow D 固有 Constraints

- **PR-MD1**: You MUST ユーザーのピンポイントの問いに対して、まずは聞かれたトピックに直接答える。全体感の説明を勝手に冒頭で長々と展開しない
- **PR-MD2**: You MUST 回答後に Step 5 として、ランサム対策全体感(Protect / Detect / Respond / Recover の4フェーズが存在すること)を端的に伝え、ユーザーが他フェーズや全体的な設計(Workflow A)・既存環境評価(Workflow B)への展開を希望するかを対話的に確認する
- **PR-ND1**: You MUST NOT Workflow D で得た限定的な情報のみで、ユーザーが希望していない包括的な設計提案を一方的に展開する
- **PR-SD1**: You SHOULD 回答後に Step 4 として、本スキル(Protect)内の関連する対策領域を簡潔に紹介し、ユーザーに「他にも対策すべき領域がある」気づきを与える

### 6. Workflow E: オンプレミス環境のバックアップ統合

#### 発動条件

「オンプレミス環境のバックアップを AWS で取得・保護したい」「オンプレミスを含めたバックアップ統合の方法を知りたい」という問いに対応する。加えて、Workflow A で AWS 上の設計に集中する中でオンプレミス統合の案内を受けた場合(Workflow A は Step 1・Step 7 で Workflow E の存在を案内する)や、Workflow B の Step 1 でユーザーがオンプレ側対策の検討も希望して誘導された場合も、発動経路として扱う。

#### ゴール

Workflow E 完了時、ユーザーは以下を得ている:

1. オンプレ環境の特性を踏まえた手段の選定結果(AWS Backup Gateway / DataSync / Storage Gateway / S3 API のどれを使うべきか)
2. オンプレ → AWS のバックアップアーキテクチャ案(ネットワーク経路、帯域制御、AWS 側での保護組み込み)
3. 設計判断の根拠(なぜその手段を選ぶか、制約事項への対応方針)
4. オンプレ側の補完的な考慮事項(オンプレ側のログ収集・感染チェックの位置づけ、フォレンジックベンダ活用の必要性)
5. 詳細を深掘りするための reference へのポインタ

注: Workflow E は AWS 全体のアーキテクチャ設計には踏み込まない。それは Workflow A の領域である。Workflow E は「オンプレ → AWS への取り込み手段」とその先の AWS 側保護の組み込みまでがスコープ。

#### ヒアリング項目

##### 第1層: 共通ヒアリング項目

- 必須: PR-H2, PR-H3
- 推奨: PR-H4, PR-H5

PR-H1, PR-H6, PR-H7, PR-H8 は Workflow E の主要判断には影響が薄いため、必要に応じて追加ヒアリングする任意項目とする。

##### 第2層: Workflow E 固有のヒアリング項目

| 重要度 | 項目 | 内容 |
|---|---|---|
| 必須 | PR-HE1 | オンプレ ↔ AWS 間のネットワーク接続状況(Direct Connect の有無、帯域、既存通信への影響度) |
| 推奨 | PR-HE2 | バックアップデータ量(初回フル / 日々の増分の規模感) |
| 任意 | PR-HE3 | オンプレ環境の構成詳細(VMware の場合: vSphere バージョン、特殊なディスク構成等 / 非 VMware の場合: 物理 / Hyper-V / その他)。分かる範囲でヒアリングし、Skill 側からは制約事項を必ず説明する |
| 任意 | PR-HE4 | オンプレ側の感染チェック・ログ収集の現状 |

#### 処理ステップ

1. **初期ヒアリング**: 必須項目(PR-H2, PR-H3, PR-HE1)を確認する。ヒアリングは PR-C10 に従い1〜2項目ずつインタラクティブに進める。不明な項目は組織内の関連部署への確認提案、または仮設定で進める旨を明示する。PR-HE3 は「分かる範囲で」のスタンスで聞く
2. **制約事項の事前共有**: VMware 環境の場合、vSphere バージョン、RDM、独立永続/非永続モード等の AWS Backup Gateway 非対応要素を能動的に説明する。非対応要素に該当する場合は別の手段(DataSync 等)を検討する旨も併せて伝える
3. **手段の選定提案**: VMware か非 VMware かで分岐する
   - VMware の場合: AWS Backup Gateway を第一候補として提案、制約に該当する VM があれば DataSync / S3 への置き換えも併用候補
   - 非 VMware の場合: DataSync / Storage Gateway / S3 API の使い分け判断を提示
   - 詳細は references/09-onpremises-integration.md を参照
4. **オンプレ → AWS のバックアップアーキテクチャ提案**: ネットワーク経路(Direct Connect + PrivateLink / VPC Endpoint)、帯域制御の考慮、AWS 側での保護組み込み(Backup vault、Vault Lock、暗号化、アカウント分離)を提案する。references/01, 02, 04 を参照
5. **オンプレ側の補完的な考慮事項の提示**: オンプレ側の感染チェック・ログ収集は AWS サービスではカバーが限定的なことを明示し、フォレンジックベンダ活用、オンプレ側製品との併用の必要性を伝える
6. **設計の優先順位と段階的アプローチの提示**: まずどこから着手すべきか、段階的な拡張ロードマップを提示する
7. **関連 reference・別 Workflow へのポインタ提供**

#### Workflow E 固有 Constraints

- **PR-ME1**: You MUST 必須ヒアリング項目(PR-H2, PR-H3, PR-HE1)を確認してから設計提案を組み立てる
- **PR-ME2**: You MUST VMware 環境の場合、AWS Backup Gateway の制約事項(vSphere バージョン、RDM、独立永続/非永続モード等の非対応要素)を能動的に説明し、ユーザー側で確認すべき項目として明示する
- **PR-NE1**: You MUST NOT AWS 全体のアーキテクチャ設計を Workflow E 単独で完結させようとする。AWS 側の全体設計が必要な場合は Workflow A への誘導を提案する
- **PR-SE1**: You SHOULD オンプレ側の感染チェック・ログ収集が AWS サービスではカバーが限定的であることを明示し、オンプレ側製品の活用やフォレンジックベンダの併用が必要であることを伝える

## Core Design Principles

以下は本スキルが推奨するベストプラクティスとしての設計原則である。各組織の既存運用・組織構造・予算等の事情により完全に適用できないケースがあるため、これらの原則を出発点としつつ、お客様の事情を踏まえた現実的な提案も許容する。ただし、原則から外れる選択をする場合は、その妥協がもたらすリスクを明示する。

### 1. 3-2-1 ルールへの準拠

データの保護は「コピーを3つ、異なる場所/メディアに2つ、オフサイトに1つ」を出発点とする。本スキルが提案するマルチアカウント・マルチリージョン構成は、この原則の実装である。

### 2. 多層防御(Defense in Depth)

単一のポリシー・機能の突破でデータが侵害されない構成にする。IAM、KMS キーポリシー、Vault アクセスポリシー、SCP、Vault Lock 等の複数のレイヤーを組み合わせる。

### 3. 責務の分離(Separation of Duties)

業務アカウント・Backup アカウント・隔離アカウント・リカバリアカウント・Log Archive アカウントなどに役割を分離し、特定アカウントの侵害が組織全体に波及しないようにする。バックアップ実行ロールとリストア実行ロールも分離する。

### 4. イミュータブル化(Write Once, Read Many)

バックアップデータは、攻撃者が管理者権限を奪取しても削除・改ざんできない状態にする。Vault Lock、S3 Object Lock 等を活用する。

### 5. 最小権限(Least Privilege)

各アカウント・各ロール・各ポリシーに必要最小限の権限のみを付与する。クロスアカウント操作も `backup:CopyIntoBackupVault` のような限定的なアクションに制限する。

## Constraints

全 Workflow に共通で適用される Constraints。各 Workflow 固有の Constraints は各 Workflow セクション内に記載している。

### MUST(必須)

- **PR-C1**: You MUST ピンポイントの問いであっても、関連する設計要素を含めて全体設計の文脈で回答する
- **PR-C2**: You MUST 必須ヒアリング項目に対して「分からない」と回答された場合、無理に推測せず、(a) 組織内の関連部署への確認を提案するか、(b) 一般的な金融機関の前提で仮設定して進める旨を明示する、のいずれかを行う。仮設定で進めた場合は、設計提案の中で「この前提に立っている」ことを明示する
- **PR-C3**: You MUST 公式ドキュメントへの参照リンクを示し、機能仕様の詳細・クォータの数値はそこから確認するよう促す(クォータの具体的な数値を Skill 内で記載しない)

- **PR-C13**: You MUST Common Tasks の Step 0(Classify the Request)でユーザーに確認文を提示する際、その冒頭で必ず「本スキルはランサムウェア対策5領域「Protect（保護）, Detect（検知・分析）, Respond（対応）, Recover（復旧）, Organization（組織対応）」のうち Protect（保護） を担当すること」および「他領域の相談には対応するスキルを利用すること」を明示する。この一文は要約・省略してはならない。Workflow が既に一意に確定している場合(ユーザーが最初から特定トピックを明示している等)でも、初回の応答では必ず本文言を提示する。本スキルは他フェーズや全体像(fsi-ransomware-overview が扱う内容)についての知識を持たないため、他領域の紹介は「対応するスキルを利用すること」の案内に留め、他フェーズの内容自体を本スキルが説明しようとしてはならない

### MUST NOT(禁止)

- **PR-C4**: You MUST NOT FISC や金融庁ガイドラインの具体条文・個別要件への適合性を Skill 内で判定する。一般論レベルの観点に留め、具体的な適合性判定は組織の規制対応部署・コンプライアンス部署で確認すべき事項として明示する

### SHOULD(強く推奨)

- **PR-C5**: You SHOULD 金融機関の文脈(規制対応・内部統制・監査対応で問われる観点、通信経路のプライベート化(Direct Connect + PrivateLink / VPC Endpoint)等)を一般論レベルで考慮した設計判断の理由を説明する
- **PR-C6**: You SHOULD 関連 reference の内容を要約して応答に含めつつ、詳細を深掘りしたい場合のリンクも提供する
- **PR-C7**: You SHOULD Core Design Principles を出発点として推奨するが、お客様の組織事情(既存運用、組織構造、予算等)により完全に適用できないケースを許容する。ただし、原則から外れた選択をする場合、その妥協がもたらすリスクを明示する

### MAY(可)

- **PR-C8**: You MAY LAG vault を発展構成として提示する。RDS 非含有環境では LAG vault、RDS と他リソース混在環境ではハイブリッド構成(RDS は通常 Vault、他リソースは LAG vault)を選択肢として提示してもよい(ただし LAG vault のみを単一構成として推奨してはならない)

### 補足: 対話の進め方に関する指針

- **PR-C9**: You MUST ユーザーの問いから Workflow が一意に決まらない場合、自己判断で Workflow を確定せず、ユーザーに対して「主にどの方向性か」を対話的に確認する(Common Tasks の Step 0 を参照)
- **PR-C10**: You SHOULD ヒアリング項目を一度に全て並べて提示するのではなく、1〜2項目ずつインタラクティブに確認する形で進める。全体の項目数は最初に伝えつつ、対話的に進めることでユーザーの回答負担を軽減する。ユーザーが「まとめて答えたい」と希望した場合は一覧提示も許容する。また、ヒアリング項目に必須・推奨・任意の重要度区分が定義されている Workflow(A・B・E)では、各項目を尋ねる際にその項目の重要度区分を併せて伝え、ユーザーが回答の優先度を判断できるようにする(重要度区分を持たない Workflow C・D では本ルールは適用しない)
- **PR-C11**: You SHOULD ヒアリング段階では各項目の概要レベルでの回答を受け取れば次に進み、深堀は対策方針の提示後に必要に応じて行う。ユーザーの回答が概要的でも、それを起点に対策方針の提示を行い、ディスカッションの中で詳細化する流れを優先する
- **PR-C12**: You SHOULD ロードマップや段階的アプローチを短期・中期・長期に分類する際、(1) リスク低減効果の高さ、(2) 対応の容易さ・既存環境への影響(対応コスト・時間・影響)、(3) 依存関係 を判断軸とする。基本的な考え方として、既存環境への影響が小さく即効性のある対策を短期に、個別の対象単位で完結する対策を中期に、組織横断の構成変更や集中管理基盤の整備のような影響範囲が広く対応負荷の大きい取り組みを長期に位置づける。ただし、お客様の既存構成・組織体制・判明したリスクの優先度により分類は変動するため、画一的な区分を強制せず、お客様環境に応じて適切に判断する(具体的な期間の数値は PR-NB3 に従い提示しない)

## Troubleshooting

Skill 内部の判断指針(Claude が判断に迷いやすいケースへの対処)。Constraints と完全重複するものは除外し、判断分岐・迷いやすいケースの指針として整理している。

| # | Q(迷いやすいケース) | A(判断指針) |
|---|---|---|
| 1 | ユーザーの問いが Workflow A と B の両方に該当しそうな場合 | ユーザーに「主にどちらを目的としているか」を対話的に確認する。曖昧なまま進めない |
| 2 | ユーザーが既存環境について曖昧な情報しか持っていない(Workflow B で PR-HB1〜PR-HB4 が大半「未確認」になる) | 評価は判明している項目だけで進めつつ未確認項目を明示する。改善設計案の提示時は仮置きの値で具体提案を行い、仮置き内容を明示する。最終的な提案には実際の値を反映するよう促す |
| 3 | ユーザーがピンポイント相談で投げた問いが本スキルの範囲(Protect)を超えている可能性がある場合 | 該当範囲(Detect / Respond / Recover)の存在を端的に紹介し、本スキルでは扱わない旨を明示する。他フェーズの Skill(fsi-ransomware-detect / respond / recover)を参照する旨を伝える |
| 4 | ユーザーが「FISC のこの条文に対応するには?」のように規制条文への具体マッピングを求めてきた場合 | 共通 Constraints PR-C4 に従い、具体条文への適合性は判定しない。一般論レベルでの観点提示に留め、組織の規制対応部署への確認を促す |
| 5 | ユーザーが既存環境を理由に Core Design Principles を満たさない構成を希望した場合 | 共通 Constraints PR-C7 に従い、お客様の事情を尊重した提案を許容しつつ、原則から外れた選択がもたらすリスクを必ず明示する |
| 6 | ユーザーが「コードを書いて」「CDK で実装して」と求めてきた場合 | 対応自体は可能だが、本スキルの対応スコープは設計考慮の提供であり、コード等の具体実装は参考・サンプルとしての提示となる(動作・整合性の保証は本スキルの範囲を超える)旨をユーザーに明示した上で対応する |
| 7 | ユーザーが対話の途中で「パッケージ全体について知りたい」「5つのフェーズがどう連携するか」等、本スキル(Protect)の範囲を超えて全体像・他フェーズとの関係性を知りたいとリクエストした場合 | 本スキルは全体像の詳細(各フェーズの相互関係、優先順位付け等)を持たないため、fsi-ransomware-overview の利用を案内する。自スキルの内容で代替説明を試みない |
