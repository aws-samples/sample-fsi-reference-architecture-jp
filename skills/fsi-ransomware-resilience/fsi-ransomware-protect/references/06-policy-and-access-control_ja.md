# ポリシー設計とアクセス制御（IAM・KMS・Vault Access・SCP）

## 概要

本リファレンスは、本スキルが採用するバックアップ・データ保護環境におけるポリシー設計とアクセス制御について示す。ランサムウェア対策の文脈では、攻撃者がアカウントの管理者権限を奪取した場合でも、バックアップデータの破壊・改ざん・不正復元を防ぐ多層的なアクセス制御が必要となる。本リファレンスでは、複数のポリシー機構を組み合わせた最小権限・多層防御の設計思想について整理する。

本リファレンスでは、6つのポリシー制御ポイント、クロスアカウントコピー成立のためのポリシー連携、SCP による予防的統制、LAG vault 採用時のポリシー設計考慮、金融機関の文脈での設計判断について整理する。

マルチアカウント構成における各ポリシーの配置は [01-multi-account-architecture.md](./01-multi-account-architecture.md)、KMS 暗号化戦略は [04-encryption-strategy.md](./04-encryption-strategy.md) を参照する。

## 基盤メカニズム: 多層防御によるアクセス制御

本スキルが採用するアクセス制御は、複数のポリシー機構を組み合わせた多層防御の設計思想に基づく。バックアップ・コピー・リストアの各操作に対して、以下のポリシー機構を適切に組み合わせることで、単一のポリシー突破では不正操作が成立しない構成を実現する。

| ポリシー機構 | 性質 | 主な役割 |
|---|---|---|
| **アイデンティティベースポリシー（IAM ポリシー）** | プリンシパル（ユーザー・ロール）に紐づく | 操作実行主体に対する権限付与 |
| **リソースベースポリシー（KMS キーポリシー、Vault アクセスポリシー）** | リソースに紐づく | リソース側からの利用許諾の制御 |
| **Service Control Policy（SCP）** | Organizations 配下の組織・OU・アカウントに紐づく | 予防的な権限上限の設定（Deny ベース） |

これらを組み合わせることで、操作主体・操作対象・組織レベルの3つの観点からアクセス制御が成立し、攻撃者が一部の権限を掌握した場合でも、別のレイヤーで操作を防御することが可能となる。

## 6つのポリシー制御ポイント

本スキルのマルチアカウント構成では、以下の6つのポリシー制御ポイントを組み合わせて設計する。

### 1. Organizations 委任ポリシー

- **対象**: Organizations 管理アカウントから Backup アカウントへの委任設定
- **統制内容**: 組織全体のバックアップポリシーの管理権限を Backup アカウントに委任することで、平時のバックアップ管理運用を Backup アカウントに集約する
- **必要な許可の概要**: バックアップポリシーの作成・更新・削除・OU やアカウントへのアタッチ・デタッチ・一覧取得・タグ管理等の権限を、委任先の Backup アカウントに対して付与する
- **最小権限の考え方**: 平時のバックアップ管理は Backup アカウントから実施する運用とし、Organizations 管理アカウントでは行わない運用統制を採用することで、両アカウントの責務を運用上分離する

### 2. バックアップ対象リソースの KMS キーポリシー（業務アカウント側）

- **対象**: 業務アカウント内の KMS CMK（バックアップ対象リソースを暗号化しているキー）
- **統制内容**: コピー先アカウントの AWS Backup がバックアップコピーを作成する際に必要となる、暗号化されたデータの復号権限を制御する
- **必要な許可の概要**: コピー先アカウントの AWS Backup ロールに対して `kms:Decrypt`、`kms:GenerateDataKey*` 等のコピー操作に必要な範囲の許可を付与する
- **最小権限の考え方**: 許可対象を AWS Backup ロールに限定し、操作内容もコピー成立に必要なものだけに絞り込むことで、業務アカウントの暗号化キーへの不要なアクセスを防ぐ

### 3. IAM ロール（バックアップ実行用、業務アカウント側）

- **対象**: 業務アカウント内の IAM Role（AWS Backup がバックアップ操作を実行する際に引き受けるロール）
- **統制内容**: 業務アカウントでバックアップを取得する際に、バックアップ対象リソースの読み取り、Backup vault への保存、暗号化キーの利用等の権限を制御する
- **必要な許可の概要**: バックアップ対象リソース（EC2、RDS、S3 等）のスナップショット作成権限、Backup vault への書き込み権限、暗号化キーの利用権限等を付与する
- **最小権限の考え方**: バックアップ実行ロールにはリストア権限を付与しないことを推奨する。バックアップ・リストアの責務分離により、特定ロールの侵害がリストア操作にまで波及することを防ぐ

### 4. IAM ロール（リストア実行用、リカバリアカウント側）

- **対象**: リカバリアカウント内の IAM Role（AWS Backup がリストア操作を実行する際に引き受けるロール）
- **統制内容**: リカバリアカウントでバックアップから新しいリソースを作成する際に、リソース作成・タグ付け・暗号化キーの利用等の権限を制御する
- **必要な許可の概要**: リストア対象リソースタイプの作成権限、リカバリアカウントの暗号化キーの利用権限、対象 Backup vault からの読み取り権限等を付与する
- **最小権限の考え方**: リストア実行ロールにはバックアップ取得権限を付与せず、リストア操作に限定する。バックアップ・リストアの責務分離を IAM ロールレベルで実現する

### 5. Vault のアクセスポリシー（リソースベースポリシー）

- **対象**: 隔離アカウント・リカバリアカウントの Backup vault（コピー先 vault）
- **統制内容**: Backup vault に対するクロスアカウントアクセスを制御するリソースベースポリシー。クロスアカウントコピーを成立させるために、コピー元アカウントからの `backup:CopyIntoBackupVault` アクションを許可する
- **必要な許可の概要**: コピー元アカウントの IAM ロール（または Organizations の組織単位）に対して `backup:CopyIntoBackupVault` を許可する
- **最小権限の考え方**: AWS Backup の仕様として、クロスアカウントで実行可能なアクションは `backup:CopyIntoBackupVault` のみに制限されており、Vault アクセスポリシーで他のアクションを許可しても拒否される。これにより、コピー先 vault への不正な操作（復旧ポイントの削除等）はクロスアカウントでは実行できない構造となっている

### 6. Vault の暗号化用 KMS キーポリシー（コピー先アカウント側）

- **対象**: 隔離アカウント・リカバリアカウントの KMS CMK（コピー先 vault の暗号化に利用するキー）
- **統制内容**: コピー先 vault でのバックアップ再暗号化に必要な、コピー元アカウントへの暗号化操作の許諾を制御する
- **必要な許可の概要**: コピー元アカウントの AWS Backup ロールに対して `kms:Encrypt`、`kms:GenerateDataKey*` 等のコピー時の暗号化に必要な範囲の許可を付与する
- **最小権限の考え方**: 許可対象をコピー元の AWS Backup ロールに限定し、操作内容もコピー時の暗号化に必要なものだけに絞り込む。各アカウントの KMS キーへのアクセスは IAM ポリシーを使用した制御を基本とする

## クロスアカウントコピー成立のためのポリシー連携

クロスアカウントコピーが成立するためには、上記の複数のポリシーが相互に連携している必要がある。それぞれが異なるレイヤーで正しく設定されていなければコピーは失敗する設計となっており、結果として多層防御として機能する。

| 必要なポリシー | レイヤー | 役割 |
|---|---|---|
| 業務アカウントの IAM ロール（バックアップ用） | プリンシパル側 | コピー操作を実行する権限 |
| 業務アカウント側 KMS キーポリシー | コピー元リソース側 | コピー元データの復号許諾 |
| 隔離・リカバリアカウントの Vault アクセスポリシー | コピー先 vault 側 | クロスアカウントからのコピー受け入れ許諾 |
| 隔離・リカバリアカウント側 KMS キーポリシー | コピー先リソース側 | コピー先データの再暗号化許諾 |

これら4つのレイヤーのいずれか1つが欠けてもコピーは成立しないため、攻撃者が一部のポリシーを侵害したとしてもクロスアカウントコピーの全体構成を破壊することは困難となる。

## SCP による予防的統制

Organizations の Service Control Policy（SCP）は、Organizations 配下の組織・OU・アカウントに対して権限上限を設定する仕組みであり、たとえアカウント内のルートユーザーや管理者権限を持つ IAM ロールであっても、SCP で Deny されたアクションは実行できない。本スキルでは、ランサムウェア対策の予防的統制として SCP を活用することを推奨する。

### ランサム対策の文脈で重要となる SCP 設計パターン

| 統制対象 | 主な意図 | 統制の例 |
|---|---|---|
| **Backup vault の削除・改ざん防止** | バックアップデータ自体の破壊を予防する | `backup:DeleteBackupVault`、`backup:DeleteRecoveryPoint` 等の破壊的操作を Deny |
| **KMS キーの削除・無効化防止** | 暗号化キーの削除によるバックアップデータの復号不能化を予防する | `kms:ScheduleKeyDeletion`、`kms:DisableKey` 等を Deny |
| **CloudTrail の停止・削除防止** | 攻撃者の活動ログ消去を予防する（フォレンジック対応の基盤確保） | `cloudtrail:StopLogging`、`cloudtrail:DeleteTrail`、`cloudtrail:UpdateTrail` 等を Deny |
| **Config の停止・削除防止** | 設定変更履歴の消去を予防する | `config:DeleteConfigurationRecorder`、`config:StopConfigurationRecorder` 等を Deny |
| **S3 バケットポリシー・Object Lock 設定の改変防止** | ログ保管 S3 バケットの改変を予防する | `s3:PutBucketPolicy`、`s3:PutBucketObjectLockConfiguration` 等を制限 |
| **組織からの離脱防止** | コピー先アカウントが組織を離脱することによるデータ持ち出しを予防する | `organizations:LeaveOrganization` を Deny |

## LAG vault 採用時のポリシー設計考慮

LAG vault（Logically air-gapped vault）を採用する場合、通常の Backup vault とは異なるポリシー設計が必要となる。

### RAM によるリソース共有

通常の Backup vault のクロスアカウントコピーは Vault アクセスポリシー（リソースベースポリシー）で制御されるが、LAG vault では AWS Resource Access Manager（RAM）を利用してリソース共有を行う。LAG vault を別アカウントから利用する場合は、RAM のリソース共有設定と RAM の権限設計が必要となる。

LAG vault 採用時には、本リファレンスで述べた6つのポリシー制御ポイントに加えて、RAM のリソース共有設定の権限制御も併せて設計することを推奨する。

### Multi-party approval によるリストアの承認統制

LAG vault には Multi-party approval 機能があり、リストア時に複数人の承認を要求することが可能となる。これは IAM ポリシーや SCP では実現が難しい「単独の攻撃者が権限を得てもリストアを実行できない」という承認ベースの統制を提供する。

ランサム対策の文脈では、攻撃者がリストア権限を奪取した場合でも、Multi-party approval により独断でのリストアを防ぐことが可能となる。LAG vault の特性については [01-multi-account-architecture.md](./01-multi-account-architecture.md) を、暗号化の管理主体については [04-encryption-strategy.md](./04-encryption-strategy.md) を参照する。

## 金融機関の文脈での設計判断

### 責務分離の徹底

金融機関では、操作権限の分離（Segregation of Duties）が組織内ルール・監査要件として求められるケースが多い。本スキルの推奨設計では、以下の責務分離を IAM ロールレベルで実現することを推奨する。

- バックアップ実行ロール（業務アカウント）とリストア実行ロール（リカバリアカウント）の分離
- Organizations 管理アカウントの管理者と Backup アカウントの管理者の分離
- KMS キーの管理者・利用者の分離（キー管理ロール、バックアップロール、リストアロールを別の IAM ロールとして設計）

### 監査要件への対応

ポリシー設計の結果として、操作ログの取得・保管が監査要件を満たす形であることを確認することを推奨する。

- 各 IAM ロール・KMS CMK・Vault に対する操作は AWS CloudTrail で記録される
- SCP による Deny の発生も CloudTrail で記録されるため、攻撃の予兆検知や事後分析に活用が可能
- ログ収集・保護の詳細は [07-log-collection-and-protection.md](./07-log-collection-and-protection.md) を参照する

### 例外運用の整理

SCP やポリシーで強い統制を適用する場合、緊急時・運用変更時に必要な例外手順を事前に整理することを推奨する。例外運用がないと、有事の対応や運用変更時に統制が運用の足かせとなるリスクがあるため、組織のセキュリティ部門・運用部門と合意形成を行うことが望ましい。

## 対策効果のサマリ表

本リファレンスで扱う各設計要素が、ランサムウェア対策としてどのリスクに有効かを整理する。

| 設計要素 | 防御するリスク | 有効なシナリオ |
|---|---|---|
| Organizations 委任ポリシーによる管理権限の分離 | Organizations 管理アカウント単独の侵害による組織全体の構成変更 | Organizations 管理アカウントが侵害された場合 |
| KMS キーポリシーによる利用主体の限定 | 暗号化キーへの不要なアクセス | 攻撃者が一部の IAM ロールを掌握した場合 |
| バックアップ実行ロールとリストア実行ロールの分離 | バックアップ・リストア権限の同時侵害 | 特定ロールが侵害された場合の被害範囲限定 |
| Vault アクセスポリシーによるクロスアカウントアクションの制限 | コピー先 vault への不正な削除・改ざん | クロスアカウントコピーは `backup:CopyIntoBackupVault` のみに制限 |
| SCP による Vault・KMS キー削除の予防的 Deny | アカウント管理者権限を奪取した攻撃者によるバックアップ破壊 | 攻撃者が業務アカウントの管理者権限を奪取した場合 |
| SCP による CloudTrail・Config の停止防止 | 攻撃者の活動ログ消去 | 攻撃者がログ操作権限を得た場合 |
| SCP による組織離脱の防止 | コピー先アカウントが組織を離脱することによるデータ持ち出し | 内部不正・アカウント侵害 |
| LAG vault の Multi-party approval | 単独の攻撃者による不正復元 | 攻撃者がリストア権限を得た場合の追加防御 |
