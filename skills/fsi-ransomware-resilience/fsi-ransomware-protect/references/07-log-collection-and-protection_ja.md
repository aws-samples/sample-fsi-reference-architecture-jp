# ログの収集と保護

## 概要

本リファレンスは、本スキルが採用するランサムウェア対策におけるログの収集と保護について示す。ランサムウェア攻撃を受けた際、侵入経路の特定、被害範囲の把握、復旧範囲の確定、原因究明等の分析を行うためには、平時からの体系的なログ収集が不可欠となる。攻撃発生後にログを取り始めても遅く、感染前後の状況を把握するためには、攻撃が起きる前から継続的に取得・保護しておくことが前提となる。

加えて、収集したログそのものも攻撃者の改変・削除の対象となるため、ログ自体に対する保護も併せて設計する必要がある。本リファレンスでは、収集すべきログのカテゴリと AWS 環境における具体的な対象、ログ自体の保護、攻撃によるログ停止・削除への対策、フォレンジック分析の専門性と外部ベンダ活用、オプショナルな統合サービスの活用について整理する。

ログ保管 S3 バケットへの Object Lock 適用は [02-immutability.md](./02-immutability.md)、SCP による予防的統制は [06-policy-and-access-control.md](./06-policy-and-access-control.md) を参照する。

## 基盤メカニズム: 平時からのログ収集と保護

### ログ収集と保護の2軸

ランサムウェア対策の文脈では、ログを「収集する」だけでは不十分であり、収集したログを「保護する」ことも併せて設計する必要がある。攻撃者は分析証跡を消すためにログ取得自体を停止・削除する、保管されたログを改変・削除するといった行動を取ることが想定されるため、以下の2軸で設計を進めることを推奨する。

| 軸 | 内容 |
|---|---|
| **収集** | 何のログを、どの粒度で、どこから取得するかの設計 |
| **保護** | 取得したログをどう保管し、改変・削除・取得停止から守るかの設計 |

## 収集すべきログのカテゴリ

ログ収集はすべてを網羅的に取得するアプローチではなく、組織のシステム・ワークロードの利用サービスや特性に応じて、有事の分析に必要となるログを取捨選択することを推奨する。網羅性とコスト・運用負荷のバランスを考慮した設計が重要となる。

その前提のもとで、ランサムウェア攻撃後の分析に備えて検討対象となる主なログのカテゴリを以下に整理する。

| カテゴリ | 内容 | 主な活用シナリオ |
|---|---|---|
| ネットワーク／通信ログ | 通信元・通信先・ポート・プロトコル・通信量等 | 横展開（lateral movement）や C2 通信の検知、外部への持ち出し検知 |
| OS ログ | OS レベルのイベント、プロセス起動、ファイルシステムの操作等 | 侵入後の活動追跡、感染経路の特定 |
| 認証／アクセス制御ログ | ログイン履歴、権限昇格、IAM 操作等 | 侵入経路や攻撃者の活動範囲の特定 |
| アプリケーションログ | アプリケーション固有のイベント、エラー、業務操作の履歴 | 業務影響範囲の特定、攻撃の業務システムへの波及確認 |
| ストレージ操作ログ | ファイル・オブジェクトの作成・更新・削除・閲覧等 | 被害範囲の特定、データ持ち出しの検知 |
| DB 操作ログ | DB クエリ、データ変更、認証履歴 | DB レイヤーの被害範囲の特定 |
| セキュリティツールのログ | EDR、AV、IDS/IPS、WAF 等の検知・遮断履歴 | 検知された攻撃の追跡、未検知攻撃の手掛かり |
| 外部サービスの操作ログ | SaaS、外部 API、サードパーティ連携の操作履歴 | 組織外サービスを経由した攻撃の追跡 |

## AWS 環境における具体的なログ対象

AWS 環境で収集対象の候補となる主なログを、レイヤー別に整理する。前述の通り、これらすべての取得を推奨するものではなく、組織のワークロード構成と分析要件に応じて取捨選択することを推奨する。

### コントロールプレーン・基盤レベル

| ログ | 主な役割 |
|---|---|
| AWS CloudTrail ログ | API 呼び出し履歴。AWS 操作の証跡として最重要 |
| AWS Config レコーダーログ | AWS リソースの構成変更履歴 |
| VPC Flow Logs | VPC 内のネットワークトラフィックメタデータ |
| Amazon Route 53 Resolver クエリログ | DNS クエリログ。C2 通信やデータ持ち出しの検知に有用 |

### アプリケーション層・ネットワーク境界

| ログ | 主な役割 |
|---|---|
| Elastic Load Balancing ログ | ALB/NLB のアクセスログ |
| Amazon CloudFront ログ | CDN アクセスログ |
| Amazon API Gateway ログ | API アクセスログ |
| AWS WAF ログ | Web ACL のリクエスト・遮断ログ |

### コンピュート・アプリケーション

| ログ | 主な役割 |
|---|---|
| EC2 インスタンスの OS ログ | syslog、Windows Event Log 等 |
| EC2 インスタンスのアプリケーションログ | アプリケーション固有のログ（CloudWatch Logs Agent 等で集約） |
| ECS on Fargate のアプリケーションログ | コンテナアプリケーションのログ |
| AWS Lambda のアプリケーションログ | Lambda 実行時のログ（CloudWatch Logs に出力） |

### ストレージ・データベース

| ログ | 主な役割 |
|---|---|
| Amazon RDS / Amazon Aurora 監査ログ | DB アクセス、クエリの監査ログ |
| Amazon DynamoDB Streams ログ | テーブルの変更履歴 |
| Amazon EFS ファイル操作ログ | マウントするクライアント側 OS で取得（EFS 自体ではファイル単位の操作ログは取得不可） |
| Amazon FSx for Windows 監査ログ | Windows ファイルアクセスの監査ログ |

### サードパーティ製品連携

サードパーティのセキュリティツール（EDR、AV、IDS/IPS 等）のログも、AWS 環境のログと突き合わせて分析できるよう、収集経路を設計することを推奨する。

## ログ自体の保護

収集したログそのものも攻撃者の標的となる。攻撃者がログを改ざん・削除すれば後の分析が不可能になるため、ログ自体に対する保護を設計する必要がある。

### ローカル保管リスクとモニタリングサービスへの転送

EC2 インスタンス等のローカルにアプリケーションログを保管した場合、以下のリスクが伴う。

- ランサムウェアによる暗号化対象になる
- 攻撃者によるログの改変・削除が可能となる
- インスタンス障害時にログ自体が失われる

これらのリスクを軽減するアプローチとして、Amazon CloudWatch Logs 等のモニタリングサービスへのリアルタイムログ転送が有効である。インスタンス上でログが書き込まれた時点で外部に転送されるため、後からインスタンス上のログが暗号化・改変・削除されても、転送済みのログは保全される。

転送には CloudWatch Logs エージェント、Unified CloudWatch エージェント、サードパーティ製のログ転送エージェント（Fluentd、Fluent Bit 等）を活用することが可能となる。

### Log Archive アカウントへの集中保管

ワークロードアカウントとは分離した Log Archive アカウント（ログデータ専用の保管アカウント）への集約を推奨する。これは AWS Security Reference Architecture（SRA）や AWS Control Tower のランディングゾーンでも標準構成として採用されている形であり、Security OU 配下にセキュリティツール用アカウントと並列で配置することが一般的である。本スキルが採用するアカウント構成における Log Archive アカウントの位置づけは [01-multi-account-architecture.md](./01-multi-account-architecture.md) を参照する。

具体的には以下のような集約が有効である。

- AWS Organizations のトレイル機能による組織全体の CloudTrail ログを Log Archive アカウントに集約
- 各アカウント・各 VPC の VPC Flow Logs を Log Archive アカウントの S3 バケットに転送
- 各種ログを Log Archive アカウントに集約

ワークロードアカウントが侵害されても、集約先アカウントへの改変は別の防御層で守られているため、ログの保全性が向上する構成となる。

### S3 多層防御の組み合わせ

ログ保管 S3 バケットに対しては、以下の機能を組み合わせた多層防御を推奨する。Object Lock の詳細は [02-immutability.md](./02-immutability.md) を参照する。

| 保護機構 | 役割 |
|---|---|
| **S3 Versioning** | オブジェクトの上書き・削除があっても旧バージョンとして残るため、復元が可能となる |
| **S3 Object Lock（Compliance mode 推奨）** | 保持期間内のオブジェクトを WORM 保護し、削除・上書きを防止する |
| **MFA Delete** | バージョンの完全削除には MFA 認証が必要となり、攻撃者による削除を実質的に防止する |
| **アクセス制御の最小権限化** | バケットポリシー・IAM ポリシーで、ログへのアクセスを限定された分析チームのみに制限する |

これらを組み合わせることで、いずれか1つの防御層が突破されても他の層でログが保護される構成となる。

## 攻撃によるログ停止・削除への対策

攻撃者は分析証跡を消すために、CloudTrail 等のログ取得自体を停止・削除しようとする可能性がある。これに対しては、以下のような多段階の防御を組み合わせることを推奨する。

| 段階 | 対策 | 役割 |
|---|---|---|
| **予防** | SCP による停止・削除アクションの Deny | ワークロードアカウント側のクレデンシャルが侵害されても、ログ停止・削除操作自体が拒否される（詳細は [06-policy-and-access-control.md](./06-policy-and-access-control.md) を参照） |
| **検知** | Amazon EventBridge による即時通知 | ログ停止・削除アクションを示すイベントを検知し、SNS 等で即座にセキュリティチームへ通知する |
| **自動復旧** | AWS Config Rules による自動修復 | ログ取得が停止された場合に Config Rules で検知し、Systems Manager Automation や Lambda で自動的に再有効化する |
| **データ保全** | ログ保管 S3 への多層防御 | 上記でも防ぎきれず実際のログが消されようとした場合に、保管側で消失を防ぐ最後の砦 |

これらを組み合わせることで、「停止・削除を予防する → 停止された場合に即座に検知する → 自動的に復旧する → 実際にログ自体が消えても保管側で残す」という多段階の保護を実現することが可能となる。

## オプショナル: 統合サービスの活用

本リファレンスで述べたログ収集・保護は AWS の標準機能の組み合わせで実現可能であるが、以下の統合サービスを活用することで実装・運用を効率化することができる。これらはオプショナルな効率化要素であり、必須要件としては今回は位置づけない。

### AWS Control Tower

AWS Control Tower を活用すると、本リファレンスで整理した以下の対策を Control Tower の機能として導入することが可能となる。

- CloudTrail / AWS Config データの収集設定がランディングゾーンのセットアップで自動化される
- ログ停止・削除の Deny を含む予防的統制が、Control Tower のガードレール（管理ポリシー）として標準提供される

新規にランディングゾーンを Control Tower で構築する場合、これらの設定が標準化された形で適用されるため、個別実装の手間が削減される。

### Amazon Security Lake

ログ集約の効率化策として、Amazon Security Lake の活用が有効となる。

- 複数の AWS アカウントから、セキュリティログ・イベントを一元管理する仕組みを提供する
- 集約対象として AWS CloudTrail、VPC Flow Logs、Amazon Route 53 Resolver クエリログ、AWS Security Hub の検出結果、AWS WAF、パートナー製セキュリティソリューション等をサポートする
- 集約したログは OCSF（Open Cybersecurity Schema Framework）形式に自動変換されるため、各種のセキュリティ分析ツール（SIEM、UEBA 等）との連携が容易となる

S3 への手作業の集約や形式変換を自前で実装する代わりに、Security Lake により標準化された形で実現することが可能となる。

### 採用判断のポイント

これらのサービスは利便性が高い一方、以下の理由で採用に慎重なケースもある。

- 既存のランディングゾーン設計（Control Tower を使わない自前構成）との整合
- セキュリティ運用基盤・SIEM 等の既存資産との接続設計
- 規制対応における説明責任の観点

新規導入や大規模なクラウド移行のタイミングで Control Tower / Security Lake を採用する判断は合理的である一方、既存環境への後付け導入はトレードオフを十分に検討することを推奨する。本スキルでは、標準機能の組み合わせでの実装を基本構成として推奨し、Control Tower / Security Lake によるオプショナルな効率化を別途の選択肢として位置づけている。

## フォレンジック分析の専門性とベンダ活用

収集したログは、以下のような分析に活用される。

- 侵入経路の特定（攻撃者がどこから・どのように侵入したか）
- 侵入時刻の特定（感染発生時刻・初期感染リソースの特定）
- 被害範囲の分析（どのリソース・データに影響が及んでいるか）
- 横展開（lateral movement）の追跡（攻撃者が組織内でどう移動したか）
- 持ち出しデータの有無の確認（情報漏洩が発生していないか）

これらのフォレンジック分析は、メモリ解析、マルウェア解析、攻撃者の TTPs（Tactics, Techniques and Procedures）の理解、法廷で通用する証拠保全等の高度な専門性が求められる領域である。平時から経験を積んでいない組織が自社で実施するのは難しいケースも想定される。

そのため、金融機関では以下の選択肢も視野に入れることを推奨する。

- フォレンジック分析を専門とするベンダへの依頼により、迅速かつ確実な分析を実現する
- インシデント発生時に急遽で契約を進めることは現実的でないため、平時から「どのベンダに依頼するか」「契約形態をどうするか」「どこまでの分析を委託するか」を検討・契約しておく

## 金融機関の文脈での設計判断

### 保持期間の設計

金融機関では、業務記録・取引記録の保管期間が法令や業界規制で定められているケースが多い。ログが規制対応の一環として位置づけられる場合、以下の点を設計に反映することを推奨する。

- 規制要件で定められた保管期間（例: 7年等）を満たすライフサイクル設計
- インシデント分析のため、一定の期間内は即時アクセス可能な状態で保管する
- 長期保管はコスト効率を考慮し、Amazon S3 Glacier 等のコールドストレージへ移行する設計を併用する

ただし、特定の規制条文への適合性判定は本スキルのスコープ外であり、組織の規制対応部署・コンプライアンス部署と連携して判断することを推奨する。

### アクセス制御の設計

ログへのアクセスは最小権限で制限し、改ざん・削除を物理的に困難にすることを推奨する。読み取り権限も限定された分析チームのみに付与する設計が望ましい。

- ログ保管バケットの読み取り権限を分析チームに限定する
- ログの書き込み権限はログ転送の仕組みのみに付与し、人手での書き換えを防ぐ
- ログ保管バケットへのアクセスログ自体も別途取得し、ログへのアクセス自体を監査可能にする

## 対策効果のサマリ表

本リファレンスで扱う各設計要素が、ランサムウェア対策としてどのリスクに有効かを整理する。

| 設計要素 | 防御するリスク | 有効なシナリオ |
|---|---|---|
| 体系的なログ収集（カテゴリ網羅） | 攻撃発生後の分析材料の不足 | 侵入経路・被害範囲の特定、フォレンジック分析の基盤確保 |
| モニタリングサービスへのリアルタイム転送 | ローカル保管ログの暗号化・改変・削除 | ランサムウェアによる暗号化、攻撃者によるログ改ざん |
| Log Archive アカウントへの集中保管 | ワークロードアカウント侵害時のログ消失 | 業務アカウントが侵害された場合でも、集約先のログは別の防御層で保護 |
| S3 多層防御（Versioning、Object Lock、MFA Delete） | ログ保管バケットへの不正な改変・削除 | 攻撃者がログ集約先 S3 バケットへの権限を得た場合 |
| SCP による CloudTrail / Config 停止防止 | 攻撃者の活動ログ消去 | ワークロードアカウントの管理者権限を奪取した攻撃者 |
| Config Rules による自動復旧 | ログ取得停止後の検知遅延 | 攻撃者がログを停止した場合の即時復旧 |
| EventBridge による即時通知 | ログ停止・削除の見逃し | 攻撃の予兆検知、迅速な対応開始 |
| アクセス制御の最小権限化 | ログ自体への不正アクセス・改変 | 内部不正、攻撃者による権限昇格後のアクセス |
| 規制要件を満たす保持期間設計 | 規制対応上のログ不足 | 法令・業界規制で保管期間が定められている業務システム |
