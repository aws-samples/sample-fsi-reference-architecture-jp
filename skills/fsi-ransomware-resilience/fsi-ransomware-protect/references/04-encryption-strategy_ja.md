# バックアップデータの暗号化戦略（KMS・キー管理）

## 概要

本リファレンスは、本スキルが採用するバックアップデータの暗号化戦略について示す。ランサムウェア対策の文脈では、暗号化は「攻撃者がアカウントを掌握した場合でも、コピー先のバックアップデータを復号できない構成を作る」という多層防御の重要な要素となる。

本リファレンスでは、AWS Backup における暗号化の基盤メカニズム、本スキルが採用するアカウント別・リージョン別の KMS CMK 分離戦略、クロスアカウント・クロスリージョンコピー時の暗号化挙動、キー管理戦略の主要観点、LAG vault と AWS 所有キーの位置づけ、金融機関の文脈での設計判断について整理する。

マルチアカウント構成における KMS キーの配置は [01-multi-account-architecture.md](./01-multi-account-architecture.md)、KMS キーポリシー設計の詳細は [06-policy-and-access-control.md](./06-policy-and-access-control.md) を参照する。

## 基盤メカニズム: AWS Backup における暗号化

### 独立暗号化（Independent encryption）の対応有無

AWS Backup の暗号化は、対象リソースタイプによって挙動が異なる。AWS Backup によりフルマネージドで管理されるリソースタイプでは、Backup vault に設定した KMS キーで独立に暗号化される（独立暗号化）。一方、AWS Backup によりフルマネージドで管理されないリソースタイプでは、ソースリソースの暗号化キーをそのまま継承する形で暗号化される。

| 区分 | 主なリソースタイプ（執筆時点） | 暗号化の挙動 |
|---|---|---|
| **独立暗号化対応** | Amazon S3、Amazon EFS、Amazon DynamoDB（Advanced backup 有効時）、Amazon Timestream、AWS CloudFormation、SAP HANA on Amazon EC2、VMware 仮想マシン | Backup vault に設定した KMS キーで暗号化される。ソースリソースの暗号化方式とは独立 |
| **独立暗号化非対応** | Amazon EBS、Amazon EC2、Amazon RDS、Amazon Aurora、Amazon DocumentDB、Amazon Neptune、Amazon Redshift、AWS Storage Gateway、Amazon FSx、Amazon DynamoDB（Advanced backup 無効時）等 | ソースリソースの暗号化キー（または暗号化なし）が継承される |

対応リソースタイプは AWS の機能拡張により変わる可能性があるため、設計時には AWS Backup 公式ドキュメントの [Encryption for backups in AWS Backup](https://docs.aws.amazon.com/aws-backup/latest/devguide/encryption.html) の最新版を参照することを推奨する。

独立暗号化が適用される場合、AWS Backup は AES-256 の暗号化アルゴリズムでバックアップデータを暗号化する。

### クロスアカウント・クロスリージョンコピー時の暗号化挙動

AWS Backup によるクロスアカウント・クロスリージョンコピーでは、コピー先の Backup vault に設定された KMS キーで暗号化される。コピー元が独立暗号化対応リソースか非対応リソースかにかかわらず、この挙動は共通である。

クロスアカウントコピーでは、独立暗号化対応リソースの場合は KMS CMK または AWS Backup の AWS マネージドキー（`aws/backup`）が利用可能となる。一方、独立暗号化非対応リソースの場合は KMS CMK または対応するサービス固有のマネージドキー（例: Amazon EBS の場合は `aws/ebs`）が必要となる。AWS マネージドキーはキーポリシーが変更不可（immutable）であるため、独立暗号化非対応リソースのクロスアカウントコピーでは利用できない仕様となっている。

詳細な挙動と前提条件は AWS Backup 公式ドキュメント [Encryption for a backup copy to a different account or AWS Region](https://docs.aws.amazon.com/aws-backup/latest/devguide/encryption.html) の最新版を参照することを推奨する。

### 設計上の重要な含意

独立暗号化の対応有無は、本スキルが採用する構成（クロスアカウント・クロスリージョンコピーを前提としたマルチアカウント構成）においてどのような影響を持つか整理する。

- **クロスアカウント・クロスリージョンコピー後のバックアップ**: 独立暗号化対応かどうかにかかわらず、コピー先 Backup vault に設定した KMS CMK で再暗号化される。これにより、隔離アカウント・リカバリアカウント・大阪リージョン等のコピー先で保管されるバックアップデータは、本スキルが採用するアカウント別・リージョン別の KMS CMK 戦略によって一元的に統制された暗号化が確実に実現される構成となる
- **業務アカウントでの初回バックアップ取得**: 独立暗号化対応リソースは Backup vault に設定した KMS CMK で暗号化される一方、独立暗号化非対応リソース（Amazon EBS、Amazon RDS、Amazon Aurora 等）はソースリソースの暗号化キーが継承される仕様となる。そのため、ソースリソース自体が KMS CMK で暗号化されていない場合、業務アカウントでの初回バックアップも暗号化されないケースが生じる

業務アカウントでの初回バックアップにおける暗号化挙動の差は、組織内のリソース暗号化ルールが徹底されていれば実務上の問題とはならない。一方、既存環境で暗号化されていないリソースが残っている場合は、ソースリソース自体の暗号化を併せて検討することを推奨する。コピー先データは前述の通りコピー先 vault の KMS CMK で再暗号化されるため、本スキルが推奨するマルチアカウント構成全体としての暗号化の堅牢性は維持される。

## 本スキルが採用するキー戦略: アカウント別・リージョン別の KMS CMK 分離

### 採用する戦略

本スキルでは、各アカウント・各リージョンで個別に管理する KMS CMK を Backup vault に設定する戦略を採用・推奨する。具体的な配置構成は [01-multi-account-architecture.md](./01-multi-account-architecture.md) を参照することを推奨するが、以下のように業務アカウント・隔離アカウント・リカバリアカウントの各リージョンで独立した KMS CMK を配置する構成となる。

### この戦略を採用する理由

KMS CMK をアカウント別・リージョン別に分離する戦略は、ランサムウェア対策の多層防御の観点から以下のメリットを得ることが可能となる。

- **単一鍵掌握リスクの回避**: 攻撃者が特定アカウントの KMS CMK を掌握しても、コピー先アカウント・コピー先リージョンの KMS CMK は独立して管理されるため、コピー先のバックアップデータの復号を防ぐことが可能となる
- **責務分離の実現**: アカウントごとに KMS CMK の管理主体（業務アカウントの管理者、隔離アカウントの管理者、リカバリアカウントの管理者）を分離することで、特定アカウントの管理者権限の侵害が組織全体の暗号化キーに波及しない構成となる
- **監査単位の明確化**: KMS の API 呼び出しは AWS CloudTrail で記録されるため、KMS CMK をアカウント別に分離することで、どのアカウントのキーがいつ使用されたかを明確に追跡することが可能となる
- **KMS マネージドキーの制約回避**: AWS マネージドキーはキーポリシーが変更不可であり、独立暗号化非対応リソースのクロスアカウントコピーで利用できないため、KMS CMK を採用することで保護対象リソースタイプを限定せずに統一的なコピー戦略を実現することができる

### クロスアカウント・クロスリージョンコピー時の再暗号化

本構成では、業務アカウントから隔離アカウントへのコピー時、業務アカウントから大阪リージョンへのコピー時、隔離アカウントからリカバリアカウントへのコピー時のいずれにおいても、コピー先 vault に設定された KMS CMK で再暗号化される。これにより、コピー元のキーを掌握した攻撃者であっても、コピー先のデータは独立した KMS CMK で保護されているため復号できない構造となる。

クロスアカウントコピーを成立させるためには、コピー元アカウントの IAM ロールがコピー先 KMS CMK を利用できるよう、コピー先 KMS CMK のキーポリシーで適切な許諾を設定する必要がある。詳細は [06-policy-and-access-control.md](./06-policy-and-access-control.md) を参照することを推奨する。

## キー管理戦略の主要観点

KMS CMK のキーポリシー設計・運用において、ランサムウェア対策の文脈では以下の観点を考慮することを推奨する。具体的なキーポリシーの設計詳細は [06-policy-and-access-control.md](./06-policy-and-access-control.md) を参照することを推奨する。

- **キー利用主体の分離**: バックアップ実行ロール、リストア実行ロール、キー管理者ロールを別々の IAM ロールとして設計し、キーポリシーで各ロールに必要最小限の権限のみを付与する
- **クロスアカウントコピーの許諾範囲の最小化**: コピー元アカウントへの利用許諾は `kms:Encrypt`、`kms:Decrypt`、`kms:ReEncrypt*`、`kms:GenerateDataKey*` 等のコピー操作に必要な範囲に絞り込む
- **キーローテーションの設定**: KMS CMK の自動キーローテーションを有効化することで、長期間同一のキーマテリアルが使われ続けるリスクを軽減する
- **キー削除耐性の確保**: KMS CMK の削除には削除待機期間が設けられているが、攻撃者が削除をスケジュールするリスクへの追加防御として、SCP による `kms:ScheduleKeyDeletion` の予防的 Deny を組み込むことを推奨する（詳細は [06-policy-and-access-control.md](./06-policy-and-access-control.md) を参照）
- **CloudTrail によるキー利用監査**: 全 KMS CMK の API 呼び出しを CloudTrail で記録し、想定外のキー利用・削除試行を検知できる体制を整える

## LAG vault と AWS 所有キーの位置づけ

LAG vault（Logically air-gapped vault）は、Backup vault の一種でありながら、暗号化に **AWS 所有キー（AWS owned key）** が使われる仕様となっている。これは顧客アカウント側で管理する KMS CMK ではなく、AWS が所有・管理するキーで暗号化されることを意味する。

### LAG vault の AWS 所有キー暗号化と顧客 KMS CMK 構成との対比

| 項目 | 顧客 KMS CMK 構成（通常の Backup vault） | LAG vault（AWS 所有キー） |
|---|---|---|
| キーの管理主体 | 顧客アカウント内の管理者 | AWS（顧客は管理権限を持たない） |
| キーポリシーの設定 | 顧客側で設計・運用 | 顧客側からは変更不可 |
| キー削除のリスク | 攻撃者が顧客アカウントを掌握すると削除のリスクが残る（SCP 等の予防的統制で軽減） | 顧客側からの削除操作自体が成立しない |

### この仕様がランサムウェア対策の観点で持つ意義

通常の KMS CMK 構成では、攻撃者が顧客アカウントの管理者権限を奪取した場合、KMS CMK の削除や無効化を試みる脅威シナリオが残る。KMS CMK を削除するとバックアップデータの復号が不可能となるため、ランサムウェア攻撃のなかでも特に深刻な被害につながる。

LAG vault が AWS 所有キーで暗号化されることで、顧客側のキー削除リスクそのものが排除される。これは LAG vault がランサムウェア対策において強固な保護機構として位置づけられる理由の一つとなる。一方、KMS CMK 構成のような顧客側でのキー管理柔軟性（キーポリシー設計、ローテーション設定等）は得られないため、組織のキー管理ポリシーとの整合性を確認した上で採用判断を行うことを推奨する。

ハイブリッド構成（LAG vault 対応リソースは LAG vault、非対応リソースは通常 Vault + Vault Lock）では、リソースタイプごとに暗号化の管理主体が分かれる構成となる。詳細は [01-multi-account-architecture.md](./01-multi-account-architecture.md) の「構成選択の3パターン」を参照する。

## 金融機関の文脈での設計判断

### 組織のキー管理ポリシーとの整合

金融機関では、暗号化キーの管理ポリシーが組織内ルールとして定められているケースが多い。本スキルが推奨する KMS CMK 戦略を採用する場合、以下の観点で組織内ルールとの整合を確認することを推奨する。

- KMS CMK（顧客管理キー）の利用が組織内ルールで認められているか
- キーポリシー設計、キーローテーション周期、キー削除手続き等の運用ルールとの整合
- キー利用監査の体制（CloudTrail ログの保管期間、レビュー周期等）

### 規制要件への対応

金融機関では暗号化に関する規制要件が定められているケースが多い。バックアップデータの暗号化が規制対応の一環として位置づけられる場合、以下の点を設計に反映する。

- 規制要件で定められた暗号化アルゴリズム強度との整合（AWS Backup の独立暗号化は AES-256 を採用）
- 暗号化キーの管理に関する要件（キー管理者の分離、キー利用ログの保管等）
- 監査証跡として活用可能な状態でのキー利用ログの取得

ただし、特定の規制条文への適合性判定は本スキルのスコープ外であり、組織の規制対応部署・コンプライアンス部署と連携して判断することを推奨する。

### LAG vault 採用時のキー管理柔軟性とのトレードオフ

LAG vault は AWS 所有キーで暗号化されるため、顧客側でのキーポリシー設計・キーローテーション設定等の管理柔軟性は得られない。組織内のキー管理ポリシーが厳格に「顧客管理キーでの暗号化」を求める場合、LAG vault の採用に組織内承認が必要となる場合がある。一方、LAG vault は顧客側のキー削除リスクを構造的に排除する強固な保護機構であるため、ランサムウェア対策の観点でのメリットと組織内ルールとの整合を踏まえた採用判断を行うことを推奨する。

## 対策効果のサマリ表

本リファレンスで扱う各設計要素が、ランサムウェア対策としてどのリスクに有効かを整理する。

| 設計要素 | 防御するリスク | 有効なシナリオ |
|---|---|---|
| アカウント別・リージョン別の KMS CMK 分離 | 単一鍵掌握による全データ復号 | 攻撃者が特定アカウントの KMS CMK を掌握した場合でも、コピー先データの復号を防止 |
| クロスアカウントコピー時の再暗号化 | コピー元の鍵を掌握した攻撃者によるコピー先データの復号 | 業務アカウントが侵害された場合でも、隔離アカウント側のデータは独立した KMS CMK で保護 |
| KMS CMK キーポリシーによる利用主体の分離 | バックアップ・リストア権限の侵害による不正操作 | 攻撃者が一部の IAM ロールを掌握した場合のリスク軽減 |
| 自動キーローテーション | 長期間同一キーが使用されることによるリスク | キー漏洩等の長期的なリスク軽減 |
| SCP による KMS キー削除の予防的 Deny | 攻撃者によるキー削除でのデータ復号不能化 | 攻撃者が顧客アカウントの管理者権限を奪取した場合の追加防御 |
| LAG vault の AWS 所有キー暗号化 | 顧客側の操作によるキー削除・無効化 | 顧客側の管理者権限が侵害された場合でも、AWS 所有キーは顧客側からの削除操作が不可能 |
| CloudTrail によるキー利用監査 | 想定外のキー利用・削除試行の見逃し | 攻撃の予兆検知、事後分析、監査対応 |
