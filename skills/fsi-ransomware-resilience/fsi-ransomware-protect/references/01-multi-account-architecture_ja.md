# マルチアカウント構成によるバックアップアーキテクチャ

## 概要

本リファレンスは、本スキルが採用するランサムウェア対策バックアップアーキテクチャの全体像を示す。AWS Backup を中心としたマルチアカウント・マルチリージョン構成により、組織内で稼働する業務システムのワークロードのバックアップを取得し、改変・削除に対する耐性を持たせる形で保護する。

まずアーキテクチャを支える基盤メカニズム（AWS Backup と AWS Organizations の連携）を整理した上で、アカウント構成、データフロー、LAG vault の適用、リージョン戦略、暗号化の前提、組織レベルでの一元管理について順に説明する。詳細なポリシー設計は [06-policy-and-access-control.md](./06-policy-and-access-control.md)、暗号化の詳細は [04-encryption-strategy.md](./04-encryption-strategy.md)、Vault Lock の詳細は [02-immutability.md](./02-immutability.md)、バックアッププラン設計は [03-backup-plan-design.md](./03-backup-plan-design.md) を参照する。

## 基盤メカニズム: AWS Backup による組織横断のバックアップ管理

本スキルが採用するバックアップ取得・保護の基盤は、**AWS Backup の cross-account management 機能と AWS Organizations のバックアップポリシーを組み合わせた組織横断管理**である。これは AWS が提供する複数のバックアップ手段（AWS Backup、各サービス個別のバックアップ機能、サードパーティ製品等）の中から、組織内の多数の業務アカウントに対して統一的なバックアップ要件を適用しやすい構成として選択・推奨している。

### 採用するメカニズムの全体像

組織内のバックアップ取得・保護は以下のメカニズムで実現する。

```
[Organizations 管理アカウント]
        │
        │ AWS Organizations
        │ (組織管理)
        ▼
[Backup アカウント]
        │ ・組織全体のバックアップポリシーを定義
        │ ・Organizations から AWS Backup の管理を委任される
        │
        │ バックアップポリシーを OU またはアカウントに適用
        ▼
[業務アカウント (複数)]
        │ ・適用されたバックアップポリシーから、対応するバックアッププランが作成される
        │ ・バックアッププランに従って AWS Backup がバックアップを実行
        │
        ▼
   バックアップ取得
   (Backup vault に保管)
        │
        │ クロスリージョン / クロスアカウントコピー
        ▼
   隔離アカウント / 大阪リージョン / リカバリアカウント
```

### バックアップポリシーとバックアッププランの関係

本構成を理解する上で重要な概念を整理する。

| 概念 | 提供サービス | 役割 |
|---|---|---|
| **バックアップポリシー (backup policy)** | AWS Organizations | 組織全体や OU に適用するバックアップ要件の定義（バックアッププランの定義、リソース割当、ライフサイクル等を JSON で記述） |
| **バックアッププラン (backup plan)** | AWS Backup | バックアップ要件を定義するポリシーであり、AWS リソースの保護に適用される。バックアップポリシーが OU やアカウントに適用されると、各業務アカウントに対応するバックアッププランが作成される |
| **バックアップルール (backup rule)** | AWS Backup | バックアッププランを構成する個別ルール（取得頻度、ライフサイクル、保管先 Vault、コピー先等） |
| **Backup vault** | AWS Backup | バックアップデータの保管先 |

このメカニズムにより、Backup アカウントで管理するバックアップポリシーを変更すれば、組織内の全業務アカウントのバックアップ動作を一元的に変更できる。各業務アカウントで個別にバックアッププランを設定する必要がなく、またバックアップのイミュータブル化、遠隔保管や冗長化等の統制を効果的に実現することが可能となる。

### Backup アカウントへの委任

本構成では、AWS Backup の管理権限を Organizations 管理アカウントから Backup アカウントに委任する（AWS Backup の delegated administrator 機能）。委任を受けた Backup アカウントで組織全体のバックアップポリシーを管理できるようになり、Organizations 管理アカウントとの責務分離が実現される。

### 取得対象リソースの選定方法

各業務アカウント内のリソースのうち、何をバックアップ対象とするかは、バックアッププランへのリソース割当（タグベース、リソースタイプベース等）で指定する。たとえばタグベースの場合、特定のタグが付いたリソースのみを対象とする運用が可能となる。

具体的なタグ運用や対象選定の判断軸は [03-backup-plan-design.md](./03-backup-plan-design.md) を参照する。

## アカウント構成

ランサムウェア対策バックアップアーキテクチャでは、責務を分離した以下のアカウント群を組み合わせる。

### バックアップに直接関わるアカウント

| アカウント | 役割 |
|---|---|
| Organizations 管理アカウント | AWS Organizations の管理をするアカウント。組織全体の SCP の設定、AWS Backup によるバックアップ管理を Backup アカウントへ委任、組織トレイル（CloudTrail）の設定等を担う |
| Backup アカウント | Organizations から AWS Backup の管理を委任され、組織全体のバックアップポリシーを集中管理する。また、組織内のバックアップ・コピー・リストアジョブを横断的にモニタリングする役割を持つ |
| 業務アカウント（複数） | 組織内で稼働する様々な業務システムのワークロードがホストされているアカウント（ランサム対策用に新設するアカウントではなく、既存で存在する業務用アカウント）。Backup アカウントから適用されたバックアップポリシーに基づいて作成されたバックアッププランに従い、AWS Backup によるバックアップが取得される |
| 隔離アカウント | 業務アカウントから切り離されたバックアップの追加保護先。クロスアカウントコピーで業務アカウントから複製を受け取り、Vault Lock により改変・削除耐性を担保する |
| リカバリアカウント | フォレンジック分析、リストアテスト、有事の際の復旧時の確認をする役割を持つ環境 |

### 周辺アカウント（別のリファレンスファイルのスコープ）

| アカウント | 役割 |
|---|---|
| セキュリティアカウント | Amazon GuardDuty、AWS Security Hub 等のセキュリティツールの集約管理（本スキルのスコープ外） |
| Log Archive アカウント | CloudTrail、AWS Config、VPC Flow Logs 等のログデータ専用の集約先（詳細は [07-log-collection-and-protection.md](./07-log-collection-and-protection.md)） |

各アカウントの責務は責務の分離（Separation of Duties）および最小権限（Least Privilege）の原則に従って区分されており、特定アカウントの侵害が組織全体に波及しないよう設計する。

### 各アカウントに配置されるリソース

| アカウント | 配置されるリソース |
|---|---|
| Organizations 管理アカウント | SCP、組織トレイル設定 |
| Backup アカウント | バックアップポリシー、組織全体のバックアップ状況のモニタリング |
| 業務アカウント | 業務ワークロード、バックアップポリシーから作成されたバックアッププラン、各リージョンの Backup vault、KMS CMK、Backup 実行用 IAM Role |
| 隔離アカウント | Backup vault（Vault Lock 適用）、KMS CMK、業務アカウントからのクロスアカウントコピーを受け入れる Vault アクセスポリシー |
| リカバリアカウント | Backup vault、KMS CMK、リストア実行用 IAM Role、隔離アカウントからのコピーを受け入れる Vault アクセスポリシー |

## データフロー

### 基本のフローと実装メカニズム

各業務アカウントで取得されたバックアップは、以下の経路で複製・保護される。

```
業務アカウント（東京）
  ├─→ 業務アカウント（大阪）       [クロスリージョンコピー]
  └─→ 隔離アカウント（東京）       [クロスアカウントコピー]
        └─→ リカバリアカウント（東京） [クロスアカウントコピー / 平時からのコピー]
```

各コピーは、バックアッププラン内の Copy Action 設定によって実行される。バックアップポリシー（Backup アカウントで管理）の中で、東京で取得したバックアップを大阪リージョンの Backup vault や隔離アカウントの Backup vault にコピーする設定を記述しておくことで、業務アカウントでバックアップが取得されるたびに、対応するコピーが作成される。

各コピーは、コピー先アカウント・コピー先リージョンで管理される独立した KMS CMK で再暗号化される（[04-encryption-strategy.md](./04-encryption-strategy.md) 参照）。コピー先 Vault のアクセスポリシーで `backup:CopyIntoBackupVault` アクションを許可することで、クロスアカウントコピーが成立する（[06-policy-and-access-control.md](./06-policy-and-access-control.md) 参照）。

### 各コピー経路の目的

| コピー経路 | 主目的 | 副次的効果 |
|---|---|---|
| 業務アカウント（東京）→ 業務アカウント（大阪） | 3-2-1 ルール準拠（異なるリージョン） | DR（リージョン障害、自然災害）対策 |
| 業務アカウント（東京）→ 隔離アカウント（東京） | 3-2-1 ルール準拠（異なるアカウント） | セキュリティ攻撃対策（アカウント侵害、内部不正、ランサムウェア） |
| 隔離アカウント → リカバリアカウント | 有事の際の迅速な復旧基盤 | フォレンジック分析・リストアテストの場 |

「3-2-1 ルールに従ってバックアップを分散配置すると同時に、アカウント分離がランサムウェア対策としても機能する」形となる。災害対策（DR）とセキュリティ攻撃対策の両方を、同一の構成で実現できるのが本構成のメリットである。

### 隔離アカウント → リカバリアカウントのコピー方針

本ナレッジでは有事の際に迅速な復旧を可能とするため、平時から継続的にコピーする設計を基本構成とする。インシデント発生後にコピーを開始する設計戦略も取ることは可能であるが、コピー所要時間の分だけ復旧着手が遅延するため、コストと復旧着手の迅速性のトレードオフとなる。各金融機関のシステムにおける復旧時の要件、組織内ルール等に応じて戦略的に選択することを推奨する。なお、復旧完了までの所要時間（RTO）はバックアップ・コピー設計だけでなく、リストア・切替・検証等の運用要素を含めて確保されるものであり、本項目はそのうちの復旧着手の準備性に寄与する位置づけである。

代替アプローチとそのトレードオフ:

| アプローチ | メリット | デメリット |
|---|---|---|
| 平時から継続的にコピー | 有事に即座に復元を開始可能、復旧着手が迅速 | ストレージコスト二重 |
| インシデント発生時にオンデマンドコピー | コスト最適化 | 復旧開始までにコピー時間が必要、復旧着手が遅延 |
| LAG vault + RAM 共有（発展構成） | コピー不要で即座にアクセス可能、ストレージコスト削減、後述の Multi-party approval による承認統制も可能 | RDS 非サポート（後述） |

LAG vault が利用可能な環境では発展構成が望ましいが、現時点での制約により、構成選択は次節の判断軸に従う。

## LAG vault の採用判断

### LAG vault とは

**Logically air-gapped vault（LAG vault）** は、AWS Backup が提供する Vault の一種で、ランサムウェア対策に特に有効な特性を持つ。通常の Backup vault と比べて以下の特徴がある。

1. **AWS Resource Access Manager (RAM) によるリソース共有**: バックアップを物理的にコピーせず、別アカウントから RAM で共有してアクセスすることができる。ストレージコスト削減と復旧時間短縮を実現する
2. **AWS 所有キーによる暗号化**: 顧客側で管理する KMS キーではなく AWS 所有キーによって暗号化される。これにより、攻撃者が顧客アカウントを掌握して KMS キーの誤削除・悪意ある削除を行ってもバックアップデータが復号不能になることを防ぐことが可能
3. **Multi-party approval**: 復元時に複数人の承認を要求する機能であり、単独の攻撃者がリストア権限を得たとしても不正な復元を防止する効果を見込むことが出来る。
4. **イミュータブル化が強制適用される**: LAG vault は作成時点で改変・削除耐性が組み込まれており、別途 Vault Lock を設定する必要はない（詳細は [02-immutability.md](./02-immutability.md) を参照）

通常の Backup vault と Vault Lock の組み合わせでもランサム対策として有効だが、LAG vault はさらに踏み込んだ保護機構として位置づけられる。

### LAG vault の対応リソースタイプ

LAG vault は ランサム対策において非常に有効な機能であるが、AWS Backup が保護対象とするすべての AWS リソースに対応しているわけではない。そのため、組織内のすべてのリソースを LAG vault に統一的に保管できるとは限らず、リソースタイプごとの対応状況に応じた構成選択が求められる。

例えば金融機関で広く使われる主要なリソースの中では、Amazon RDS（single instance / cluster）が LAG vault の対応外となっている（2026年6月執筆時点）。RDS を業務システムで使用している環境では、RDS のバックアップを LAG vault で保護できないため、後述の「構成選択の3パターン」で示すハイブリッド構成や基本構成の検討対象となる。

LAG vault の対応リソースタイプは AWS の機能拡張により随時変わるため、設計時には RDS に限らず、保護対象とするリソースタイプの対応状況を AWS 公式ドキュメントで適宜確認することを推奨する。

### 構成選択の3パターン

LAG vault の対応リソースタイプの状況に応じて、隔離アカウントの Vault 構成を3パターンから選択する。

| 構成パターン | 対象環境 | 隔離アカウントの Vault 構成 | 備考 |
|---|---|---|---|
| **基本構成** | LAG vault 非対応リソース（RDS 等）が保護対象の中心となる環境 | 通常の Backup vault + Vault Lock | 全リソースを統一的に保護できる。Vault Lock のコンプライアンスモードで改変・削除耐性を担保 |
| **発展構成** | LAG vault に対応するリソースのみで構成される環境 | LAG vault（+ RAM 共有 + Multi-party approval） | LAG vault の特性を享受できる |
| **ハイブリッド構成** | LAG vault 対応リソースと非対応リソースが混在する環境 | LAG vault 対応リソースは LAG vault、非対応リソース（RDS 等）は通常 Vault + Vault Lock に分割保護 | リソースタイプごとに最適な保護機構を選択 |

### 構成選択時の補足

- 「LAG vault 非対応リソースがあるから全て通常 Vault」と画一的に判断するのではなく、リソースごとに最適な保護機構を選ぶアプローチがハイブリッド構成の本質
- 将来的に RDS をはじめとする現時点での非対応リソースが LAG vault でサポートされた場合、ハイブリッド構成 → 発展構成への移行を検討する余地がある
- LAG vault の対応リソースタイプは AWS の機能拡張により変わる可能性があるため、設計時には公式ドキュメントで最新情報を確認すること
- LAG vault 採用時、Amazon EC2 復旧ポイントへのマルウェアスキャンは増分スキャンが利用できずフルスキャンが必要となるため、運用コスト・実行時間の観点も併せて検討することを推奨する（詳細は [05-malware-protection.md](./05-malware-protection.md) を参照）

## リージョン戦略

リージョンは東京（プライマリ）+ 大阪（クロスリージョンコピー先）を基本とする。

| リージョン | 役割 |
|---|---|
| 東京（ap-northeast-1） | 業務アカウントのプライマリリージョン、隔離アカウント、リカバリアカウント |
| 大阪（ap-northeast-3） | 業務アカウントのクロスリージョンコピー先（DR 対応） |

3-2-1 ルールにおける「異なる場所/メディア」の要件を、リージョン分散により満たす。日本国内でデータを保管する要件を持つ金融機関に対しても、東京・大阪の両リージョンを活用することで対応できる。

## 暗号化の前提

本構成では、バックアップデータの暗号化に各アカウント・各リージョンで個別に管理する KMS CMK を使用する。これは、暗号化キーの管理主体をアカウントごとに分離することで、単一の鍵掌握による全データ復号を防ぐ設計である。

### KMS CMK の配置

| 配置場所 | 管理主体 | 用途 |
|---|---|---|
| 業務アカウント（東京）の KMS CMK | 業務アカウントの管理者 | 東京リージョンで取得するバックアップの暗号化 |
| 業務アカウント（大阪）の KMS CMK | 業務アカウントの管理者 | 大阪リージョンへのコピー時の再暗号化 |
| 隔離アカウントの KMS CMK | 隔離アカウントの管理者 | 隔離アカウントへのコピー時の再暗号化 |
| リカバリアカウントの KMS CMK | リカバリアカウントの管理者 | リカバリアカウントへのコピー時の再暗号化 |

クロスアカウント・クロスリージョンコピーの実行時には、コピー先のキーで再暗号化される。これにより、コピー元のキーを管理する主体とコピー先のキーを管理する主体が分離され、攻撃者がコピー元の鍵を掌握してもコピー先のデータは復号できない構造になる。

なお、LAG vault 採用時は AWS 所有キーが使われるため、上記の構成からは外れる（[02-immutability.md](./02-immutability.md) も参照）。

詳細なキーポリシー設計は [04-encryption-strategy.md](./04-encryption-strategy.md) と [06-policy-and-access-control.md](./06-policy-and-access-control.md) を参照する。

## 組織レベルでの一元管理

### バックアップポリシーによる一元管理

前述の通り、AWS Organizations のバックアップポリシーを通じて、組織全体に共通する AWS Backup の設定を Backup アカウントから一元的に管理できる。マルウェアスキャンを含む各種設定もバックアップポリシーで定義し、組織全体に対して一括で適用できる。

各機能の組織レベル設定の詳細は、各機能のリファレンスを参照する:
- マルウェアスキャン: [05-malware-protection.md](./05-malware-protection.md)
- ログ収集（CloudTrail / Config）の集約: [07-log-collection-and-protection.md](./07-log-collection-and-protection.md)
- バックアップ運用の監視: [08-monitoring-and-audit.md](./08-monitoring-and-audit.md)

### SCP による予防的統制

Organizations 管理アカウントから SCP（Service Control Policy）を組織配下のアカウントに適用することで、攻撃者がワークロードアカウントを掌握した場合でも、バックアップやログの破壊的操作を予防的に Deny できる。

ランサム対策の文脈で重要となる SCP の設計（CloudTrail 停止防止、Vault 削除防止、KMS キー削除防止等）は [06-policy-and-access-control.md](./06-policy-and-access-control.md) を参照する。

## 対策効果のサマリ表

本構成の各要素が、ランサムウェア対策としてどのリスクに有効かを整理する。

| 対策要素 | 防御するリスク | 有効なシナリオ |
|---|---|---|
| アカウント分離（業務 / 隔離 / リカバリ） | 業務アカウント侵害時のバックアップデータへの被害・復旧オペレーション妨害 | 攻撃者が業務アカウントの権限を奪取した場合 |
| クロスアカウントコピー（業務 → 隔離） | 業務アカウント単独でのバックアップ消失 | アカウント侵害、内部不正、誤操作 |
| クロスリージョンコピー（東京 → 大阪） | リージョン障害・大規模災害でのデータ消失 | リージョン全体が利用不能になる事態 |
| Vault Lock（隔離アカウント） | バックアップの削除・改ざん | 攻撃者が Vault 操作権限を得た場合 |
| LAG vault の AWS 所有キーによる暗号化（発展構成） | 顧客 KMS キーの削除・無効化によるデータ復号不能 | 攻撃者が KMS キーを悪意で削除する場合 |
| LAG vault の Multi-party approval（発展構成） | 単独の攻撃者による不正復元 | 攻撃者がリストア権限を得た場合 |
| 平時からのリカバリアカウントへの継続的なコピー | 有事の復旧着手の遅延 | 有事の際に即座に復元を開始する必要がある場合 |
| Backup アカウントによる集中管理 | 各業務アカウントでの設定漏れ・不整合 | 組織全体での統一的な保護を担保する必要がある場合 |
| 各アカウント・各リージョン個別の KMS CMK | 単一鍵掌握による全データ復号 | 攻撃者が特定アカウントの KMS キーを掌握した場合 |
| クロスアカウントコピー時の再暗号化 | コピー元の鍵を掌握した攻撃者によるコピー先データの復号 | 業務アカウントが侵害された場合でも、隔離アカウント側のデータは独立した鍵で保護される |
