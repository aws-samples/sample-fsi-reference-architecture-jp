# バックアッププラン設計（取得頻度・対象選定・保持期間・ライフサイクル）

## 概要

本リファレンスは、本スキルが採用するバックアッププラン設計について示す。バックアッププランは AWS Backup の中核となる構成要素であり、組織内のどのリソースを、どの頻度で、どの保管先に、どれくらいの期間保管するかを定義する役割を持つ。

ランサムウェア対策の文脈では、業務影響度別に求められるバックアップ要件（取得頻度・周期・保持期間）と規制要件（保管期間義務等）を踏まえてバックアッププランを適切に設計することが、有事の際の復旧力に直結する。本リファレンスでは、取得頻度の設計、対象リソースの選定、保持期間の設計、ライフサイクル管理、金融機関の文脈での設計判断について整理する。

マルチアカウント構成における配置は [01-multi-account-architecture.md](./01-multi-account-architecture.md)、Vault Lock との関係は [02-immutability.md](./02-immutability.md) を参照する。

## 基盤メカニズム: バックアッププランとバックアップルール

### バックアッププランの構成

AWS Backup のバックアッププランは、1つ以上のバックアップルールから構成される。さらに、バックアッププランに対して保護対象とする AWS リソースを関連付ける「リソース割当」を別途設定することで、バックアップが実行される対象範囲が定まる。

| 構成要素 | 役割 |
|---|---|
| **バックアッププラン (backup plan)** | バックアップ要件を定義する単位。1つ以上のバックアップルールから構成される |
| **バックアップルール (backup rule)** | バックアッププランを構成する個別ルール。取得頻度、バックアップウィンドウ、ライフサイクル、保管先 Vault、コピー先等を定義する |
| **リソース割当 (resource assignment)** | バックアッププランに対して、保護対象とする AWS リソースを関連付ける設定。リソースタイプ単位、リソース ID 単位、タグ条件による絞り込みが可能 |

組織内で複数のバックアップ要件が並存する場合（例: 業務影響度の高いシステムは1時間ごと、低いシステムは日次）、バックアッププランを業務影響度ごとに分けて作成し、それぞれ異なるバックアップルールとリソース割当を設定する運用が可能である。

### Organizations のバックアップポリシーとの関係

本構成では、AWS Organizations のバックアップポリシーを通じてバックアッププランを組織全体に展開する（[01-multi-account-architecture.md](./01-multi-account-architecture.md) 参照）。バックアッププランの設計内容は、Backup アカウントで管理されるバックアップポリシーとして JSON で記述され、組織内の各業務アカウントに適用される際に対応するバックアッププランが作成される。

そのため、本リファレンスで述べる設計判断は、バックアップポリシーの JSON 定義として表現されることになる。

## 取得頻度の設計

### 取得頻度の選択肢

AWS Backup のバックアップルールでは、以下の取得頻度を設定することが可能である。

| 種別 | 概要 |
|---|---|
| **定期バックアップ（コンソール選択肢）** | 1時間ごと、12時間ごと、日次、週次（曜日指定）、月次（日付指定）から選択 |
| **Cron 式による任意のスケジュール** | 最短1時間ごとから任意のスケジュールを Cron 式で指定。AWS CLI / API 経由でも同様に指定可能 |
| **Continuous backup（継続的バックアップ）** | サポートされるリソースタイプで利用可能。Point-in-Time Recovery (PITR) を実現する |

### 取得頻度の設計判断

取得頻度は、業務影響度別に求められるバックアップ要件（許容できるデータ損失の度合いに応じた取得間隔）から決定する。データ損失の許容範囲よりも短い間隔でバックアップを取得することで、有事の際のデータ損失を許容範囲内に収めることが可能となる。

ランサムウェア対策の文脈では、以下の観点で取得頻度を設計することを推奨する。

- **業務影響度の高いシステム**: 時間単位でのバックアップ取得や Continuous backup の活用を検討する。短い取得間隔の要件を満たすことで、データ損失を最小化する
- **業務影響度の低いシステム**: 週単位/月単位等、ビジネス影響・コスト最適化・業務要件のバランスを取りながらバックアップ周期を判断する
- **規制要件で取得頻度が指定されているシステム**: 規制で定められた頻度を遵守する

ランサムウェア攻撃を受けた場合、感染前のクリーンなバックアップに復元する必要があるが、攻撃者がアカウント侵入後に長期間潜伏する事例もあるため、複数世代のバックアップを保持することが重要となる。取得頻度と保持期間の組み合わせで、十分な世代数のバックアップが保持される設計とすることを推奨する。

### Continuous backup の活用

Continuous backup は、サポートされるリソースタイプ（RDS、Aurora、S3 等）で利用可能であり、Point-in-Time Recovery を実現する。秒〜分単位での復旧時点指定が可能となるため、許容できるデータ損失が極めて小さい（短い取得間隔が求められる）システムで活用が可能である。

ただし、Continuous backup は以下の制約があるため、設計時には注意する。詳細な最新仕様は公式ガイドラインの確認を推奨する。

- 保持期間が最大35日に制限される（スナップショットによる定期バックアップは最大100年または無期限）
- Continuous backup はコールドストレージへの移行に対応していない（Continuous backup の最大保持期間が、コールドストレージ移行で求められる最低保管期間を下回るため）
- Continuous backup を有効化したリソースは、定期バックアップとは別に設定が必要となる

## 対象リソースの選定

### リソース割当の方法

バックアッププランへのリソース割当は、以下の方法をサポートする。

| 方法 | 概要 |
|---|---|
| **全リソースタイプを対象** | AWS Backup がサポートする全リソースを対象とする。現存リソースに加え、将来追加されるリソースも自動的に対象となる |
| **リソースタイプ単位での選択** | 特定のリソースタイプ（EC2、RDS、S3 等）を選択し、対象範囲を絞り込む。さらに個別リソースの選択/除外、リソース ID 単位での除外も指定可能 |
| **タグによる絞り込み** | 上記の選択にタグ条件を追加可能。複数タグ指定時は AND 条件で評価される |

タグ条件では、以下の演算子を指定することが可能である。

- `Equals`（完全一致）、`Contains`（部分一致）、`Begins with`（前方一致）、`Ends with`（後方一致）
- 上記各演算子の否定形

例として、`env: prod` AND `role: application` の両方のタグを持つリソースのみをバックアップ対象とする運用が可能である。

### タグベース運用の推奨

本スキルでは、タグベースのリソース割当を採用することを推奨する。理由は以下の通り。

- 新規リソースが作成された際にも、対応するタグを付与すれば自動的にバックアップ対象に含まれる運用が可能となる
- 業務影響度の差分（例: タグ `Backup-Tier: critical` / `Backup-Tier: standard`）に応じた異なるバックアップルールの適用が容易となる
- リソース ID 単位の管理と比べて、運用負担が大幅に軽減される

タグベース運用を採用する際には、組織内でタグ命名規則を標準化することが重要となる。AWS Organizations のタグポリシー機能を併用することで、組織全体でのタグ命名統一が実現可能である。

## 保持期間の設計

### 保持期間の選択肢

バックアップルールで設定可能な保持期間は、以下の通りである。最新の仕様は公式ガイドラインの確認を推奨する。

| 種別 | 設定範囲 |
|---|---|
| **スナップショット（定期バックアップ）** | 1日〜100年、または無期限（Always） |
| **Continuous backup** | 1日〜35日 |

### 保持期間の設計判断

保持期間は、業務要件・規制要件・ランサムウェア対策の観点から設計する。

- **業務要件**: 障害発生時にどの程度過去のバックアップから復旧する可能性があるかを考慮する。直近の障害だけでなく、過去に取得した特定時点のバックアップが必要となるケースもあるため、業務継続性の観点から保持期間を決定する
- **規制要件**: 金融機関では業務記録・監査記録の保管期間が法令や業界規制で定められているケースが多い（例: 7年間の保管義務等）。バックアップが規制対応の一環として位置づけられる場合は、規制要件を満たす保持期間を設定する
- **ランサムウェア対策**: 攻撃者がアカウント侵入後に長期間潜伏する事例もあるため、感染前のクリーンなバックアップを保持できる十分な期間を確保する

### Vault Lock の保持期間との整合

[02-immutability.md](./02-immutability.md) で述べた通り、Vault Lock の最小保持期間・最大保持期間と、バックアップライフサイクルの保持期間は連動する。Vault Lock の保持期間範囲外のバックアップライフサイクル設定は許容されないため、両者を整合させて設計する必要がある。

特に Compliance mode の Vault Lock を採用する場合、grace time 経過後は保持期間の変更ができないため、設計段階で慎重に決定することが重要となる。

## ライフサイクル管理

### ストレージクラス間の移行

AWS Backup のライフサイクル管理では、バックアップをウォームストレージから低コストのコールドストレージへ自動的に移行することが可能である。これにより、長期保管が必要なバックアップのストレージコストを最適化できる。

| ストレージクラス | 用途 |
|---|---|
| **ウォームストレージ** | 通常のバックアップ保管。高速なリストアが可能 |
| **コールドストレージ** | 長期保管向けの低コストストレージ。リストア時間は長いが、ストレージコストは大幅に削減 |

### コールドストレージ移行時の制約

コールドストレージへ移行する際には、以下の制約に注意する。

- コールドストレージには最低保管期間の仕様が定められており、保持期間の設計（ウォームストレージで保管する期間とコールドストレージで保管する期間の合計）はこの仕様を満たす形で行う必要がある
- 一度コールドストレージに移行されたバックアップは、移行設定（コールドストレージへの移行タイミング）を後から変更できない
- コールドストレージ対応のリソースタイプは限定されるため、対象リソースが対応しているか公式ドキュメントで確認する
- Vault Lock のコンプライアンスモードで保護されている Vault では、コールドストレージへの移行設定も Lock の対象となるため、移行設計を含めて慎重に行う必要がある

### ライフサイクル設計の推奨アプローチ

本スキルでは、ライフサイクル設計について以下のアプローチを推奨する。

- **業務継続性の観点で頻繁に参照される直近のバックアップ**: ウォームストレージで保管し、迅速なリストアを可能とする。AWS Backup 公式ドキュメントにおいても、ウォームストレージで一定期間以上保管することが推奨されている
- **規制対応や監査対応で長期保管が必要なバックアップ**: 一定期間後にコールドストレージへ移行し、コスト最適化を図る
- **Vault Lock との整合**: コールドストレージ移行のタイミングと保持期間を Vault Lock の制約と合わせて設計する

## バックアップウィンドウとコピー先

### バックアップウィンドウ

バックアップルールでは、バックアップ実行のタイミングを以下の3要素で制御することが可能である。

- **開始時刻**: バックアップを開始する時刻
- **開始猶予時間**: 開始時刻から実行が遅延した場合の許容時間
- **完了猶予時間**: バックアップ完了までの許容時間

業務システムの繁忙時間帯を避けてバックアップを実行する設計や、夜間バッチ処理との兼ね合いを考慮した設計が可能となる。

### 開始タイミングの仕様と金融機関にとっての含意

AWS Backup におけるバックアップ実行は、設定した開始時刻ちょうどに開始されるわけではなく、開始時刻から開始猶予時間（開始ウィンドウ）内のどこかで開始される仕様となっている。開始猶予時間のデフォルトは8時間であり、設定可能な最小値は60分である。この仕様は、AWS Backup のバックアップポリシー（バックアッププラン）によるスケジュール実行だけでなく、StartBackupJob API によるオンデマンド実行にも同じく適用される。

加えて、RDS をはじめとする AWS データベースサービスや FSx では、メンテナンスウィンドウの直前・期間中はバックアップが開始されない仕様であり、開始ウィンドウの遅延に加えてさらに開始制約が加わる場合がある。対象サービスや具体的な制約は機能拡張により変わる可能性があるため、AWS Backup 公式ドキュメントの [Backup plan options and configuration](https://docs.aws.amazon.com/aws-backup/latest/devguide/plan-options-and-configuration.html) の最新版を参照することを推奨する。

これらの仕様は、金融機関が以下のような厳密な業務要件を持つ場合に課題となり得る。

- 業務システムの静止点（夜間バッチ後の整合性が取れた状態等）を厳密に捉える要件
- 「業務時間外の特定時間帯に必ず取得を完了させる」等の時間制約のあるシステム要件
- 関連する複数システムを同時刻に静止状態にしてバックアップを取得したい要件

### 対処方針の選択肢

執筆時点のAWS Backup の機能で開始タイミングを厳密に制御することは仕様上難しいため、上記の要件がある場合は以下の選択肢を組み合わせて設計検討することを推奨する。

- **Continuous backup（PITR）の活用**: サポートされるリソースタイプであれば、特定の静止点を設けずに任意時点へ復元することが可能となるため、開始タイミング厳密性の課題自体を回避することができる
- **AWS Backup と各サービス固有のバックアップ機能の併用**: AWS Backup のスケジュール仕様で要件を満たせない場合、各サービスが提供するネイティブのバックアップ機能（RDS の自動バックアップ、各種スナップショット機能等）との併用も含めた設計検討を行う。ただし、本スキルが推奨するマルチアカウント構成・イミュータブル化・組織横断管理の効果は AWS Backup を経由する範囲で得られるため、サービス固有機能を併用する場合は保護機構の整合性を別途確認する必要がある

### 補足: 静止点バックアップの運用整理

ここで述べた開始タイミングの仕様は AWS Backup 固有の課題ではなく、AWS の各サービスのネイティブなスナップショット機能を直接利用する場合も、本質的には類似の整理が必要となる。アプリケーション整合性のある静止点を取得するためには、「業務側のジョブ完了 → 業務アプリケーションを静止状態にする → バックアップを取得する」という運用順序が前提となり、これは AWS Backup を経由する場合もネイティブのスナップショット機能を使う場合も同様である。業務側ジョブの完了との連携設計等が、いずれの場合も本質的に求められる。

ただし、AWS Backup を経由する場合は開始ウィンドウの仕様により API 実行時刻からバックアップ実開始までに時間差が生じることがあるため、業務システムの静止状態を維持する時間がその分伸びる可能性がある。厳密な業務影響の許容範囲がある場合は、開始ウィンドウを許容範囲内に設定する、業務側ジョブ完了との連携を取る等の運用設計を行うことを推奨する。

なお、本論点が実際にどの程度問題になるかは、保護対象のリソースタイプによって大きく異なる。

- **データベースサービス（RDS、Aurora、S3 等の PITR 対応サービス）**: Continuous backup（PITR）を活用することで、特定時刻のスケジュール実行を前提とせず、任意時点への復元が可能となるため、開始ウィンドウの遅延リスクに対応することが可能となる。ただし、PITR が提供するのはデータベースのトランザクション整合性に基づく復元であり、業務処理サイクル単位での整合性確保には別途業務側での連携設計を要する場合がある
- **ステートレスに設計された EC2 等のコンピュートリソース**: AWSのベストプラクティスの通り永続データを外部サービス（RDS、S3 等）に保管する設計を採用している場合は、コンピュートリソース側のスナップショット時点の静止点厳密性は本質的に論点とならないことが考えられる。クラウドネイティブな設計を推奨する観点でも、このパターンが望ましい
- **EFS / FSx 等のファイルストレージや、永続データを保持する EC2**: PITR 対応外のため、業務側ジョブ完了との連携や運用での静止状態確保が依然として必要となる。本論点が実際の運用上の課題となる主な対象はこのカテゴリになるものと想定する。

リソースタイプごとに本論点の影響度を整理し、影響度の高いリソースに対しては設計上の対処方針を組み込むアプローチを推奨する。

### コピー先の設定

バックアップルール内のコピー設定（Copy Action）により、バックアップの取得と同時にクロスアカウント・クロスリージョンのコピーを作成することが可能である。本スキルが採用するマルチアカウント構成では、業務アカウントでの取得と同時に、隔離アカウント・大阪リージョンへのコピーが作成される設計となる（詳細は [01-multi-account-architecture.md](./01-multi-account-architecture.md) を参照）。

## 金融機関の文脈での設計判断

### 業務影響度に応じたバックアッププラン分割

金融機関の業務システムは多岐にわたり、業務影響度の差分が大きいケースが多い。例えば、勘定系システムは秒〜分単位の取得間隔が求められる一方、社内管理用システムは日次バックアップで十分な場合がある。

このような環境では、単一のバックアッププランで全リソースを統一的に取得するよりも、**業務影響度別に複数のバックアッププランを作成**し、それぞれ異なる取得頻度・保持期間を設定する設計を推奨する。具体的には以下のような構成が考えられる。

- 業務影響度: 高（タグ `Backup-Tier: critical`） → Continuous backup または1時間ごと取得、長期保管
- 業務影響度: 中（タグ `Backup-Tier: standard`） → 12時間ごとまたは日次取得、中期保管
- 業務影響度: 低（タグ `Backup-Tier: low`） → 日次または週次取得、短〜中期保管

業務影響度の判定は、組織内の業務継続計画（BCP）と照らし合わせて決定することを推奨する。

### 規制要件への対応

金融機関では業務記録・取引記録の保管期間が法令や業界規制で定められているケースが多い。バックアップが規制対応の一環として位置づけられる場合、以下の点を設計に反映する。

- 規制要件で定められた保管期間を満たす Vault Lock の保持期間設定
- Vault Lock コンプライアンスモードによる改変・削除耐性の確保（[02-immutability.md](./02-immutability.md) 参照）
- 監査証跡として活用可能な状態でのバックアップ取得

ただし、特定の規制条文への適合性判定は本スキルのスコープ外であり、組織の規制対応部署・コンプライアンス部署と連携して判断することを推奨する。

### コスト最適化と業務要件のバランス

バックアッププランの設計では、以下のトレードオフを意識する。

- 取得頻度を高くする / 保持期間を長くする → 復旧力・規制対応力が高まるが、ストレージコストが増加する
- ライフサイクルでコールドストレージへ移行する → コスト削減できるが、リストア時間が長くなる
- 業務影響度別にバックアッププランを分割する → 必要十分な保護を実現しつつ、コスト最適化が可能となる

金融機関の文脈では、業務継続性・規制対応を最優先とした上で、コスト最適化を組み込むアプローチが望ましい。

## 対策効果のサマリ表

本リファレンスで扱う各設計要素が、ランサムウェア対策としてどのリスクに有効かを整理する。

| 設計要素 | 防御するリスク | 有効なシナリオ |
|---|---|---|
| 業務要件に応じた取得頻度の設計 | データ損失（許容を超えるデータの喪失） | 障害・攻撃発生時に許容範囲を超えるデータ損失が発生するリスクを軽減 |
| 複数世代のバックアップ保持 | 攻撃者の長期潜伏による感染済みバックアップしか存在しない事態 | 攻撃者が侵入から数週間〜数か月後にランサムウェアを実行する場合 |
| Continuous backup の活用 | 短い取得間隔が求められるシステムでのデータ損失 | 業務影響度の極めて高いシステムでの分単位の復旧要件 |
| タグベースのリソース割当 | バックアップ対象漏れ（新規リソースが保護されない） | 組織内でリソースの増減が頻繁に発生する場合 |
| 業務影響度別のプラン分割 | 全リソース統一プランによるコスト増・保護不足 | 業務影響度の差分が大きい組織での効率的な保護 |
| 規制要件を満たす保持期間設計 | 規制対応上のバックアップ不足 | 法令・業界規制で保管期間が定められている業務システム |
| ライフサイクルによるコールドストレージ移行 | 長期保管時のストレージコスト膨張 | 規制対応で長期保管が必要なバックアップ |
