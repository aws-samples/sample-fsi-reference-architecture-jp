# 検知の設計(サービス影響の検知とセキュリティ攻撃の検知)

## 概要

本リファレンスは、本スキルが推奨するランサムウェア対策の検知の設計について示す。ここでの「検知」とは、ランサム被害・脅威の兆候に気づき、アラート(通知)を起点としてインシデント対応プロセスを開始するまでを指す。検知した事象を深掘りして分析・調査する段階は [02-log-analysis-and-investigation.md](./02-log-analysis-and-investigation.md) で扱う。

検知は大きく 2 つの観点で構成される。1 つはサービスへの影響(利用者・サービスへの影響)を捉える「サービス影響の検知」、もう 1 つは攻撃・侵入・ウイルス混入そのものを捉える「セキュリティ攻撃の検知」である。前者は「何かが、どこで起こった」ことを把握する起点となり、後者は原因可能性まで含めた把握につながる。両者は段階的な切り分けの関係にあるが、その順序は固定ではない(セキュリティ攻撃の検知がサービス影響の検知より先に立つこともある)。

本リファレンスでは、サービス影響の検知の考え方(監視の深さ)、セキュリティ攻撃の検知の手段(Amazon GuardDuty の保護プラン、サードパーティ製品)、アラート発生後に外部攻撃(ランサム等)かを見極める原因切り分けオペレーション(利用者による手動確認)、検知の集約・委任管理、そしてアラートを起点としたインシデント対応プロセスの開始について整理する。具体的な監視・検知手法そのものの設計詳細は、本スキルのスコープ(ランサムウェア対策)を超えるため、AWS 公式ガイドラインへの参照に委ねる。

なお、本リファレンスが前提とする検知の枠組みは、NIST Cybersecurity Framework の検知機能における「継続的な監視による検知」、および AWS のインシデント対応の考え方における「検知(Detection)」の段階に対応する。検知した事象の分析は次段の「分析」に対応する。

ログの収集・保護の設計は保護(Protect)フェーズのスコープであり、本スキルは「収集済みログを活用する」前提に立つ。アカウント構成の設計も保護(Protect)フェーズのスコープであり、本リファレンスは「検知の集約・委任管理」の観点でそれを活用する。

## 基盤となる考え方: アラートを起点としたインシデント対応プロセスの開始

検知の主要素はアラート(通知)である。サービス影響の検知・セキュリティ攻撃の検知のいずれであっても、検知した事象をアラートとして関係者に通知し、それを起点としてインシデント対応プロセスを開始する。

アラートによる検知の精度には本質的な難しさがある。インシデントが発生したか、進行中か、将来発生するかを完全な確実性をもって判定することは常に可能とは限らない。検知の仕組みはベースラインからの逸脱・既知のパターン・内外からの通知に基づいて成り立っており、攻撃者の手法・技術・手順(TTPs)は時間とともに変化するためである。また、アラート自体は「何かが起きた」ことを示すが、それが外部攻撃(ランサム等)によるものか、通常の障害・運用上の事象によるものかまでは、アラートの内容だけでは判別できないことが多い。したがって、アラートによる自動検知を起点としつつ、利用者による手動確認を中心とした原因切り分けオペレーションを組み合わせ、外部攻撃かどうかを見極める設計とすることが望ましい。

## サービス影響の検知

### 設計の考え方

サービス影響の検知は、ランサム被害等によってサービス・利用者に影響が生じていることを迅速に捉えることを目的とする。これはセキュリティに限定した話ではなく、一般的なサービス監視の設計・運用によって実現する事項である。この検知の時点では原因がセキュリティ攻撃であるかは判明しないが、「何かが、どこで起こった」ことを把握できることが、その後の調査・対応に向けた重要な起点となる。

ランサム感染のような事象は、必ずしもセキュリティ検知で最初に顕在化するとは限らず、サービスの異常(応答低下・エラー増加・停止等)として先に現れることがある。そのため、セキュリティ検知とは別軸で、サービス影響そのものを捉える監視を備えておくことに意味がある。

### 監視の深さ

サービス影響を迅速に検知できるかは、監視がどの深さまで到達しているかに依存する。リソースの稼働状況のみを見る監視では、利用者から見たサービスの異常を捉えきれないことがある。以下のように、監視の深さを段階的に捉えて設計することが望ましい。

| 監視の深さ | 捉えられるもの(例) |
|---|---|
| リソース監視 | CPU・メモリ・ディスク・接続数等、インフラリソースの稼働状況 |
| サービス監視 | エラー率・レイテンシ・スループット等、サービスとしての稼働状況 |
| 外形監視 | 外部から実際にエンドポイント・画面へアクセスし、到達性・応答・画面表示を確認する(Amazon CloudWatch Synthetics 等) |
| アプリケーションレベルの監視(業務指標) | ログイン数・取引数・契約数・閲覧数等、業務が正常に流れているかを示す業務指標 |

リソース監視のみで止まっていると、リソースは正常に見えても利用者にはサービスが提供できていない、という状況を見逃す可能性がある。サービス監視・外形監視・アプリケーションレベルの監視(業務指標)まで組み合わせることで、利用者影響をより確実に捉えることができる。

### 金融機関の文脈: 重要度に応じた監視レベルの設計

すべてのシステムを一律の監視レベルで設計するのではなく、システムの重要度に応じて監視レベルを適切にラベリングし、重要システム(基幹系・重要業務系等)とそれ以外で監視の手厚さ・検知のレベルを段階的に設計することが望ましい。これにより、限られた運用リソースを重要システムに重点配分しつつ、有事のサービス影響検知の実効性を高めることができる。

この「システムの重要度に応じて要求レベルを段階的に設定する」考え方は、IPA(独立行政法人 情報処理推進機構)の非機能要求グレードでも示されている(重要なシステム=モデルシステムを選定し、重要項目から段階的に非機能要求レベルを決定する手順。可用性・運用/保守性といった監視運用に関わる項目を含む)。

### 具体的な監視手法の参照先

サービス影響の検知に用いる具体的な監視手法(リソース監視・サービス監視・外形監視・アプリケーションレベルの監視)の設計詳細は、セキュリティを主題とする本スキルのスコープを超えるため、本スキルでは深掘りせず、以下の AWS 公式ガイドラインへの参照に委ねる。

| 位置づけ | ガイドライン |
|---|---|
| 監視・可観測性の考え方の中核 | AWS Well-Architected Framework 運用上の優秀性の柱「Implement observability」。メトリクス・ログ・トレースを軸に、KPI 定義(業務指標の監視に相当)・アプリケーションテレメトリ(サービス監視に相当)・ユーザー体験テレメトリ(外形監視に相当)・依存関係テレメトリ・分散トレーシングを包括的に扱う |
| 監視サービスの選定指針 | Choosing an AWS monitoring and observability service(AWS Decision Guide)。Amazon CloudWatch 等の使い分けの指針 |
| サービス単位の監視レシピ | AWS Observability Best Practices。Amazon EC2・Amazon ECS 等のサービス単位の監視の実践 |
| 金融機関の文脈(参考) | IPA「システム構築の上流工程強化(非機能要求グレード)」。重要度に応じた監視レベル設計の考え方の参考 |

URL は「参考: 公式ドキュメント」セクションに整理する。

## セキュリティ攻撃の検知

### 設計の考え方

セキュリティ攻撃の検知は、不審なアクティビティや不審なファイル等、悪意のある攻撃・ウイルス混入を捉えることを目的とする。サービス影響の検知が「影響(結果)」を捉えるのに対し、こちらは「攻撃・侵入(原因可能性)」を捉える点で、影響だけでなく原因可能性まで含めた検知を実現する。

検知の手段は、(1) AWS マネージドサービスによる検知、(2) サードパーティ製品による検知、の複数の層があり、これらを組み合わせて多角的に攻撃を捉える。加えて、これらの自動検知でアラートが発生した際に、それが外部攻撃によるものかを見極める原因切り分けオペレーション(利用者による手動確認)を組み合わせる。

### Amazon GuardDuty による検知

Amazon GuardDuty は、AWS 環境における脅威検知のマネージドサービスであり、ランサムウェア対策の検知に活用できる。GuardDuty を有効化すると、追加コストなしで以下が自動的に動作する。

- **基盤検知(Foundational threat detection)**: AWS CloudTrail 管理イベント・VPC フローログ・DNS ログを自動的に取り込み、脅威を検知する。
- **拡張脅威検知(Extended Threat Detection)**: 複数のデータソース・複数のリソース・時間をまたぐ多段階の攻撃シーケンスを検知する。S3 Protection を有効化すると、Amazon S3 リソースに影響する多段階攻撃の検知精度が向上する。

加えて、ユースケースに応じて任意で有効化する保護プラン(protection plans)が用意されている。ランサムウェア対策の検知に関連が深い保護プランとして、以下のようなものが挙げられる。

| 保護プラン | 概要 |
|---|---|
| Malware Protection for EC2 | Amazon EC2 インスタンスにアタッチされた Amazon EBS ボリュームをスキャンし、マルウェアの存在を検知する(オンデマンド実行も可能) |
| Malware Protection for S3 | Amazon S3 バケットに新規アップロードされたオブジェクトのマルウェアを検知する(オンデマンド実行も可能) |
| Runtime Monitoring | Amazon EKS・Amazon EC2・Amazon ECS(AWS Fargate を含む)の OS レベルのイベントを監視し、ランタイムの脅威を検知する |
| S3 Protection | Amazon S3 バケットに対するデータの持ち出し・破壊の試み等のリスクを検知する |

保護プランは追加・変更されることがあり、また各保護プランの対応リソース・検知できる脅威の種類・クォータ等の詳細仕様も機能拡張により変わる可能性がある。そのため、設計提案・評価の際は AWS GuardDuty 公式ドキュメントの最新版で現行の保護プランと対応範囲を確認した上で提示することを推奨する。どの保護プランを有効化すべきかは、保護・監視対象のリソースや脅威モデルによって異なる。

### サードパーティ製品による検知

サードパーティ製品(EDR 等)を Amazon EC2 上で運用し、セキュリティ攻撃を検知することも可能である。金融機関では既存のセキュリティ製品が運用されているケースが多く、AWS ネイティブの検知(GuardDuty 等)とサードパーティ製品を併用する選択肢を、お客様の既存運用・方針を尊重した上で提示する。

### 検知対象とするリソースの考え方

ランサムウェア対策の検知では、どのリソースを対象とするかを、リソースの性質に応じて整理する。本スキルでは、お客様のワークロード(アプリケーション)やデータが直接稼働・保管され、マルウェア感染やランサム被害のチェック対象となるリソースをフォーカスとする。リソースは大きく次の 3 つに整理できる。

- **コンピューティング(Amazon EC2、Amazon ECS、Amazon EKS、AWS Fargate 等)**: マルウェアの実行・感染が起こりうる実行環境であり、ランタイムの脅威検知・マルウェアスキャンの主な対象となる。AWS Fargate はホスト OS・基盤を AWS が管理するが、その上で稼働するコンテナ内の実行環境・データは引き続きお客様のワークロードであり、感染・侵害のチェック対象となる点で他のコンピューティングと同様に扱う。
- **ストレージ(Amazon S3、Amazon EFS、Amazon FSx 等)**: データの暗号化・破壊・持ち出しの対象となる。Amazon S3 はマルウェアスキャン・不審アクティビティ検知の直接の対象となる。Amazon EFS・Amazon FSx 等の共有ファイルストレージは、それ自体を直接スキャンするのではなく、マウント元のコンピューティング(EC2・コンテナ)の検知と、ログを活用した分析・調査([02-log-analysis-and-investigation.md](./02-log-analysis-and-investigation.md))で不審アクセスを捉える形でカバーする。
- **マネージドサービス(Amazon RDS、Amazon Aurora、Amazon DynamoDB、Amazon SQS、AWS Lambda 等)**: ユーザーが OS・ランタイムを管理せず、ウイルスファイルが実行される環境ではないため、ランタイム的なマルウェア検知(感染チェック)は本スキルの対象外とする。データ自体が暗号化・破壊されるリスクはありうるが、その対策はデータ保護(保護(Protect)フェーズ)や、ログを活用した分析・調査での不審アクセス検知で捉える。なお、マネージドサービスに対しても、サービスによっては不審なアクセスを検知する仕組みが提供される場合がある(例として、Amazon GuardDuty の RDS Protection は RDS / Aurora のログインアクティビティの異常を検知する。マルウェアスキャンではなく不審アクセスの検知である)。

どのリソースがマルウェアスキャンや各種脅威検知の対象となるかは、AWS サービスの機能拡張により変わっていく。**マルウェアスキャンの直接の対象となるのは、執筆時点では Amazon EC2(EBS)と Amazon S3 である**が、対象リソース・検知の種類は今後拡張されうるため、設計提案・評価の際は AWS GuardDuty 公式ドキュメントの最新版で現行の対応範囲を確認した上で提示する。

### アラート発生後の原因切り分けオペレーション(手動確認)

サービス影響の検知・セキュリティ攻撃の検知のいずれかでアラートが発生した際、それが外部攻撃(ランサム等)によるものか、通常の障害・運用上の事象(アプリケーションの不具合、想定内の負荷増、設定ミス等)によるものかを、アラートの内容だけで直ちに判別できるとは限らない。この判別を担うのが、利用者による手動確認を中心とした原因切り分けオペレーションである。

手動確認は、日常的に独立して実施する予防的なモニタリングとしては現実的ではない(すべてのシステムを常時人手で確認し続けることには限界がある)。有効に機能するのは、**サービス影響検知・セキュリティ攻撃検知のアラートが発生した後、外部攻撃の可能性を判断するための切り分けオペレーション**としての位置づけである。整備すべき観点は、誰が実施するか(一次対応者・当直・SOC 等)、どのタイミングで実施するか(アラート発生後何分以内か等)、どのような手順で確認するか、の 3 点である。

具体的な原因切り分けの手順の例:

- Web システムにブラウザで実際にアクセスして動作を確認する(Web サイトに脅迫文が表示されていないか、想定外のエラー画面になっていないか等)
- SSH や AWS Systems Manager のセッションマネージャを使ってサーバにログインし、不審なファイルの有無を確認する(暗号化された不審なファイルがサーバ内に存在しないか等)

ランサムウェア攻撃による事象かどうかを判断する観点としては、暗号化ファイルの発生、不審なプロセス・プログラムの実行、怪しいドメイン・国外への外部通信の有無等が挙げられる。これらの観点を、アラート発生時に実施する切り分け手順としてあらかじめ整備しておくことで、外部攻撃か否かの判断を迅速化できる。

## 検知の集約・委任管理

マルチアカウント環境では、各アカウントで個別に検知結果を確認するのではなく、セキュリティアカウントに集約する形で組織内の検知・管理を一元化することが望ましい。これにより、組織横断で検知結果を一元的に可視化でき、検知の見逃しや対応の遅れを防ぐことができる。

- Amazon GuardDuty は AWS Organizations による委任管理者(delegated administrator)を指定することで、組織内のアカウントの検知結果を集約・一元管理できる。AWS Organizations を用いた管理が推奨される。
- AWS Security Hub を併用することで、GuardDuty を含む複数のセキュリティサービスの検知結果を集約し、組織横断で優先度付け・可視化することができる。

アカウント構成そのものの設計(セキュリティアカウントや Log Archive アカウントの位置づけ等)は保護(Protect)フェーズで扱うため、本リファレンスでは扱わない。アカウント構成の検討が必要な場合は、保護(Protect)フェーズのスキル(fsi-ransomware-protect)の活用をお客様にガイダンスする。本リファレンスは、既存のアカウント構成を前提として「検知をどこに集約し、どう一元管理するか」の観点に絞る。

## 金融機関の文脈での設計判断

### 検知態勢の段階的な整備

検知態勢の整備は一度にすべてを実現しようとすると負荷が大きい。対応の容易さ・既存環境への影響・リスク低減効果を踏まえ、段階的に整備することが現実的である。たとえば、既存環境への影響が小さく即効性のある対策(GuardDuty の有効化、重要システムへの監視レベルの設定等)から着手し、組織横断での検知集約・一元管理のような影響範囲が広い取り組みは段階的に位置づける、といった考え方となる。具体的なフェーズ分類の判断軸は本スキルの Constraints(DT-C12)に従い、具体的な期間の数値は提示しない。

### 監視の網羅性と運用負荷のバランス

監視・検知を手厚くするほど運用負荷・コストは増す。重要度に応じた監視レベルの設計(前述)により、重要システムに重点を置きつつ、組織全体として持続可能な運用負荷に収める設計が望ましい。

### 規制対応・監査対応の観点

検知態勢の整備状況は、内部監査・外部監査・規制当局による検査の際に問われることがある。ただし、特定の規制条文への適合性判定は本スキルのスコープ外であり、組織の規制対応部署・コンプライアンス部署と連携して判断することを推奨する。

## 対策効果のサマリ表

本リファレンスで扱う各設計要素が、ランサムウェア対策としてどのリスクに有効かを整理する。

| 設計要素 | 防御するリスク | 有効なシナリオ |
|---|---|---|
| サービス影響の検知(監視の深さの確保) | サービス影響・利用者影響の見逃し | リソースは正常に見えても利用者にサービスが提供できていない状況の早期把握 |
| 重要度に応じた監視レベルの設計 | 重要システムでの検知漏れ、運用リソースの分散 | 基幹系・重要業務系での迅速な影響検知 |
| GuardDuty による攻撃検知 | 攻撃・侵入・マルウェア混入の見逃し | EC2/S3 等への攻撃、マルウェア感染、多段階攻撃の検知 |
| サードパーティ製品との併用 | AWS ネイティブ検知の範囲外の脅威 | 既存 EDR でのチェックが必須の環境、二重チェック体制 |
| アラート発生後の原因切り分け(手動確認) | アラートが外部攻撃によるものか判断できず対応が遅延するリスク | サービス影響・攻撃検知のアラート発生後、脅迫文の表示・暗号化ファイルの発生等を直接観測して外部攻撃かを判断する |
| 検知の集約・委任管理 | 各アカウントでの個別確認による見逃し・対応遅延 | 組織横断での検知結果の一元可視化 |
| アラート起点のインシデント対応開始 | 検知から対応開始までの遅延 | 検知を確実に対応プロセスへつなげる |
