総合評価

お客様の検知・分析態勢は、Amazon CloudWatch による基本的なリソース・メトリクス監視や、一部アカウントでの Amazon GuardDuty の有効化など、検知の出発点となる仕組みは整いつつある。サービス影響に気づくための土台は部分的に存在している。

一方で、ランサム対策の観点では不足が見られる。サービス監視がリソース監視中心にとどまり、外形監視・アプリケーションレベルの監視(業務指標)まで到達していないため、利用者影響の検知に漏れが生じうる。また、GuardDuty の保護プランの有効化・対象リソースのカバレッジが未統一で、攻撃検知に空白が残る。さらに、検知結果が各アカウントに分散し、セキュリティアカウントへの集約・一元管理ができていないため、組織横断での見逃し・対応遅延のリスクがある。

早急に着手すべきは、サービス監視の深さの点検・拡充と、GuardDuty の保護プランの有効化・カバレッジ確保である。これらは既存環境への影響が小さく即効性が高い。検知・分析の集約・一元管理は影響範囲が広いため、段階的に整備することを推奨する。

評価項目の詳細

1
サービス影響検知の整備
一部対応

現状の整理

Amazon CloudWatch で主要リソースのメトリクス・ログ監視を実施している。外形監視は一部の公開系システムのみで、アプリケーションレベルの監視(業務指標。ログイン数・取引数等)は重要システムでも未整備である。

判定の根拠

サービス影響に気づくための監視は存在するが、監視の深さがリソース監視・一部のサービス監視にとどまり、利用者視点での影響を捉える外形監視・業務指標の監視まで到達していないため「一部対応」と判定した。

不足している要素 / なぜそれが問題か

  • 外形監視が公開系の一部に限定され、重要システムを網羅していない
  • アプリケーションレベルの監視(業務指標)が未整備で、リソースが正常でも利用者にサービスが提供できていない状況を見逃しうる
  • システムの重要度に応じた監視レベルのラベリングがなく、監視の重点配分ができていない

想定されるリスクシナリオ

ランサム被害でサービスが実質停止 → リソースメトリクスは正常範囲のまま → 利用者からの問い合わせで初めて影響に気づき、検知が遅延する

2
セキュリティ攻撃検知の整備
一部対応

現状の整理

Amazon GuardDuty を一部アカウントで有効化している。保護プランの有効化状況や、各製品が対象とするリソースのカバレッジは組織内で統一されていない。

判定の根拠

攻撃検知の仕組みは導入されているが、有効化範囲・保護プラン・対象リソースのカバレッジに空白があり、組織全体で一貫した攻撃検知ができていないため「一部対応」と判定した。

不足している要素 / なぜそれが問題か

  • GuardDuty が一部アカウントのみで、未有効化のアカウントに検知の空白がある
  • ランサム関連の保護プラン(Malware Protection for EC2 / S3、Runtime Monitoring、S3 Protection 等)の有効化が未統一
  • 対象リソースに対する検知カバレッジが整理されていない

想定されるリスクシナリオ

GuardDuty 未有効化のアカウントで不審なアクティビティが発生 → 攻撃の兆候が検知されず、被害が拡大してから判明する

3
原因切り分けオペレーション(手動確認)の整備
NG

現状の整理

サービス影響検知・セキュリティ攻撃検知のアラートが発生した際に、それが外部攻撃(ランサム等)によるものかを判断するための手動確認(Web サイトの脅迫文の有無、サーバ上の暗号化ファイル・不審プロセス・不審な外部通信の確認)について、整備された手順は存在せず、対応は属人的である。

判定の根拠

アラート発生後に外部攻撃かどうかを判断する原因切り分けの手順が整備されておらず、誰が・どのタイミングで実施するかも定まっていないため「NG」と判定した。

不足している要素 / なぜそれが問題か

  • 原因切り分けの観点・手順がチェックリスト化されていない
  • 誰が・どのタイミングで実施するかが定まっておらず、属人的で再現性がない
  • アラート発生後、外部攻撃かどうかの判断が遅れ、対応開始が遅延するリスクがある

想定されるリスクシナリオ

サービス異常のアラートが発生 → 外部攻撃か通常の障害かを判断する手順がなく、対応方針の決定が遅れる → その間に暗号化が進行してから発覚する

ログを活用した分析基盤
OK

現状の整理

調査に必要なログは収集・保管されており、参照・クエリ可能な状態にある。検知した事象を分析・調査する基盤は確保されている。

判定の根拠

収集済みログを活用して分析・調査できる状態にあり、検知から分析への接続が成立しているため「OK」と判定した。なお、分析の高度化(Amazon Detective / SIEM on Amazon OpenSearch Service の本格活用)は今後の検討余地がある。

不足している要素 / なぜそれが問題か

  • (現状は充足) 分析の高度化・可視化は今後の余地として残る
  • 分析ハードルが高い場合のフォレンジックベンダ連携の事前準備は別途整理が望ましい

想定されるリスクシナリオ

検知した事象について、収集済みログを参照して影響範囲を分析でき、初動の絞り込みが可能

5
検知の集約・可視化
NG

現状の整理

検知結果は各アカウントで個別に確認しており、セキュリティアカウントへの集約・委任管理は行われていない。組織横断での一元的な可視化ができていない。

判定の根拠

検知結果が分散し、組織横断で一元的に把握する仕組みがないため「NG」と判定した。アカウント数が多いほど見逃し・対応遅延のリスクが高まる。

不足している要素 / なぜそれが問題か

  • GuardDuty / Security Hub の委任管理者による検知結果の集約が未実施
  • 各アカウントを個別に確認する運用で、見逃し・対応遅延が生じやすい
  • 組織横断での優先度付け・可視化ができていない

想定されるリスクシナリオ

あるアカウントで検知が上がる → 集約された可視化がなく、担当者が個別アカウントを見るまで気づけない → 対応開始が遅延する
