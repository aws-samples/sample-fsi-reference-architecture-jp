ABOUT THIS REPORT

本レポートは、ランサムウェア対策の 4 フェーズ（保護（Protect）・検知（Detect）・対応（Respond）・復旧（Recover））のうち 検知（Detect）フェーズ を対象としている。保護・対応・復旧の各フェーズは別途扱う。

本レポートは、AWS 金融リファレンスアーキテクチャ日本版で公開されているランサムウェア対策向けの SKILL を用いて、お客様の既存の検知・分析態勢に対する改善ロードマップを整理したものである。「評価結果レポート」で示した不足ポイントに対する具体的な実装ロードマップ (短期・中期・長期) と、各施策の設計判断・期待される効果をまとめている。

短期 既存環境への影響が小さく即効性のある対策

1
サービス監視の深さの点検・拡充
短期

位置づけ

サービス影響を迅速に検知できるかは、監視の深さに依存する。リソース監視のみでは利用者影響を捉えきれないため、サービス監視・外形監視・アプリケーションレベルの監視(業務指標)まで点検・拡充する。既存の監視基盤を活かせるため即効性が高く、後続の検知設計の土台となる。

設計内容

監視の深さ拡充の方向
リソース監視(現状で実施) CPU・メモリ・I/O・接続数等を継続
サービス監視エラー率・レイテンシ等のサービス稼働指標を追加
外形監視利用者視点の到達性・応答監視を重要システムへ拡大
アプリケーションレベルの監視(業務指標)ログイン数・取引数等の業務指標を監視対象に追加

具体的な監視手法の設計は、セキュリティを主題とする本スキルのスコープを超えるため、AWS 公式ガイドライン(Well-Architected の可観測性、監視サービスの選定指針、Observability Best Practices 等)を参照する。

期待される効果

シナリオ現状改善後
ランサム被害でサービスが実質停止リソースは正常範囲に見え、利用者影響に気づけない外形監視・業務指標の監視で利用者影響を即時検知
2
GuardDuty の有効化・保護プランの整備
短期

位置づけ

セキュリティ攻撃そのものを捉えるため、Amazon GuardDuty を組織全体で有効化し、ランサム対策に関連が深い保護プランを対象リソースのカバレッジを踏まえて有効化する。有効化は既存環境への影響が小さく即効性が高い。

設計内容

GuardDuty を有効化すると、基盤検知(CloudTrail / VPC フローログ / DNS ログの自動分析)と拡張脅威検知(多段階攻撃の検知)が追加コストなしで動作する。加えて、以下のようなランサム関連の保護プランを有効化する。

保護プラン(例)概要
Malware Protection for EC2EC2 にアタッチされた EBS ボリュームのマルウェアを検知
Malware Protection for S3S3 へ新規アップロードされたオブジェクトのマルウェアを検知
Runtime MonitoringEKS / EC2 / ECS(Fargate)の OS レベルイベントを監視
S3 ProtectionS3 へのデータ持ち出し・破壊の試みを検知

保護プランは追加・変更されることがあり、対応リソースも機能拡張により変わる可能性があるため、有効化の判断時には公式ドキュメントの最新版で現行の保護プランと対応範囲を確認する。サードパーティ製品(EDR 等)の併用も、既存運用・方針を尊重して検討する。

期待される効果

シナリオ現状改善後
未有効化アカウントで不審なアクティビティが発生検知の空白があり、攻撃の兆候に気づけない組織全体で攻撃の兆候をアラートとして検知
3
重要システムの監視レベルのラベリング
短期

位置づけ

限られた運用リソースを重要システムに重点配分するため、システムの重要度に応じて監視レベルをラベリングする。重要システム(基幹系・重要業務系等)とそれ以外で監視の手厚さ・検知のレベルを段階的に設計する。

設計内容

システムの重要度を分類し、重要度に応じて監視の深さ・アラートのしきい値・通知先を段階的に設定する。「システムの重要度に応じて要求レベルを段階的に設定する」考え方は、IPA の非機能要求グレード等でも示されている。

期待される効果

シナリオ現状改善後
重要システムでの異常発生一律の監視で重要システムの異常が埋もれる重要システムに重点配分した監視で優先的に検知

中期 個別に進められる対策

4
原因切り分けオペレーション(手動確認)の運用手順の整備
中期

位置づけ

サービス影響検知・セキュリティ攻撃検知のアラートが発生した際、それが外部攻撃(ランサム等)によるものかを見極める原因切り分けオペレーション(手動確認)を、属人的な対応から脱却させ、誰でも再現できる手順として整備する。日常的な独立した予防監視ではなく、アラート発生を起点とする切り分け手順として位置づける。

設計内容

原因切り分けの観点をチェックリスト化する。例として、Web システムへのブラウザアクセスによる脅迫文の有無確認、SSH / SSM セッションマネージャでのサーバログインによる不審ファイルの確認、OS ログからの暗号化ファイルの発生・不審なプロセス・怪しいドメインや国外への外部通信の確認が挙げられる。実施者(一次対応者・当直・SOC 等)・実施タイミング(アラート発生後何分以内か)・エスカレーション先を定める。

期待される効果

シナリオ現状改善後
サービス異常のアラートが発生切り分け手順がなく、外部攻撃かの判断が遅れて対応方針の決定が遅延するチェックリストに沿った確認で外部攻撃かどうかを迅速に判断できる
5
ログを活用した分析基盤の整備
中期

位置づけ

検知した事象を深掘りし、外部攻撃かどうか・影響範囲を見極めるため、収集済みのログを活用した分析・調査基盤を整備する。検知から分析への接続を強化する。

設計内容

Amazon Detective で検知結果(GuardDuty Findings 等)を起点にエンティティのつながり・時系列の挙動を可視化する。SIEM on Amazon OpenSearch Service で複数ログソースを横断した相関分析を行う。分析に用いるログの多くは検知にも用いられるものと共通であり、平時から参照・クエリ可能な状態にあることが前提となる。

ログの収集・保護そのものの設計は保護(Protect)フェーズで扱うため、本項目では「収集済みログを活用できる状態か」に焦点を当てる。ログ収集・保護の検討が必要な場合は、保護(Protect)フェーズのスキルの活用をご案内する。

期待される効果

シナリオ現状改善後
検知した事象の影響範囲を確認したいログが散在し、影響範囲の分析に時間を要する分析基盤で不審アクティビティの広がりを可視化し、初動を絞り込める
6
フォレンジックベンダ連携の事前準備
中期

位置づけ

根本原因(侵入経路)・被害範囲の特定には高度な専門技能を要し、画一的な調査手法も存在しない。自組織で対応する範囲と、専門組織へ依頼する範囲をあらかじめ整理し、有事に速やかに連携できる準備を平時から整える。

設計内容

  • フォレンジックベンダへの連携手順(誰が・いつ・どのように依頼するか)の整理
  • ベンダへ提供する分析対象データの受け渡し方法や、外部組織とのデータ連携に関する社内ルール・契約面の調整
  • 自組織で対応する範囲と、専門組織へ依頼する範囲の区分の整理

検知した事象に対する証拠保全の実行や本格的なフォレンジック分析の実施そのものは、対応(Respond)フェーズで扱う。これらが必要な場合は、対応(Respond)フェーズのスキルの活用をご案内する。

期待される効果

シナリオ現状改善後
自組織での分析に限界が生じる事象が発生連携先を有事に探し始め、原因究明・被害範囲特定が遅延平時準備に沿って速やかに専門組織と連携できる

長期 組織横断・集中管理の領域

7
検知・分析の集約・委任管理
長期

位置づけ

各アカウントで個別に検知結果を確認するのではなく、セキュリティアカウントに集約して組織内の検知・管理を一元化する。組織横断の集中管理基盤の整備にあたるため、長期に位置づける。

設計内容

Amazon GuardDuty は AWS Organizations による委任管理者(delegated administrator)を指定することで、組織内アカウントの検知結果を集約・一元管理できる。AWS Security Hub を併用することで、複数のセキュリティサービスの検知結果を集約し、組織横断で優先度付け・可視化できる。

アカウント構成そのものの設計(セキュリティアカウントや Log Archive アカウントの位置づけ等)は保護(Protect)フェーズで扱う。アカウント構成の検討が必要な場合は、保護(Protect)フェーズのスキルの活用をご案内する。本項目は、既存のアカウント構成を前提として検知の集約・一元管理に焦点を当てる。

期待される効果

シナリオ現状改善後
あるアカウントで検知が上がる個別アカウントを見るまで気づけず、対応開始が遅延集約された可視化で組織横断に即時把握し、優先度付けできる
8
検知から対応への連携設計の高度化
長期

位置づけ

検知・分析で捉えた事象を、対応(Respond)フェーズへ円滑につなぐ連携を高度化する。検知から対応への橋渡しを確実にすることで、被害の封じ込め・復旧までの時間短縮につなげる。

設計内容

検知のアラートを起点に、対応プロセス(証拠保全・隔離・専門組織連携)へ速やかに引き継ぐ連携を整理する。検知・分析の集約基盤(項目 7)を前提に、検知から対応開始までのフローを定める。

証拠保全の実行・隔離・本格的なフォレンジック分析は対応(Respond)フェーズで扱う。対応フェーズの設計が必要な場合は、対応(Respond)フェーズのスキルの活用をご案内する。本項目は、検知・分析から対応への橋渡しに焦点を当てる。

期待される効果

シナリオ現状改善後
攻撃を検知・分析した後の対応着手検知から対応への引き継ぎが不明確で、対応開始が遅延検知を起点に対応プロセスへ速やかに引き継げる
