ABOUT THIS REPORT

本レポートは、AWS 金融リファレンスアーキテクチャ日本版で公開されているランサムウェア対策向けの SKILL を用いて、お客様のランサム被害・脅威の検知・分析態勢の全体設計をまとめたものである。AWS Well-Architected Framework、AWS のインシデント対応に関するガイダンス等の AWS 公式ガイダンスをベースに、金融機関の文脈で求められる設計考慮を加味したうえで、お客様環境に合わせた設計提案を行っている。

ランサムウェア対策は、保護（Protect）・検知（Detect）・対応（Respond）・復旧（Recover）の 4 つの観点で体系的に整備することが有効である。本レポートは、このうち 検知（Detect）フェーズ ― 被害・脅威を迅速に検知し、検知した事象を分析・調査する態勢の設計 ― を対象とする。保護・対応・復旧の各フェーズは別途扱う。

各設計領域には、対応の優先度・スピード感を示すフェーズ(短期 / 中期 / 長期)を付している。具体的な実装手順・設計判断の根拠・期待される効果については、本レポートに続けて「ロードマップ詳細レポート」を生成することができる。

検知の主要素はアラート(通知)。アラートを起点にインシデント対応を開始し、外部攻撃かどうかは手動確認による原因切り分けオペレーションで見極める。

3検知と分析の連携・専門連携への橋渡し

検知した事象を収集済みログで分析し、自組織で対応する範囲と専門組織へ依頼する範囲を整理する。

Overall Direction

本設計は、ランサム被害・脅威を「気づき(検知)」から「見極め(分析)」まで一気通貫で捉える態勢を、既存の監視・セキュリティ基盤を活かして組み立てることを目標形とする。検知はサービス影響の検知とセキュリティ攻撃の検知の両面で構成し、いずれもアラートを起点にインシデント対応へつなぐ。

サービス影響の検知では、リソース監視に留まらず、サービス監視・外形監視・アプリケーションレベルの監視(業務指標)まで監視の深さを確保することが要点となる。セキュリティ攻撃の検知では、Amazon GuardDuty を中心に、対象リソースへの検知カバレッジを確保する。

検知した事象は、収集済みのログを活用して分析・調査する。根本原因や被害範囲の特定には高度な専門技能を要するため、自組織で対応する範囲と、フォレンジックベンダ等の専門組織へ依頼する範囲をあらかじめ整理し、必要に応じて速やかに連携できる準備を平時から整えておくことを推奨する。

段階的アプローチとしては、既存環境への影響が小さく即効性のある対策(監視の深さの点検、GuardDuty の有効化等)から短期で着手し、検知・分析の組織横断での集約・一元管理は影響範囲が広いため長期に位置づける。なお、ログの収集・保護そのものの設計は保護(Protect)フェーズ、証拠保全の実行・本格的なフォレンジック分析は対応(Respond)フェーズで扱うため、必要な場合はそれぞれのフェーズのスキルの活用をご案内する。

既存環境を踏まえた重要な判断ポイント

Key Decisions
  1. サービス影響の検知は監視の深さが要点。リソース監視に留まらずサービス監視・外形監視・アプリケーションレベルの監視(業務指標)まで段階的に拡充する。
  2. セキュリティ攻撃の検知は GuardDuty を中心に、保護プランの有効化と対象リソースへのカバレッジを確保する。保護プランは変化しうるため、設計時に公式ドキュメントで最新を確認する。
  3. 検知をアラートとして確実にインシデント対応へつなぐ。アラート発生後、それが外部攻撃によるものかは手動確認(脅迫文・暗号化ファイル・不審通信の直接確認)による原因切り分けオペレーションで見極める体制を整備する。
  4. 根本原因・被害範囲の特定は専門技能を要するため、自組織と専門組織の対応範囲を整理し、フォレンジックベンダ連携を平時から準備する。

検知の設計

S
サービス影響の検知
短期
Design Core サービス・利用者への影響を迅速に捉え、「何かが、どこで起こった」ことを把握する一次調査の起点とする。監視の深さ(リソース監視 → サービス監視 → 外形監視 → アプリケーションレベルの監視(業務指標))を確保することが要点。既存の監視基盤の点検・拡充から進められるため、短期に位置づける。

監視の深さの段階

監視の深さ捉えられるもの
リソース監視CPU・メモリ・ディスク・接続数等のインフラリソースの稼働状況
サービス監視エラー率・レイテンシ・スループット等、サービスとしての稼働状況
外形監視外部から実際にエンドポイント・画面へアクセスし、到達性・応答・画面表示を確認(Amazon CloudWatch Synthetics 等)
アプリケーションレベルの監視(業務指標)ログイン数・取引数・契約数・閲覧数等の業務指標

リソース監視のみでは、リソースが正常でも利用者にサービスが提供できていない状況を見逃す可能性がある。金融機関では、システムの重要度に応じて監視レベルをラベリングし、重要システムに監視を重点配分することが望ましい。具体的な監視手法の設計は AWS 公式ガイドライン(Well-Architected の可観測性等)を参照する。

Notes 具体的な監視アプローチ(ログ監視・メトリクス監視・外形監視・アプリケーション監視)の設計詳細は、セキュリティを主題とする本スキルのスコープを超えるため、AWS 公式ガイドラインへの参照に委ねる。詳細は、続けて生成できるロードマップ詳細レポートで扱う。
G
セキュリティ攻撃の検知
短期
Design Core 不審なアクティビティ・ウイルス混入等、攻撃そのものを捉え、影響だけでなく原因可能性まで含めた検知を実現する。Amazon GuardDuty の有効化は既存環境への影響が小さく即効性が高いため、短期に位置づける。

検知の手段

Amazon GuardDuty を中心に据える。有効化すると基盤検知(CloudTrail / VPC フローログ / DNS ログの自動分析)と拡張脅威検知(多段階攻撃の検知)が追加コストなしで動作する。加えて、ランサム対策に関連が深い保護プラン ― Malware Protection for EC2 / Malware Protection for S3 / Runtime Monitoring / S3 Protection 等 ― を、対象リソースのカバレッジを踏まえて有効化する。サードパーティ製品(EDR 等)の併用も組み合わせる。

アラート発生後の原因切り分けオペレーション(手動確認)

サービス影響検知・上記のセキュリティ攻撃検知のいずれかでアラートが発生した際、それが外部攻撃(ランサム等)によるものかを見極める原因切り分けの体制を整備する。誰が(一次対応者・当直・SOC 等)、どのタイミングで(アラート発生後何分以内か)、どのような手順で確認するか(Web サイトへのブラウザアクセスによる脅迫文の確認、サーバへのログインによる暗号化ファイル・不審プロセス・不審な外部通信の確認等)を定めておくことで、外部攻撃かどうかの判断を迅速化する。

利用リソースに応じた保護プランの選定

ヒアリングで把握したお客様の利用リソース(DT-H1)に応じて、有効化を検討する保護プランを整理する。以下はお客様環境(Amazon EC2・コンテナ(Amazon ECS / Amazon EKS / AWS Fargate)・Amazon S3 を利用)を想定した例である。

利用リソース有効化を検討する保護プラン(例)
Amazon EC2 / Amazon EBSMalware Protection for EC2(EBS ボリュームのマルウェアスキャン)、Runtime Monitoring(OS レベルの脅威検知)
コンテナ(Amazon ECS / Amazon EKS / AWS Fargate)Runtime Monitoring(コンテナのランタイム脅威検知)
Amazon S3Malware Protection for S3(アップロードオブジェクトのスキャン)、S3 Protection(データ持ち出し・破壊の検知)

Amazon EFS / FSx 等の共有ファイルストレージは、それ自体を直接スキャンするのではなく、マウント元のコンピューティングの検知とログを活用した分析・調査でカバーする。Amazon RDS / Aurora / DynamoDB / AWS Lambda 等のマネージドサービスは、ランタイム的なマルウェア検知の対象外とし、データ保護や不審アクセスの検知(サービスにより提供される場合がある)で捉える。マルウェアスキャンの直接の対象は本レポート作成時点では Amazon EC2(EBS)と Amazon S3 である。

Notes GuardDuty の保護プランおよびマルウェアスキャン・脅威検知の対象リソースは追加・変更されることがある。設計時には公式ドキュメントの最新版で現行の保護プランと対応範囲を確認する。

分析・調査の設計

D
ログを活用した分析・調査
中期
Design Core 検知した事象を、収集済みのログを活用して分析・調査し、「外部攻撃によるものか」「影響範囲はどこまでか」を見極める。分析基盤の整備は個別に進められるため、中期に位置づける。

Amazon Detective で検知結果(GuardDuty Findings 等)を起点にエンティティのつながり・時系列の挙動を可視化し、不審アクティビティの広がりを把握する。SIEM on Amazon OpenSearch Service で複数ログソースを横断した相関分析を行う。あわせて、サーバ上の感染兆候(暗号化ファイル・不審プロセス・怪しい外部通信)を確認する。

Notes 分析に用いるログの多くは検知にも用いられるものと共通であり、平時から収集・保管されていることが前提となる。ログの収集・保護そのものの設計は保護(Protect)フェーズで扱うため、本設計では「収集済みログを活用できる状態か」に焦点を当てる。ログ収集・保護の検討が必要な場合は、保護(Protect)フェーズのスキルの活用をご案内する。
F
フォレンジックベンダ連携の事前準備
中期
Design Core 根本原因(侵入経路)・被害範囲の特定には高度な専門技能を要し、画一的な調査手法も存在しない。自組織で対応する範囲と、専門組織へ依頼する範囲をあらかじめ整理し、必要に応じて速やかにフォレンジックベンダと連携できる準備を平時から整える。

連携手順(誰が・いつ・どのように依頼するか)、ベンダへ提供する分析対象データの受け渡し方法や外部組織とのデータ連携に関する社内ルール・契約面の調整、自組織と専門組織の対応範囲の区分を、平時に検討・整備しておく。

Notes 検知した事象に対する証拠保全の実行(スナップショット取得・ディスクイメージの退避・証拠の連続性の確保)や本格的なフォレンジック分析の実施そのものは、対応(Respond)フェーズで扱う。これらが必要な場合は、対応(Respond)フェーズのスキルの活用をご案内する。

検知・分析の集約・委任管理

C
検知・分析の集約・委任管理
長期
Design Core 各アカウントで個別に検知結果を確認するのではなく、セキュリティアカウントに集約して組織内の検知・管理を一元化する。組織横断の集中管理基盤の整備にあたるため、長期に位置づける。

Amazon GuardDuty は AWS Organizations による委任管理者(delegated administrator)を指定することで、組織内アカウントの検知結果を集約・一元管理できる。AWS Security Hub を併用することで、複数のセキュリティサービスの検知結果を集約し、組織横断で優先度付け・可視化できる。これにより、検知の見逃しや対応の遅れを防ぐ。

Notes アカウント構成そのものの設計(セキュリティアカウントや Log Archive アカウントの位置づけ等)は保護(Protect)フェーズで扱う。アカウント構成の検討が必要な場合は、保護(Protect)フェーズのスキルの活用をご案内する。本設計は、既存のアカウント構成を前提として「検知をどこに集約し、どう一元管理するか」に焦点を当てる。

段階的ロードマップ

対応コスト・時間・既存環境への影響が小さく即効性のある対策から短期で着手し、影響は大きいが効果の高い対策を中期・長期へ段階的に位置づける。各フェーズの具体的な期間は組織の体制・予算・既存運用により変動するため、組織側で判断する前提とする。各項目には対策前のリスクと対策後に見込める効果を併記する。

短期 既存環境への影響が小さく即効性のある対策

  • サービス監視の深さの点検・拡充(リソース監視に留まらず、サービス監視・外形監視・アプリケーションレベルの監視(業務指標)へ)
  • Amazon GuardDuty の有効化と、ランサム関連の保護プランの有効化(対象リソースのカバレッジ確保)
  • 重要システムの監視レベルのラベリング

中期 個別に進められる対策

  • アラート発生後の原因切り分けオペレーション(手動確認)の運用手順の整備(実施者・実施タイミング・確認手順のチェックリスト化)
  • ログを活用した分析基盤の整備(Amazon Detective / SIEM on Amazon OpenSearch Service)
  • フォレンジックベンダ連携の事前準備(連携手順・対応範囲の整理)
シナリオ対策前のリスク対策後
検知した事象の影響範囲を確認したいログが散在し、影響範囲の分析に時間を要する分析基盤で不審アクティビティの広がりを可視化できる
自組織での分析に限界が生じる事象が発生連携先を有事に探し始め、原因究明・被害範囲特定が遅延平時準備に沿って速やかに専門組織と連携できる

長期 組織横断・集中管理の領域

  • 検知・分析の集約・委任管理(セキュリティアカウントへの集約、組織横断の一元可視化)

本レポートの構成について

ランサムウェア対策の他のフェーズ(保護(Protect)等)では、設計提案レポートと実装ロードマップ詳細レポートを 2 本に分けて生成する。一方、本フェーズ(検知・分析(Detect))では、これらを 1 本のレポートに集約している。

検知・分析態勢の具体的な実装(監視・サービス検知の導入設計、フォレンジック分析の手法等)は、AWS のアーキテクチャ設計から離れ、各サービスの公式リファレンスや専門領域に委ねられる部分が主となる。そのため本フェーズでは、詳細な実装ロードマップレポートは別途作成せず、設計提案と段階的ロードマップの方針を本レポートに集約している。具体的な監視手法は公式ガイドライン、フォレンジック分析は専門組織の知見を適宜活用することを推奨する。
