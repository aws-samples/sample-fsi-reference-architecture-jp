# レポートテンプレート仕様書 (template-spec)

本ファイルは `fsi-ransomware-detect` Skill の Workflow 完了時に生成するレポートについて、AI エージェントが毎回同じフォーマット・粒度・デザインで生成するための仕様書である。本ファイルおよび同階層の HTML テンプレートに完全準拠してレポートを生成すること。

レポートを生成する Workflow と生成物は以下のとおり。

| Workflow | レポート 1 | レポート 2 |
|---|---|---|
| Workflow A (検知・分析態勢の全体設計) | 設計提案レポート (design-proposal)。設計提案と段階的ロードマップを 1 本に集約 | (なし) |
| Workflow B (既存の検知・分析態勢の十分性評価) | 評価結果レポート (evaluation-report) | ロードマップ詳細レポート (roadmap-detail) |

**Workflow A は設計提案レポート 1 本構成**である。検知・分析態勢の具体的な実装(監視・サービス検知の導入設計、フォレンジック分析の手法等)は、AWS のアーキテクチャ設計から離れ、各サービスの公式リファレンスや専門領域に委ねられる部分が主となるため、詳細な実装ロードマップレポートは別途生成せず、設計提案と段階的ロードマップを 1 本のレポートに集約する(この主旨はレポート内の「本レポートの構成について」セクションに明記する)。**Workflow B は 2 レポート構成**で、2 つ目のロードマップ詳細レポートは `roadmap-detail-template.html` を用いる。本スキルは保護(Protect)フェーズのレポートテンプレートを雛形とし、フォーマット・構造・配色をほぼ踏襲しつつ、検知・分析フェーズ固有の内容と Detect 独自の表紙色に差し替えている。

## 本ディレクトリのファイル構成

```
report-templates/
├── template-spec.md                       (本ファイル: 仕様書)
├── design-proposal-template.html          (Workflow A: 設計提案レポートのテンプレート)
├── evaluation-report-template.html        (Workflow B: 評価結果レポートのテンプレート)
└── roadmap-detail-template.html           (Workflow B 専用: ロードマップ詳細レポートのテンプレート)
```

AI エージェントは以下を順に参照する。

1. 本ファイル (template-spec.md): 仕様・粒度・スタンスを把握
2. 対象 Workflow の 1 つ目のレポートテンプレート (Workflow A は design-proposal-template.html、Workflow B は evaluation-report-template.html): スタイル・構造のリファレンス
3. (Workflow B のみ) roadmap-detail-template.html: ロードマップ詳細レポートのスタイル・構造のリファレンス

## レポート生成のタイミングと進め方

Workflow によって生成するレポートの本数が異なる。

- **Workflow A**: 設計提案レポート 1 本のみ。ロードマップ提示の完了後、設計提案レポート (設計提案と段階的ロードマップを 1 本に集約) を MUST で自動生成する。ロードマップ詳細レポートは生成しない (理由は後述・レポート内に明記)。
- **Workflow B**: 2 レポート構成。ロードマップ提示の完了後に 2 段階で生成する。1 つ目の評価結果レポートは MUST で自動生成し、2 つ目のロードマップ詳細レポートはユーザー承認後に生成する。

レポート生成に対応する処理ステップ番号は Workflow ごとに異なる (Workflow A は SKILL_ja.md の Step 6、Workflow B は Step 8・9)。

### Workflow A: 設計提案レポート生成 (MUST、1 本のみ)

ロードマップ提示完了後、設計提案レポートを Markdown と HTML の両形式で自動生成する。

出力先:
```
fsi-ransomware-detect/report/workflow-a-{YYYYMMDD}-{NN}/
├── html/
│   └── design-proposal.html
└── md/
    └── design-proposal.md
```

`{YYYYMMDD}` は生成日 (ローカルタイムでの 8 桁日付)、`{NN}` は同日内の連番 (`01` から開始する 2 桁ゼロパディング)。生成完了後、保存先パス (HTML / Markdown) をユーザーに提示する。Workflow A ではロードマップ詳細レポートを別途生成しないため、生成可否の確認は行わない。

### Workflow B Step A: 評価結果レポート生成 (MUST、ユーザー確認なしで実行)

ロードマップ提示完了後、評価結果レポートを Markdown と HTML の両形式で自動生成する。

出力先:
```
fsi-ransomware-detect/report/workflow-b-{YYYYMMDD}-{NN}/
├── html/
│   └── evaluation-report.html
└── md/
    └── evaluation-report.md
```

`{YYYYMMDD}` は生成日 (ローカルタイムでの 8 桁日付)、`{NN}` は同日内の連番 (`01` から開始する 2 桁ゼロパディング)。同一日に複数回同じ Workflow を実行した場合、連番が増えていく形でディレクトリが分かれる。

生成完了後、ユーザーに以下を提示する。

- 評価結果レポートの保存先パス (HTML / Markdown)
- 続けてロードマップ詳細レポートを生成する旨と、内容量が多いため生成に相当な時間を要する旨
- 生成に進んでよいかの対話的な確認

### Workflow B Step B: ロードマップ詳細レポート生成 (ユーザー承認後に実行)

ユーザーから生成同意を得た後、ロードマップ詳細レポートを Markdown と HTML の両形式で生成する。

出力先 (Step A と同じディレクトリの html / md 配下):
```
fsi-ransomware-detect/report/workflow-b-{YYYYMMDD}-{NN}/
├── html/
│   └── roadmap-detail.html
└── md/
    └── roadmap-detail.md
```

生成完了後、保存先パスをユーザーに提示する。

### ディレクトリ命名規則

- ベースパス: `fsi-ransomware-detect/report/`
- セッション単位ディレクトリ: `workflow-{a|b}-{YYYYMMDD}-{NN}` (Workflow 種別 + 生成日 8 桁 + 同日内連番 2 桁ゼロパディング)
- 同一セッションで生成された 4 ファイル (1 つ目のレポート + ロードマップ詳細、各 HTML/Markdown) は同一の `workflow-{a|b}-{日付}-{連番}/` 配下に格納する

### 連番の決定方法

- AI エージェントは正確な時刻を取得する手段を持たないため、時刻ではなく日付ベース + 連番で管理する
- レポート生成前に `fsi-ransomware-detect/report/` 配下をリストアップする
- `workflow-{a|b}-{今日の日付}-*` に該当する既存ディレクトリを抽出する (Workflow 種別ごとに連番を管理する)
- 既存ディレクトリの連番の最大値 + 1 を採用 (該当なしの場合は `01`)
- 例: 同日に Workflow A を 3 回目の生成なら `workflow-a-20260603-03/` を作成する

### レポートのディレクトリ整合性 (Workflow B)

- Workflow A は設計提案レポート 1 本のみのため、`workflow-a-{YYYYMMDD}-{NN}/` 配下に design-proposal の HTML / Markdown を配置する。
- Workflow B では、評価結果レポートとロードマップ詳細レポートは必ず同一の `workflow-b-{YYYYMMDD}-{NN}/` ディレクトリ配下に配置する。
  - Step A → Step B の通常フローでは、Step B は Step A と同じディレクトリに追加生成される
  - ユーザーが既存の評価結果レポートに対するロードマップ詳細レポートを後追いで希望した場合、AI は新規ディレクトリを作成せず、対象となる既存ディレクトリをユーザーに対話的に確認した上で、そのディレクトリに追加格納する
  - 完全な新規セッションとして Workflow を最初から実行する場合は、新規連番ディレクトリを作成する

### 日付の取得

- AI エージェントが認識している現在日付 (年月日) をそのまま使用する
- 時刻は使用しない (時刻は AI が正確に取得できないため、仮の時刻を入れるとレポート信頼性が損なわれる)
- レポート内の表紙・フッターの日時表記も日付のみとする (例: `GENERATED — 2026-06-03`)

## 共通の執筆スタンス (両レポート共通)

### 表現の禁止事項

- **「執筆時点」「対応 (執筆時点)」「対応 / 非対応」のような Skill 開発側のメタな表記を使ってはならない**。レポートはお客様向け成果物のため、Skill 内部視点の表現は不適切である
- **開発者目線・スキル間整合のメタな記述 (「Protect フェーズと整合させる」等) をレポートに含めてはならない**。他フェーズに触れる場合は「他フェーズのスキルの活用をお客様にガイダンスする」表現とする (`01-skill-format-guide.md`「スキルの独立性の原則」に準拠)
- 機能・サービスの対応リソースを示す場合、対応リソースのみを肯定列挙する。対象外リソースは別段落で補完への導線として 1 〜 2 行で言及する
- GuardDuty の保護プラン等、今後変化しうる機能名・対応範囲は断定列挙にせず「等」を添え、最新情報は公式ドキュメントで確認する前提を示す
- **ロードマップの各項目に具体的な期間 (「1〜2 ヶ月」「Phase 1: 2〜3 ヶ月」「2〜3 週間」等) を提示してはならない**。期間は顧客側の組織体制・予算・既存運用等により大きく左右されるため、短期・中期・長期のフェーズ分類のみで示す
- Before/After 比較表で現状を示す際は、「成功する」「実行できる」のような曖昧表現ではなく、**「リスクあり」「検知できない」「気づけない」** のように明示する。改善後は「即時検知できる」「アラートで通知される」「一元的に把握できる」のように検知・分析の効果が明確に伝わる表現を用いる

### 推奨される表現

- 総合評価コメントでは、できていること・足りないこと・早急対応すべきことを 3 段構成で記述。重要キーワード (「サービス監視の深さ」「攻撃検知のカバレッジ」「検知の集約・一元管理」等) は `<strong>` タグで赤字強調 (HTML 側で `color: var(--ng)` が適用される)
- 「より詳細な改善設計について」セクションのアピール文は `<span class="callout">` でティール色の太字を付与
- 文体は Skill 全体の規約に従い、断定すぎない柔らかい文末を選ぶ (「〜することが可能」「〜効果を見込むことができる」等)。Constraints の MUST/MUST NOT のような強制ルールは明確に断定する

## データ構造 (AI が内部で保持すべき構造化データ)

レポート生成時、AI は以下の構造化データを内部で保持してから HTML/Markdown を組み立てる。

### 入力情報 (お客様の検知・分析態勢の前提情報 + 現状)

```
[
  { id: 1, label: "感染検知の主な対象となる利用中のリソース", answer: "..." },
  { id: 2, label: "マルチアカウント構成・組織構成", answer: "..." },
  ...
]
```

注: ID は **連番 (1〜)** とする。Skill 内部の DT-H1〜DT-H4、DT-HB1〜DT-HB5 のような識別子はレポートに出さない。前提情報には要件項目 (DT-H 系)、現状には Workflow B の DT-HB 系が対応する。

### 評価結果 (Workflow B)

```
[
  {
    no: 1,
    viewpoint: "サービス影響検知の整備",
    current: "...",
    verdict: "ng" | "partial" | "ok" | "unknown",
    gap: "...",
    risk: "...",
    detail: {
      currentSummary: "...",
      verdictReason: "...",
      missingElements: ["...", "..."],
      riskScenario: "...",
      relatedItem: "中期 N サービス監視の深さの拡充",
      reference: "references/01-detection-strategy.md"
    }
  },
  ...
]
```

評価項目は 5 項目 (DT-EVAL1〜DT-EVAL5)。Workflow B は評価項目 1〜5 と現状ヒアリング DT-HB1〜DT-HB5 が 1 対 1 対応する構造であり、評価結果レポートの各評価項目を埋める情報が必須ヒアリングで取得できることを担保している。

### ロードマップ項目

```
[
  {
    phase: "short" | "mid" | "long",
    no: 1,
    title: "...",
    positioning: "...",
    designDetails: { ... },
    expectedEffects: [
      { scenario: "...", before: "検知できない", after: "アラートで即時検知" },
      ...
    ]
  },
  ...
]
```

## Detect 独自の表紙色 (Protect との区別)

本スキルのレポートは、保護(Protect)フェーズと視覚的に区別するため、表紙(cover)のグラデーションと文字色を **ティール〜グリーン系の Detect 独自色** とする。本文のメイン背景・カード配色・判定色 (OK / 一部対応 / NG / 未確認)・フェーズ色 (短期=緑 / 中期=青 / 長期=紫)・フォント・各種シャドウは保護(Protect)フェーズと共通 (踏襲) とする。

| レポート | 表紙グラデーション | 文字色 | アクセント |
|---|---|---|---|
| 設計提案 (Workflow A) | `linear-gradient(120deg, #7FD1C4 0%, #6FC3CE 45%, #8FD9D0 100%)` (明るいティール〜シアン) | `#0C3B38` (濃色) | `#0E7C7B` |
| 評価結果 (Workflow B) | `linear-gradient(135deg, #0E7C7B 0%, #1A8C8A 60%, #3FB8AD 100%)` (深いティールグリーン) | `#FFFFFF` (白) | `#BFF0E8` |
| ロードマップ詳細 (共通流用) | `linear-gradient(180deg, #AEE0DA 0%, #BFE3DC 50%, #CFEAE6 100%)` (淡いミントグリーン) | `#0A3330` (濃色) | `#0E7C7B` |

レポート種別は同一色相帯の明度・彩度差で区別する (設計提案=明るい / 評価結果=深い・白文字 / ロードマップ詳細=淡い)。

## 表紙のフェーズインジケータ (4 フェーズ表示)

各レポートの表紙には、ランサム対策 4 フェーズ (保護 / 検知 / 対応 / 復旧) を横並び・日英併記で表示するフェーズインジケータ (`.cover .phase-nav`) を設ける。本スキルは検知・分析フェーズを扱うため、**検知 (Detect) のみ `class="phase active"` で強調**する (塗りチップ + 白文字 + 太字)。他フェーズは淡色・枠線のみ。並び順は 保護(Protect) → 検知(Detect) → 対応(Respond) → 復旧(Recover)。

強調色 (`.phase.active` の背景) は各レポートの表紙アクセント色に合わせる (設計提案・ロードマップ詳細 = `#0E7C7B` 系、評価結果 = `#BFF0E8` を背景にする場合は濃色文字、もしくは白文字が読める濃色チップ)。各テンプレートの実装に従う。

## 設計提案レポートのセクション構成と粒度 (Workflow A)

`design-proposal-template.html` のセクション順・スタイルに完全準拠する。本レポートは「評価」ではなく「設計提案」がメインである点が Workflow B の評価結果レポートとの違いである。

### 設計提案レポートの位置づけ

- Workflow A は既存環境を活かして検知・分析態勢を新たに組み立てる提案である
- 各設計領域には、対応の優先度・スピード感を示すフェーズ (短期 / 中期 / 長期) を付す。フェーズは重要度ではなく「対応の容易さ・既存環境への影響の小ささ」を軸に分類する (SKILL_ja.md の DT-C12 に準拠)
- 詳細な実装ステップ・期待される効果はロードマップ詳細レポートに委ね、本レポートは設計方針と各領域の核心・概略に集中する

### セクション順序 (固定)

1. 表紙 (フェーズインジケータ = 検知 active)
2. このレポートについて
3. 提案サマリ (設計方針の柱 + ロードマップ早見表 + Overall Direction)
4. ヒアリング結果 (必須項目 + 未確認項目を表形式)
5. 設計方針の大枠 (検知・分析の全体像図 + 採用 AWS サービス表 + 判断ポイント)
6. 検知の設計 (サービス影響の検知 + セキュリティ攻撃の検知)
7. 分析・調査の設計 (ログを活用した分析・調査 + フォレンジックベンダ連携の事前準備)
8. 検知・分析の集約・委任管理
9. 段階的ロードマップ (短期 / 中期 / 長期の項目一覧 + 各フェーズの対策前のリスク vs 対策後の効果表)
10. 未確認事項とフォローアップ推奨
11. 本レポートの構成について (1 本に集約している理由)
12. 付録 (参照 reference 一覧)

### 表紙

- ラベル: `FSI RANSOMWARE DETECT — WORKFLOW A`
- タイトル: `【検知・分析フェーズ】<br>AWS ランサムウェア対策設計提案レポート` (`<br>` で 2 行に改行)
- フェーズインジケータ: 4 フェーズ横並び、**検知 (Detect)** のみ active
- サブタイトル: 設計提案レポートでは表紙にサブタイトルを設けない
- 生成日: `GENERATED — {YYYY-MM-DD}` (日付のみ)
- 表紙背景は明るいティール〜シアン (`linear-gradient(120deg, #7FD1C4 0%, #6FC3CE 45%, #8FD9D0 100%)`)、文字色は濃色 (`#0C3B38`)、アクセントは `#0E7C7B`

### このレポートについて (静的文言)

以下の文言を必ず使用する。

> 本レポートは、AWS 金融リファレンスアーキテクチャ日本版で公開されているランサムウェア対策向けの SKILL を用いて、お客様のランサム被害・脅威の検知・分析態勢の全体設計をまとめたものである。AWS Well-Architected Framework、AWS のインシデント対応に関するガイダンス等の AWS 公式ガイダンスをベースに、金融機関の文脈で求められる設計考慮を加味したうえで、お客様環境に合わせた設計提案を行っている。

2 段落目で、ランサム対策は保護・検知・対応・復旧の 4 観点で体系的に整備することが有効であり、本レポートはこのうち検知（Detect）フェーズ（検知に加えて、検知した事象の分析まで）を対象とすること（検知 (Detect) を `.phase-hl` で強調）を明示する。3 段落目で、各設計領域にフェーズ (短期 / 中期 / 長期) を付していること、詳細な実装手順・効果はロードマップ詳細レポートに記載していることを明示する。

### 提案サマリ

- 設計方針の柱: カード形式 (検知と分析を組み合わせた態勢 / アラート起点のインシデント対応開始 / 自組織と専門組織の対応範囲の整理 等、本スキルの Core Design Principles に沿う柱)
- ロードマップ早見表: フェーズ × 主要な取り組みの 2 列表
- Overall Direction: **約 400〜500 字**。設計の方向性・検知と分析の連携・アラート起点・段階的アプローチを記述。重要キーワードは `<strong>` で赤字強調

### ヒアリング結果

- 必須項目 (感染検知の主な対象リソース / マルチアカウント構成 / 既存の監視・セキュリティ基盤) と推奨項目 (フォレンジック分析の実施方針) を 1 つの表で提示。これらは設計の前提となる要件・外観・方針であり、現状の検知・分析の整備状況そのものではない
- ID は連番 (1〜)。Skill 内部の DT-H1〜DT-H4 識別子は使用しない
- 未取得項目は `<span class="verdict unknown">未確認</span>` バッジで明示し、推測で埋めない

### 設計方針の大枠

- 検知・分析の全体像図: HTML/CSS の構造化図 (`.arch` / `.arch-node` / `.arch-arrow`) で表現する。ASCII アートは使用しない。「サービス影響の検知 / セキュリティ攻撃の検知 → アラート起点でインシデント対応開始 → 収集済みログを活用した分析・調査 → 必要に応じて専門組織連携」の流れと、検知・分析を集約するセキュリティアカウントの位置づけを示す
- 採用 AWS サービス表: サービス名と役割の 2 列 (Amazon GuardDuty / Amazon CloudWatch / Amazon Detective / SIEM on Amazon OpenSearch Service / AWS Security Hub 等)
- 重要な判断ポイント: ハイライト枠 (`.core`) で 4 点程度を箇条書き

### 検知の設計 / 分析・調査の設計 / 集約・委任管理 (領域カード)

各領域はフェーズ色付きカード (`.domain` + `.domain-header.{short|mid|long}`) で展開する。各カードに「設計の核心 (`.core.{short|mid|long}`)」「主要パラメータの簡略表」「注意点 (`.note`)」を含める。GuardDuty の保護プランは「等」を添えて例示し、最新は公式ドキュメントで確認する旨を注意点に記す。セキュリティ攻撃の検知カードには、ヒアリングで把握したお客様の利用リソース (DT-H1) に応じて有効化を検討する保護プランを整理する「利用リソースに応じた保護プランの選定」表を含める (例: Amazon EC2/EBS → Malware Protection for EC2・Runtime Monitoring、コンテナ (Amazon ECS / Amazon EKS / AWS Fargate) → Runtime Monitoring、Amazon S3 → Malware Protection for S3・S3 Protection)。これによりヒアリング結果がレポートの設計提案に反映される (お客様固有化)。

### 段階的ロードマップ / 未確認事項 / 本レポートの構成について / 付録

- 段階的ロードマップ: 短期 / 中期 / 長期の 3 見出しで項目を箇条書き。DT-C12 の判断軸に沿う。期間の数値は記載しない。各フェーズに「対策前のリスク vs 対策後」の効果表 (`table.compare`) を添える。実装具体は AWS アーキテクチャ設計から離れ公式・専門領域に委ねられるため、Protect のロードマップ詳細のような深い実装ステップには踏み込まず、効果は 1〜2 行のシナリオで簡潔に示す
- 未確認事項とフォローアップ推奨: 未取得のヒアリング項目と影響箇所を表で提示。推測で設計値に組み込まない
- 本レポートの構成について: 本フェーズが設計提案レポート 1 本構成である理由を明記する。他フェーズ (保護(Protect)等) は設計提案とロードマップ詳細の 2 本構成だが、検知・分析フェーズの具体的な実装 (監視・サービス検知の導入設計、フォレンジック分析の手法等) は AWS のアーキテクチャ設計から離れ各サービスの公式リファレンスや専門領域に委ねられる部分が主となるため、詳細な実装ロードマップレポートは別途作成せず 1 本に集約している旨を、冒頭に「他フェーズは 2 本だが本フェーズは 1 本」という主旨を置いた上で記述する。具体的な監視手法は公式ガイドライン、フォレンジック分析は専門組織の知見を適宜活用することを推奨する旨を添える
- 付録: 参照 reference 一覧 (references/01-detection-strategy.md / 02-log-analysis-and-investigation.md をリンク列挙)
