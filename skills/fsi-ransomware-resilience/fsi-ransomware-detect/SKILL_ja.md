# 金融機関向けランサムウェア対策:検知・分析(Detect)

## Overview

本スキルは、金融サービス業界の組織が AWS 上で構築するランサムウェア対策のうち、被害・脅威を「検知」し、検知した事象を「分析」する態勢について、設計と既存態勢評価を支援する。本スキルが提供する内容:

- サービス影響の検知の設計支援(リソース監視に留まらず、サービス監視・外形監視・アプリケーションレベルの監視(業務指標)まで、サービス影響を迅速に検知できる仕組みになっているか)
- セキュリティ攻撃の検知の設計支援(Amazon GuardDuty の保護プラン、サードパーティ製品)
- アラートを起点としたインシデント対応プロセスの開始の考え方、および検知後に外部攻撃(ランサム等)かを見極める原因切り分け(手動確認)の設計支援
- 検知した事象の分析・調査の設計支援(収集済みログを活用した Amazon Detective / SIEM on Amazon OpenSearch Service による不審アクティビティの分析、感染兆候の確認)
- 検知・分析の集約・委任管理(セキュリティアカウントへの集約による組織内の検知・管理の一元化)
- 分析ハードルが高い場合の、フォレンジックベンダ連携の事前準備の位置づけ
- 上記を踏まえた検知・分析態勢の段階的な設計・改善ロードマップと、お客様向けレポートの生成

本スキルが対応する範囲:

- ランサムウェア対策のうち「検知(Detect)」フェーズに焦点を当て、検知に加えて、検知した事象の分析までを扱う
- 保護(Protect)、対応・隔離(Respond)、復旧(Recover)の各フェーズは別スキルで扱う
- ログの収集・保護の設計は保護(Protect)フェーズのスコープであり、本スキルは「収集済みログを活用する」前提に立つ
- 証拠保全の実行・本格的なフォレンジック分析・隔離は対応(Respond)フェーズのスコープであり、本スキルは「自組織で対応する範囲と専門組織へ依頼する範囲を整理し、保全・専門調査へ橋渡しする」までを扱う
- オンプレミス環境の影響・攻撃検知は対象外。オンプレミス環境の検知は、AWS サービスで効率的に実現するというより、オンプレミス側のモニタリング製品・ウイルスチェック製品・フォレンジックツールとオペレーションを組み合わせた設計運用が主となるものとし、本スキルでは扱わない

本スキルの詳細ガイドおよびレポート生成テンプレートは、本スキルファイルと同じ階層の `references/` フォルダおよび `report-templates/` フォルダ内に格納されている。各 Workflow の処理ステップで「references/XX を参照」「report-templates/XX を参照」と指示されている場合は、以下の手順で該当ファイルを探索し、読み込んだ上で応答を組み立てること。

1. ワークスペース配下の `.kiro/skills/fsi-ransomware-detect/{references,report-templates}/` を試す
2. 見つからない場合、ユーザーレベルの `~/.kiro/skills/fsi-ransomware-detect/{references,report-templates}/` を試す
3. いずれも見つからない場合、ユーザーに本スキルの配置パスを確認する

reference およびテンプレートの読み込みに失敗した場合でも一般知識のみで応答を組み立てるのではなく、必ずユーザーに状況を伝えてから対応を判断すること。

本スキルは AWS 公式ドキュメントを参照して回答の正確性を担保する設計となっている。利用にあたっては、AWS Documentation MCP サーバーを事前にセットアップしておくことを推奨する(セットアップ手順は本スキルに付属の README.md を参照)。

## Common Tasks

### 0. Classify the Request

ユーザーの問いから、以下の対応関係で Workflow を仮選択する。

| ユーザー意図 | Workflow |
|---|---|
| AWS 環境のランサム被害の検知・分析態勢を新たに設計したい / 何から始めるべきかを相談したい | A |
| 既存の検知・分析態勢のランサム対策としての十分性を評価し、不足を特定して改善したい | B |
| 検知・分析のベストプラクティスの全体感を概要レベルで知りたい / 学習目的で対話的に深掘りしたい | C |
| 検知・分析に関する特定トピック(サービス監視、攻撃検知、GuardDuty、ログを活用した分析・調査 等)についてピンポイントで深掘り相談したい | D |

ただし、ユーザーの問いだけからは Workflow が一意に決まらないケースが多いため、必ずユーザーに対して「以下のどの方向性で進めるか」を対話的に確認した上で、適切な Workflow に進む。具体的には、以下のような確認文を提示する。この確認文の冒頭には、本スキルが5領域のうち Detect のみを担当することを示す一文を必ず含める(DT-C13 を参照)。また、以下の例のとおり、グルーピング見出しの太字化と選択肢 A〜D の Markdown 箇条書き構造を保持したまま出力し、プレーンテキストの1段落に連結してはならない(DT-C14 を参照)。

> このスキルはランサムウェア対策の5領域「Protect(保護), Detect(検知・分析), Respond(対応), Recover(復旧), Organization(組織対応)」のうち「Detect(検知・分析)」を担当し、被害・脅威の検知および検知した事象の分析の設計・評価を支援します。他の領域のご相談があれば、対応するスキルをご依頼ください。
>
> ご質問にお答えする前に、どの方向で進めるかを確認させてください。本スキルは、ランサム被害・脅威の「検知」に加えて、検知した事象の「分析」までを扱います(証拠保全の実行や本格的なフォレンジック分析、ログ収集の設計、オンプレミス環境の検知は本スキルの対象外です)。
>
> **【設計/評価レポートを作成】**
> - A. 検知・分析態勢の全体設計をこれから組み立てる
> - B. すでにある検知・分析態勢のランサム対策としての十分性を評価したい(既存態勢の評価・改善)
>
> **【対話形式でガイダンス】**
> - C. 検知・分析のベストプラクティスの全体感をまずは概要レベルで知りたい(対話的に深掘りしながら、必要に応じて A・B・D の Workflow へガイダンス)
> - D. 特定のトピック(サービス監視、攻撃検知、GuardDuty、ログを活用した分析 等)についてピンポイントで知りたい
>
> 主にどの方向性に該当しますか?複数該当する場合もお聞かせください。

ユーザーからの回答を踏まえて、適切な Workflow に進む。

### 1. 共通ヒアリング項目

Workflow A・B・C・D で共通利用する。これらは検知・分析態勢を設計・評価する上での前提となる「要件・外観・方針」を把握するための項目であり、現状の検知・分析の整備状況そのものを評価するための項目ではない(現状の整備状況は Workflow B 固有の現状ヒアリング項目 DT-HB1〜DT-HB5 で扱う)。各 Workflow ごとに必須・推奨の振り分けは異なる。ログの収集・保護設計やアカウント構成設計そのものは保護(Protect)フェーズのスコープであるため、本スキルのヒアリングは検知・分析の設計に必要な範囲に絞る。

| # | ヒアリング項目 |
|---|---|
| DT-H1 | 感染検知の主な対象となる利用中のリソース。お客様のワークロード(アプリケーション)やデータが直接稼働・保管され、マルウェア感染やランサム被害のチェック対象となるリソースが検知設計のフォーカスポイントとなる(例: Amazon EC2 / Amazon ECS / Amazon EKS / AWS Fargate / Amazon S3 / その他)。攻撃検知のカバレッジ範囲・保護プラン選定を検討する前提となる |
| DT-H2 | マルチアカウント構成・組織構成(AWS Organizations / Control Tower の利用有無、アカウント数の規模感、セキュリティアカウントの有無。検知・分析の集約・委任管理を設計する前提となる)。アカウント構成設計そのものは保護(Protect)フェーズのスコープ |
| DT-H3 | 既存の監視・セキュリティ基盤と継続方針(既存の監視基盤(Amazon CloudWatch 中心かサードパーティ監視製品か)、EDR / AV、SIEM 等の有無と継続利用方針。既存資産を活かした検知・分析設計の前提となる。ここでは整備状況の十分性を評価するのではなく、設計に組み込む前提としての有無・方針を把握する)。ログの収集・保護自体は保護(Protect)フェーズのスコープ |
| DT-H4 | フォレンジック分析の実施方針(検知した事象の分析・調査を、(a) 自組織で実施していく方針か、(b) 組織内で分析スキルを醸成していく見通しか、(c) 専門技能を持つ外部のフォレンジックベンダに依頼していく方針か。複数併用もありうる。方針に応じて、分析基盤の整備とベンダ連携の事前準備のどちらに設計の重心を置くかが変わる) |

DT-H1 で対象リソースを確認する際、リソースの性質に応じて検知の扱いが異なる。(1) コンピューティング(Amazon EC2、Amazon ECS、Amazon EKS、AWS Fargate 等)はマルウェアの実行・感染が起こりうる実行環境であり、ランタイムの脅威検知・マルウェアスキャンの主な対象となる(AWS Fargate もコンテナ内の実行環境・データはお客様のワークロードであり、感染チェック対象として他のコンピューティングと同様に扱う)。(2) ストレージ(Amazon S3、Amazon EFS、Amazon FSx 等)はデータの暗号化・破壊・持ち出しの対象で、Amazon S3 は検知の直接の対象、Amazon EFS / FSx 等はマウント元のコンピューティングの検知とログを活用した分析・調査でカバーする。(3) マネージドサービス(Amazon RDS、Amazon Aurora、Amazon DynamoDB、AWS Lambda 等)はユーザーが OS・ランタイムを管理せずウイルスファイルが実行される環境ではないため、ランタイム的なマルウェア検知(感染チェック)は本スキルの対象外とし、データ・不審アクセスはログを活用した分析・調査や保護(Protect)フェーズで捉える(サービスによっては不審アクセスを検知する仕組みが提供される場合がある。詳細は references/01-detection-strategy.md を参照)。マルウェアスキャンの直接の対象となるのは執筆時点では Amazon EC2(EBS)と Amazon S3 だが、対応範囲は機能拡張により変わるため、設計提案・評価時は AWS GuardDuty 公式ドキュメントの最新版で確認する。

### 2. Workflow A: 検知・分析態勢の全体設計

#### 発動条件

「AWS 環境のランサム被害の検知・分析態勢を新たに設計したい」「検知の仕組みをこれから組み立てたい」「何から始めるべきか相談したい」という問いに対応する。既存態勢の評価・改善が目的の場合は Workflow B を選択する。

#### ゴール

Workflow A 完了時、ユーザーは以下を得ている:

1. 継続的な監視による検知(サービス影響・セキュリティ攻撃)と、検知した事象の分析・調査を組み合わせた態勢の設計案
2. 採用すべき検知・分析サービスとそれぞれの役割・使い分け(Amazon GuardDuty / Amazon CloudWatch / Amazon Detective / SIEM on Amazon OpenSearch Service 等)
3. アラートを起点に対応へつなぐ設計、収集済みログを活用した分析・調査の設計
4. 分析ハードルが高い場合のフォレンジックベンダ連携の事前準備の位置づけ(保全実行は対応(Respond)フェーズへ橋渡し)
5. 設計の優先順位と段階的ロードマップ(まず何から始めるか)
6. 設計提案レポート(検知・分析態勢の設計方針・各設計領域・段階的ロードマップを 1 本に集約した HTML / Markdown レポート。本フェーズでは設計提案とロードマップを 1 本のレポートに集約し、ロードマップ詳細レポートは別途生成しない)
7. 詳細を深掘りするための reference や別 Workflow・他フェーズ Skill へのポインタ

#### ヒアリング項目

共通ヒアリング項目から以下を選択する:

- 必須: DT-H1, DT-H2, DT-H3
- 推奨: DT-H4

#### 処理ステップ

1. **初期ヒアリング**: 必須項目(DT-H1, DT-H2, DT-H3)を確認する。ヒアリングは DT-C10 に従い1〜2項目ずつインタラクティブに進める。不明な項目は組織内の関連部署への確認提案、または仮設定で進める旨を明示する
2. **大枠の検知・分析方針の提示**: 「継続的な監視で検知 → アラートを起点に対応を開始 → 検知した事象を分析」という流れを大枠として提示する。サービス影響の検知と攻撃の検知はどちらが先に立つこともあり、検知の順序は固定ではない旨を添える
3. **検知の設計提案**: サービス影響の検知(監視の深さ: リソース監視・サービス監視・外形監視・アプリケーションレベルの監視(業務指標))と、セキュリティ攻撃の検知(GuardDuty の保護プラン、サードパーティ)を提案する。あわせて、アラート発生後に外部攻撃(ランサム等)かを見極める原因切り分けオペレーション(手動確認)の体制整備(誰が、どのタイミングで実施するか)を提案する。システムの重要度に応じた監視レベル設計の考え方にも軽く触れる。具体的な監視・検知手法の詳細は公式ガイドラインへの参照に委ねる。references/01-detection-strategy.md を参照
4. **分析・調査の設計提案**: 収集済みログを活用した分析・調査(Amazon Detective / SIEM on Amazon OpenSearch Service)、感染兆候の確認観点を提案する。根本原因・被害範囲の特定には高度な専門技能を要するため、分析ハードルが高い場合はフォレンジックベンダ連携を検討する旨と、そのための事前準備(連携手順・外部調整)の位置づけを伝える。ログの収集・保護自体は保護(Protect)フェーズへ委ねる旨を明示する。references/02-log-analysis-and-investigation.md を参照
5. **設計の優先順位と段階的ロードマップの提示**: DT-C12 のフェーズ判断軸(リスク低減効果・対応の容易さ/既存環境への影響・依存関係)に従い、短期・中期・長期のロードマップを提示する。具体的な期間の数値は提示しない(DT-NA2)
6. **設計提案レポートの自動生成 (MUST)**: ロードマップ提示完了後、設計提案レポート(設計方針・各設計領域・段階的ロードマップを 1 本に集約)を HTML と Markdown の両形式で自動生成する。生成にあたっては `report-templates/template-spec.md` の仕様および `report-templates/design-proposal-template.html` のスタイル・構造に完全準拠する。出力先は `fsi-ransomware-detect/report/workflow-a-{YYYYMMDD}-{NN}/html/design-proposal.html` と `fsi-ransomware-detect/report/workflow-a-{YYYYMMDD}-{NN}/md/design-proposal.md` とする。`{YYYYMMDD}` は生成日(8 桁)、`{NN}` は同日内連番(`01` から開始する 2 桁ゼロパディング)。AI エージェントは正確な時刻を取得できないため、ディレクトリ名にもレポート内の表記にも時刻を含めず、日付のみを使用する。本フェーズでは設計提案とロードマップを 1 本のレポートに集約するため、ロードマップ詳細レポートは別途生成しない(その理由はレポート内に明記する。詳細は template-spec.md を参照)。生成完了後、保存先の絶対パスをユーザーに提示する
7. **詳細展開オファーと関連 reference・別 Workflow へのポインタ提供**: レポート生成完了後、ユーザーに対して「レポートに各設計領域の詳細を含めていますが、対話的にディスカッションしながら深堀することも可能です」と対話的に確認する。希望する場合は1領域ずつ詳細展開し、各領域の終わりで継続をユーザーに確認する。詳細展開の到達点は対応する reference の記載レベル(設計判断、判断根拠、金融機関文脈での留意点まで)とする。希望しない場合は、関連する reference や別 Workflow への誘導を簡潔に示してから Workflow を終了する。あわせて、検知した事象の保全・本格的なフォレンジック分析が必要な場合は対応(Respond)フェーズの Skill への誘導を行う

#### Workflow A 固有 Constraints

- **DT-MA1**: You MUST 必須ヒアリング項目(DT-H1, DT-H2, DT-H3)を確認してから設計提案を組み立てる
- **DT-MA2**: You MUST Step 5(ロードマップ提示)完了後、設計提案レポート(Step 6)を HTML と Markdown の両形式で自動生成する。生成にあたっては `report-templates/template-spec.md` の仕様および `report-templates/design-proposal-template.html` のスタイル・構造に完全準拠する。フォーマット・粒度・配色・フォントに関する独自判断を行ってはならない。本フェーズでは設計提案とロードマップを 1 本のレポートに集約するため、ロードマップ詳細レポートは別途生成しない。生成完了後、保存先パスをユーザーに提示する
- **DT-NA2**: You MUST NOT ロードマップの各項目に具体的な期間(「1〜2 ヶ月」「6〜12 ヶ月」等)を提示してはならない。期間は顧客側の組織体制・予算・既存運用等により大きく左右されるため、短期・中期・長期のフェーズ分類のみで示す
- **DT-NA3**: You MUST NOT ログの収集・保護の設計詳細に踏み込んではならない。ログ収集・保護は保護(Protect)フェーズのスコープであり、本 Workflow では「収集済みログを活用する」前提に立ち、保護(Protect)フェーズへの誘導に留める
- **DT-NA4**: You MUST NOT 証拠保全の実行・本格的なフォレンジック分析・隔離の詳細に踏み込んではならない。これらは対応(Respond)フェーズのスコープであり、本 Workflow では「自組織で対応する範囲と専門組織へ依頼する範囲を整理し、保全・専門調査へ橋渡しする」までに留める
- **DT-NA5**: You MUST NOT レポート生成時、テンプレートにない独自セクションの追加、テンプレートの章順・カラム構成の変更、配色・フォント・グラデーションの変更を行ってはならない。データ部分(お客様情報・設計提案内容・ロードマップ内容)のみテンプレートから差し替える

### 3. Workflow B: 既存の検知・分析態勢の十分性評価

#### 発動条件

「既存の検知・分析態勢のランサム対策としての十分性を評価したい」「ベストプラクティスとの照合をしたい」「不足ポイントを特定したい」「既存の検知・分析態勢を改善したい」という問いに対応する。

#### ゴール

Workflow B 完了時、ユーザーは以下を得ている:

1. 評価項目ごとの判定結果(OK / NG / 一部対応 / 未確認)と判定根拠
2. 不足している項目の整理(何が不足しているか、なぜそれが問題か)
3. 改善の方向性と優先順位(どの不足から手をつけるべきか、リスク評価込みで)
4. 不足項目に対する具体的な改善設計案(アーキテクチャレベル、Workflow A 並みの詳細さ)
5. 段階的な実装ロードマップ
6. 評価結果レポートとロードマップ詳細レポート
7. 詳細を深掘りするための reference へのポインタ

#### ヒアリング項目

##### 第1層: 共通ヒアリング項目(要件・前提)

検知・分析態勢の前提となる要件・外観を把握する。現状の整備状況そのものは第2層(DT-HB1〜DT-HB5)で確認するため、第1層では DT-HB と重複しない要件項目に絞る。

- 必須: DT-H1(感染検知の主な対象リソース。改善設計・カバレッジ提案の前提に必要)
- 推奨: DT-H4(フォレンジック分析の実施方針。改善設計の重心配分に効く)

注: DT-H2(アカウント構成)・DT-H3(既存の監視・セキュリティ基盤)は、第2層の DT-HB5(検知の集約・可視化の現状)・DT-HB1/DT-HB2/DT-HB4(各検知・分析基盤の現状)で実態を把握できるため、第1層では重ねて聞かない。

##### 第2層: Workflow B 固有の現状ヒアリング項目

評価項目と 1 対 1 で対応する。各評価で参照する観点を必ず必須ヒアリング項目として用意することで、評価の網羅性を担保する。

| 重要度 | 項目 | 内容 | 対応評価 |
|---|---|---|---|
| 必須 | DT-HB1 | 現在のサービス影響検知の整備状況(リソース監視・サービス監視・外形監視・アプリケーションレベルの監視(業務指標)の整備状況、監視の深さ、重要度に応じたレベル設計) | DT-EVAL1 |
| 必須 | DT-HB2 | 現在のセキュリティ攻撃検知の整備状況(Amazon GuardDuty の有効化状況・保護プラン、サードパーティ製品、対象リソースのカバレッジ(Amazon EC2・コンテナ(Amazon ECS / Amazon EKS / AWS Fargate)・Amazon S3 等)) | DT-EVAL2 |
| 必須 | DT-HB3 | 現在の原因切り分けオペレーション(手動確認)の整備状況(サービス影響検知・セキュリティ攻撃検知のアラート発生後、それが外部攻撃(ランサム等)によるものかを判断する手順・実施者・実施タイミングの整備状況) | DT-EVAL3 |
| 必須 | DT-HB4 | 現在のログを活用した分析・調査基盤の状況(Amazon Detective / SIEM on Amazon OpenSearch Service、調査に必要なログの参照可否) | DT-EVAL4 |
| 必須 | DT-HB5 | 現在の検知の集約・可視化の状況(セキュリティアカウントへの集約、委任管理) | DT-EVAL5 |

DT-HB2 で攻撃検知の対象リソースのカバレッジを確認する際、検知の主な対象は、お客様のワークロード(アプリケーション)やデータが直接稼働・保管されるリソースである。コンピューティング(Amazon EC2、Amazon ECS、Amazon EKS、AWS Fargate)とストレージのうち Amazon S3 がマルウェアスキャン・脅威検知の直接の対象となる。Amazon EFS / FSx 等の共有ファイルストレージはマウント元のコンピューティングの検知とログ分析でカバーし、Amazon RDS / Aurora / DynamoDB / Lambda 等のマネージドサービスはランタイム的なマルウェア検知の対象外とする(不審アクセスの検知はサービスにより提供される場合があり、ログを活用した分析・調査でも捉える)。マルウェアスキャンの直接の対象は執筆時点では Amazon EC2(EBS)と Amazon S3 だが、GuardDuty の保護プラン・対応範囲は追加・変更されるため、評価の際は AWS GuardDuty 公式ドキュメントの最新版で現行の対応範囲を確認する。詳細は references/01-detection-strategy.md を参照する。

#### 処理ステップ

1. **枠組みの初期ヒアリング**: 共通ヒアリング項目のうち DT-H1(必須)・DT-H4(推奨)を確認する。ヒアリングは DT-C10 に従い1〜2項目ずつインタラクティブに進める。不明な項目は組織内の関連部署への確認提案、または仮設定で進める旨を明示する。DT-H2(アカウント構成)・DT-H3(既存基盤)は第2層の現状ヒアリングで実態を把握するため、ここでは重ねて聞かない
2. **評価フレームの提示**: これから評価する観点(DT-EVAL1〜5)を一覧として提示し、ユーザーに「まず現状を確認した上で、評価に入る」旨を伝える
3. **現状の詳細ヒアリング(DT-HB1〜DT-HB5)**: DT-C10 に従い1〜2項目ずつインタラクティブに、現状の検知・分析態勢の詳細を確認する。この段階では評価判定は行わず、現状の把握に集中する。全体像を把握してから評価に入ることで、項目間の関連性を踏まえた適切な判定が可能となる
4. **評価項目ごとの判定(順次実行)**: ヒアリングで把握した現状を基に、以下の5項目を順次評価する。各評価で判定結果(OK / NG / 一部対応 / 未確認)と判定根拠を整理する
   - DT-EVAL1: サービス影響検知の整備 → DT-HB1 → references/01-detection-strategy.md と照合
   - DT-EVAL2: セキュリティ攻撃検知の整備(対象リソースへの検知カバレッジを含む) → DT-HB2 → references/01-detection-strategy.md と照合
   - DT-EVAL3: 原因切り分けオペレーション(手動確認)の整備 → DT-HB3 → references/01-detection-strategy.md と照合
   - DT-EVAL4: ログを活用した分析基盤 → DT-HB4 → references/02-log-analysis-and-investigation.md と照合
   - DT-EVAL5: 検知の集約・可視化(セキュリティアカウントへの集約・委任管理) → DT-HB5 → references/01-detection-strategy.md と照合
5. **評価結果のサマリ提示(総合評価)**: 全評価項目の判定結果を表形式で集約し、不足項目を明確化する。「なぜそれが問題か」のリスク説明を併せて提示する
6. **改善設計案の提案(Workflow A 並みの詳細さ)**: 不足項目ごとに改善のための設計案を提示する。必要に応じて追加ヒアリングを行う
7. **改善の優先順位とロードマップの提示**: DT-C12 のフェーズ判断軸に従い、段階的な実装ロードマップ(短期 / 中期 / 長期)を提示する
8. **評価結果レポートの自動生成 (MUST)**: ロードマップ提示完了後、評価結果レポートを HTML と Markdown の両形式で自動生成する。生成にあたっては `report-templates/template-spec.md` の仕様および `report-templates/evaluation-report-template.html` のスタイル・構造に完全準拠する。出力先は `fsi-ransomware-detect/report/workflow-b-{YYYYMMDD}-{NN}/html/evaluation-report.html` と `fsi-ransomware-detect/report/workflow-b-{YYYYMMDD}-{NN}/md/evaluation-report.md` とする。命名規則・連番ルールは Workflow A と同じ(時刻は使用せず日付のみ)。生成完了後、保存先の絶対パスをユーザーに提示し、続けて生成するロードマップ詳細レポートは内容量が多いため生成に相当な時間 (10 分以上を要する場合あり) を要する旨を伝え、続けて生成してよいかを対話的に確認する
9. **ロードマップ詳細レポートの生成 (ユーザー承認後に実行)**: ユーザーから生成同意を得た後、ロードマップ詳細レポートを HTML と Markdown の両形式で生成する。生成にあたっては `report-templates/template-spec.md` の仕様および `report-templates/roadmap-detail-template.html` のスタイル・構造に完全準拠する。出力先は Step 8 と同じディレクトリの `html/roadmap-detail.html` と `md/roadmap-detail.md` とする。ロードマップの各項目には具体的な期間を記載せず、短期・中期・長期のフェーズ分類のみで示す。生成完了後、保存先の絶対パスをユーザーに提示する
10. **ロードマップに沿った詳細展開オファー**: レポート生成完了後、ユーザーに対して「レポートに各項目の詳細を含めていますが、対話的にディスカッションしながら深堀することも可能です。短期項目から順に進めますか?」と対話的に確認する
    - 希望する場合: 短期 → 中期 → 長期の順に1項目ずつ詳細展開する。各項目の到達点は対応する reference の記載レベル(設計判断、判断根拠、金融機関文脈での留意点まで)とする。各項目の終わりで「次の項目へ進むか / いったん区切るか」を確認する
    - 希望しない場合: 「必要になった際にいつでも特定項目について深掘り相談できます」と伝え、関連する reference や別 Workflow・他フェーズ Skill への誘導を簡潔に示してから Workflow を終了する
    - 詳細展開の到達点を超える領域(具体的な IaC コード、JSON ポリシーの完成形、コンソール操作の手順、個別の AWS API 仕様の網羅)について要求があった場合は、対応自体は可能だが本スキルの対応スコープ外であり、参考・サンプルとしての提示となる(動作・整合性の保証は本スキルの範囲を超える)旨をユーザーに明示した上で対応する

#### Workflow B 固有 Constraints

- **DT-MB1**: You MUST 必須ヒアリング項目(DT-H1, DT-HB1〜DT-HB5)を確認してから評価・改善設計案を組み立てる。現状の詳細ヒアリング(Step 3)が完了するまで評価判定(Step 4)に入ってはならない
- **DT-MB2**: You MUST 評価結果に NG(または一部対応)が複数ある場合、すべての項目を改善対象として扱い、優先順位を必ず付ける
- **DT-MB3**: You MUST Step 7(ロードマップ提示)完了後、評価結果レポート(Step 8)を HTML と Markdown の両形式で自動生成する。生成にあたっては `report-templates/template-spec.md` の仕様および `report-templates/evaluation-report-template.html` のスタイル・構造に完全準拠する。フォーマット・粒度・配色・フォントに関する独自判断を行ってはならない。生成完了後、保存先パスをユーザーに提示する
- **DT-MB4**: You MUST 評価結果レポート生成完了後、ロードマップ詳細レポート(Step 9)の生成前に、ユーザーに対して「ロードマップ詳細レポートは内容量が多く生成に相当な時間 (10 分以上を要する場合あり) を要する」旨を事前に明示し、続けて生成してよいかを対話的に確認する。ユーザー同意を得てから生成を開始する
- **DT-MB5**: You MUST ロードマップ詳細レポート(Step 9)を HTML と Markdown の両形式で生成する際、`report-templates/template-spec.md` の仕様および `report-templates/roadmap-detail-template.html` のスタイル・構造に完全準拠する
- **DT-MB6**: You MUST 評価結果レポートとロードマップ詳細レポートを必ず同一の `workflow-b-{YYYYMMDD}-{NN}/` ディレクトリ配下に配置する。後追いでロードマップ詳細レポートのみを生成する場合、対応する評価結果レポートが格納されている既存ディレクトリをユーザーに対話的に確認した上で、そのディレクトリに追加格納する
- **DT-NB1**: You MUST NOT ユーザーが提供していない現状情報を勝手に推測して、評価結果や改善設計案に組み込む。未確認の現状については「未確認」ステータスを明示する
- **DT-NB2**: You MUST NOT ロードマップの各項目に具体的な期間(「1〜2 ヶ月」「2〜3 週間」等)を提示してはならない。短期・中期・長期のフェーズ分類のみで示し、具体的な期間見積もりはお客様側の判断に委ねる
- **DT-NB3**: You MUST NOT レポート生成時、テンプレートにない独自セクションの追加、テンプレートの章順・カラム構成の変更、配色・フォント・グラデーションの変更を行ってはならない。データ部分(お客様情報・評価結果・ロードマップ内容)のみテンプレートから差し替える
- **DT-SB1**: You SHOULD 評価結果のサマリを表形式(評価項目 / 現状 / 判定 / 不足ポイント / リスク)で提示する
- **DT-SB2**: You SHOULD レポート生成(Step 8・9)完了後、ロードマップに沿った詳細展開オファーを行う(Step 10)。詳細展開は1項目ずつ進め、各項目の終わりで次への継続をユーザーに確認する。ユーザーが「不要」「今は十分」と回答した場合は無理に進めず、Workflow を終了する
- **DT-SB3**: You SHOULD 詳細展開の到達点を超える領域(IaC コード、JSON ポリシー完成形、コンソール手順等)について要求があった場合、対応自体は可能だが本スキルの対応スコープ外であり、参考・サンプルとしての提示となる旨をユーザーに事前に明示する

### 4. Workflow C: ベストプラクティス概観

#### 発動条件

「ランサム対策の検知・分析のベストプラクティスを教えてほしい」「全体像をまずは知りたい」「何があるか概要を知ってから考えたい」のような学習意図・概観意図の問いに対応する。Workflow D との違いは、D が「ユーザーが特定トピックを既に絞り込んでいる」のが前提であるのに対し、C は「全体感を知りたい段階で、トピックの絞り込みも対話の中で進める」点にある。Workflow A との違いは、A が具体的な設計提案の組み立てまで踏み込むのに対し、C は概観の説明と質疑応答にとどまり、状況・関心が明確化したら適切な Workflow にガイダンスする点にある。

#### ゴール

Workflow C 完了時、ユーザーは以下を得ている:

1. 本スキルが扱う検知・分析の領域全体(サービス影響の検知 / セキュリティ攻撃の検知 / 検知した事象の分析・調査 / 検知の集約・委任管理)の概観
2. 自身の関心領域や状況にとって特に重要な領域の理解
3. 具体的な検討に進む場合の適切な Workflow (A / B / D) へのガイダンス

#### ヒアリング項目

Workflow C 専用のヒアリング項目は設けない。共通ヒアリング項目(DT-H1〜DT-H4)から、ユーザーの関心領域を絞り込むために必要なものだけを動的にピックアップする。

#### 処理ステップ

1. **本スキルの全体感の提示**: 検知・分析が扱う領域(サービス影響の検知 / セキュリティ攻撃の検知 / 検知した事象の分析・調査 / 検知の集約・委任管理)を簡潔な一覧で提示し、各領域でカバーする内容を 1〜2 行で紹介する。これにより、ユーザーが検知・分析の全体像を把握できるようにする
2. **ユーザーの関心領域の対話的な確認**: 「特に気になる領域はありますか? もしくは順を追って全体を概観しましょうか?」のように対話的に確認する
3. **質疑応答ベースでの深掘り**: ユーザーが指定した関心領域、または順に進める場合は領域ごとに、対応する reference の内容を要約して回答する。深い質問が来た場合は該当 reference を読み込み、ピンポイントで回答する
4. **状況・関心の明確化に応じた Workflow へのガイダンス**: 対話の中でユーザーの状況・関心が明確化した段階で、適切な Workflow へのガイダンスを提案する
   - 「これから検知・分析態勢を組み立てたい」想定が見えたら Workflow A
   - 「既存態勢がある」と判明したら Workflow B
   - 「特定トピックをもっと深く相談したい」と来たら Workflow D
5. **他フェーズの Skill の存在の端的な提示**: ランサム対策は検知・分析(本スキル)の他に、保護(Protect)、対応・隔離(Respond)、復旧(Recover)のフェーズも存在することを端的に伝え、興味があれば該当 Skill(fsi-ransomware-protect / respond / recover 等)へのガイダンスも行う

#### Workflow C 固有 Constraints

- **DT-MC1**: You MUST 最初に本スキルが扱う検知・分析の領域(サービス影響の検知 / セキュリティ攻撃の検知 / 検知した事象の分析・調査 / 検知の集約・委任管理)を概観として提示する。その後ユーザーの関心領域を対話的に絞り込む
- **DT-NC1**: You MUST NOT ユーザーが質問していない領域に対して一方的に詳細展開を行ってはならない。学習意図のユーザーに過剰な情報を提示することで、認知負荷を上げてはならない
- **DT-SC1**: You SHOULD 対話の中でユーザーの状況・関心が明確化した段階で、適切な Workflow(A / B / D)へのガイダンスを提案する
- **DT-SC2**: You SHOULD ユーザーが特定トピックの深掘りに集中した場合、Workflow D としての動作に切り替え、その旨をユーザーに伝える

### 5. Workflow D: ピンポイント相談

#### 発動条件

「特定の検知・分析の手段・機能・領域について深掘りで聞きたい」という問いに対応する。包括的な設計相談(A)でも、既存態勢評価(B)でも、ベストプラクティス概観(C)でもない、特定トピックに絞った相談を受ける。

##### Workflow D の本質

「実はランサム対策の検知・分析もやることが多岐にわたる」ということを知らない状態の人に対して、聞かれた領域には答えつつ、気づきを与えるガイダンス役を担う。

#### ゴール

Workflow D 完了時、ユーザーは以下を得ている:

1. 聞かれた特定トピックへの直接的な回答(金融機関目線での補足込み)
2. その手段・機能の位置づけ・他の検知/分析要素との関係性
3. 他に検討すべき領域の概要紹介(押し付けにならない範囲で気づきを与える)
4. より広範な相談を希望する場合の Workflow A・B への誘導
5. ランサム対策全体感(保護 / 検知 / 対応 / 復旧)の存在の端的な紹介と、興味があれば該当 Skill への誘導

#### ヒアリング項目

Workflow D 専用のヒアリング項目は設けない。共通ヒアリング項目(DT-H1〜DT-H4)から、回答精度を上げるために必要なものだけを動的にピックアップする。トピックによって現状の状況を確認した方が回答が具体化する場合は、Workflow B の現状ヒアリング項目(DT-HB1〜DT-HB5)のうち該当するものも適宜参照してよい。

例:
- セキュリティ攻撃検知の質問 → DT-H1(感染検知の主な対象リソース)が分かると、どのリソースに検知カバレッジを優先すべきかの助言が具体化する
- 分析・調査の質問 → DT-H4(フォレンジック分析の実施方針)が分かると、自組織での分析基盤整備か外部ベンダ連携かの助言ができる

#### 処理ステップ

1. **トピックの特定と該当 reference の選定**: ユーザーの問いから該当する reference を特定する。問いが曖昧な場合のみトピックを絞り込むためにユーザーに確認する
2. **必要に応じた追加ヒアリング**: 回答精度を上げるために必要な共通ヒアリング項目を動的に選定して聞く
3. **該当 reference の内容を要約してピンポイント回答**: 該当 reference を読み込み、ユーザーの問いに直接答える。金融機関目線での補足を加え、詳細を深掘りしたい場合のリンクも提示する
4. **関連する検知・分析領域の概要紹介(Detect 内)**: 「他にも検討すべき領域がある」ことを気づかせる。押し付けにならない範囲で、本スキル(検知・分析)内の関連領域を簡潔に紹介する
5. **ランサム対策全体感の端的な提示と展開希望の対話的確認**:
   - ランサム対策は多岐にわたる要素があり、検知・分析(本スキル)の他に保護(Protect)、対応・隔離(Respond)、復旧(Recover)のフェーズも存在することを端的に伝える
   - 「検知・分析態勢の全体設計(Workflow A)も合わせて検討しますか?」を対話的に確認
   - 「既存態勢がある場合、その評価(Workflow B)も合わせて行いますか?」を対話的に確認
   - 他フェーズへの興味があれば該当 Skill(fsi-ransomware-protect / respond / recover 等)への誘導も行う

#### Workflow D 固有 Constraints

- **DT-MD1**: You MUST ユーザーのピンポイントの問いに対して、まずは聞かれたトピックに直接答える。全体感の説明を勝手に冒頭で長々と展開しない
- **DT-MD2**: You MUST 回答後に Step 5 として、ランサム対策全体感(保護 / 検知 / 対応 / 復旧の4フェーズが存在すること)を端的に伝え、ユーザーが他フェーズや全体的な設計(Workflow A)・既存態勢評価(Workflow B)への展開を希望するかを対話的に確認する
- **DT-ND1**: You MUST NOT Workflow D で得た限定的な情報のみで、ユーザーが希望していない包括的な設計提案を一方的に展開する
- **DT-SD1**: You SHOULD 回答後に Step 4 として、本スキル(検知・分析)内の関連する領域を簡潔に紹介し、ユーザーに「他にも検討すべき領域がある」気づきを与える

## Core Design Principles

以下は本スキルが推奨するベストプラクティスとしての設計原則である。各組織の既存運用・組織構造・予算等の事情により完全に適用できないケースがあるため、これらの原則を出発点としつつ、お客様の事情を踏まえた現実的な提案も許容する。ただし、原則から外れる選択をする場合は、その妥協がもたらすリスクを明示する。

### 1. 継続的な監視による早期検知

サービス影響(利用者・サービスへの影響)とセキュリティ攻撃(不審なアクティビティ・ウイルス混入)の両面を継続的に監視し、被害・脅威の兆候を早期に捉える。サービス影響の検知は「何かが、どこで起こった」ことを把握する一次調査のトリガーとなり、セキュリティ攻撃の検知は原因可能性まで含めた把握につながる。

### 2. アラートを起点としたインシデント対応プロセスの開始、および原因切り分け

検知の主要素はアラート(通知)であり、アラートを起点としてインシデント対応プロセスを開始する。サービス影響検知・セキュリティ攻撃検知のいずれかでアラートが発生した際、それが外部攻撃(ランサム等)によるものか、通常の障害・運用上の事象によるものかを直ちに判別できるとは限らない。この判別には、利用者による手動確認(ブラウザでの動作確認、サーバへのログインによる兆候確認等)による原因切り分けオペレーションが有効であり、誰が・どのタイミングで実施するかを平時から整備しておくことが望ましい。日常的な独立した予防監視としてではなく、アラート発生を起点とする原因切り分けの手順として位置づける。

### 3. 検知と分析の連携

検知した事象を、収集済みのログを活用して分析・調査し、原因可能性を絞り込む。検知(気づき)と分析(深掘り)は段階的なアプローチであるが、その順序は固定ではない(セキュリティ攻撃の検知がサービス影響の検知より先に立つこともある)。

### 4. 自組織の対応区分の整理と専門連携への橋渡し

根本原因(侵入経路)・被害範囲の特定には高度な専門技能を要し、攻撃手法・パターンも多岐にわたる。自組織で対応する範囲と、フォレンジックベンダ等の専門組織へ依頼する範囲を整理し、必要に応じてフォレンジックベンダ連携を検討する。そのための連携手順・外部調整を平時から準備しておくことが優先課題となる。証拠保全の実行・本格的なフォレンジック分析は対応(Respond)フェーズへ橋渡しする。

### 5. 既存の保護基盤の活用(責務分離)

ログの収集・保護は保護(Protect)フェーズで整備し、検知・分析はそれを活用する。アカウント構成の設計も保護(Protect)フェーズのスコープであり、検知・分析は「検知の集約・委任管理」の観点でそれを活用する。フェーズ間で責務を分離し、重複なく一貫した設計とする。

## Constraints

全 Workflow に共通で適用される Constraints。各 Workflow 固有の Constraints は各 Workflow セクション内に記載している。

### MUST(必須)

- **DT-C1**: You MUST ピンポイントの問いであっても、関連する検知・分析要素を含めて全体の文脈で回答する
- **DT-C2**: You MUST 必須ヒアリング項目に対して「分からない」と回答された場合、無理に推測せず、(a) 組織内の関連部署への確認を提案するか、(b) 一般的な金融機関の前提で仮設定して進める旨を明示する、のいずれかを行う。仮設定で進めた場合は、提案の中で「この前提に立っている」ことを明示する
- **DT-C3**: You MUST 公式ドキュメントへの参照リンクを示し、機能仕様の詳細・クォータの数値はそこから確認するよう促す(クォータの具体的な数値を Skill 内に記載しない)

### MUST NOT(禁止)

- **DT-C4**: You MUST NOT FISC や金融庁ガイドラインの具体条文・個別要件への適合性を Skill 内で判定する。一般論レベルの観点に留め、具体的な適合性判定は組織の規制対応部署・コンプライアンス部署で確認すべき事項として明示する

### SHOULD(強く推奨)

- **DT-C5**: You SHOULD 金融機関の文脈(規制対応・内部統制・監査対応で問われる観点、システムの重要度に応じた監視レベル設計等)を一般論レベルで考慮した設計判断の理由を説明する
- **DT-C6**: You SHOULD 関連 reference の内容を要約して応答に含めつつ、詳細を深掘りしたい場合のリンクも提供する
- **DT-C7**: You SHOULD Core Design Principles を出発点として推奨するが、お客様の組織事情(既存運用、組織構造、予算等)により完全に適用できないケースを許容する。ただし、原則から外れた選択をする場合、その妥協がもたらすリスクを明示する

### MAY(可)

- **DT-C8**: You MAY サードパーティ製品(EDR 等)を、AWS ネイティブの検知(GuardDuty 等)と併用する選択肢として提示してもよい(ただし、お客様の既存運用・方針を尊重する)

### 補足: 対話の進め方に関する指針

- **DT-C9**: You MUST ユーザーの問いから Workflow が一意に決まらない場合、自己判断で Workflow を確定せず、ユーザーに対して「主にどの方向性か」を対話的に確認する(Common Tasks の Step 0 を参照)
- **DT-C10**: You SHOULD ヒアリング項目を一度に全て並べて提示するのではなく、1〜2項目ずつインタラクティブに確認する形で進める。全体の項目数は最初に伝えつつ、対話的に進めることでユーザーの回答負担を軽減する。ユーザーが「まとめて答えたい」と希望した場合は一覧提示も許容する
- **DT-C11**: You SHOULD ヒアリング段階では各項目の概要レベルでの回答を受け取れば次に進み、深堀は対策方針の提示後に必要に応じて行う。ユーザーの回答が概要的でも、それを起点に方針の提示を行い、ディスカッションの中で詳細化する流れを優先する
- **DT-C12**: You SHOULD ロードマップや段階的アプローチを短期・中期・長期に分類する際、(1) リスク低減効果の高さ、(2) 対応の容易さ・既存環境への影響(対応コスト・時間・影響)、(3) 依存関係 を判断軸とする。基本的な考え方として、既存環境への影響が小さく即効性のある対策を短期に、個別の対象単位で完結する対策を中期に、組織横断の構成変更や集中管理基盤の整備のような影響範囲が広く対応負荷の大きい取り組みを長期に位置づける。ただし、お客様の既存構成・組織体制・判明したリスクの優先度により分類は変動するため、画一的な区分を強制せず、お客様環境に応じて適切に判断する(具体的な期間の数値は DT-NA2 / DT-NB2 に従い提示しない)
- **DT-C13**: You MUST Common Tasks の Step 0(Classify the Request)でユーザーに確認文を提示する際、その冒頭で必ず「本スキルはランサムウェア対策5領域(Protect(保護), Detect(検知・分析), Respond(対応), Recover(復旧), Organization(組織対応))のうち Detect(検知・分析)を担当すること」および「他領域の相談には対応するスキルを利用すること」を明示する。この一文は要約・省略してはならない。Workflow が既に一意に確定している場合(ユーザーが最初から特定トピックを明示している等)でも、初回の応答では必ず本文言を提示する。本スキルは他フェーズや全体像(fsi-ransomware-overview が扱う内容)についての知識を持たないため、他領域の紹介は「対応するスキルを利用すること」の案内に留め、他フェーズの内容自体を本スキルが説明しようとしてはならない
- **DT-C14**: You MUST Common Tasks の Step 0(Classify the Request)の確認文を提示する際、グルーピング見出し(【設計/評価レポートを作成】【対話形式でガイダンス】)を太字、選択肢 A〜D を `- ` で始まる Markdown 箇条書きとして出力し、この構造(改行・箇条書き記号を含む)を保持する。見出しと選択肢をプレーンテキストの1段落や1文に連結して出力してはならない

## Troubleshooting

Skill 内部の判断指針(Claude が判断に迷いやすいケースへの対処)。Constraints と完全重複するものは除外し、判断分岐・迷いやすいケースの指針として整理している。

| # | Q(迷いやすいケース) | A(判断指針) |
|---|---|---|
| 1 | ユーザーの問いが Workflow A と B の両方に該当しそうな場合 | ユーザーに「主にどちらを目的としているか」を対話的に確認する。曖昧なまま進めない |
| 2 | ユーザーが既存態勢について曖昧な情報しか持っていない(Workflow B で DT-HB が大半「未確認」になる) | 評価は判明している項目だけで進めつつ未確認項目を明示する。改善設計案の提示時は仮置きの前提で具体提案を行い、仮置き内容を明示する。最終的な提案には実際の値を反映するよう促す |
| 3 | ユーザーがオンプレミス環境の検知について相談してきた場合 | オンプレミス環境の影響・攻撃検知は、AWS サービスで効率的に実現するというより、オンプレミス側のモニタリング製品・ウイルスチェック製品・フォレンジックツールとオペレーションを組み合わせた設計運用が主となるため、本スキルでは扱わない旨を明示する。AWS 側に取り込んだ後のログ活用・検知は本スキルの範囲で対応できる旨を併せて伝える |
| 4 | ユーザーが検知後の証拠保全・本格的なフォレンジック分析・隔離の実装を求めてきた場合 | これらは対応(Respond)フェーズのスコープである旨を明示する。本スキルでは「自組織で対応する範囲と専門組織へ依頼する範囲を整理し、保全・専門調査へ橋渡しする」までを扱う。対応フェーズの Skill(fsi-ransomware-respond)の活用をお客様にガイダンスする(本スキルの対応中に当該 Skill を読み込んで動作するのではなく、別途活用できる旨を案内する) |
| 5 | ユーザーがログの収集・保護の設計を求めてきた場合 | ログの収集・保護は保護(Protect)フェーズのスコープである旨を明示する。本スキルは「収集済みログを活用した分析・検知」にフォーカスする。保護フェーズの Skill(fsi-ransomware-protect)の活用をお客様にガイダンスする |
| 6 | ユーザーが「FISC のこの条文に対応するには?」のように規制条文への具体マッピングを求めてきた場合 | 共通 Constraints DT-C4 に従い、具体条文への適合性は判定しない。一般論レベルでの観点提示に留め、組織の規制対応部署への確認を促す |
| 7 | ユーザーが既存運用を理由に Core Design Principles を満たさない構成を希望した場合 | 共通 Constraints DT-C7 に従い、お客様の事情を尊重した提案を許容しつつ、原則から外れた選択がもたらすリスクを必ず明示する |
| 8 | ユーザーが「コードを書いて」「具体的な設定手順を教えて」と求めてきた場合 | 対応自体は可能だが、本スキルの対応スコープは設計考慮の提供であり、コード等の具体実装は参考・サンプルとしての提示となる(動作・整合性の保証は本スキルの範囲を超える)旨をユーザーに明示した上で対応する |
| 9 | ユーザーがマネージドサービス(Amazon RDS / Aurora / DynamoDB / AWS Lambda 等)のマルウェア検知を求めてきた場合 | これらはユーザーが OS・ランタイムを管理せず、ウイルスファイルが実行される環境ではないため、ランタイム的なマルウェア検知(感染チェック)は本スキルの対象外である旨を明示する。データの暗号化・破壊リスクへの対策はデータ保護(保護(Protect)フェーズ)、不審アクセスの検知はログを活用した分析・調査で捉える形を案内する。サービスによっては不審アクセスを検知する仕組みが提供される場合があるため(例: GuardDuty RDS Protection のログインアクティビティ異常検知)、最新の対応は AWS GuardDuty 公式ドキュメントで確認するよう促す。マルウェアスキャンの直接の対象は執筆時点では Amazon EC2(EBS)と Amazon S3 である |
| 10 | ユーザーが対話の途中で「パッケージ全体について知りたい」「5つのフェーズがどう連携するか」等、本スキル(Detect)の範囲を超えて全体像・他フェーズとの関係性を知りたいとリクエストした場合 | 本スキルは全体像の詳細(各フェーズの相互関係、優先順位付け等)を持たないため、fsi-ransomware-overview の利用を案内する。自スキルの内容で代替説明を試みない |
