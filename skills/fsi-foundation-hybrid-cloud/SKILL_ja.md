# FSI ハイブリッド（AWS Outposts）リファレンスアーキテクチャ

## ワークロード概要

本スキルは、「金融リファレンスアーキテクチャ日本版 / BLEA for FSI」v1.6 プログラムの
**ハイブリッド（ハイブリッド）** リファレンスアーキテクチャを扱う。**AWS クラウドと
オンプレミスを組み合わせる** ワークロードを対象とし、特に **AWS Outposts** 上に構築される
リファレンスアーキテクチャを記述する。

重要な前提として、**Outposts の責任共有モデル** がある。これは AWS リージョンのモデルとは
異なり、**Outpost が設置される顧客データセンターの物理セキュリティ、電源、ネットワーク、
キャパシティ管理は顧客の責任** となる。詳細は AWS ホワイトペーパー「AWS Outposts high
availability design and architecture considerations」を参照のこと。

本書全体で使用する重要な Outposts の用語（いずれも同ホワイトペーパーで定義されている）:

- **AWS Outposts** — 同一の AWS インフラストラクチャ、AWS サービス、API、およびツールを
  ほぼあらゆるデータセンター、コロケーションスペース、またはオンプレミス施設に提供し、
  真に一貫したハイブリッド体験を実現するフルマネージドサービス。
- **Outpost（論理 Outpost）** — 物理的に接続された AWS Outposts ラックを単一の論理エンティティ
  として管理し、AWS のコンピューティング、ストレージ、ネットワーキングのプールを顧客サイトに
  デプロイする環境。
- **親リージョン（Parent Region）** — Outpost をデプロイするために必要な管理、コントロール
  プレーンのサービス、およびリージョンレベルの AWS サービスを提供する AWS リージョン。
- **アンカーアベイラビリティゾーン（Anchor AZ）** — Outpost のアンカーポイントをホストする、
  親リージョン内のアベイラビリティゾーン。Outpost はアンカー AZ の拡張として機能する。
- **アンカーポイント（Anchor point）** — リモートにデプロイされた Outposts からの接続を受ける、
  アンカー AZ 内のエンドポイント。
- **サービスリンク（Service link）** — Outpost を親リージョンのアンカー AZ に接続する、
  暗号化された VPN トンネル群。
- **ローカルゲートウェイ（LGW）** — Outpost とオンプレミスネットワーク間の通信を可能にする、
  論理的な相互接続の仮想ルーター。

本アセットは、低レイテンシーの **証券取引システム**、**メインフレーム周辺システム**、
**データレジデンシー** の適用、および **オンプレミスデータベースへの低レイテンシーアクセス**
という 4 つの代表的なユースケースを提示する。それぞれの詳細な技術的説明と、Outposts と AWS 間の
物理ネットワークレイヤーについては、[references/architecture.md](references/architecture.md)
に記載している。

## ベストプラクティスと主要コンポーネント

### ベストプラクティス

- MUST: 各 Outposts ラックに冗長なネットワーク接続と、AWS クラウド内のアンカーポイントへの
  信頼性の高い接続を確保するため、オンプレミスネットワークをプロビジョニングすること。
  論理 Outpost の管理、監視、サービス運用が正しく機能するには、アンカー AZ への回復力のある
  接続が不可欠であるため。
- SHOULD: AWS リージョンへの接続に回復力を持たせるため、複数の Direct Connect ロケーションに
  またがる複数の AWS Direct Connect 接続を使用すること。
- SHOULD: 別ロケーションの AWS Direct Connect や AWS Site-to-Site VPN 接続など、Outposts と
  AWS 間の AWS Direct Connect リンクのバックアップを用意すること。
- SHOULD: 低レイテンシー要件のある機能（マルチキャスト、高速なプログラム実行）を EC2
  インスタンスで実行し、低レイテンシー要件のない機能はコンテナ上の Amazon ECS タスクとして
  実行することで、リソース効率の良い運用を行うこと。
- SHOULD: 取引所との高速な通信を必要とする証券取引システムの執行管理システム（EMS）および
  注文管理システム（OMS）を、AWS Outposts bmn-sf2e インスタンスを搭載した Outposts ラックに
  配置し、証券取引所の近くのデータセンターで運用して高速取引を可能にすること。
- SHOULD: フロントエンドや、低レイテンシーアクセスを必要としないデータベースについては、
  AWS クラウドのスケーラビリティを活用すること。
- SHOULD: 高可用性を必要とするメインフレーム周辺システムでは、Outposts のマルチ AZ 構成を
  採用すること。
- SHOULD: データレジデンシーが必要な場合に、Outpost に閉じた VPC を明確にガバナンスするため、
  Outposts サブネット用の専用 VPC を作成し、AWS リージョンから分離すること。
- SHOULD: スナップショットデータを AWS リージョンから隔離し Outpost に閉じた状態に保つため、
  Outposts 上の Amazon EBS ローカルスナップショットを S3 on Outposts に保存すること。
- SHOULD: スナップショットデータを AWS リージョンから隔離し Outpost に閉じた状態に保つため、
  シングル AZ の RDS on Outposts インスタンスのスナップショットを S3 on Outposts に保存すること。
- SHOULD: Outposts 環境を AWS リージョンから分離してデータレジデンシーを強制するため、
  AWS リージョンへのデータ転送／コピーおよび EC2 スナップショットの作成を拒否する
  サービスコントロールポリシー（SCP）を適用すること（具体的な SCP JSON は architecture.md を参照）。
- SHOULD: データベースをオンプレミスから移行できない場合に、低レイテンシーでデータベースに
  アクセスできるよう、バックエンドインスタンスとデータベースを同一データセンターに配置すること。
- SHOULD: 高可用性を実現するため、複数の AZ にまたがるアクティブ／スタンバイ構成を取るか、
  複数の AZ ／ Outposts ラックにまたがって構成すること。
- SHOULD: Outposts と通信する顧客側ネットワーク機器の予備を用意すること。
- SHOULD: 可用性を高めるため、Outposts を複数のデータセンターに設置すること。
- MUST: オンプレミス環境において、顧客側でファイアウォールを運用し、適切な対策を講じること。
- MUST: Outpost が設置される顧客データセンターの物理セキュリティおよび管理を、顧客自身の責任で
  実施すること。
- MAY: オンプレミスのメインフレームと、Outposts 上のクラウドデータレイク／OLAP との間の
  中継処理を実施すること。
- MAY: 検証時に障害を再現するため、AWS Fault Injection Service の利用を検討すること。
- WILL: Outposts を発注した AWS アカウント内で作成された VPC は、Outposts にシームレスに
  拡張される。
- WILL: AWS リージョン障害が発生した場合でも、顧客データセンター内の Outposts は正常に
  動作し続ける。

### 主要コンポーネント

#### bmn-sf2e インスタンス搭載の Outposts ラック（証券取引）

- **コンポーネント概要**: ミッションクリティカルで低レイテンシーの証券取引システム（EMS および
  OMS）を、証券取引所の近くに設置した Outposts ラック上で実行する。bmn-sf2e（ベアメタル）
  インスタンスは、ベアメタルネットワーキングおよび Precision Time Protocol（PTP）をサポートし、
  AWS Nitro アーキテクチャ上で動作し、AMD Solarflare X2522 ネットワークカードを搭載し、
  レイヤー 2 マルチキャストをサポートする。取引所または金融情報ベンダーからマルチキャストで
  配信されるマーケットデータを処理し、各システムへ配信する。
- **想定される AWS サービス**: AWS Outposts（bmn-sf2e インスタンス）、Amazon EC2、Amazon ECS、
  Amazon Aurora、Amazon ElastiCache。

#### Outposts と AWS 間の物理ネットワークレイヤー

- **コンポーネント概要**: 論理 Outpost をそのアンカー AZ に接続する、耐障害性のある物理接続を
  提供する。各 Outposts ラックには冗長なネットワーク接続が与えられ、AWS リージョンへの
  プライベート接続は AWS Direct Connect 経由で提供され、複数の Direct Connect ロケーションに
  またがる複数の接続で回復力を持たせる。
- **想定される AWS サービス**: AWS Direct Connect、AWS Site-to-Site VPN（バックアップリンクとして）、
  ローカルゲートウェイ（LGW）、サービスリンク。

#### メインフレーム周辺・連携システム

- **コンポーネント概要**: 高可用性のためのマルチ AZ Outposts 構成。フロントエンドは AWS クラウドの
  スケーラビリティを活用し、Application Load Balancer と EC2 インスタンスを用いて AWS リージョンに
  構築する。バックエンドは、メインフレームなどのオンプレミスデータも活用するために Outposts 上で
  処理する。Outposts は、オンプレミスのメインフレームとクラウドデータレイク／OLAP との間の
  中継処理も実施できる。
- **想定される AWS サービス**: AWS Outposts、Application Load Balancer、Amazon EC2、加えて
  分析バリアント向けの AWS クラウドデータレイク／OLAP サービス。

#### データレジデンシーの強制（Outposts に閉じた VPC）

- **コンポーネント概要**: AWS リージョンから分離した Outposts サブネット用の専用 VPC を作成する
  ことでデータレジデンシーを強制し、データを顧客データセンターに閉じた状態に保つ。
  サービスコントロールポリシー（SCP）により、リージョンへのデータ転送／コピーおよび EC2
  スナップショットの作成を拒否する。Outposts 上の EBS ローカルスナップショットおよびシングル AZ の
  RDS on Outposts スナップショットは、スナップショットデータをリージョンから隔離するため
  S3 on Outposts に保存する。
- **想定される AWS サービス**: AWS Outposts、Amazon VPC、AWS Organizations のサービスコントロール
  ポリシー（SCP）、Amazon EBS（Outposts 上のローカルスナップショット）、Amazon RDS on Outposts、
  Amazon S3 on Outposts。

#### オンプレミスデータベースへの低レイテンシーアクセス

- **コンポーネント概要**: トランザクションごとのネットワークレイテンシーの累積（例: バッチ処理）が
  クリティカルとなるレガシーワークロードでは、データベースと同一のオンプレミスデータセンターに
  配置した Outposts 上で処理を実行する。フロントエンドは AWS リージョンへ、バックエンドは
  Outposts へ移行することで、移行できないオンプレミスデータベースへの低レイテンシーアクセスを
  可能にする。
- **想定される AWS サービス**: AWS Outposts、Amazon EC2（バックエンドインスタンス）、
  オンプレミスデータベース（顧客管理）。

## FISC コンプライアンスサマリー

本アセットは、AWS Outposts ベースのハイブリッドワークロードについて、**FISC 安全対策基準
実務基準（FISC Security Guidelines, practical standards）** に対してマッピングされている。
このマッピングでは、共通のコントロール環境（**ガバナンスベーステンプレート**）が提供する
コントロールと、リファレンスアーキテクチャおよびユーザー側で期待される追加の対策／考慮事項とを
区別している。

主なハイライトとしては、ユーザー保護および MFA のための IAM Identity Center、AWS Control Tower
のガードレール、AWS KMS CMK による暗号化、転送中データのための TLS、監査証跡のための CloudTrail
および AWS Config、検知のための Amazon GuardDuty ／ Security Hub、CloudWatch による監視、
さらには、データセンターの物理セキュリティに対する顧客責任、オンプレミス環境における顧客側の
ファイアウォール運用、Direct Connect の冗長化、AWS リージョン障害時の Outposts の継続動作といった
Outposts 固有の項目が含まれる。プロセス、開発、およびアプリケーションレイヤーのコントロールの
多くは対象外（out of scope）としてマークされている。

エントリーごとの完全な FISC マッピング表（実 1 から実 149 まで）は、
[references/fisc-mapping.md](references/fisc-mapping.md) に保存している。
