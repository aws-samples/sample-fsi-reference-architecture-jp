# FSI サイバーレジリエンス

## ワークロード概要

サイバーレジリエンスとは、サイバー攻撃を受けることを前提として、攻撃を予防し、検知し、対応し、復旧
する能力を総合的に高めることである。従来の「攻撃を防ぐことに主眼を置く」という考え方から、「攻撃を
受けても事業を継続し、迅速に復旧する」という考え方への転換が求められている。特に可用性に影響を与える
DDoS 攻撃やランサムウェア攻撃といったサイバーイベントに対する防御は実装が急務とされている。

本アセットは金融機関向けの**ドキュメントのみ**のリファレンスアーキテクチャである。BLEA for FSI の
**勘定系ワークロード**をベースに、勘定系ユースケースの CDK サンプルとして提供される以下の 3 つの
機能を追加する。

1. **論理的エアギャップバックアップ** — AWS Backup の復旧ポイントを、論理的に隔離された
   **データバンカーアカウント**に複製することで、ランサムウェアに感染したデータがバックアップコピーへ
   密かに伝播したり改ざんされたりすることを防ぐ。
2. **新規環境へのクロスアカウント復旧** — 本番データセンターが依然として感染している可能性を前提に、
   全く新しい**リストアアカウント**で復旧を行う。データバンカーアカウントへの直接アクセスは付与せず、
   AWS Resource Access Manager（RAM）でバックアップを共有する。
3. **自動ネットワーク隔離** — Amazon GuardDuty で Critical な脅威を検知し、Lambda 関数で
   Network ACL を書き換えて侵害された勘定系ワークロードを隔離し、影響範囲を最小化する。

本設計はランサムウェアのシナリオを明示的に前提としている。感染したデータがバックアップにコピーされる
可能性があるため、バックアップを論理的に隔離し、復旧先を本番とは完全に別の環境とする。参考：金融庁
「金融分野におけるサイバーセキュリティに関するガイドライン」の 2.3.3.（データ保護）。

## ベストプラクティスと主要コンポーネント

### ベストプラクティス

- MUST: ワークロードアカウントで AWS Backup によりバックアップを取得し、その復旧ポイントを別個の
  論理的に隔離されたデータバンカーアカウントへ複製すること。
- MUST: 複製したバックアップは **AWS Backup Logically Air-gapped Vault** に保管し、保持期間中は
  管理者権限を持つユーザーや攻撃者でさえも、読み取り・変更・削除を不可能にすること。
- MUST: ワークロードアカウントとデータバンカーアカウントは**同一の AWS Organizations** に属させる
  こと。クロスアカウントのバックアップコピーおよび RAM 共有の動作に必要である。
- MUST NOT: 復旧が必要な場合にデータバンカーアカウントへ直接アクセスしないこと。バックアップデータの
  不正アクセスや改ざんを防止するため、**AWS Resource Access Manager** でリストアアカウントへ
  ボールトを共有すること。
- MUST: 本番環境が侵害されている前提で、本番へ戻すのではなく新規の**リストアアカウント**へ復旧する
  こと。
- SHOULD: リストアアカウントでアプリケーションとインフラを CDK で自動的に再構築し、バックアップ
  からのデータベース復旧を AWS Step Functions で自動化すること。
- MUST NOT: 復旧したデータベースのワークロードへの再接続を自動化しないこと。業務影響度の評価とリスク
  判断が必要なため、切り替えは手作業の運用手順とすること（ECS タスク定義の環境変数をリストア後の
  データベースに更新し、ECS タスクを再起動する）。
- MUST: バックアップからの復旧作業に着手する前に、バックアップデータの完全性を評価すること。
- MUST: サイバーイベント発生時には、影響を受けたシステムを速やかに隔離し、インシデント調査のための
  証拠を保全すること。
- SHOULD: 自動ネットワーク隔離は GuardDuty の **Severity 9.0 以上（Critical）** の Finding の
  みでトリガーすること。本機能は Critical レベルのみに反応する。
- SHOULD: 隔離では Network ACL を動的に作成し、2 つのアベイラビリティゾーンにまたがるワークロードの
  サブネット間の通信のみを許可し、その他の inbound/outbound 通信を全て遮断すること。
- MUST: 隔離が完了したら Amazon SNS で管理者に通知し、エラー発生時も通知を送信すること。
- PREFER: 隔離が業務に影響を及ぼす場合は、完全自動での隔離ではなく、Critical 通知と隔離処理の間に
  人による判断を介在させることが望ましい。
- WILL: 勘定系ワークロードは Amazon ECS Fargate を用いており、コンテナホストが AWS の管理責任下に
  あるため調査箇所が限られていることから、フォレンジックアカウントのデプロイおよび手順は本アセットでは
  省略している。
- MAY: 改ざん検出、マルウェアスキャン、データの完全性とアプリケーション依存関係の確認のために、別途
  フォレンジックアカウントをデプロイしてよい。本ワークロードでは対象外である（AWS Security IR の
  フォレンジックリソース参照）。

### 主要コンポーネント

#### ワークロードアカウント

- **コンポーネント概要**: 勘定系システム等が稼働する本番アカウント。AWS Backup でバックアップを取得し、
  そのバックアッププランでデータバンカーアカウントのエアギャップボールトへ復旧ポイントをコピーする設定を
  行う。
- **想定 AWS サービス**: AWS Backup、Amazon ECS（Fargate）、Amazon Aurora、Amazon DynamoDB、
  Amazon VPC。

#### データバンカーアカウント

- **コンポーネント概要**: バックアップデータを保管する論理的に隔離されたアカウント。復旧ポイントの
  クロスアカウントコピーを受け取る AWS Backup Logically Air-gapped Vault をホストし、直接アクセスを
  許可せず必要時に RAM でリストアアカウントへ共有する。
- **想定 AWS サービス**: AWS Backup（Logically Air-gapped Vault）、AWS Resource Access
  Manager、AWS Organizations。

#### リストアアカウント

- **コンポーネント概要**: 本番が侵害されている前提での復旧先となる新規アカウント。アプリケーションと
  インフラは CDK で再構築し、共有されたバックアップからのデータベース復旧は Step Functions で自動化
  する。復旧後のデータベースへのワークロード再接続は手作業で行う。
- **想定 AWS サービス**: AWS Step Functions、Amazon Aurora、Amazon DynamoDB、Amazon ECS
  （Fargate）、Elastic Load Balancing（ALB）、AWS Resource Access Manager。

#### フォレンジックアカウント（対象外）

- **コンポーネント概要**: 侵害されたシステムの改ざん検出、マルウェアスキャン、データの完全性とアプリ
  ケーション依存関係の確認用アカウント。ECS Fargate のホストが AWS の管理責任下にあり調査箇所が
  限られるため、デプロイおよび手順は省略している。
- **想定 AWS サービス**: 本アセットではデプロイしない。AWS Security Incident Response のフォレン
  ジックリソースを参照。

#### 自動ネットワーク隔離

- **コンポーネント概要**: Critical な GuardDuty Finding を受けて EventBridge ルールが Lambda
  関数をトリガーし、勘定系の Protected Subnet に Network ACL を作成・適用する。AZ 間のサブネット
  通信のみを許可し、その他の通信を全て遮断した上で SNS で管理者へ通知する。Primary Region のみで
  動作する。
- **想定 AWS サービス**: Amazon GuardDuty、Amazon EventBridge、AWS Lambda、Amazon SNS、
  Amazon VPC（Network ACL）。

## FISC 対応の概要

本アセットには BLEA for FSI v1.6 のソースにおいて**専用の FISC マッピングファイルは存在しない**。
ソースドキュメントに含まれる規制上の考慮事項は以下のみである。

- 金融庁（FSA）は「金融分野におけるサイバーセキュリティに関するガイドライン」を策定し、バックアップに
  関する規程整備やランサムウェア攻撃への対応事項を定義している。本アセットは、バックアップの論理的隔離
  および本番とは完全に別環境での復旧の根拠として、その 2.3.3.（データ保護）を引用している。
- 上記の金融庁ガイドラインを受けて、**FISC 安全対策基準**でもサイバーレジリエンス強化に関する基準
  項目が新設され、本リファレンスアーキテクチャを活用した対策内容が更新されている。ソースは、実務基準の
  対策について本アセット独自のマッピングではなく、**勘定系アセット**の FISC マッピングファイル
  （`fisc-mapping-core-banking.md`）を指している。

サイバーレジリエンス固有の FISC 統制とサービスのマッピングはソースに存在しないため、ここでも一切主張
しない。

## リファレンスアーキテクチャ

エンドツーエンドのアーキテクチャ — アカウント設計（ワークロード／データバンカー／リストア／フォレン
ジック）、3 段階のバックアップ・リストアフロー、自動ネットワーク隔離フロー、および参照される全ての
AWS ドキュメント・ホワイトペーパー・ガイドライン — は `references/architecture.md` に詳述している。

運用の手順は以下にまとめている。

- `references/backup-procedures.md` — データバンカーアカウントへの Logically Air-gapped Vault の
  デプロイと、クロスアカウントバックアップコピーの設定。
- `references/restore-procedures.md` — RAM 共有、Step Functions によるデータベース復旧、リストア
  アカウントでの手作業によるワークロード再接続。
- `references/isolation-procedures.md` — GuardDuty トリガーの自動ネットワーク隔離のアーキテク
  チャ、デプロイ、テスト、制限事項。

## CDK サンプルの概要

本アセット専用の CDK サンプルディレクトリは BLEA for FSI v1.6 では提供されておらず、本アセットは
ドキュメントのみである。手順書が参照する CDK デプロイアセットは、**勘定系（core-banking）**ユース
ケース（`usecases/guest-core-banking-sample`）内に存在し、同ユースケースの `bin/parameter.ts` に
ある `CyberResilienceParameter` の `option` 配列（`'backup' | 'restore' | 'isolation'`）で選択
する。正確なデプロイコマンドはソースに記載のとおり、リファレンスファイルを参照のこと。
