# 金融業界での生成 AI ユースケース

## ワークロード概要

本ケーススタディは、金融機関（銀行、保険会社、証券会社）における生成 AI 活用の
具体的なユースケースを紹介する。いずれの例も **Amazon Bedrock** とそれを補完する
AWS サービス群で構成され、各ユースケースには公開サンプル実装が存在する。ケース
スタディは 4 つのユースケースを収録し、それぞれが金融サービスにおける異なる業務課題に
対応する。

1. **文書・コンテンツ審査（RAPID）** — 金融機関における膨大な文書審査業務を Human-in-the-Loop
   で効率化する。ガイドライン文書から自動的にチェックリストを生成し、対象文書を生成 AI が
   審査し、人間が最終判断を行う。
2. **AI 営業ロールプレイ** — 営業担当者が AI の演じる顧客と音声で対話し、金融商品の営業
   スキルを向上させる研修システム。感情、コンプライアンス、映像（表情・アイコンタクト）、
   リファレンスの正確性をリアルタイムに評価する。
3. **契約書業務アシスタント** — 契約書の新規作成、既存契約の照会、契約に関する質問対応と
   いった契約業務を、Amazon Bedrock 上のスーパーバイザー + 専門エージェントのマルチ
   エージェント構成で包括的に支援する AI アシスタント。
4. **ATM 不正検知（高齢者電話利用）** — 監視カメラ映像を Amazon Nova（マルチモーダル）で
   解析し、詐欺の可能性がある行動パターン（電話をしながら ATM を操作する高齢者など）を
   自動検知して、振り込め詐欺や特殊詐欺の被害を未然に防ぐ。

**金融サービスにおける目的・意義。** これらのユースケースは、業界に共通する課題に対応する。
すなわち、手作業による重い文書審査負荷、一貫した営業品質とコンプライアンス遵守（適合性
原則や金融商品規制における説明義務など）の必要性、契約業務の効率的な処理、そして顧客
（特に高齢者）を詐欺から保護することである。4 つに共通するビジネスドライバーは、業務
効率化（24 時間対応、定型業務の自動化）、品質標準化（担当者ごとのばらつき解消）、コスト
削減（人件費削減）、透明性・説明責任（AI の判断根拠を明示し、説明可能性と監査対応を支援
する）である。

## ベストプラクティスと主要コンポーネント

### ベストプラクティス

- MUST: 文書審査では最終判断に人間を介在させる（Human-in-the-Loop）。AI が一次審査を行い、
  人間が最終判断と承認を行う（RAPID の Human-in-the-Loop モデル）。
- MUST: AI の判断根拠を明示し、合否判定の理由を提示できるようにして説明責任を確保する。
- MUST: 顧客対応・営業研修シナリオでは生成 AI の出力にコンプライアンスガードレールを
  適用する。金融機関では FinanceCompliance と GeneralCompliance が推奨され、金融商取法や
  銀行法に基づくチェックを行う。
- MUST: 営業ロールプレイでは法的に要求される説明項目（リスク説明、手数料説明、適合性
  確認）を網羅し、漏れを防ぐことで、説明義務違反による法的リスクを軽減する。
- MUST: ロールプレイシナリオではコンプライアンス関連・法的要求事項に対して必須ゴールと
  明確な判定基準を設定する（コンプライアンス・法的要求事項には優先度 5 を割り当てる）。
- SHOULD: スーパーバイザー + 専門エージェントのマルチエージェント構成（Amazon Bedrock
  マルチエージェントコラボレーション）を用い、単一のインターフェースから多様な契約要求を
  最適な専門エージェントへ自動的に振り分ける。
- SHOULD: 有効期限付き（5 分）の署名付き URL によるブラウザから S3 への直接アップロードを
  用いて、大容量の動画ファイルでもセキュアに、かつ API Gateway のペイロード制限を回避して
  アップロードする。
- SHOULD: 監視動画には S3 ライフサイクルポリシーを、DynamoDB には TTL を適用し、古い・
  不要なデータを自動削除して、コストとデータ管理の両面に対応する。
- SHOULD: 正常な顧客行動（短時間の通話、落ち着いた様子、スムーズな操作）を適切に識別して
  誤検知を最小化し、業務効率と顧客体験を維持する。
- PREFER: これらの生成 AI ワークロードには、疎結合な層構成によりスケーラビリティと運用
  効率を両立するサーバーレスアーキテクチャ（API Gateway + Lambda + Amazon Bedrock + S3 +
  DynamoDB）を採用する。
- PREFER: AI 営業ロールプレイのサンプルは、事前準備不要の AWS CloudShell からデプロイし、
  提供される `bin.sh` デプロイスクリプトを実行する。
- MAY: ロールプレイのサンプルではデプロイオプション（`--disable-self-register`、
  `--bedrock-region`）でセルフサインアップの無効化や特定 Bedrock リージョンの指定を行う。
- MAY: 組織独自のコンプライアンス要件がある場合はカスタムガードレール（例：金融商取法
  ガードレール — 断定的判断の提供禁止、重要事項説明義務、適合性原則の遵守、誇大広告の禁止）
  を定義する。
- WILL: 高リスクの詐欺を検知すると、即座に店舗スタッフへ通知し、スタッフが顧客に声をかける
  ことで被害を未然に防ぐ。
- WILL: ATM 不正検知の Amazon Nova 解析は、映像と音声の両方を統合的にマルチモーダル解析し、
  詐欺パターンを識別する。
- WILL: 契約書業務アシスタントが生成した契約書ドラフトは S3 に保存されユーザーに提供され、
  サンプルテンプレートには購入契約書、フランチャイズ契約書、タイムアンドマテリアル契約書が
  含まれる。

### 主要コンポーネント

#### Amazon Bedrock（生成 AI 基盤）

- **コンポーネント概要**：4 つのユースケースすべてに共通する中核の生成 AI エンジン。
  文書解析・審査（RAPID）、ロールプレイ対話とコンプライアンスチェック（Anthropic Claude
  経由）、マルチエージェントによる契約処理、マルチモーダル映像解析（Amazon Nova 経由）で
  使用する LLM をホスティングする。マルチエージェントコラボレーションおよびガードレール
  機能も提供する。
- **想定される AWS サービス**：Amazon Bedrock、Amazon Nova、Anthropic Claude（Bedrock 上）、
  Bedrock Agents、Bedrock マルチエージェントコラボレーション、Bedrock Guardrails。

#### マルチエージェントオーケストレーション（契約書業務アシスタント）

- **コンポーネント概要**：スーパーバイザーエージェント（Contract Agent）がユーザーの契約
  問い合わせを受け取り、意図を分析して、3 つのサブエージェント（契約書作成、既存契約確認、
  契約関連質問対応）のうち最適なものへ振り分け、最終回答を作成する。Amazon Bedrock マルチ
  エージェントコラボレーションで実装される。
- **想定される AWS サービス**：Amazon Bedrock（Agents、マルチエージェントコラボレーション）、
  AWS Lambda（既存契約確認）、Amazon S3（生成契約書・テンプレート）、Amazon OpenSearch
  Service（契約 Q&A のナレッジベース）。

#### サーバーレス処理層

- **コンポーネント概要**：署名付き URL 生成、解析トリガー、ステータス確認、一般的な
  アプリケーションロジックを扱う、イベント駆動のサーバーレスコンピュート。ATM 不正検知では
  3 つの Lambda 関数（署名付き URL、自動解析、ステータス確認）で構成される。疎結合な層
  （フロントエンド、API、処理、AI 解析、データ）により、柔軟な拡張と保守を可能にする。
- **想定される AWS サービス**：AWS Lambda、Amazon API Gateway。

#### データ・ストレージ層

- **コンポーネント概要**：文書、動画、シナリオデータ、評価結果、チェックリスト、解析
  メタデータを保存する。S3 は文書（RAPID）、生成契約書とテンプレート（契約書アシスタント）、
  動画ファイル（不正検知）、シナリオ・評価データ（ロールプレイ）を保持する。DynamoDB は
  チェックリストと審査結果（RAPID）、解析結果・メタデータ（不正検知）、ユーザー情報・進捗
  （ロールプレイ）を管理する。
- **想定される AWS サービス**：Amazon S3、Amazon DynamoDB。

#### Web 配信・API 層

- **コンポーネント概要**：ブラウザベースの UI と REST API を配信する。CloudFront は Web
  アプリケーションを低レイテンシで配信し、API Gateway は REST API エンドポイントを提供し、
  認証・認可とレート制限を管理する。ATM 不正検知の API は署名付き URL エンドポイント
  （`GET /presigned-url`）とステータスエンドポイント（`GET /status/{videoId}`）を公開する。
- **想定される AWS サービス**：Amazon CloudFront、Amazon API Gateway。

#### マルチモーダル・メディア解析サービス

- **コンポーネント概要**：テキスト以外のモダリティを処理するサービス。Amazon Nova（Bedrock
  上）は ATM 監視動画・音声を解析して詐欺パターンを識別する。AI 営業ロールプレイでは
  Amazon Transcribe が音声をテキスト化し、Amazon Rekognition が映像を分析して非言語
  コミュニケーション（表情、アイコンタクト、身振り手振り）を評価する。
- **想定される AWS サービス**：Amazon Nova（Amazon Bedrock 上）、Amazon Transcribe、
  Amazon Rekognition。

#### 運用・監視

- **コンポーネント概要**：ワークロードの可観測性（ATM 不正検知のユースケースで詳細に記述）。
  CloudWatch Metrics/Logs でメトリクス収集とログ集約を行い、CloudWatch Alarms で異常を検知し、
  SNS 経由で運用チームに通知し、統合ダッシュボードで可視化する。監視項目には Lambda 実行時間
  とエラー率、API Gateway のレイテンシ/エラー、DynamoDB の読み書きキャパシティ、S3 の
  ストレージ使用量、Bedrock API の呼び出し回数とエラーが含まれる。
- **想定される AWS サービス**：Amazon CloudWatch（Metrics、Logs、Alarms）、Amazon SNS。

## FISC 対応サマリー

本ケーススタディには **専用の FISC マッピングファイルは存在しない**。また、ソース文書には
明示的な FISC 安全対策基準のマッピングは含まれていない。したがって
`references/fisc-mapping.md` は作成しない。

ただしソース文書は、FISC 準拠のガバナンスに関連する金融規制・コンプライアンスの観点を
定性的に扱っている。

- 金融商取法および銀行法に基づくコンプライアンスガードレール（FinanceCompliance /
  GeneralCompliance）。断定的判断の提供禁止、重要事項説明義務、適合性原則、誇大広告の
  禁止を含む。
- 営業活動における説明義務の遵守と顧客保護（リスク説明、手数料説明、適合性確認）。
- 透明性・説明責任：AI の判断根拠を明示して説明可能性と監査対応を支援すること。検知履歴と
  対応記録を体系的に管理して監査に対応すること（ATM 不正検知）。
- 法令・規制ガイドライン（金融庁監督指針、業界自主規制規則など）、社内コンプライアンス規程、
  情報セキュリティポリシーに対する文書審査（RAPID の審査基準カテゴリ）。

これらのソース記載の観点を超える FISC 統制マッピングは推論しない。

## CDK サンプル概要

本ケーススタディには CDK サンプルは提供されていない。個々のユースケースは、それぞれの
公開サンプルリポジトリ（日本語リファレンスファイルに記載）からデプロイする。例えば AI
営業ロールプレイのサンプルは、AWS CloudShell と提供されるデプロイスクリプト（`bin.sh`）を
用いてデプロイする。このケーススタディアセット自体には CDK コードは含まれていない。
